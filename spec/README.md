# spec/ — the protocol

This directory is not documentation about the protocol. It **is** the protocol.

`core/` is *a* reference implementation of what is written here. An independent implementation that passes these vectors is a peer, not a fork — which is what allows the maintainer of this repository to eventually be nobody in particular, and what makes "fork away from us" a real option rather than a slogan.

## Contents

| Path | What it is |
|---|---|
| `params.json` | The frozen parameter set of the main network. |
| `params.testnet.json` | The public testnet: mainnet in every value except the six its `PURPOSE` note names, so that what it measures is mainnet's economics rather than its own. |
| `params.devnet.json` | A throwaway development network: short epochs, short TTLs, a trivial proof-of-work target. |
| `chain-ids.json` | The allocation ledger: which network each chain id was allocated to, and which genesis it was spent on. A chain id is allocated once and never reused. Embedded like the parameter files, so `spec.CheckChainID` can refuse a retired id — or a live id deriving the wrong genesis — at node startup, and not only in `go test ./spec`. |
| `../docs/spec/wire.md` | The peer-to-peer protocol, specified independently of `node/p2p`. Almost entirely transport rather than consensus — a node that speaks none of it and receives blocks on a USB stick computes the same chain — with one exception, §9 rule 7, called out below. |
| `vectors/*.json` | The golden vectors: `(pre-state, block) → (post-state \| invalid, outcomes, fees)`. |
| `vectors/difficulty/*.json` | The difficulty vectors: `(params, headers) → next_target`. A second, parallel corpus — see below — because the statement above cannot express a claim about the difficulty rule at all. |

## The parameter files

Everything in them is frozen at genesis and changeable only by a hard fork. They are embedded into the binary at compile time, so a build and the parameters it was built from can never drift apart, and the parameter hash a release announces is a property of the binary you can check:

```sh
zcd genesis            # network, chain id, params hash, genesis id, state root
zcd params             # the values themselves
```

Unknown fields are rejected on load. A parameter that nothing reads is a parameter somebody thought was doing something.

The one exception is `notes`, which carries prose about the traps in this file — JSON has no comments and a parameter editor should meet a trap where the parameter is, not in an adversarial review they may never read (R2-S4). It is consensus-inert.

**The two announced values commit to different things, and the difference matters:**

- The **params hash** is `blake3` over the file *bytes*, `notes` included. It pins the exact document a launch announcement referred to. Editing a note changes it.
- The **genesis id** is derived from the parameter *values*. Two files with identical values and different notes produce the same genesis block.

An implementation is conformant if it reproduces the genesis id and passes the vectors. The params hash is what proves you are looking at the same document, not the same protocol.

## How a list is rooted

Three of the values this corpus commits to are merkle roots — a vector's `post_root`, and the `CertRoot` and `CitesRoot` carried inside every `block` — and all three are built from one internal node function and one list-root spelling. SSZ fixes the *shape* of both and neither of the two decisions below, so they are fixed here by value. This is stated because it was measured: a second implementation of the epoch state root, written from these documents, derived everything else about the commitment and had to open `core/ssz` for exactly this line.

**The internal node function.**

```
node(left, right) = blake3("zcd/node/v1" ‖ left ‖ right)
```

`left` and `right` are 32 bytes each, the tag is the ASCII string `zcd/node/v1`, and the three parts are concatenated with no length prefix — the `blake3(tag ‖ payload)` shape every hash in this protocol has. **Every internal node of every merkle tree in the protocol is this function**, and the tag's value is normative: it is what keeps a 32-byte leaf preimage from also being readable as an internal node. `core/crypto`'s `TagSSZNode` is an implementation of this line, not its source — the value used to exist nowhere but in that constant's comment, which is not a place a second implementation is obliged to look.

**The tag is not the whole separation, because `Sum` has no length prefixes.** Every hash in the protocol is

```
Sum(tag, p₁, p₂, …) = blake3(tag ‖ p₁ ‖ p₂ ‖ …)
```

with the parts concatenated and nothing recording where one ends. Injectivity is therefore a property of the *call sites* rather than of the function: **two sites under one tag share a preimage as soon as their concatenated payloads can be equal.** Where the digest is a storage word that is two purposes on one state cell, with no error and no symptom until the two values disagree. So a second implementation must reproduce the **encoded widths** below, not only the tags — a payload widened, narrowed or padded to a common size is a different protocol even when every tag matches.

- **Under `zcd/addr/v1`.** An address is `version ‖ blake3(TagAddr ‖ version ‖ payload)[:31]`, and the Era-0 derivations present exactly two payload shapes: a user address hashes `version ‖ pubkey`, **33 bytes**; an asset address hashes `version ‖ chain_id ‖ issuer ‖ seq`, **49 bytes** (1 + 8 + 32 + 8, the two integers little-endian `uint64`). **That the two widths differ is what makes the two preimages disjoint**, and it is the only thing that does — the derivation itself imposes no constant version byte, so the leading byte is not a separator the hash can rely on. Both widths must be preserved exactly.
- **Under `zcd/protoword/v1`.** This tag's call sites mix shapes: some hash a bare label, some a label followed by an 8-byte little-endian ring index. The family rule that follows is arithmetic rather than convention — **a bare label names the same cell as an indexed family whenever it begins with that family's label and is exactly eight bytes longer.** A new protocol word must be checked against every indexed family before it is added; the choice of label is not free.

**What this does *not* claim.** It is not a statement that the widths are what stop a key from claiming authority over an asset address. They are not: the address version byte is checked independently, in `core/validity`, before authorisation reads an address. The claim here is about preimages only — two call sites under one tag, held apart by the lengths of what they hash.

`core/crypto`'s `TestNoTwoVariableLengthHashCallSitesCanShareAPreimage` is this tree's tripwire for both families: it reads the call sites out of the source and refuses any pair whose payloads can coincide. A second implementation has no equivalent unless it writes one, which is why the rule is stated here rather than left in that test.

**Merkleising against a capacity.** `merkleise(chunks, capacity)` is the root of a perfect binary tree of depth `d`, the least integer with `2^d ≥ capacity`. Its first `len(chunks)` leaves are the chunks in order; its remaining `2^d − len(chunks)` leaves are the 32-byte zero chunk; every internal node is `node`. The depth is fixed by the *capacity* and never by how full the list happens to be, which is what stops a root's meaning from moving with the list's length. The capacity is a genesis constant for `CertRoot` (`cert_list_capacity`) and for `CitesRoot` (`max_cites_per_block`), and is `nextPow2(leaf count)` for each of the two subtrees of the state root — the one dynamic capacity in the protocol ([`../docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) §14, F14).

**Binding the length, which is the line SSZ does not determine.**

```
list_root(chunks, capacity) = node(merkleise(chunks, capacity), length_chunk)

length_chunk: len(chunks) as a little-endian uint64 in bytes 0–7, zero in bytes 8–31
```

SSZ fixes `mix_in_length(merkleize(chunks, limit), len)` and stops there. It is written against a bare SHA-256 with no domain separation and no tagged node function, so it answers neither question a tagged protocol has to answer, and an implementer who supplies SSZ's own answers computes a different root for **every** merkleised list here. **Both answers below are this protocol's decisions rather than deductions**, and both are recorded so that a second implementation reads them as choices:

1. **The length is folded in with `node` itself — the same tagged function the tree is built from — and not under a tag of its own.** The protocol has exactly one primitive for combining two 32-byte values into one, and this mix-in is such a combination; a `zcd/listlen/v1` would be a second constant every implementation must agree on, and it would separate a position the capacity already fixes, since the length chunk is the right child of the single node standing above a tree of depth `d`. This is the decision a careful reader is most likely to get wrong, precisely because every other step here *is* separately tagged. **What that argument does not claim**, on the axis it would be natural to over-read it: `zcd/node/v1` separates tree nodes from leaves, and nothing in this line separates one list's root from another's. Where that separation is needed it is the caller's, not the tree's — `state_root` re-tags its two sub-roots under `zcd/stateroot/v1`, and `CertRoot` and `CitesRoot` sit at fixed offsets in a header.
2. **The length is little-endian in the chunk's low eight bytes — not big-endian, and not a 256-bit big-endian integer.** The ambiguity is real rather than theoretical, because this protocol carries both conventions: a state cell's *value* is a 32-byte big-endian integer, while every integer on the wire — every SSZ `uintN`, the nonce, the seed epoch — is little-endian. The length is an SSZ `uint64` widened into a chunk, so it takes the wire convention and the widening is on the right. A big-endian reading puts the same number in bytes 24–31 and produces a different root for every non-empty list.

**`nextPow2(0) = 1`.** `nextPow2(n)` is the least power of two at or above `n`, **and an empty list is rooted at capacity one rather than zero**, so that the capacity is always a positive power of two and `merkleise` is never asked for a tree of no leaves. Capacities 0 and 1 both give `d = 0` and therefore the same root, so this fixes a value rather than moving one — but capacity 2 does not, and an empty list is not hypothetical: `spent_root` is exactly the value below whenever the spent registry is empty, which was measured to be the case for every `post_root` in this corpus. It is still the case for nine of the eleven `post_root`s here, and the two exceptions do not bind the same things. `059-epoch-boundary-over-a-spent-registry` is the vector that condition closed and commits a **two**-leaf spent subtree; `063-coinbase-burned-into-a-payee-spent-in-the-same-block` commits a **one**-leaf one. At one leaf the tree is the leaf — `d = 0`, no internal node, and a one-element array has one permutation — so `063` binds the spent-leaf tag and the `nextPow2` capacity, which at one entry is still a choice (`nextPow2(1) = 1`, not 2), and binds the ordering not at all. Measured, not derived from the shape alone: moving the tag fails both vectors, giving the subtree capacity `nextPow2(n+1)` fails both, and reversing the comparator fails `059` and `011` while `063` passes.

```
list_root([], 1) = node(zero_chunk, zero_chunk)
                 = d7fbcf8a642492eca279c437a841b2686966f5a4b05e39f4af4d328a219f3b88
```

That constant is the cheapest self-check an independent implementation has here: get either decision above wrong and it does not appear. `core/ssz`'s `TestTheDocumentFixesTheListRootSpellingByValue` reads the tag and the constant back out of this section and holds them against what the tree computes, for the reason *Coverage* below gives for every other number this document publishes — a document normative for a second implementation is checked against the tree, not maintained alongside it.

## What the corpus cannot bind

The section above fixes by value two decisions the vectors commit to and cannot explain. This one is about a smaller and more dangerous set: rules the vectors **cannot commit to at all**, so that the only artefact holding a second implementation to them is this document. Each entry says what the rule is, why no vector can reach it, and — where the rule is a choice rather than a consequence — what the alternative was and why it lost.

**The entries below are unreachable for three different reasons, and which one applies decides how the entry is written.** The first two are about *parameter sets*, and they are the two a number can move. A rule can be unreachable *at the parameter sets this release ships*: the input is well-formed, the rule has a definite answer, and only this release's numbers put that answer out of reach, so some other legal parameter set — a future era's re-pin, an operator's private chain — exhibits it immediately. **Those get the answer fixed here**, because the day the parameter moves is the day two already-deployed implementations disagree about a value in `ConsensusRoot()`. Or a rule can be unreachable *by construction of the quantity it is about*: no parameter set, at any era, admits the input at all. **Those get their domain fixed here and no answer invented outside it** — not even the answer this implementation happens to compute — because an answer over an empty domain is a rule nobody chose, which a later reader will mistake for one somebody did. Moving a parameter moves the wall in the second case; it never opens it.

**The third reason is not about parameter sets at all**, and it is written down because the first draft of this section stamped an entry of this kind as the second and the stamp did not govern what the entry then did. A rule can be one whose inputs *every* parameter set admits, where what cannot be exhibited is a **separating** input — one this rule answers differently from a plausible implementation that omits it — because producing one would mean breaking a cryptographic assumption. **Those keep their answer**, because the rule is consensus and that answer is the one every implementation owes; what the entry records instead is that no vector, no test and no differential can hold anyone to it, together with any weaker entailment an implementation of a different shape would lose. The wall here is hardness rather than arithmetic: no era boundary moves it, but neither does it make the input ill-formed, so there is no domain to fix and fixing one would be false.

**An entry added here must say which of the three it is, and the label has to govern what the entry then does** — if it does not, either the entry is wrong or this rule is, and the fix is never to leave the label standing over something it does not govern.

**None of the three is closed by writing a test, and attempting one makes it worse.** An assertion that cannot fail reads as coverage, and a promise wider than the check behind it is worse than no promise. Where a witness test at a legal but unshipped parameter set can supply the antecedent, the entry names that test; where the separating input does not exist at all, the entry says so instead of naming something.

**The health gate admits the epoch that exactly meets its rate.** An epoch is healthy — and so may grow `T` — when `cited_count × 10000 ≤ health_gate_bps × epoch_length`. The comparison is **`≤`**, not `<`, and it is a **choice**: an epoch landing exactly on its rate may grow. `<` was the alternative and it loses because the gate bounds *unhealth*, and an epoch that meets the bound has not exceeded it — the reading whitepaper §8.1's constants take when they state the gate as "cited competing headers ≤ 2% of blocks per epoch", and the same direction `../docs/ARCHITECTURE.md` §8's F2b writes it in. *Why no vector reaches it:* `cited_count` is an integer, so the left side is always a multiple of 10,000, and the two spellings differ only where the two sides are **equal** — which needs `health_gate_bps × epoch_length` to be a multiple of 10,000 too. It is `200 × 2880 = 576,000` on mainnet and on the testnet, and `200 × 64 = 12,800` on devnet, putting the boundary at 57.6 and at 1.28 cited headers. No block can cite a fractional competitor, so no vector in this corpus and no differential can separate `≤` from `<` on any shipped set, and **this sentence is the artefact that separates them.** *Which kind:* **unreachable at the shipped parameters.** The answer exists; a legal parameter set whose product *is* a multiple of 10,000 exhibits it on the first cited header. Both `health_gate_bps` and `epoch_length` are in `ConsensusRoot()`, so such a set must be adopted deliberately rather than inherited. `core/fold`'s `TestTheHealthGateAdmitsTheEpochThatExactlyMeetsItsRate` is the witness test, at exactly such a set; `TestTheHealthGateBoundaryHasNoIntegerAtAnyShippedParameterSet` is the standing assertion that no shipped set has drifted onto the boundary. Do not add a test at a shipped set: it cannot fail, and an assertion that cannot fail reads as coverage of a question it never asked.

**The block ceilings are defined for `T ≤ seq_gas_capacity` and for nothing else.** `T` is the *clamped* sequential target, so `../docs/ARCHITECTURE.md` §15's ceiling table says nothing about a larger `T` — and that is a statement, not an omission. *Which kind:* **unreachable by construction.** Four independent facts close it, and a second implementation should confirm all four rather than any one, because each of them alone is a line somebody could change: a parameter set with `seq_gas_capacity < seq_gas_target_genesis` is refused at load; the epoch controller applies the capacity clamp **before** the genesis floor, so its output never exceeds the capacity; genesis writes `seq_gas_target_genesis` into the target cell and nothing else does at height 0; and the generator behind this corpus writes `T` at exactly four places, every one of them *below* `seq_gas_target_genesis`, to bring a ceiling within reach of a small block — `T₀/64` twice and `T₀/256` once for the two count-ceiling vectors and the burst-bound vector, and one value that is **not** a divisor of `T₀` at all for `064-burst-forfeiture-where-two-floors-are-not-one-division`, which needs a `T` at which F11's two floors and the single exact division disagree and therefore cannot use one that divides the producer's subsidy share. No chain and no conformance artefact can present a larger `T`, at any parameter set, in any era. **So the domain is what is fixed here, and nothing outside it is.** Inside the domain every reading of the table returns the same value for every input, because the input is already under the bound that the disputed clamp would apply to it — so there is no answer inside the domain for this entry to fix, and outside it there is no input for an answer to be about. Above the domain this document therefore chooses nothing, and it withholds the choice **uniformly**: not from the three clamped ceilings while granting it to the four unclamped ones, but from all seven, which is what the label requires. `core/params` extends the table by substituting the argument into the right-hand side as it stands, and so clamps its output; `core/params/naive` refuses a `T` above the capacity outright. **Both are conformant, and a second implementation may do either or a third thing**, because the disagreement is confined to inputs no parameter set admits. What this entry owes a reimplementer is the domain and the four facts that close it — not a convention over the empty part, which would be an answer nobody chose and which a later reader would mistake for a reachable rule.

**Two of V2's strictness clauses admit no separating input, and that is a fact about the rule rather than a gap in this corpus.** `../docs/ARCHITECTURE.md` §7's V2 requires a canonical encoding of the public key and of the signature's `R`, and requires the public key to lie in the prime-order subgroup. Of those, only the subgroup clauses can be recorded by a vector, and both now are: `invalid-low-order-signer` records the low-order case and `invalid-mixed-order-signer` records the mixed-order case `A = A' + T`, which is the one a small-order blocklist can never reach. The two **encoding** clauses cannot be recorded by anything, and it is worth knowing why rather than filing it as coverage still owed. *Why no vector reaches the public key's encoding:* a non-canonical encoding is one with `y ≥ p`; since `p = 2^255 − 19` and the encoded field element occupies 255 bits, the non-canonical encodings are exactly the nineteen values `y ∈ {p, …, p+18}`. Every one of them that is on the curve and is not low order is an ordinary point **whose discrete log nobody knows**, so a signature that *verifies* under one cannot be exhibited — and the low-order ones are already the low-order clause's business. *Why no vector reaches `R`'s encoding:* cofactorless verification reconstructs `R` and byte-compares its re-encoding, so it refuses every non-canonical spelling before this clause is consulted. Deleting either clause changes no answer on any input, so a vector for either would pass both ways and pin nothing. *Which kind:* **the third — no separating input can be exhibited.** This is deliberately *not* the by-construction label, and the difference decides how the entry ends. Every parameter set admits a non-canonical encoding as an **input**; the bytes are well-formed and a verifier is handed them. What no parameter set and no era boundary does is make one exhibitable *in a form that verifies*, and the obstacle is the discrete log rather than any number in `ConsensusRoot()`. So there is no domain to fix here, and fixing one would be false — the domain is everything. **The clauses therefore keep their answer**, because V2 is consensus and not an assumption about a library, and what this entry adds is the record that nothing can hold an implementation to them, plus the entailment an implementation of a different shape loses: **a cofactored verifier, including any batch path, inherits neither, and must test `[L]R` explicitly.** That is the sentence a second implementation has to act on, and no vector will ever tell it so.

## The vector format

Each vector is one executable statement about the protocol.

```jsonc
{
  "name": "transfer-skipped-stale",
  "description": "Two spends of one balance, ordered by Seq…",
  "params": "devnet",                  // which parameter file: "mainnet", "testnet" or "devnet"
  "pre": {
    "cells": [{ "addr": "0x…", "word": "0x…", "value": "6942000000000" }],
    "spent": ["0x…"],                  // the permanent spent-address registry
    "seen":  [{ "id": "0x…", "ttl": 41 }]
  },
  "block": "0x…",                      // hex-encoded ssz(block)
  "expect": {
    "valid": true,
    "outcomes": [                      // in FOLD order, not block order
      { "id": "0x…", "outcome": "APPLIED", "charged": "…", "refunded": "…" }
    ],
    "seq_gas_used": 1200,      // every included certificate: bounds the ceilings
    "par_gas_used": 3668,
    "seq_gas_applied": 600,    // only those that APPLIED: drives the base fees
    "par_gas_applied": 1834,
    "burned": "…",
    "miner_reward": "…",       // the producer's share of the subsidy, plus applied tips
    "treasury": "…",           // the subsidy's treasury share: issuance only, never fees
    "matured": "…",
    "post_root": "0x…",                // present only on epoch-boundary blocks
    "post": { "cells": [], "spent": [], "seen": [] }
  }
}
```

Notes that carry weight:

- **The block is hex-encoded SSZ, not structured JSON.** An implementation that cannot parse the wire format has not implemented the protocol, and a vector that handed it a pre-parsed block would hide that.
- **All numbers that can exceed 2^53 are decimal strings.** JSON numbers are IEEE-754 doubles in most parsers, and a fee that rounds is a consensus failure.
- **Outcomes are in fold order** — sorted by `(underwriter, seq, cert_id)` — not in the order the proposer put them in the block. Erasing the proposer's choice is the point of the sort.
- **`cert_id` is `blake3("zcd/certid/v1" ‖ ssz(certificate with an empty signature list))`.** It covers the authorizing fields and **never the signatures**, which is what makes it one key per authorization rather than one key per encoding — see [the wire specification](../docs/spec/wire.md) §3.1 for why an implementation that hashes the signatures into it is monetarily broken. The `seen` lists in `pre` and `post`, and the `id` on every outcome, are this value. The block's `CertRoot`, by contrast, is a root over each certificate's exemplar hash, `blake3("zcd/cert/v1" ‖ ssz(certificate))`, which does cover the signatures.
- **`expect.rule` on an invalid block IS a conformance requirement, and `expect.reason` is not.** The rule id names which protocol rule rejects the block; the reason is prose about it, and implementations are held to the verdict and the rule, never to the wording. See *What an invalid vector pins* below.
- **`expect.post` is present even for invalid blocks**, where it must equal `pre`: a rejected block changes nothing.
- **`*_gas_used` and `*_gas_applied` are different quantities and are both asserted.** Used counts every included certificate and bounds the block ceilings; applied counts only the ones that applied and is the sole input to the base fees. Conflating them is the R2-H2 hole.

**What the vectors deliberately do not cover, and where the rest of the protocol lives.** A vector is a statement about the *fold*: given this state and these bytes, what state results. It is not a statement about whether a node should have accepted the block in the first place, and it is not a statement about the block's proof of work — no vector's block carries a solved nonce, and every one of them is nonetheless `"valid": true`, because the fold does not evaluate work and never has, and `fold.ApplyBlock`'s only contact with `Header.Target` is recording the declared value (`core/fold`), never checking it. Passing the corpus therefore makes an implementation a peer *at the fold*, and three more things are required of a whole node:

- **The block's own proof of work** — that the sealed header's hash actually satisfies its declared target (`pow.CheckWork`) — checked at every ingress and by fork choice (`../docs/spec/wire.md` §5, §9). No vector exercises this, and none can: it is a property of the engine (RandomX at M3, a trivial BLAKE3 pass on devnet), not of the fold.

  **What the corpus *does* pin about proof of work is the key schedule** (`046`–`051`), because that half is arithmetic rather than engine: the key is derived from the header's height, and a block header must declare the matching epoch in `PoW.SeedEpoch` (B0b, `../docs/ARCHITECTURE.md` §12). Every one of those vectors sits at a key boundary or one block short of it, which is the only place the rule has content — below the first boundary the correct answer and the not-implemented-at-all answer are both zero, so a corpus without those heights cannot tell the two apart. Mainnet and devnet are both covered, because the boundary is a function of parameters and mainnet's is 2,112 while devnet's is 72. The testnet set's boundary (576, from `randomx_key_interval` 512 and `randomx_key_lag` 64) is not covered by a key-schedule vector: `054-genesis-testnet` pins that network's genesis and nothing further.
- **What the declared target must itself equal** (`pow.NextTarget`, whitepaper §8.1/`../docs/spec/wire.md` §9) — this is what the difficulty vectors below are for. They close the *value* half of the gap; `CheckWork` above is the *proof* half, and stays uncovered by design (see the vector format below for why).

  **"Recorded, never checked" does not mean "outside consensus": the recorded value is inside the commitment.** F2c writes `Header.Target` verbatim into the `prev_target` protocol cell ([`../docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) §8), which is a live cell like any other and therefore a leaf of the epoch state root — every `post_root` in this corpus commits to the declared target of the block that produced it. That same cell is what C4 reads: the next block's citations are held against it, `cited_count` gates whether `T` grows, and `T` moves the block ceilings. So a block declaring a fabricated target folds cleanly and the fabrication is **committed** rather than discarded, surfacing one block later through C4 and one epoch later through `T`. Two consequences for a second implementation, and both are conformance rather than policy: an implementation that validates the target inside the fold **rejects blocks this corpus calls valid**, and one that writes anything but the declared value into that cell — a re-derived target, a clamped one — **computes a different `post_root`**. Checking that the declared target is the one `pow.NextTarget` requires is a node-layer obligation ([`../docs/spec/wire.md`](../docs/spec/wire.md) §9, [`../docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) §12); the fold's obligation is to commit what the header said, unaltered.
- **The proof of work of every competing header a block cites** (`../docs/spec/wire.md` §9 rule 7). This one is easy to miss and is genuinely consensus: cited headers feed the epoch health signal, which gates whether the sequential ceiling grows (whitepaper §8.1), so an implementation that counts unverified citations derives a different ceiling and forks. It is the one consensus rule that is specified in the wire document rather than here, because the fold cannot evaluate work without paying a cost §3 of the whitepaper exists to avoid.

  **That rule's second clause — that the checks on a citation are *exhaustive* — is a negative rule, and no vector can bind it.** A cited header's `Time`, `CertRoot`, `CitesRoot`, `StateRoot`, `EmissionAddr` and `PoW.SeedEpoch` are unconstrained, and a node that constrains one of them counts fewer citations than its peers, derives a different `T`, and forks — so adding a check there is as much a consensus change as removing one. The clause *is* expressible as a `"valid": true` vector, since `checkCites` is in the fold, but such a vector refutes only the constraints its chosen field values happen to violate and passes both ways against every other one; choosing those values is choosing which constraints a reimplementer is plausibly tempted by, and that is a judgement no vector in this corpus makes. It is therefore held by `../docs/spec/wire.md` §9 rule 7 as the normative statement, plus `core/fold`'s `TestACitationCarryingValuesNoPlausibleConstraintAdmitsIsStillCounted` as this tree's executable hold — one sub-case per field, each naming the block rule it refutes if `checkCites` ever grows it (B9, B11, B0b, B14, B16, and the ingress drift window) — exactly as the first clause is held by `node/p2p`'s and `node/sync`'s `citedwork_test.go` rather than by anything here. **Neither clause is claimed as corpus coverage, and a second implementation is held to both by the wire document alone.**

One parameter remains uncovered, for a reason worth stating rather than leaving to be rediscovered. **`undo_depth`** is read only by `node/chain`'s fork choice and `node/sync`; it never reaches the fold, so it belongs to the paragraph below rather than to a missing vector.

**`max_certs_per_block_genesis`** was the other, and is now covered at both parameter sets: `033-invalid-cert-count-over-ceiling` at devnet, `044-mainnet-invalid-cert-count-over-ceiling` at mainnet. Both vectors are small because the ceiling is not a constant: `MaxCertsPerBlock(T) = max_certs_per_block_genesis × T / seq_gas_target_genesis` is read from the pre-state cell at every height past 0, so a vector that observes the rule needs `ceiling+1` certificates at *whatever `T` the pre-state declares*, not at the genesis ceiling. Seeding `T` to `T₀/64` puts the devnet ceiling at 4 and `T₀/256` puts the mainnet ceiling at 15, against the 256 and 4000 a genesis-`T` vector would have to carry. That `T` is off-manifold — a live chain floors `T` at `seq_gas_target_genesis` — in the same way every vector's unsolved nonce is, and for the same reason: the fold is what the corpus states, and the fold reads the cell it is given.

**The two vectors carry different certificate shapes, and that is the interesting part.** Both ceilings scale linearly from the same `T`, so to a first approximation the bytes each set allows per certificate does not move with `T`: devnet's `2500000/256` is 9765 B/cert and mainnet's `2500000/4000` is 625 B/cert. Both figures are the naive ratio and both are a little generous: a block spends 236 bytes on itself and four more per certificate out of the same ceiling, so the budget for a certificate *body* is 9760.7 B at devnet and 620.9 B at mainnet. Measured against `core/types`' encoding, a one-move `TRANSFER` carries 1 read and 2 writes and is 848 B, while a one-address `RETIRE` carries 0 reads and 1 write and is 558 B — the cheapest certificate the Era-0 program set admits (`ISSUE` is 1043 B, `MINT` 1074 B). Devnet clears its budget with either; mainnet clears it only with the `RETIRE`. So the devnet vector uses a transfer — the network's representative verb — and the mainnet vector uses retires, which is whitepaper §4's state-compaction verb and a block shape wallets do emit. Neither vector hand-rolls a certificate; both are `wallet.Builder` output.

**Mainnet's count rule is observable only for a band of `T`, and the band's lower edge is ragged.** `MaxCertsPerBlock` and `BlockByteLimit` both floor, and the block is exactly `562n + 236` bytes for `n` certificates, so its utilisation of the byte ceiling is neither constant nor monotone in `T`: ~90 % asymptotically, 91.2 % at `T₀/64`, 94.5 % at `T₀/256` (this vector), 96.5 % at `T₀/320`, and over 100 % — no longer fitting at all — at `T₀/333`. A ceiling of 13 or more fits at *every* `T` that yields it, with 21 B of slack at the worst; a ceiling between 3 and 12 fits only in the upper part of its range, which is why 12 fits at `T₀/320` and not at `T₀/333`; a ceiling of 2 or less never fits. A divisor therefore has to be checked rather than assumed. `T₀/256` was chosen inside the band, and among the divisors yielding a readable number of certificates it has the most slack, not the least. The generator asserts both that the byte ceiling does not bind first and that the block stays under `SeqGasBurst(T) = 4T`, so a parameter change, or a divisor picked outside the band, fails the build loudly instead of silently converting the vector into a byte-ceiling or a B5 test. **The second assertion was against the `2T` soft threshold until the sequential target was lowered, and it was moved rather than relaxed, because at `seq_gas_target_genesis` = 1,600,000 no `T` in `[1, seq_gas_capacity]` satisfies it.** The count ceiling admits `⌊T/400⌋` certificates and the cheapest one the Era-0 program set admits costs 800 sequential gas, so a ceiling+1 block declares `800·(⌊T/400⌋+1)`, which exceeds `2T` at every `T` — the count ceiling and the soft threshold coincide exactly at the encoding floor now, `2 × 1,600,000 = 4000 × 800`. The property the old assertion protected is not lost: what it guarded against was the vector silently becoming a burst-forfeiture scenario, and F11 never evaluates on a block the fold rejects, while the vector's own `expect.rule` pins **B12** and `4T` is the threshold at which that would change to **B5**. All four worked examples above are bit-identical before and after the parameter move, because at `T = T₀/D` every ceiling is `genesis_value/D` and `T₀` cancels.

**The parameter question behind these vectors is not closed here.** An earlier reading concluded that mainnet's 625 B/cert made `max_certs_per_block_genesis = 4000` unreachable and that no vector could exist; that generalised from the transfer shape alone and is wrong as stated — `044-mainnet-invalid-cert-count-over-ceiling` exists. But the design observation underneath survives measurement: reaching 4000 certificates requires *every* certificate in the block to be the protocol's cheapest shape, and even then the block sits at ~90 % of the byte ceiling. A single transfer anywhere in it costs 848 B against a 625 B budget. So for any realistic block mix the byte ceiling binds well before the count ceiling, and 4000 is reachable only in the degenerate all-`RETIRE` case. Whether that is the intended relationship between `block_byte_limit_genesis` and `max_certs_per_block_genesis` is a parameter-set question, not a corpus question. It is tracked with the parameter set rather than settled here — the corpus's own obligation, covering the rule at both parameter sets, is discharged.

`core/fold`'s `TestCertCountCeilingRejects` covers the rule at both sets in Go as well, and still earns its place: it tightens `max_certs_per_block_genesis` directly, which a vector cannot do — a vector records a params *name*, resolved back to the canonical set at replay time — so it observes the rule at each set's genesis `T` with no seeded state at all, and it pins that the comparison is `>` and not `>=`.

Fork choice and header-sequence validation (`node/chain`, `node/sync`) are the same kind of gap for the same reason: they judge a *chain*, and a vector judges one block against a state that is handed to it, never derived by replaying history. Nothing in this corpus format can state "node X, fed these blocks in this order, converges to this tip" — that is what the differential runner and the chaos soak are for (`CONTRIBUTING.md`).

## What an invalid vector pins

An invalid vector carries no outcomes and no fees, so everything it states is in three fields:

```jsonc
{
  "name": "mainnet-invalid-cert-count-over-ceiling",
  "pre":  { "cells": [ /* 240 entries */ ], "spent": [], "seen": [] },
  "expect": {
    "valid": false,
    "rule": "B12",                       // WHICH rule rejects it — a conformance requirement
    "reason": "fold: invalid block: B12: 16 certificates exceeds the ceiling of 15",
    "post": { "cells": [ /* the same 240 entries */ ], "spent": [], "seen": [] }
  }
}
```

`post` is a full copy of `pre`, not an empty object: a rejected block changes nothing, and the corpus states that by repeating the state rather than by omitting it. This vector's is 240 cells.

**Why the rule and not only the verdict.** A replaying implementation used to be held to three conditions — an error, an invalid-block error, and an unchanged post-state — and to nothing else. An implementation that rejected the block for an entirely different reason passed, and the corpus recorded the intended rule only in prose no machine reads. That was not hypothetical: with B4's sequential clause deleted from `core/fold`, `028-invalid-cap-below-base` still passed all three, because the block then reached F9 and tripped a conservation assertion instead. The vector claimed to pin the billing law and could not tell the billing law from a backstop.

**Why the rule id and not the reason string.** Comparing `reason` would freeze English prose into a consensus surface: a clearer message, a translated one, or one carrying a measurement would all be conformance failures. The id is a name in a fixed vocabulary and the message is free to change under it — the same split `core/validity` has made since it was written, whose `RuleError` doc comment has always said golden vectors record the rule and not the message.

**Where the ids come from.** [`../docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) §7 and §8, which are normative for them: `B0`, `B0b`, `B1`–`B18` for the block rules, `C0`–`C5` for a citation's, `V1`–`V9` for a certificate's, `F13` and `F14` for the two fold rules that can reject. An id used by a vector must be *defined* there, because a second implementation has nowhere else to look it up, and `TestVectorRulesAreDefinedInTheArchitectureSpec` holds the corpus to it.

**An invalid vector's block breaks exactly one rule.** Nothing in the protocol fixes the order rules are evaluated in, so a block that broke two could be reported either way by two conformant implementations and `expect.rule` would have no answer. That is a fact about this tree, not a worry: `core/fold` and `sim/refold` answer differently on such a block, one checking citations before the seed epoch and the other after.

Three things hold the property, and none of them proves it — so it is worth knowing which does what.

- **A cross-check against a second implementation.** `sim`'s `TestBothFoldsAgreeOnTheRuleTheCorpusRecords` replays all thirty invalid vectors through `sim/refold` and requires the same id. Because the two folds order citations and the seed epoch oppositely, agreement is evidence of single-rule-ness for any pair they order differently. `TestOverDeterminationIsVisibleToThisCheck` beside it builds a two-rule block from a committed vector and requires the two folds to disagree on it, so the cross-check is armed rather than assumed.
- **Per-vector assertions in the generator, where the margin is thin.** `044-mainnet-invalid-cert-count-over-ceiling` is 9228 bytes against B13's ceiling of 9765 while breaking B12, and a `RETIRE` certificate is 562 bytes — one more certificate and the same block breaks both, so `spec/gen` fails the build rather than emitting it.
- **A necessity sweep, and it is a test rather than a ritual.** `sim`'s `TestEveryInvalidVectorsRuleIsNecessary` deletes each vector's own recorded rule from `sim/refold` and requires the block to become *valid*: had a second rule been carrying it, deleting the first would leave it rejected. All thirty pass, and a single deletion settles it for good — the recorded rule is in the set the block breaks, because a fold reported it, so if that set had a second member the block would still be rejected and the gate would fail. Over-determination of any size fails on the first deletion; the check is complete rather than a sample. It deletes from `sim/refold` rather than `core/fold` for a second reason beyond the one below: `refold` carries one non-rule backstop (a single `panic`) against `core/fold`'s thirteen `conservationFailure` sites, so `028` above becomes plainly valid here instead of falling through to an assertion. The question the sweep asks is whether a second *rule* was carrying the block, and a backstop is not a rule — which makes the naive fold the better instrument for it. This is the check that does not care about evaluation order, and so it is the only one that covers a pair of rules both folds order the same way — `B3` before `B8`, which is where the two re-signed-exemplar vectors (`052`, `053`) live. Its companion `TestNecessityCatchesTheOverDeterminedBlockAgreementMisses` builds exactly that block (the in-block duplicate, with the authorization also in the seen set) and requires the sweep to refuse it, so the gate is armed rather than merely green. The deletion switch is in `sim/refold` and deliberately **not** in `core/fold`: a rule-disabling switch inside the consensus fold would be a way to build a node that silently does not enforce a rule, which is a worse thing to own than the property it would prove.

**What states the intent.** `expect.rule` records what the fold did; `rejectedBy` in `spec/invalid_rules_test.go` records what the vector is *for*, by hand, beside the vector's name. `TestInvalidVectorsPinTheRuleTheyAreNamedFor` folds each block and holds the fold's answer, the committed id and the table to each other. The table is what catches a *new* vector whose block breaks a rule other than the one its name claims — a case where the JSON and the fold agree with each other and are both beside the point.

## The difficulty vector format

`pow.NextTarget` takes a window of preceding headers and a parameter set, and nothing else — no consensus state, no block. That statement cannot be squeezed into the `(pre-state, block)` shape above, so it is a second, parallel vector kind rather than an optional section bolted onto the first:

```jsonc
{
  "name": "short-window-early-chain",
  "description": "Three headers…",
  "params": "mainnet",                 // which parameter file: "mainnet", "testnet" or "devnet"
  "headers": ["0x…", "0x…", "0x…"],    // ssz(header), oldest first — the exact window
  "expect": {
    "next_target": "883423532389192164791648750371459257913741948437809479060803100646309888"
  }
}
```

- **Headers are hex-encoded SSZ, oldest first** — the same "cannot parse the wire format" discipline `vectors/*.json`'s `block` field already follows.
- **`headers` may hold as few as one entry.** A real chain calls `pow.NextTarget` with fewer than `DIFFICULTY_WINDOW+1` headers for its first `DIFFICULTY_WINDOW` blocks — `chain.RecentHeaders` returns whatever exists, oldest first, never padded — and the vectors deliberately include that shape rather than only the steady-state full window.
- **`next_target` is decimal**, for the same 2^53 reason every other unbounded number in this corpus is.
- Replay is `pow.NextTarget(headers, params)` and a comparison — nothing else. `TestGoldenDifficultyVectors` in `spec/vector_test.go` is that replay arm.

## Running them

```sh
go test ./spec        # the reference implementation against both corpora
zcd vectors          # any build of zcd against the corpus
```

For an independent implementation, the whole conformance harness is about fifty dull lines per corpus: load the pre-state, decode the block, fold it, compare — or, for the difficulty corpus, decode the headers, call the difficulty rule, compare. `spec/vector_test.go` is both harnesses, written as dully as possible so either is easy to port on its own.

## Changing them

```sh
make vectors          # regenerate from spec/gen, then verify
```

The vectors are generated rather than hand-written, because a hand-written 800-byte SSZ block is a typo waiting to become a protocol. What makes them meaningful is not where the bytes came from but that they are committed, reviewed, and thereafter frozen. `spec/gen`'s `capture` builds a `vectors/*.json` entry by driving `fold.ApplyBlock`; `captureDifficulty` builds a `vectors/difficulty/*.json` entry by driving `pow.NextTarget` directly, since no block or state is involved.

**A regeneration that changes an existing vector is a consensus change.** It shows up as a diff in a pull request, and it is reviewed as one. If you did not intend to change consensus and a vector moved, that is the finding.

**The difficulty vectors are pinned against `core/pow.NextTarget` as it stands, not against what it should be.** Defects filed against that function land on this corpus in two very different ways:

- **The floor-at-zero on a backwards solve time** (**fixed in `core/pow` as of this revision**: the accumulator is signed and the per-sample clamp symmetric at ±maxSolve) — **no pre-existing vector depended on it, and the fix moved none of them.** Every one of the first twelve windows here uses strictly increasing timestamps, so the signed rule computes the identical answer for all of them; that is why this revision regenerates the corpus without a single `next_target` moving. `TestOnlyBackdatedVectorsDependOnTheSignedSolveTime` recomputes those vectors under the *retired* floor-at-zero rule and fails if any answer moves — note the polarity, its mutation arm now models the rule `core/pow` had before the fix, not a proposed one. It first proves, on a deliberately backdated window, that the mutation it applies changes the answer at all — a guard whose mutation cannot fire is not a guard. Two vectors added here *do* depend on the fix, deliberately: `signed-backdate-cancels` and `signed-backdate-cancels-devnet`, whose windows carry a genuinely decreasing timestamp, so that the fix cannot be silently reverted. A third, `on-time-holds`, is the paired control — its own window is strictly increasing, so it does *not* depend on the fix; it is the committed "nothing happened" answer the backdated pair is read against, and `TestBaselineVectorsAreAReadableControl` is what holds it to that role.
- **The normalisation basis** (closed: the ratio is applied to the window's **average** target, canonical Zawy LWMA) — **exactly one vector depends on it, deliberately.** `normalises-against-the-window-average` is the only vector whose window declares *different* targets, and it is the only one that can see the difference: on a window whose targets are all equal the two bases coincide identically. Without it, `core/pow` could be switched back to last-target normalisation and the entire corpus — and `make vectors` — would stay byte-for-byte green, which is precisely the hole that lets a second implementation write the wrong form, pass conformance, and fork at the first retarget. Its committed value is exactly 7/3 of `GENESIS_TARGET`, the average of the window's declared 4×/2×/1× targets — which is what the vector predicted before the fix landed, and the only expected value the fix moved.

The same reasoning is why `relative-ceiling-boundary` is written to be agnostic between the two mechanisms that enforce the per-block rise today (the per-sample cap, and a post-hoc comparison that is unreachable given the cap): it pins the observable bound, not the branch. The cap's own existence and value are pinned separately, by `per-block-solve-cap`, on a window where both clamps are far away.

## Coverage

The corpus is checked for coverage by `TestVectorCoverage`, and what that test enforces is worth stating exactly, because an earlier form of this sentence was a misdescription of it rather than a promise about the corpus. The test **derives** the outcome vocabulary from `core/fold` instead of listing it: an AST scan of the `Outcome` constant block and a round trip through `Outcome.String()`, each required to account for the other, so an outcome added to the fold arrives already demanded here and one added without a wire name fails rather than disappearing (the established pattern — a document normative for a second implementation is checked against the tree, not maintained beside it). Every derived outcome must then **either appear in the corpus or stand in a closed exemption table that says why it cannot**. Three appear: `APPLIED`, `SKIPPED_STALE` and `DROPPED`.

**`SKIPPED_OVERFLOW` is the single exemption, and the reason is unreachability rather than an unwritten vector.** For any asset the sum of every balance cell equals its `minted` cell, which a `GUARD_LE` holds at or below the asset's immutable cap, and for the native coin the sum equals what has been emitted; so no credit can carry a cell past 2^256 and no guarded debit can underflow. That is I1-L8 in [`../docs/adversarial/I1.md`](../docs/adversarial/I1.md), and `core/fold`'s `TestMaxCapSupplyBoundsEveryCreditBelowOverflow` runs the fold at the boundary the argument turns on — a slot minted to one unit below the largest cap the protocol admits, credited to exactly the cap. The outcome and its code path are kept, because unreachability is a property of the Era-0 operation set and not of the fold. The exemption is not a standing licence: the table must be a subset of the derived set, and an outcome listed in it that *does* appear in a vector fails the test, so the era that makes this outcome reachable retires the exemption instead of inheriting it. **What the corpus therefore states about `SKIPPED_OVERFLOW` is nothing**, and an implementation that never returns it passes every vector here — the hole is written down rather than covered.

The vocabulary is implemented twice, which makes it rule 12's shape: `sim/refold` carries its own copy as strings. `sim`'s `TestBothFoldsNameTheSameOutcomeVocabulary` reads both — the reference enum through `String()`, the naive one out of its own source — and requires the same set, so a fifth outcome added to one fold and not the other fails there rather than quietly narrowing this gate to whichever copy the corpus happens to name.

The corpus must also contain both valid and invalid blocks. The invalid half is checked twice more, for the reasons *What an invalid vector pins* gives: `TestInvalidVectorsPinTheRuleTheyAreNamedFor` requires every invalid vector to be rejected by the rule it is named for, and `TestVectorRulesAreDefinedInTheArchitectureSpec` requires every id it names to be defined in the architecture specification. Beyond that, the scenarios deliberately concentrate on the rules that exist because somebody tried to break them — replay, expiry, unbounded TTLs, caps below the base fee, one-shot burn-and-refund cycles, the mint-cap race, deposits from burned addresses, and blocks of pure skips.

**The stateless rules are covered as a class, not as a list.** An independent audit of the consensus axis measured what this corpus separated of §7's V-rules and found two of nine: V2 and V5. The consequence it named is the reason `TestEveryVRuleIsSeparatedByTheCorpus` exists — **an implementation that omits V3 entirely used to pass every golden vector and every corpus test**, because V3 is the only rule tying declared writes to the program, and a certificate declaring an extra `DELTA_ADD` needs no signature under V4 and trips nothing in V1, V5, V6, V7 or V9. That is an *over-acceptance* gap, and it is invisible to every other check here: each of them asks whether a rejection is correct, and none asks whether a rule has any vector at all. The test reads the V-rule ids out of `../docs/ARCHITECTURE.md` §7 — the document that is normative for them, so the next era's rule arrives already counted **provided it is written in the shape its neighbours are: a top-level bullet, `- **V10 — …`, at column zero.** That is how the scan finds a rule, and it is the sharpest limit on this gate: a rule §7 states as an indented sub-bullet, inside a table, or in prose is not counted, no exemption is demanded of it, and the test passes. The scan's landmarks catch the list being reformatted wholesale; nothing catches one addition that does not match. **A rule added to §7 must be added as a top-level bullet, or it is outside this corpus's coverage guarantee.** The test requires each counted rule to be recorded by an invalid vector or to appear in a closed exemption table whose reason it then *arms*. `055`–`058` are the vectors it demanded: a transfer signed for another chain (V1), a write the program does not derive (V3), a debit no signature authorises (V4), and a `MINT` into the one-shot cell that funds it (V6). Three rules are exempt and each exemption is a mechanical claim rather than a sentence: V8 is stated in §7 but enforced as a block rule, so the corpus pins it under `B2`; V7 and V9 are unreachable through `validity.Check` in Era 0, because no Era-0 derivation produces a protocol cell or an unknown address version, so V3 answers first and a vector aimed at either would record V3 and pin nothing. The test builds those certificates and requires both halves to still hold — the predicate answers V3, *and* the exempt rule still rejects them when asked directly — so an era that makes either reachable fails here instead of inheriting the exemption.

**Four vectors, `059`–`062`, came from auditing the corpus as an artifact in its own right rather than from noticing a gap while doing something else**, which is what two independent audits asked for on finding the corpus binding less than it appeared to. Each was required to be shown *failing* against a verifier missing exactly its clause and passing against the one that has it — a vector that passes both ways states nothing — and each names what it does not reach:

- **`059-epoch-boundary-over-a-spent-registry`** is the first `post_root` here taken over a non-empty spent registry. Every earlier committed root was taken over `list_root([], 1)`, so the spent-leaf tag, the registry's sort order and its `nextPow2` capacity were inside no commitment at all, and an implementation that got any of them wrong replayed the whole corpus green and then diverged at F14 the first time a boundary landed with an address burned. Two entries and not one: at capacity 1 the subtree is a single leaf with no internal node, so a reversed comparator computes the same value. *Not reached:* the padding of a partially filled subtree, and every capacity above 2 — held instead by `core/state`'s differential against `core/state/naive`, which is a merkleisation that does not import `core/ssz`.
- **`060-invalid-transfer-of-a-non-asset-id`** records V3 at `deriveTransfer`'s asset whitelist: a move whose `Asset` is a well-formed `0x01` address, a version V9 admits and no asset can carry. Its declared reads and writes are exactly what the derivation produces once the id is admitted, which is what makes an implementation without the whitelist *accept* the block rather than reject it for a mismatch.
- **`061-invalid-signature-count-over-the-ceiling`** records **B18**, the per-block signature ceiling `MaxSigsPerBlock(T)` — and it is the same block that used to record **B5**, which is worth stating rather than renaming quietly. The first block here refused by B5 was built the hard sequential ceiling `SeqGasBurst(T) = 4T`, out of the gas-densest Era-0 family: RETIRE of fifteen one-shot addresses paying its deposit from a sixteenth. That family spends **one signature per 706 sequential gas**, so reaching 4T needs far more signatures than `max_sigs_per_block_genesis` scaled to the same `T` admits — and B18 is checked *before the loop that verifies a signature*, which is the whole of the rule, so it is checked before B5. **What the vector pins is that ordering:** an implementation that counts signatures after verifying them has bounded nothing, and this block is the input that says so. *The shape of the claim:* the count is derived from the ceiling at `T = T₀/64`, and the block sits inside B5's 4T bound while above the 2T soft threshold — a forfeiture, not a rejection — which is what keeps it single-rule. **The cost, recorded rather than glossed: the corpus no longer carries a B5 vector.** B5 is not thereby unreachable; nobody has taken a census of the Era-0 shape space, and `core/fold`'s `TestB18BindsBeforeB5OnTheGasDensestFamily` states exactly what is measured — that B5 is out of reach *on the family that used to witness it*, and nothing wider. B5 joins B11 and B16 as a rule an implementation must enforce with no vector to catch it.
- **`062-invalid-mixed-order-signer`** records V2's torsion clause with a public key `A = A' + T` that is *not* small order, so no blocklist of any finite size names it. The Go standard library's cofactorless `ed25519.Verify` accepts the signature; this tree refuses it because V2 requires `[L]A = O`. `031-invalid-low-order-signer` does not cover this: deleting the torsion test leaves `031` passing, which is how the gap was measured.

**Two more, `063` and `064`, came from the same audit applied to the prose rather than to the corpus**: both were found by asking, of every paragraph in a document being compressed, whether a test, vector or constant pins the fact it states. Both are *valid* blocks, so what separates them is not a rule id but a number the fold reports and a cell it writes; each was shown failing against a fold missing exactly its clause while every other vector passed.

- **`063-coinbase-burned-into-a-payee-spent-in-the-same-block`** is the only artefact in this tree that reaches **F12**'s burn arm, where a matured reward owed to an address that has since burned its signing authority is destroyed rather than credited. Nothing reached it before, and structurally rather than by oversight: every mining payout here is a persistent address, and a persistent address can never enter the spent registry — consensus permits a `0x01` payout (B11 admits any user address; the `0x02` rule is a wallet and command-line guard), which is exactly why the arm exists. What it pins beyond the arm is the **stage order**: F12 rolls the ring *after* the certificate loop, so a `RETIRE` in this very block is seen by the release side, and a fold that rolled the ring first would find the payee unspent and credit it. The block is on an epoch boundary, so the disagreement is inside a committed root rather than only in `matured` and `burned`. *Not reached:* the zero-reward arm, which is a different property held directly by `core/fold` and `sim/refold`; and the case of a payee burned by an *earlier* block, which takes the same arm but cannot observe the order.
- **`064-burst-forfeiture-where-two-floors-are-not-one-division`** is the only vector that reaches **F11**'s burst valve at all. A block between `2T` and `4T` is valid and forfeits the producer's block revenue — its subsidy share plus the block's fees, since the base was re-denominated — as `floor(floor(base × excess / 2T) × excess / 2T)`, which is not the integer the single division `floor(base × excess² / (2T)²)` gives; the two-step form is chosen because `(2T)²` leaves 64 bits once `T` has grown for decades. The single certificate is *dropped* — an empty one-shot deposit cell — which is the case the rule is about, since the valve is assessed on included gas, applied and skipped alike; nothing else in the block burns anything, so `burned` is the forfeited integer itself. *The shape of the claim:* the two forms differ at a counted subset of the `T` this shape admits, and this vector takes one of them; it is **not** a claim that they differ everywhere, and at every `T` dividing the producer's share they provably collapse. *Not reached:* the band's two edges, where the forms agree by construction, and the wide-`T` regime the two-step form exists for, which no parameter set this corpus can carry reaches.

**What this does not claim is one vector per *term*, and that is now a decision rather than a gap.** Several V-rules are conjunctions, and a vector separates the rule rather than every clause of it: V4's minimality clause (a signature authorising nothing), V6's debit-coverage and provable-overflow clauses, and V1's ordering, limit and fee-bid canonicity clauses. The corpus's claim is the one a second implementation needs first — that a rule *exists* at all — and `core/validity` is where a rule's interior is held. The reason the line is drawn there and not one level down is the artefact's own vocabulary: a vector records `expect.rule`, a single id, and has no field naming *which term* fired. Sixteen more frozen vectors all recording `V1` would carry their discriminating purpose only in their bytes, checkable by nothing — which is the failure `TestInvalidVectorsPinTheRuleTheyAreNamedFor` exists to prevent one level up, reproduced one level down with no machinery. Several of the terms cannot be frozen at all: V1's list bounds, sort orders and fee-bid canonicity are re-enforced by `types.UnmarshalCertificate`, so a vector for them would not decode and would pin the decoder rather than the rule, and four of V6's seven terms are unreachable through `validity.Check` in Era 0, so a vector aimed at one would record V3.

So the interior is counted where terms have identity — at the rejection site itself. `core/validity`'s `TestEveryRejectionTermIsSeparated` reads every `failf(rule, …)` site of V1 through V6 out of that package's own source and requires one separating input per site: thirty-eight terms, thirty-eight inputs, no two inputs keyed to one site. Before that test existed, "stated by `core/validity`'s own tests" is what this paragraph claimed and it was not true — V6 had seven terms and three inputs, and V1 through V4's twenty-two were counted by nothing. **Its limit is its discovery rule, and it is the same shape as the one above: a term is a `fail`/`failf` site inside `core/validity`.** That limit points in two directions and both are real.

*Outward:* a clause enforced in another package is outside the count. `types.UnmarshalCertificate`'s copy of V1's bounds, orderings and fee-bid canonicity is exactly that, and a second implementation reading this paragraph should take it as a statement about `core/validity`'s predicate, not about every place this tree happens to refuse the same bytes.

*Inward:* two of the thirty-eight sites are formatless `fail(rule, err)` pass-throughs that forward a delegated check's error — V1 forwards `Program.CheckShape`, V3 forwards `DeriveCert` — and **a pass-through counts its delegate's whole interior as one term.** `DeriveCert` is itself in `core/validity` and spells thirteen distinct sentinels across **nineteen** return sites, all reported as one under V3; eighteen are deletable without a compile error. `CheckShape` spells two sentinels across six sites, also reported as one under V1.

**Both interiors are counted by a second enrolment, and it does not reuse the first one's key.** `core/validity`'s `TestEveryDerivationTermIsSeparated` and `TestEveryProgramShapeTermIsSeparated` read the delegates' rejection sites out of the source and demand one separating input each, as a bijection rather than a list. A site is keyed by **(enclosing function, sentinel)** in `derive.go` and by **(switch arm, sentinel)** in `CheckShape`, because sentinel identity alone is not a key: five of `derive.go`'s thirteen sentinels appear at two sites each — `ErrEmptyProgram`, `ErrZeroAmount`, `ErrBadDst`, `ErrZeroCap` and `ErrAmountOverCap` — and one of those collisions is `deriveMint`'s `ErrAmountOverCap` against `slotSums.add`'s, which is the one site in the file with an unbounded consequence. Both keys are checked to be injective, so a second site sharing one fails the test rather than silently sharing an input.

**Those seventeen were not peers before they were separated, and the worst of them was not a matter of test vocabulary.** Seven of them had no input at all and survived deletion with `core/validity`, `core/types` and `spec` all green. Three were over-determined — something else answers and the certificate stays invalid. Three made `validity.Check` accept a malformed certificate. **One is committed inflation:** with `slotSums.add`'s overflow guard removed, a two-move `TRANSFER` summing to exactly 2^256 derives a `GUARD_GE` of 0 and a `DELTA_SUB` of 0 against its source while crediting 2^256−1 to a destination — `validity.Check` returns nil, `UnmarshalCertificate` returns nil, **`fold.ApplyBlock` returns APPLIED on a valid block**, the sender pays only the fee, and total supply moves from 10^9 to 2^256−1 in one block. Nothing downstream catches it: `stageWrites` checks per-cell overflow only, every `conservationFailure` site is a fee, subsidy or treasury accumulator, and `core/fold`'s own overflow-unreachability proof rests on conservation (I1-L8) — the invariant that single guard upholds. That site now carries two checks: an input through the whole predicate, and `TestDerivationEmitsExactSumsOrRefuses`, which requires every accepted derivation to emit **exact integer sums** — the property the guard upholds, stated over a domain rather than at a point. That sweep is **exhaustive over one and two moves** across an alphabet whose amounts cross the word (three user addresses, two assets, amounts 1, 2, 2^255 and 2^256−1), plus a **reduced** three-move pass that drops one address, one asset and the amount 2. Two moves is where a wrap can first appear and, because `slotSums.add` returns before it stores, where every wrap must appear — so the three-move pass is insurance rather than coverage, and a second implementation should read it that way rather than as a uniform exhaustive sweep.

**That guard is present and correct in this tree, and eighteen of the nineteen sites fire today.** The nineteenth is `Derive`'s own `default:` arm returning `types.ErrProgramKind`, which is unreachable — `Program.CheckShape` runs first and its own switch already refuses every kind outside the four. That is swept exhaustively rather than sampled: all 256 program kinds against all 16 subsets of the four body pointers, the complete domain the type admits, with no escapes. It is a Go exhaustiveness stub with no protocol content, which is why it is also the one site that cannot be deleted without a compile error, and it is the one site the second enrolment declines to demand an input for — structurally, as the sole return inside a `default:` clause, with the two scans required to agree on how many such sites exist. **A second implementation should therefore read eighteen behavioural clauses here, not nineteen** — the nineteen counts *sites a scan can see*, and one of them is scaffolding. So *thirty-eight terms* is likewise the count of sites this scan can see, not of clauses the predicate contains, and the term-level claim is bounded by that.

**What the second enrolment still cannot do, stated because the first one's limits are:** `errors.Is` tells an input which sentinel answered, never which site. Two sites sharing a sentinel are therefore separated by *construction* of the input, backed by one further observable — the program kind, which is injective against the sentinel across all eighteen sites and is compared per input. An input that drifted from `slotSums.add` to `deriveMint`'s `ErrAmountOverCap` would have to have changed program kind from `TRANSFER` to `MINT` to do it. That is the strongest observable available from outside the package; it is not a proof of site identity.

**Every number in these paragraphs is derived from the source by a test, not restated here.** `core/validity`'s `TestSpecReadmeNumbersAreDerivedNotAsserted` parses them back out of this document and compares each against what an AST scan of the tree actually finds — the thirty-eight and its two pass-throughs, the thirteen and the eighteen, the seventeen, and `CheckShape`'s two and six — and fails if the document and the tree disagree, or if the phrasing it reads disappears. This follows `spec/invalid_rules_test.go`, which reads V-rule ids out of `docs/ARCHITECTURE.md` §7 for the same reason: a document normative for a second implementation has to be *checked against* the tree rather than maintained alongside it. **The one number that is not bound is the seven that used to survive** — that is a mutation-testing result, and no passing test can derive it without writing the mutants into the tree. It is a statement about the tree *before* the second enrolment: with that enrolment in place all seventeen are killed, by deletion of the return and by neutering the condition, which is re-measured by hand and cited from here rather than asserted.

**The provenance of "eighteen" belongs beside it, because a count is only as good as the scan behind it and this one was wrong once:** it is a `return` of a named error at any arity, methods included. An earlier version matched only `return nil, nil, Err…` and missed the bare return inside `slotSums.add` — which is the inflation site above, found by re-deriving the count rather than by the scan. **And the term scan that produces thirty-eight has a shape it cannot see:** it matches a call whose function is a plain identifier, so a `fail`/`failf` reached through a function-valued variable is skipped silently. No such call exists in the tree, so the miss is latent; it is stated because a number published as conformance text should carry the shape of the scan that produced it.

The difficulty corpus is small enough to state its coverage by hand: the early-chain window too short to hold any solve (`len(recent)<2`) and the two-header window immediately past it (the branch's own edge, where an off-by-one in the threshold is a tenfold disagreement on block 2), a short window still filling (`n` shrunk below `DIFFICULTY_WINDOW`), a window *longer* than the rule may use (truncated to the newest `DIFFICULTY_WINDOW+1`, a shape no caller in this tree produces and a second implementation's header store easily does), a full window's linear weighting away from every clamp in each direction, which target the ratio is applied to, the per-sample solve cap observed well inside both clamps, the relative floor and the relative ceiling each firing, the absolute ceiling `MAX_TARGET` firing, the final floor at one, a full on-goal window holding the target steady as the declared control case, a genuinely backdated timestamp cancelling across the two intervals it touches instead of donating to one of them on both parameter sets, and a gap of 2^63 seconds — the one input on which taking the solve magnitude in `uint64` before signing it differs from widening the raw difference to `int64` first, which is the natural way to get the sign wrong and is otherwise invisible to the whole corpus.

What it does have instead of a coverage counter is a **non-vacuity check**, which is the stronger statement of the two. CONTRIBUTING requires that a test of a rule assert the rejected rule would answer differently *in that test's own scenario*; `TestDifficultyVectorsAreNotVacuous` enforces exactly that for every vector here. It carries a second implementation of the rule that can omit one clause at a time, a table naming for each vector the clause it exists to pin, and a requirement that the table and the corpus name the same set — a new vector arrives with its discriminating rule stated, or it does not arrive. Two clauses of `NextTarget` are currently unpinned, and it is worth knowing which rather than rediscovering them under a mutation sweep. One is dead code: the `weights == 0` fallback, unreachable because `Params.Validate` rejects `difficulty_window == 0` and the early return guarantees at least two headers. The other is live and reachable under legal block production, and is unpinned only in that no vector here names it yet: the guard that lifts a non-positive numerator to one fires whenever the window's weighted solve time falls to or below zero, and that is what the target's fall to the absolute floor is *made of* in the backward direction — not a window built to be about nothing else. It is reached not by *more* backdating but by a particular **mixture**: a producer holding six of every eleven headers backdates against the honest minority's clamped positives until the weighted accumulator goes non-positive; eleven-of-eleven does *not* reach it, because with every header backdated to `median+1` the declared series advances monotonically and the sum stays positive. `core/pow/median_bound_test.go`'s `TestTheDeclaredClockThresholdIsWhereTheControllerLeavesGenesis` measures the branch directly on mainnet parameters — the weighted accumulator is non-positive on 709 of 1300 blocks at six-of-eleven and on none at five-of-eleven, every header one `CheckMedianTime` admits — so this is legal production, not a constructed window. Whether the corpus should gain a vector on this guard is a corpus decision and is left open here. The post-hoc relative up-clamp used to be listed here as the third: it was dead only while the ratio was applied to `last`, the same value its own bound derives from, and normalising against the window average makes base and bound different quantities that can diverge, so it is live and pinned now — `relative-ceiling-boundary` names it in `pinnedBy`, and `core/pow/upper_clamp_test.go` drives it directly.

It caught two vectors during this corpus's own construction: one whose expected answer coincided with the answer a missing early return would give, and one whose solve times sat exactly at the cap it claimed to test, so removing the cap changed nothing.
