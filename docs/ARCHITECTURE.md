# Zycord Node — Architecture & Implementation Specification

**v0.8 — engineering companion to the whitepaper. Scope: the Era-0 reference node (`zycordd`).**

**This document is not normative.** The protocol is `spec/params*.json`, `spec/vectors/`, `spec/README.md`, and the named rules (V\*, B\*, F\*, I\*) wherever they are defined; `docs/spec/wire.md` carries the peer-layer MUSTs. This file explains that surface and records the decisions behind it. Where it disagrees with the normative surface, the normative surface wins and this text is corrected — a stale sentence here is a reading cost, not a defect of the product. No number written by hand below is a source of truth: it is generated from code, asserted by a named test, or an illustration nothing else may cite.

Revision history is in git, and the network has not launched, so nothing below describes what a rule *used to be*. Three closures are recorded rather than dropped, because deleting them invites the work to be redone: both divergences from whitepaper §8.1 — *producer*-subsidy rather than full-subsidy forfeiture at the bound, and all three block ceilings elastic rather than the sequential one alone — were ratified and closed **in the paper** (§15 decisions 1–2); and the certificate id's exclusion of `Sigs` closed a third the same way, the paper having enumerated the id's preimage with the signatures in it (§4).

## 0. How to read this

Sections 1–2 set principles and the shape of the system. Sections 3–5 fix primitives, encoding, and data structures — the things that cannot change after genesis. Sections 6–12 specify consensus behavior: the cell model, stateless validity, the fold, native operations, deposits and billing, and proof-of-work. Sections 13–15 cover the node around the consensus core: networking, storage, fees. Sections 16–20 cover code organization, phase gating, testing, genesis, and milestones. Section 21 is the decisions log.

Terminology is inherited from the whitepaper: *certificate*, *fold*, *skip*, *underwriter*, *cell*, *epoch beacon*. This spec adds **drop** (a non-billed non-event, §10) and the system's billing law: **one signature, at most one bill, never at a position its signer could not avoid** (§8, §10).

## 1. Engineering principles

**P1 — The fold is sacred.** The state-transition function lives in one pure package with no I/O, no clocks, no goroutines, no map iteration, and no floating point. It is exhaustively covered by golden vectors (§18) and is the only code whose bugs are unfixable after the fact. Everything else in the node is replaceable plumbing.

**P2 — Determinism beats performance.** Any optimization that risks nondeterminism (parallel fold application, unordered iteration, platform-dependent arithmetic) is rejected in consensus code. Performance belongs in the stateless pipeline, where it is safe.

**P3 — No admin keys, no privileged RPC.** There is no code path by which any key can pause, upgrade, mint, or reorganize. Feature activations are height-gated constants compiled into releases (§17). If it isn't in the fold rules, it doesn't exist. The treasury (whitepaper §14.1) is not an exception, and the distinction is the one a sceptical reader will press: genesis contains **no key and no spend path at all**, so there is no privilege to hold, delegate, or steal, and the 3-of-5 quorum of Era 2 is pinned by a *future hard fork* — the same social mechanism as any other consensus change, subject to the same refusal, and able to move exactly one cell even then. A quorum that only appears if the network agrees to write it in, and that then holds one cell, is a spending rule; an admin key is one that exists before anyone consented and reaches everything.

**P4 — Small consensus surface.** Consensus-critical code (`core/`) imports nothing outside the standard library. The rest of the node may use ecosystem libraries; the core may not.

**P5 — Spec-first.** Golden test vectors in `spec/` are the protocol. The Go code is *a* reference implementation; an independent implementation that passes the vectors is a peer, not a fork. This is what allows the maintainer to eventually be nobody in particular.

**P6 — Reproducible from v0.1.** Every release builds byte-identically from source: pinned Go toolchain, `-trimpath`, pinned dependencies (`go.sum`; the tree carries no `vendor/` directory — pinning is by checksum, not by copy), and — because RandomX is cgo — a pinned C toolchain and RandomX commit inside the canonical build container. Trust moves from the binary to the code, which is the only trust an anonymous author can offer.

**P7 — Era 0 ships nothing it doesn't need.** No VM, no bonds, no sequencers, no lease scheduler in the genesis binary. Interfaces exist so Phase 1 is an addition, not a rewrite (§17), but unreachable code is unauditable code and is excluded.

## 2. System overview

The life of a certificate, end to end:

```
 wallet                      network                        every full node
┌────────────┐   gossip   ┌──────────────┐               ┌─────────────────────┐
│ build cert │ ─────────► │ cert topic   │ ─────────────►│ STATELESS PIPELINE  │
│ (reads,    │            │ (TLS gossip) │               │ V1..V8, batch sigs, │
│ writes,    │            └──────────────┘               │ native re-exec      │
│ sigs, seq, │                                           │  → mark VALID       │
│ deposit)   │                                           └──────────┬──────────┘
└────────────┘                                                      │ mempool
                                                                    ▼
                            miner (any node)              ┌─────────────────────┐
                          ┌───────────────────┐  block    │ FOLD (sequential)   │
                          │ assemble ordered  │ ────────► │ F-rules per cert:   │
                          │ hash list + bodies│  gossip   │ APPLY / SKIP / DROP │
                          │ + RandomX solve   │           │  → new state        │
                          └───────────────────┘           └─────────────────────┘
```

Two predicates, two engines. **Validity** (stateless, parallel, §7) runs once per certificate per node, before and independent of blocks. **Applicability** (stateful, sequential, §8) runs inside the fold at the certificate's committed position. The miner runs no execution; it orders hashes it has already seen validated and solves proof-of-work. The fold is a tight loop over an in-memory working set: compare, add, write.

## 3. Cryptographic primitives

| Role | Choice | Notes |
|---|---|---|
| Signatures | **Ed25519** | Batch verification (the GPU on-ramp), no malleability, tiny keys. Verification is `crypto/ed25519` under a strictness layer in `core/crypto`, and nothing else: there is no vendored point library in the tree, and replacing the strictness layer with one is an open performance option (§21), not something already taken. Strict rules fixed at genesis, stated in full at §7's V2: **canonical encodings required** for the public key and `R`, the public key **torsion-free and not of low order**, and verification **cofactorless** (RFC 8032). Torsion rejection is what makes the batch path safe: a mixed-order key `A = A′ + T` is not small-order, so no blocklist reaches it, and it is exactly where a cofactored batch verifier and a cofactorless single verifier disagree. With `A` and `R` in the prime-order subgroup the two are provably equivalent — so a batch verifier may be cofactored **provided it applies the same encoding and torsion rules before batching**. That obligation is the price of the choice, and the batch verifier does not exist yet. |
| Hashing | **BLAKE3** | Certificate/block IDs, addresses, state root. Fast enough to hash at relay line rate; parallel-friendly for the epoch state root. Isolated behind `core/crypto.Hash`; swappable until genesis, frozen after. |
| Proof-of-work | **RandomX** | CPU-optimized (§12). Via cgo binding to the reference C library, pinned by commit, behind the `randomx` build tag. The only cgo in the tree, and absent from a build without the tag. `POW_ENGINE` names the function a network requires and is in the consensus root, so a binary holding the wrong engine refuses to start rather than accepting the wrong proof (§12). |
| Domain separation | mandatory | Every hash is `blake3(tag ‖ payload)` with tags like `"zcd/cert/v1"`, `"zcd/block/v1"`, `"zcd/addr/v1"`, `"zcd/pow/v1"`. Signatures sign `blake3("zcd/sig/v1" ‖ chain_id ‖ consensus_root ‖ cert_body_root)` — chain-id inclusion kills cross-network replay between networks holding *different* chain ids (mainnet vs testnets), and consensus-root inclusion kills replay across two incarnations of one network, since a respin always moves `genesis_time`. Neither binding separates two networks that agree on both, so the guarantee rests on a rule outside the preimage: a chain id is **allocated once and never reused**, not by a respin and not by a fork (`spec/chain-ids.json`, §7's V2). The ledger is embedded in every binary and read again at startup: a node refuses to come up on a retired id, or on a live id whose parameters derive a genesis other than the pinned one (`spec.CheckChainID`). |

## 4. Canonical encoding and identifiers

All consensus objects are **SSZ** containers. SSZ gives a single canonical byte encoding (no map ordering, no optional-field ambiguity), fixed offsets for cheap partial parsing, and native merkleization — which the epoch state root and future light clients reuse. `cert_id = blake3("zcd/certid/v1" ‖ ssz(certificate with an empty signature list))`, `cert_exemplar = blake3("zcd/cert/v1" ‖ ssz(certificate))`, `block_id = blake3("zcd/block/v1" ‖ ssz(header))`. The first two are different digests answering different questions and the paragraph below says which is which; an implementation that uses one where the other belongs is monetarily broken.

**What the id commits to.** Whitepaper §2 gives the principle — the id "commits to what a certificate *authorizes* and never to what it merely *demonstrates*" — and enumerates it to match. The signatures are outside the preimage because a signature is a randomized demonstration: the signer picks the nonce, every nonce yields another valid and perfectly canonical signature over the same body, and no verifier can check which was used. Were they inside, one authorization would have unboundedly many ids, each billable, each producible by any *one* of its required signers out of the others' authority (the measurement and the rejected alternatives are in §21). Canonical-encoding rules (V2) cannot reach that — a signer varies the nonce, not the encoding — so only leaving evidence out of the preimage can.

`FeeBid` is **inside** the id, and that is a monetary decision rather than a layout one. A bid outside the id would be a bid anyone in transit could rewrite — inflated to burn the signer's balance through the base fee, or zeroed to keep the certificate out of every block that enforces B4. What a certificate pays is part of what its signer authorized, so it is hashed and it is signed. The reason is recorded here because a later encoding change that "moves the fee out of the signed body for relay flexibility" would look like an optimization and would be a theft vector.

**The forward constraint is a constraint on the era that is running.** Evidence — `Sigs` today, the range proofs of whitepaper §12 later — must sit **outside** the id's preimage, because a proof is randomized and re-randomizable. Evidence outside the id is then evidence anyone in transit can replace, so the block must commit to it separately. **That makes evidence a `Header`/`Block` concern, not a `Certificate` field addition.** It is discharged today by `CertRoot` being a root over exemplar hashes: the exemplar hash covers the whole encoding, so it commits to the authorization and to the evidence at once and a second leaf would add nothing. What that buys, stated narrowly because the wide version of it is wrong and was believed here: a block's id determines the signature bytes it carries, so a relay cannot serve two different bodies under one block id (`TestABlockCommitsToTheSignaturesItCarries`). It does **not** buy immunity from a receiver that refuses a body and then holds the refusal against the block id — that failure is in the receiver's own bookkeeping, it fires for any refusal reason, and an id-keyed root neither causes nor cures it (`docs/spec/wire.md` §3.1 states it as a receiver obligation). When evidence becomes separable field by field, `CertRoot` grows into a root over `(id, evidence hash)` pairs, and that is still the right place for it.

Rule: **parse, don't validate twice.** Decoding enforces canonical form (rejects non-minimal encodings, out-of-range enums, unsorted lists where sortedness is required). A decoded object is structurally valid by construction; V-rules and F-rules never re-check shape.

## 5. Data structures

```go
// core/types — all integers are fixed-width; all lists carry genesis-fixed max lengths.

type Slot struct {           // a cell coordinate
    Addr [32]byte            // §6: version byte ‖ 31-byte hash
    Word [32]byte            // sub-key within the address
}

type Read struct {
    Slot    Slot
    Access  uint8            // 0=EXACT, 1=GUARD_GE, 2=GUARD_LE, 3=GUARD_EQ
    Operand [32]byte         // EXACT: the declared value. GUARD_*: the bound.
}

type Write struct {
    Slot  Slot
    Op    uint8              // 0=SET, 1=DELTA_ADD, 2=DELTA_SUB, 3=MARK_SPENT (addr-wide; Word ignored)
    Value [32]byte           // SET: new value. DELTA_*: unsigned magnitude. MARK_SPENT: zero.
}

type Deposit struct {
    Cell     Slot             // native-coin balance cell, debit-authorized by a signer
    Amount   [32]byte         // reserved up front; must be ≥ fee ceiling (§10)
    RefundTo Slot             // remainder is credited HERE at settlement — never to Cell, and
                              // never to any address this certificate marks spent (V5), so
                              // depositing from a one-shot address being burned is safe (R1-C3).
                              // Amount is what a one-shot deposit cell keeps: the certificate
                              // burns the address, so a wallet reserves the whole balance and
                              // takes the change back through RefundTo (wallet.SweepDeposit) —
                              // whatever it does not reserve is stranded under a spent address
}

type Certificate struct {
    ChainID   uint64
    Seq       uint64          // intra-underwriter order (R1-C2): the fold sorts by it, so
                              // dependent certs from one signer commit in signed order
    Program   Program         // Era 0: native op + params (§9). Phase 1+: code ref.
    Reads     []Read          // sorted by Slot; no duplicate slots
    Writes    []Write         // sorted by Slot; ≤1 SET or MARK_SPENT per slot; deltas pre-merged (§7 V3)
    Sigs      []Sig           // pubkey+signature pairs; sorted by pubkey
    Deposit   Deposit
    TTL       uint64          // last height at which this cert may be committed (bounded, §7 V8)
    FeeBid    FeeBid          // seq_gas & par_gas price bids (§15)
    // Underwriter identity in Era 0 = Deposit.Cell owner address (self-insured).
    // Co-signer underwriter variants activate in Phase 1 (§17) reusing (id, Seq) ordering.
}

type Header struct {
    Version      uint32
    Height       uint64
    ParentID     [32]byte
    Time         uint64      // miner-declared; consensus lower bound + FTL withhold (§12);
                             // never read by programs
    CertRoot     [32]byte    // ssz merkle root of ordered cert-id list
    CitesRoot    [32]byte    // ssz merkle root of the cited-competing-header list (§8.1, §8, §15)
    StateRoot    [32]byte    // zero except on epoch-boundary blocks (§8, F14)
    EmissionAddr [32]byte    // miner payout address
    PoW          PoWSeal     // {Nonce u32, ExtraNonce u32, SeedEpoch u64} (§12)
    Target       [32]byte    // LWMA-derived difficulty target
}

type Block struct {
    Header Header
    Certs  []Certificate     // full bodies; bodies are chain data (whitepaper §13)
    Cites  []Header          // competing headers this block reports seeing (§8.1, §15);
                             // bounded by MaxCitesPerBlock, a static structural capacity
}
```

Limits at genesis (illustrative, frozen in `spec/params.json`): ≤ 64 reads, ≤ 64 writes, ≤ 16 sigs per certificate; ≤ 4 cited headers per block (`MaxCitesPerBlock`, §8.1 — a static structural bound, not a policy ceiling). **Certificate count, block bytes, and both gas ceilings are no longer genesis constants** — each is a function of T, the sequential target (§8.1, §15), scaled from a genesis value that is itself illustrative and conservative (R1-M4 — a young network's fork rate is its scarcest resource) — bounded jointly against `CertListCapacity`, the one ceiling that *is* still a fixed genesis constant, because it fixes `CertRoot`'s merkle depth and cannot move with height without changing what every past `CertRoot` means.

## 6. The cell model

A **cell** is the value at a `Slot`. Cell values are unsigned 256-bit integers stored big-endian in 32 bytes. Absent cells read as zero. Separately, the protocol keeps a **spent-address registry**: a permanent consensus set of `0x01` addresses whose signing authority has been burned.

**Addresses.** `Addr = version ‖ blake3("zcd/addr/v1" ‖ version ‖ payload)[:31]`.

| version | kind | payload | debit authorization |
|---|---|---|---|
| `0x01` | one-shot user | Ed25519 pubkey | owner sig; any debiting certificate MUST also carry an explicit `MARK_SPENT` of the address (V6) — after it applies, every read and write under the address fails forever |
| `0x02` | persistent user | Ed25519 pubkey | owner sig; reusable forever (merchants, hot wallets) |
| `0x03` | asset | `chain_id ‖ issuer ‖ seq` (§9) | governed by the asset's immutable authority cells |
| `0x00` | protocol | reserved | fold-only (epoch beacon, base-fee cells, coinbase maturity ring, treasury cell) |
| `0x04` | **reserved — hidden-value cell (Era S)** | — | unreachable in Era 0; see below |

One-shot vs persistent is a *wallet policy surfaced as an address bit*, not two ledgers: the chimeric model in one rule. Wallets default to `0x01` per payment received; anyone who wants an account uses `0x02`.

**`0x04` is reserved now rather than allocated later**, because whitepaper §4 requires a hidden-value cell to be distinguishable from an ordinary one *by its address*: a Pedersen commitment and a u256 balance are both 32 bytes, so a guarded delta aimed by error or malice at a commitment slot would have the fold add an integer to a curve-point encoding — arithmetic that passes every check and leaves a cell nobody can ever spend. This table is frozen at genesis, so the byte is claimed here and left unreachable. **Unreachable by V9**, and by which rule matters because the obvious answer is wrong: V4's `CheckAuthorization` treats `crypto.IsUserAddress` as a *condition for requiring a signature* rather than as a whitelist, so a write to a `0x04` address would need no signature at all under V4 alone, and V3 closes the gap only for certificates a program actually derived.

**Spent semantics (R1-C3).** `MARK_SPENT` is an **explicit, signed write**, address-wide — and because it is address-wide, F8b empties the address as it burns: the native balance cell, and every cell under the address the certificate itself names, move to the same word under `Deposit.RefundTo.Addr` rather than being left where no key can reach them. **A balance in an asset the certificate never names is outside that scope and is still lost, deliberately**: the assets under an address are not derivable from a slot, so no rule can reach them without a full-table scan ([decisions/one-shot-burn-scope](decisions/one-shot-burn-scope.md)). Once applied: certificate reads on any word under the address evaluate false (F6), certificate writes guard-fail, and the address can never be resurrected — because pruning (§14) may delete cell *values* under a spent address after the undo horizon, but **never deletes the registry entry**. The registry is append-only consensus state (~33 B/address, forever) — the protocol's honest open problem, shared structurally with every nullifier-set design.

**Billing is fold-level, not certificate-level (R1-C3).** Deposit reservation, settlement, refunds, fee credits, and coinbase are operations the fold performs directly. They bypass guards and the spent registry **at the destination**, exactly as coinbase always must. Certificates cannot express them (V7); the exemption is uniform and small.

Two boundaries on that exemption (I1-C3, I1-M2). At the **source**, a reservation is subject to both its own `GUARD_GE` *and* the registry: F3 refuses to reserve from a deposit cell whose address is spent, because pruning may delete cell values under spent addresses and a reservation that could read a prunable value would make the fold depend on when a node pruned. At the **destination**, a remainder or a matured coinbase owed to an address that has already burned its authority is **burned**, deterministically, rather than written into a cell nobody can ever read — and the outcome record says which happened (`RefundBurned`, not `Refunded`), because a destroyed remainder reported as a refund is a loss no consumer can see. That rule covers an address burned by some *earlier* certificate; one burned by the *same* certificate is rejected statelessly by V5 and V6 (F-FOLD-1).

**Authorization is stateless.** Which writes need which signatures is derivable from the certificate alone: a `DELTA_SUB`, `SET`, or `MARK_SPENT` on a `0x01/0x02` cell requires a signature whose pubkey hashes to that address (V4). Asset-privileged writes use the **immutable-cell authorization pattern**: the certificate carries an `EXACT` read of the asset's authority cell (immutable ⇒ can never go stale) and a signature matching the declared value; V-rules check sig-against-declared-read statelessly, and the fold's exact-match check guarantees the declared value is the real one. This pattern is the template for all future privileged operations.

**The epoch beacon** occupies three protocol words under the `0x00` address: `beacon.epoch`, `beacon.height`, `beacon.entropy` (16 bytes of `Header.ParentID` — the last block of the epoch that just ended — zero-padded; I1-M6). The source is `ParentID` and not the block at `H − EPOCH_LENGTH` for two reasons, the second deciding: `ParentID` needs no history cell, and it is **revealed only at the boundary**, whereas a block one whole epoch back is known an epoch in advance and would hand anything consuming this value a full epoch of prediction. Both are equally miner-grindable, and R1-L1 applies to each: this is proof-of-work output and is **unfit for high-value lotteries** until a Phase-2 VRF arrives. Programs express time as ordinary guards on these cells — `GUARD_GE(beacon.epoch, e)` — never as ambient reads; F2 refreshes the beacon at each boundary so mid-epoch guards cannot go stale.

**The treasury cell** is the protocol address's own native balance — `NativeBalanceSlot(0x00…)`, credited by F11 and read by nobody. Choosing the ordinary balance word over a bespoke protocol word is the decision that carries this feature, and it was made for the accounting: the conservation property sums every cell whose word is the native balance word and ignores the address, so it counts the treasury without being told the treasury exists. A bespoke word would have needed a special case there, in the state root's readers, and in every later audit — and a special case nobody remembers to add is how a conservation check stops being a check. Nothing else is needed: V7 and F13 already reject every certificate write to a `0x00` address by version byte, and the fold's own credit is an ordinary journalled `set`, so a reorg reverses it. **Era 0 ships no debit path — the seal of whitepaper §14.1 is the *absence* of a rule, not a rule**, which is the only form of seal a chain with no admin keys can offer (P3, P7).

**The elastic sequential ceiling's own cells** (whitepaper §8.1) are five more protocol words, all read and written only by F2b/F2c (§8):

| Slot | Holds | Written |
|---|---|---|
| `seq_gas_target` | T, the current sequential target | F2b, at every epoch boundary but the first; initialised to `SeqGasTargetGenesis` at height 0 |
| `applied_gas_sample[i]`, `i ∈ [0, EpochLength)` | one epoch position's applied sequential gas | F2c, every block, at index `height mod EpochLength` |
| `cited_count` | competing headers cited so far this epoch | F2c, every block that carries citations; zeroed by F2b at each boundary once read |
| `prev_parent_id` | the previous block's `ParentID` — this block's grandparent, from the next block's perspective | F2c, every block, unconditionally |
| `prev_target` | the previous block's declared `Target` | F2c, every block, unconditionally |

The sample ring costs one cell write per block and `EpochLength` reads once per epoch — the honest price of a *median* rather than a mean, chosen because the paper's lineage here is Monero's penalty-median mechanism, and a mean would be a different mechanism with different resistance to stuffing. `prev_parent_id`/`prev_target` exist so a citation can be checked against exactly what a sibling of the parent would have shared, without the fold holding more than one block of lookback (§8).

## 7. Stateless validity (V-rules)

Run by every node on every certificate, in parallel, before mempool admission and during block verification. Requires zero state.

- **V1 — Canonical form.** SSZ decodes canonically; lists sorted; limits respected; `ChainID` matches.
- **V2 — Signature set.** Every `Sig` verifies over the signing root — `blake3("zcd/sig/v1" ‖ chain_id_le ‖ consensus_root ‖ cert_body_root)`, where `consensus_root` is the digest over every consensus parameter that block 0 carries as its `ParentID` (R3-1). Both bindings are part of the rule: the chain id is what a certificate declares and V1 compares, and the consensus root is what makes a signature name one *incarnation* of a network rather than its name, so a respin — which always moves `genesis_time` — does not inherit its predecessor's certificates. What no preimage separates is two incarnations whose parameter values are identical; `spec/chain-ids.json` is the allocation ledger that covers those. The signing root binds the certificate body and never the signature list, which is why one authorization has many valid exemplars (§4). And **a signature’s encoding must be canonical**: an unreduced scalar is invalid, as is a non-canonical point encoding, and a verifier that reduces before checking rather than rejecting is not an implementation of this rule. The reason is cross-implementation agreement, not hygiene: a verifier that accepts an encoding its peers reject forks the network on a certificate nobody can call invalid. (It is **not** the replay defence. Signatures are evidence and sit outside the id's preimage (§4), and canonicity could never have closed that hole, because a signer varies the *nonce* rather than the encoding.) Go's standard library rejects an unreduced `S` and forces `R` to re-encode canonically, but *reduces* a public key's `y` modulo p rather than rejecting `y >= p`, and accepts an `x` of zero carrying a sign bit — so `core/crypto.VerifyStrict` checks the point encodings itself and relies on the standard library only for the scalar.

  **The rule also covers torsion, and only one of the two elements is *tested*** — an auditor diffing this section against the code should expect exactly one `[L]P`. The public key's membership is **computed** (`[L]A == identity`), never tabulated, because the keys it must catch are the mixed-order ones `A = A' + T`, of which there are about 2^252; a small-order blocklist is not a weaker version of this rule but a different and insufficient one (§21). `R`'s membership is **entailed**: cofactorless verification reconstructs `R = S·B − h·A`, which lies in the prime-order subgroup whenever `A` does. That is the whole of the rule for `R`, and the boundary is normative because an earlier implementation crossed it: **`R` must not additionally be tested for low order**, since the only low-order point in the prime-order subgroup is the identity and such a test rejects exactly `R = identity`, a zero nonce that RFC 8032, `crypto/ed25519` and this rule all accept. A *cofactored* verifier, including any future batch path, gets no entailment and must test `[L]R` explicitly. Pinned by `TestSignaturesAreNotMalleable`, `TestLowOrderKeysAreRefused`, `TestNonCanonicalPubKeysAreRefused`, `TestMixedOrderKeysAreRefused`, `TestRIdentityIsAcceptedAsRFC8032Requires` and `TestCofactorlessVerificationIsPinned` — the last asserting cofactorless semantics against the standard library, which does not promise it, so a toolchain that changed would fail CI rather than consensus. Golden vectors `invalid-low-order-signer` and `invalid-mixed-order-signer` are the two vectors in the corpus a naively correct verifier fails, and they are what makes the rule binding on a second implementation. They are not interchangeable and neither is redundant: `isLowOrder` and `isTorsionFree` each catch a key the other does not — `[L]O` is the identity, so the identity key passes the torsion test — and each vector is separated by exactly one of them. Deleting the torsion clause alone leaves `invalid-low-order-signer` passing and the mixed-order block **accepted**, which is the measurement this bullet's blocklist sentence exists to make binding.

  **Of V2's remaining strictness clauses exactly one admits a vector, and that is a fact about the rule rather than a gap in the corpus.** The **torsion** clause admits one: a mixed-order key `A = A' + T` verifies under a cofactorless equation whenever the challenge scalar is divisible by eight, which is a grind rather than a construction problem, and `TestMixedOrderKeysAreRefused` already builds such a key — so a vector was **owed**, and `spec/vectors/062-invalid-mixed-order-signer` is it. It is the one a plausible second implementation fails, since a small-order blocklist plus a cofactored batch verifier is what a reimplementer naturally builds and is exactly what this rule refuses. The two **encoding** clauses admit none, on either side. A public key's non-canonical encodings are exactly the nineteen values `y ∈ {p, …, p+18}`, and every one of them that is on the curve and not low order is a point whose discrete log nobody knows, so a signature that *verifies* under one cannot be exhibited. `R`'s has none either, for the entailment reason above: cofactorless verification re-encodes the `R` it reconstructs and byte-compares, refusing every other spelling before this clause is consulted. **Deleting either encoding clause changes no answer on any input**, so a vector for either would pass both ways and pin nothing — which is the state such a vector would exist to fix. They are stated because V2 is consensus and not an assumption about a library, and because the conditional above — a cofactored verifier inherits neither entailment — is the sentence a second implementation must act on and that no vector will ever tell it. Whitepaper §2 states the rule.

- **V3 — Program agreement, canonicalized.** Era 0: `derive_cert(Program, Deposit.Cell) == (Reads, Writes)`. The write set is the program's derivation **plus the deposit cell's own `MARK_SPENT` when that cell is `0x01`** — the deposit is a debit the fold performs rather than a write (F3), but the authority it spends is burned like any other one-shot debit, and V4 requires the deposit cell's signature. Without that clause V6's unconditional one-shot demand and V3's exact equality are jointly unsatisfiable for `ISSUE`, `MINT`, `RETIRE`, and any `TRANSFER` paying its deposit from an address it does not spend (F-VAL-5). `validity.DeriveCert` is the single definition, used by the rule and by `wallet.Builder` alike, so a wallet cannot derive a write set the rule disagrees with. Derivation **merges all debits and credits per slot** into one guard + one delta before comparison (R1-M1 — guards within one certificate are claims about a single coherent snapshot), and rejects out-of-range operands, e.g. `MINT` with `Δ > cap` (R1-M2). (Phase 1+: run cEVM over declared reads, compare writes.)
- **V4 — Authorization.** Every write that needs a signature (§6) has a matching pubkey in `Sigs`; privileged writes carry their immutable-cell authorization reads. **The deposit cell carries its own signature unconditionally**: V4 requires an authorising signature for `Deposit.Cell.Addr` whatever its version byte, not only when it is a `0x01/0x02` user address. That is defence in depth for the treasury, which is `NativeBalanceSlot(protocol address)` — an ordinary native balance cell — and whose debit at F3 happens outside the declared write set, so V7 and F13 never see it. `crypto.ProtocolAddress` is not a hash, so no key satisfies the requirement and the cell is refused by V4 and V5 alike; at `0x03`, where an address *is* key-derivable, V5's narrower test is still the only gate.
- **V5 — Deposit shape.** `Deposit.Cell` is a native-coin balance cell debit-authorized by a signer; `RefundTo` is a well-formed native-coin slot; `Amount ≥ fee ceiling(cert)` — computable statelessly because `SKIP_FEE` is a protocol constant (§10, R1-H1) — **and `Amount ≤ cumulative emission at `TTL``**, the total coinbase §14.2's schedule can have paid by the last height at which this certificate may be committed. The upper bound stays stateless because cumulative emission is a pure function of a height and the four issuance constants, and because the height comes out of the certificate: `TTL` is the last height `B1` admits it at, and the schedule is non-decreasing, so the bound is the supremum of the coin supply over every height at which the certificate can still commit. **It is not the fix for drop-stuffing and must not be read as one** — §10 states what it does and does not buy. **`RefundTo` must survive the certificate:** it may not name the one-shot deposit cell (R1-C3-i), and it may not name *any* address the certificate's own write set marks spent. F8 commits those `MARK_SPENT`s before F9 settles, so such a refund would be destroyed at settlement while the outcome reported an ordinary refund — and settle cannot tell that case from a legitimately pre-burned target, so the rule has to be stateless and here (F-FOLD-1).
- **V6 — Self-consistency & one-shot hygiene.** No write to a slot also read `EXACT` with a contradictory implied result; delta magnitudes fit; every `DELTA_SUB` write is accompanied by a read on the same slot of access `EXACT`, `GUARD_GE`, or `GUARD_EQ` — never `GUARD_LE` alone, which bounds only from above and cannot license a subtraction — whose operand the subtracted amount does not exceed (generalises R1-M1: every subtraction must be bounded from below by a read on the same slot, so the guard and the delta are claims about one coherent snapshot); any certificate debiting a `0x01` address — the deposit cell included — carries that address's `MARK_SPENT` with an authorizing sig (R1-C3); and **no `DELTA_ADD` may credit an address the certificate marks spent**, which is the write-side form of V5's refund rule (F-FOLD-1).
- **V7 — Protocol exclusion.** Ordinary certificates never write `0x00` cells and never express billing operations.
- **V8 — TTL bound.** `TTL ≤ inclusion_height + TTL_MAX` is enforced as a *block* rule (below); wallets sign TTLs accordingly. This is consensus, not relay policy (R1-H4): without it, seen-set entries are immortal state spam.
- **V9 — Known address versions.** Every address a certificate names — by a read, a write, the deposit cell, or the refund target — must carry a version byte this release defines (`crypto.IsKnownAddressVersion`, `0x00`–`0x03`). Defense in depth, not new coverage today: V3's closed Era-0 program set already never derives an address of any other kind. What it closes is the gap V3 does *not* cover — a certificate built by hand rather than derived — and it is the surface Era S's hidden-value cells (`0x04`, §6) would arrive on.

V4 additionally requires the signature set to be **minimal** (I1-M4): every required address or key is satisfied, and every signature satisfies at least one requirement. Minimality is what makes the id sufficient now that its preimage excludes the signatures. Sufficiency and minimality together make the legal signer set a pure function of the body, so two valid certificates sharing an id carry the same signer list — hence the same signature count, the same encoded length, the same parallel gas and the same fee ceiling. One id, one authorization, one cost. Without minimality a proposer could pick a fatter exemplar of an authorization and bill its signer for gas the signer never agreed to.

A certificate failing any V-rule is *invalid*. Invalid certificates never enter an honest mempool; one included in a block makes **the block invalid** in Era 0 — the PoW is wasted, and the miner is the only underwriter of block well-formedness before bonds exist.

## 8. The fold (F-rules)

`core/fold` exposes one function: `ApplyBlock(state, block, params) → (*Result, err)`, where `Result` carries the per-certificate outcomes, the four gas quantities (§15), the value burned, the producer's reward, the treasury share, what matured, the epoch state root and the undo log. `err != nil` only for *block-invalidity*. Per-certificate problems are never errors; they are outcomes.

Outcomes: `APPLIED`, `SKIPPED(STALE | OVERFLOW)` — billed to the deposit — and `DROPPED` — deposit reservation failed, nothing billable, no state touched, **not** marked seen (re-submittable once funded).

**Block-level ceilings and citations** (whitepaper §8.1), checked before B0–B4 and before certificate-count/byte-count are even meaningful, because computing `CertRoot`/`CitesRoot` on an oversized list would panic rather than fail (§5, `ssz.Merkleize`'s own contract):

```
B12 len(B.Certs) ≤ MaxCertsPerBlock(T)          // T from state (§6), genesis value at height 0
B18 Σ len(c.Sigs) ≤ MaxSigsPerBlock(T)          // checked BEFORE any signature is verified
B13 len(B.Bytes) ≤ BlockByteLimit(T)
B14 CertRoot  = ComputeCertRoot(B)              // against CertListCapacity, the static bound (§5)
B15 len(B.Cites) ≤ MaxCitesPerBlock             // static; checked before ComputeCitesRoot for the
                                                 //   same reason as the certificate count above
B16 CitesRoot = ComputeCitesRoot(B)
    checkCites(B)                               // C0–C5 below; proof of work is not one of them
```

**A citation's own proof of work is checked in `node/`, not here — a cost argument, not a dependency one.** `core/pow` imports only other `core/` packages, so `core/fold` importing it would create no cycle; what the fold cannot afford is *evaluating* work, which is memory-hard by design (milliseconds per evaluation under RandomX) in the one stage whose whole point is that it only touches memory. So `checkCites` verifies everything a citation's *bytes* can prove, and `node/p2p.Engine.OnBlock` and `node/sync.Fetch` check the work alongside the block's own.

**That split has a consequence the vectors cannot express.** `cited_count` is consensus state — it feeds the health gate, which moves `T` — so an implementation that skipped the citation work check would accept blocks this one rejects and derive a different ceiling: a chain split, not a policy difference. The golden vectors cannot carry it, because they scope the *fold* and the fold does not check work (the block's own PoW is equally absent from every vector). It is therefore specified normatively in [spec/wire](spec/wire.md) §9 rule 7, which is where an independent implementation is obliged to look for peer-layer MUSTs.

```
B17 H ≤ 1 ⇒ len(B.Cites) = 0                     // genesis is unique and a competing genesis is a
                                                 //   different network, so no sibling can exist
checkCites(B), for citation c at height H:
  C0 c.Version = HeaderVersion                   // must be something that could have been a block
  C1 c.Height = H − 1                            // a sibling of the parent, nothing older
  C2 c.ParentID = prev_parent_id                 // shares the parent's own parent
  C3 c.ID() ≠ B.Header.ParentID                  // not the parent restated as a competitor
  C4 c.Target = prev_target                      // mined at the difficulty the parent's height required
  C5 citations strictly increasing by id         // R2-M2's discipline, applied here too
```

**This list is exhaustive, and saying so is part of the specification.** Every other field of a cited header — `Time`, `CertRoot`, `CitesRoot`, `StateRoot`, `EmissionAddr`, `PoW.SeedEpoch` — is **unconstrained**, and an implementation that adds a constraint forks as surely as one that drops a rule: two nodes that disagree about how many citations a block carried derive different targets `T`. The trap is easy to walk into, because `node/sync.ValidateHeaders` rejects a chain header whose `Version` is unknown and a second implementer may reasonably apply the rest of that function's checks to citations too. C0 exists because an unknown version could never have been a block; it is stated here rather than only in `core/fold`, which is where it lived for one commit and **where a normative rule must never live alone**. The normative statement, with the `PoW.SeedEpoch` exemption argued in full, is [spec/wire](spec/wire.md) §9 rule 7.

**Block-validity preconditions** (checked before/during the fold; any failure ⇒ invalid block, R1-C1/H3/H4):

```
B0  header linkage, PoW, target, time lower-bound (§12); V1..V9 pass for all certs (parallel)
B0b PoW.SeedEpoch == seed_epoch(Height)     // §12's key schedule, pinned in the fold
B1  ∀c: B.Height ≤ c.TTL                        // stateless: expired certs are unincludable
B2  ∀c: c.TTL ≤ B.Height + TTL_MAX              // stateless: bounds the seen-set
B3  ∀c: ¬seen(c.ID)                             // stateful (all full nodes hold the seen set):
                                                //   c.ID is over the AUTHORIZATION, not the bytes
                                                //   replayed certs are unincludable
B4  ∀c: c.FeeBid ≥ B's base fees (both markets) // deterministic: an unpayable cert is unincludable
B5  Σ seq_gas(c) ≤ 4T                           // the hard bound (§8.1); between 2T and 4T a block is
                                                //   valid and F11 forfeits the producer's subsidy share
                                                //   AND the block's fees against it
B6  Σ par_gas(c) ≤ ParGasLimit(T)               // the parallel market has no burst valve — hard always
B7  Header.Version = HeaderVersion              // an unknown version is invalid outright, not
                                                //   folded into "header linkage" above
B8  ∀i≠j: B.Certs[i].ID() ≠ B.Certs[j].ID()      // no certificate appears twice in one block
                                                //   (in-block only; B3 is the cross-block half)
B9  ¬IsEpochBoundary(B.Height) ⇒ Header.StateRoot = 0     // zero everywhere off a boundary; F14
                                                //   is the only rule permitted to set it
B10 B.Height = 0: len(B.Certs)=0 ∧ ParentID=ConsensusRoot(params) ∧ EmissionAddr=0 ∧ IsEpochBoundary(0)
    B.Height > 0: ParentID ≠ 0                  // genesis is a reproducible artifact, checked in full
                                                //   (checkGenesisShape); not a ceremony with free fields
B11 B.Height > 0 ⇒ IsUserAddress(Header.EmissionAddr)     // must be a payee that can actually receive —
                                                //   0x00 pays the protocol, 0x03 an asset's metadata
                                                //   address, and F12 matures the reward into either
                                                //   silently. (At height 0, B10 already forces it to 0.)
```

**The rule ids are a conformance surface, not a filing convention.** Every rejection `core/fold` produces carries the id of the rule that produced it (`fold.RuleError`, the block-level twin of `validity.RuleError`), each invalid golden vector records that id in `expect.rule`, and `spec/vector_test.go` compares it on replay — which is what makes a vector a statement about a *rule* rather than about a verdict (`spec/README.md`, "What an invalid vector pins"). Two consequences follow and both are normative. **An id used by a vector must be defined here**, because a second implementation has nowhere else to look it up: B0, B0b, B1–B18 above, C0–C5 above, V1–V9 in §7, F3, F13 and F14 below. And **an invalid vector's block breaks exactly one rule** — nothing here fixes the order rules are evaluated in, so a block breaking two could be reported either way by two conformant implementations and `expect.rule` would have no answer; `core/fold` and `sim/refold` do in fact answer differently on such a block. Four tests hold the property and none is a proof of it: `TestBothFoldsAgreeOnTheRuleTheCorpusRecords` catches rules the two folds order differently and `TestOverDeterminationIsVisibleToThisCheck` arms it; `TestEveryInvalidVectorsRuleIsNecessary` deletes each vector's recorded rule from `sim/refold` and requires the block to become valid — order-independent, so it covers rules the two folds order *identically* — and `TestNecessityCatchesTheOverDeterminedBlockAgreementMisses` arms that. **The deletion switch lives in `sim/refold` and never in `core/fold`**, because a rule-disabling switch inside the consensus fold would be a way to build a node that silently does not enforce a rule.

**B7–B11 are not covered by the exhaustiveness note above**, which scopes a *cited* header's fields; B7, B9, B10 and B11 constrain the block's **own** header. In particular B11 is the answer to whether `Header.EmissionAddr` is constrained: for a cited header it is not, for the block's own header it is, and a reader skimming only the citation note is missing the rule that governs the field the miner is paid through.

**There is deliberately no rule about the coinbase amount.** Earlier drafts carried one, and it was removed rather than implemented: the header names a payout address and no amount, so there is no declared number to disagree with. What the producer is owed is derived by the fold at F11 from the height and the block's applied tips, identically on every node. A rule can only check a claim, and the cheapest way to make a claim uncheckable-and-therefore-unbreakable is not to let it be made.

B1–B4 are the enforcement of the **billing law**: *one signature, at most one bill, never at a position its signer could not avoid.* A signer accepts staleness risk by signing (STALE/OVERFLOW skips are billable); it never accepts miner-manufactured expiry, duplication, or fee-market drift — so those cannot occur in a valid block at all.

```
ApplyBlock(S, B):
  F1  C ← stable_sort(B.Certs, key = (underwriter_id, Seq, cert_id))
      // underwriter_id in Era 0 = Deposit.Cell owner address (R1-C2). Dependent
      // certificates from one signer commit in signed order; Phase-1 sequencer
      // pipelines inherit the identical rule.
  F2  if epoch_boundary(B.Height): write beacon cells (epoch, height, entropy)
  F2b if epoch_boundary(B.Height) and B.Height > 0:                  // §8.1's controller
        median ← lower_median(applied_gas_sample[0..EpochLength-1])  // the epoch that just
                                                                       //   ended; a fixed
                                                                       //   convention, not an
                                                                       //   average — see §6
        healthy ← cited_count × 10000 ≤ HEALTH_GATE_BPS × EpochLength
        hi ← T + T/Γ if healthy else T           // growth withheld, never decay or the floor
        lo ← T − T/Δ
        T ← min(clamp(2×median, lo, hi), SEQ_GAS_CAPACITY)           // §15's wall, then
        T ← max(T, SEQ_GAS_TARGET_GENESIS)                           //   the floor always wins
        cited_count ← 0                          // the epoch beginning now starts unmeasured
      // T takes effect from THIS boundary onward; see the note below F16.
      if B.Height = 0: T ← SEQ_GAS_TARGET_GENESIS                    // genesis has no epoch to read
  F3  for c in C:
        c.Deposit.Cell.Addr version ∉ {0x01, 0x02} ⇒ INVALID BLOCK   // see below
        r ← reserve(S, c.Deposit)              // fold-level: GUARD_GE + debit on deposit cell
        if !r:                     outcome(c, DROPPED); continue
  F6    ok ← ∀ (slot,a,x) ∈ c.Reads:
            slot.Addr ∈ spent_registry ⇒ false
            EXACT:    S[slot] = x
            GUARD_GE: S[slot] ≥ x     GUARD_LE: S[slot] ≤ x     GUARD_EQ: S[slot] = x
        if !ok:   settle(c, SKIP_FEE); refund_remainder(c); mark_seen(c.ID, c.TTL)
                  outcome(SKIPPED_STALE); continue
  F7    stage writes on a scratch overlay: SET / DELTA_ADD / DELTA_SUB / MARK_SPENT;
        any arithmetic leaving [0, 2^256) ⇒ discard overlay,
                  settle(c, SKIP_FEE); refund_remainder(c); mark_seen(c.ID, c.TTL)
                  outcome(SKIPPED_OVERFLOW); continue
  F8    commit overlay to S; add MARK_SPENT addresses to spent_registry
  F8b   a burn strands nothing the fold can name. For every address a with
        a MARK_SPENT in c.Writes, and for each cell
            native_balance_slot(a), and every w.Slot in c.Writes with w.Slot.Addr = a
        move whatever the cell still holds to the same WORD under
        c.Deposit.RefundTo.Addr, zeroing the source. A destination whose authority
        an EARLIER certificate burned, or whose cell would carry past 2^256, is NOT
        written: the value stays exactly where it was, which is what the fold did
        before F8b existed. Reported as outcome.swept / outcome.swept_stranded,
        both counting NATIVE drops only.
        F8B NEVER DESTROYS AND NEVER FAILS, AND IT IS AN EFFECT AND NOT A
        VERDICT. Both properties are load-bearing and both were learned from a
        design that broke them; the argument, the measurements and the rejected
        alternatives are in §21 and docs/decisions/one-shot-burn-scope.md.
  F9    settle(c, seq_fee + par_fee); refund remainder → c.Deposit.RefundTo (fold-level,
        exempt from guards, but NOT from the registry: a remainder owed to an address
        already burned is burned instead, and reported as outcome.refund_burned rather
        than as outcome.refunded); mark_seen(c.ID, c.TTL); outcome(APPLIED)
  F2c bookkeeping for §8.1's controller, run every block, boundary or not:
        applied_gas_sample[B.Height mod EpochLength] ← seq_gas_APPLIED (this block's)
        cited_count ← cited_count + len(B.Cites)  // joins the epoch now in progress; F2b
                                                    //   already zeroed it if this block opened one
        prev_parent_id ← B.Header.ParentID
        prev_target    ← B.Header.Target
      All four are consensus state and all four are journalled: a reorg that
      restored some but not others would fork the chain silently.
      PREV_TARGET IS COPIED VERBATIM AND THE FOLD NEVER CHECKS IT. The
      difficulty rule is a function of the preceding DIFFICULTY_WINDOW+1
      headers; the fold holds no window, no ancestors and no engine, so it
      cannot evaluate that rule and does not try. What a declared target must
      equal is an ingress and fork-choice rule (wire §9), stated by its own
      vector kind rather than by any (pre-state, block) vector. The
      consequence a second implementation has to be told, because it is not
      visible from the fold's own text: the value copied here ENTERS THE EPOCH
      STATE ROOT and is C4's entire basis, so a block whose target is
      fabricated folds cleanly and COMMITS the fabrication, and the divergence
      surfaces later through C4 -> cited_count -> T. The rule that keeps that
      unreachable lives OUTSIDE the fold, on every path by which a block from
      another node reaches the chain, and it is load bearing there rather than
      defence in depth. A block a node produces itself is not on
      one of those paths: node/miner constructs the target from the rule and
      applies directly, and wire §9 covers the producer with its own clause.
  F10 prune seen-set entries with ttl < B.Height − 1
  F11 split this block's subsidy and credit the treasury (whitepaper §14.1):
        subsidy  ← emission(B.Height)
        treasury ← (subsidy × TREASURY_SHARE_BPS) / 10000        // floor
        producer ← subsidy − treasury                            // the remainder
        treasury_cell ← treasury_cell + treasury
      The floor goes to the treasury and the remainder to the producer, so the
      two always sum to the subsidy exactly and integer division can neither
      create nor destroy a drop. The share applies to every block including the
      tail, and to the SUBSIDY ONLY: fees are never touched. At height 0 the
      subsidy is zero, so the rule runs from block 0 without allocating.
      The burst valve (§8.1), against the producer's share alone — the
      treasury above is not a party to the producer's choice to burst:
        if seq_gas_USED > 2T:                    // B5 already capped it at 4T
          excess  ← seq_gas_USED − 2T             // ≤ 2T
          forfeit ← floor(floor(producer×excess/2T)×excess/2T)   // two floors, not one combined
          producer ← producer − forfeit           // division — see §8.1's rationale below
      Then credit Σ(tips of APPLIED certificates) to the miner (fold-level, via
      the maturity ring at F12); burn all base fees and all skip fees. Tips
      arise on the applied path only, so a builder maximising revenue is
      maximising application and can never profit from a skip (I1-H2, R1-C1)
  F12 roll the coinbase maturity ring (I1-C2): at index (B.Height mod
      COINBASE_MATURITY) — always the entry written at B.Height − maturity —
      credit (payee, amount) into the payee's spendable balance, then overwrite
      the entry — EXCEPT that a reward of zero clears it rather than writing
      the payout address against it:
        reward ← producer + Σ tips
        if reward = 0: entry ← (0, 0)
        else:          entry ← (Header.EmissionAddr, reward)
      THIS MUST NOT BE CONFLATED with F11's "a zero credit is skipped rather
      than written" one rule above, and the difference is the whole reason this
      clause is normative. F11's treasury cell is a SINGLE ACCUMULATOR, so
      skipping a zero credit is state-EQUIVALENT to performing it and moves no
      root — tidy. F12's ring entry is a PAIR of cells written independently,
      which makes the choice OBSERVABLE: the amount half is zero and therefore
      absent either way, while the address half is zero under one rule and the
      payout address under the other. The entry rule MOVES THE STATE ROOT where
      F11's does not — load bearing.
      Why the pair is cleared rather than half-written: the release side reads
      the AMOUNT alone, so an entry whose amount is zero can never pay anybody
      at any height; and since a cell set to zero is deleted rather than stored,
      the unconditional write would leave a payout address standing inside the
      state root, for COINBASE_MATURITY blocks, against a payment that does not
      exist. Block 0 fixes the reading: its subsidy is zero and B10 forbids it
      certificates, so every chain that has ever run takes this branch at
      genesis, and "no allocations of any kind" (§19) is what it must produce
      there. This paragraph was previously an unconditional overwrite, which
      disagreed with BOTH folds on a committed state root at parameter values
      Validate accepts; the folds were right and the text was wrong.
      A payee that has burned its authority is burned instead (I1-M2) — this
      burns the producer's share only; the treasury's was credited at F11 and
      does not pass through the ring. Maturity cannot be a V-rule: balances are
      fungible, so no stateless rule can tell a young coin from an old one.
  F12b update the two base-fee cells from this block's APPLIED gas (I1-H1,
      R2-H2 — see the three definitions in §15):
      seq_base_fee ← next(seq_base_fee, seq_gas_APPLIED, T)
      par_base_fee ← next(par_base_fee, par_gas_APPLIED, PAR_GAS_TARGET(T))
      T here is the same pre-F2b value B5/B6 and the burst valve were measured
      against: §8.1's elastic T and §8's EIP-1559 base fee are two independent
      controllers over the same number, and each must compare a block's usage
      to the target the block actually operated under.
      Height 0 initialises them from spec/params.json instead.
  F13 assert no certificate wrote a 0x00 cell (defense in depth; V7 already forbids)
  F14 if epoch_boundary(B.Height): compute state_root; assert equals Header.StateRoot.
      TWO independent SSZ list-roots, not one merged tree, each over its leaves sorted
      by slot/address (cell addr‖word, registry address) with capacity =
      nextPow2(leaf count):
        cell_root  ← ListRoot({blake3("zcd/stateleaf/v1"‖addr‖word‖value) : live cells},
                               nextPow2(#live cells))
        spent_root ← ListRoot({blake3("zcd/spentleaf/v1"‖addr) : spent-registry entries},
                               nextPow2(#spent entries))
        state_root ← blake3("zcd/stateroot/v1" ‖ cell_root ‖ spent_root)
      The capacity is DYNAMIC, unlike every other merkleised list in this protocol: §5's
      argument for CertListCapacity's *static* bound does not apply here, and an
      implementation that gives either subtree a fixed capacity computes a different root
      the moment the live count crosses a power of two. The seen set is EXCLUDED — not an
      oversight: it is prunable, fully reconstructible from recent history, and every full
      node holds it anyway for B3, so committing it would tie the root to the pruning
      schedule rather than to consensus-relevant state.
  F15 append (slot, old_value) pairs for every touched slot, registry additions,
      seen additions AND seen removals (I1-M3) to undoLog[B.ID]. Without the
      removals, a block that pruned a seen entry and was later reorged away
      would leave an already-billed certificate includable again — R1-C1's
      re-billing, reached through a reorg instead of through a proposer.
  F16 return
```

Notes that carry weight:

- **`ListRoot`, `node` and the dynamic `nextPow2` capacity are defined by value in the spec, not here.** F14 above names `ListRoot` and its two subtree capacities but does not fix them; their normative definition — the internal `node` function, the merkleise-against-a-capacity rule, the length mix-in and `nextPow2(0) = 1` — is [`spec/README.md`](../spec/README.md#how-a-list-is-rooted)'s *How a list is rooted*, whose executable form is `core/ssz`'s `ListRoot` and which `core/ssz`'s `TestTheDocumentFixesTheListRootSpellingByValue` holds against the tree. Named here rather than restated so the two documents cannot drift.
- **Every billed outcome marks seen (F6/F7/F9).** With B3, this is the mechanical half of the billing law: a signature can be billed at most once per canonical chain. Reorgs preserve the invariant — undo restores both the balance and the seen/registry state, so re-inclusion on the new branch nets to one bill.
- **Reserve-first (F3)** makes billing possible for every non-dropped outcome. Reservation is itself a guarded delta — the deposit mechanism is built from the same two primitives it protects.
- **F3 refuses the *block* for a non-user deposit cell, and drops the certificate for its other two refusals.** The asymmetry is the rule, not an inconsistency. A spent deposit address and a balance that moved describe states an honest proposer can legitimately assemble against, so they are ordinary `DROPPED` outcomes; a certificate arriving at F3 with a `0x00` or `0x03` deposit cell is one **V4 and V5 both refuse statelessly**, so reaching the reservation at all means a stateless rule regressed. Dropping would bill nothing and still let the block stand on a premise already known to be broken. That is exactly F13's reasoning — defence in depth against a write V7 already forbids — and this takes F13's answer. It is the third predicate that was asked for and **it is dead code in Era 0**: B0 runs `validity.Check` over every certificate before the fold sees one, so no block can carry a certificate that reaches it, no certificate's outcome changes and no state root moves. What it buys is that the site which would drain the treasury — F3 debits `Deposit.Cell` outside the declared write set, where V7 and F13 never see it (§9's treasury note) — holds an opinion of its own instead of borrowing one from two rules in another package. Both folds state it, per rule 12; neither can be driven to it through `ApplyBlock`, so each pins it by calling its own per-certificate step directly (`core/fold/deposit_version_internal_test.go`, `sim/refold/deposit_version_test.go`).
- **Skips are total, never partial.** A certificate applies all its writes or none (the F7 overlay).
- **A burned address holds no drops (F8b).** Four existing rules keep it empty afterwards: F7 fails every write under a spent address, settlement burns a remainder owed to one, F12's ring burns a reward owed to one, and F3 refuses to reserve from one. The law they add up to is stated over the whole state by `sim.TestNoBurnedAddressHoldsDrops` rather than inferred. It also means F3's registry check can no longer be *reached* by the rules; it stays because pruning may delete cell values under a spent address, and a reservation that could read one would make the fold depend on when a node pruned.
- **No fold rule's verdict may read a cell a stranger can credit.** The general form of §5's attribution theorem as a constraint on *rule placement* rather than on write sets: a rule deciding APPLIED versus SKIPPED from a balance is a rule any third party can operate, because a credit needs no signature (§9's lemma 3). Rules of that shape belong after the verdict, as effects. `core/fold/theorem_test.go`'s fourth lemma checks it by running the fold, which is why it catches what the first three could not.
- **Value-equality applicability** (whitepaper §3): F6 compares values, not versions. ABA tolerance falls out; no version counters exist anywhere in state.
- **The lease machinery is absent.** In Era 0 every certificate is self-underwritten and applies immediately at its position; scheduled application and slot leases (whitepaper §7) protect co-signer pipelines and activate with co-signers in Phase 1 (§17).
- **Reorg support is native.** F15's undo log is cheap *because writes are declared*: undo is the reversed pair list. `UndoBlock` restores state, seen ids and registry entries; certificates from abandoned blocks with live TTLs re-enter the mempool (§13).
- **The fold has no clock.** `Header.Time` is consensus-bounded (§12) but never enters F-rules or programs; only beacon cells express time.
- **No elliptic-curve arithmetic in the fold, ever.** Whitepaper §3 states this as a rule rather than an observation, and the temptation is real, because Pedersen commitments are homomorphic and summing them in the fold looks natural. A point addition costs hundreds of nanoseconds against the ~1 ns of a u256 add, so one curve operation in the only stage that does not parallelize would spend the entire budget this architecture exists to protect. The rule: commitment-valued cells are **stored** into fresh cells and **compared** for byte equality, both memory operations, and every curve operation happens in the stateless stage or in the owner's wallet.
- **The id is computed once, and not yet where the paper wants it.** `cert_id` is needed at three points in the sequential stage and is computed once at fold entry and carried. Whitepaper §3 asks for it to be computed *in the parallel stage* instead, since it depends on the certificate's bytes and nothing else; closing that gap is the first real consumer of the pre-verification seam §11 describes as unused. It moves no rule, and the golden vectors must come out byte-identical, which is the check that matters rather than the benchmark.
- **T takes effect one block later than it is computed (§8.1).** F2b runs before F3, so the block that crosses a boundary is itself still judged — by B5/B6, and by F11's burst valve — against the T that was in state *before* F2b touched it. Same rule B4 already applies to the base fees, restated for a second controller over the same kind of number.
- **F2b's two clamps are both consensus, and the order between them is too.** `SeqGasCapacity` binds after the growth/decay clamp and before the genesis floor, exactly as `params.NextSeqGasTarget` computes it and as §15 states it. This bullet exists because the F2b block above once omitted the capacity clamp, and `sim/refold` transcribed the pseudocode rather than the code and carried a live cross-fold divergence until it was caught — the document did to this project's own second implementation exactly what it would do to somebody else's.
- **F2b's health comparison is `≤`, and it is a choice rather than a consequence.** An epoch satisfying `cited_count × 10000 ≤ HEALTH_GATE_BPS × EpochLength` is **healthy**, so an epoch landing exactly on its rate may grow `T`. The alternative was `<`; it lost because the gate is a bound on *unhealth*, and an epoch that meets the bound has not exceeded it — the reading whitepaper §8.1 takes when it writes the gate as "cited competing headers ≤ 2% of blocks per epoch". This is the sibling of the lower-median bullet below and worse in one respect: the median convention is at least *observable* and this one is not. **No parameter set this release ships can exhibit the difference** — `cited_count` is an integer, so the left side is always a multiple of 10,000 and the two spellings disagree only where the sides are equal, which needs `HEALTH_GATE_BPS × EpochLength` to be a multiple of 10,000 too. It is 576,000 on mainnet and on the testnet and 12,800 on devnet, putting the boundary at 57.6 and 1.28 cited headers, and no block can cite a fraction of a competitor; inverting the comparator survived `core/validity`, `core/fold`, `spec` and `sim`. **Do not close that by adding a test at a shipped parameter set** — it cannot fail, and an assertion that cannot fail reads as coverage. The honest instrument is a witness test at a legal but unshipped set where the product *is* a multiple of 10,000, which `TestTheHealthGateAdmitsTheEpochThatExactlyMeetsItsRate` is, paired with `TestTheHealthGateBoundaryHasNoIntegerAtAnyShippedParameterSet`. Both constants are in `ConsensusRoot()`, so the day either moves is the day this bullet starts deciding a fork rather than describing one, and `sim/refold`'s `Cmp(…) <= 0` has to be confirmed to still say the same thing.
- **The lower median, not an average, and that choice is load-bearing.** `EpochLength` is even at genesis, so "the median of an even-length list" needs a fixed convention or two conforming implementations disagree on the last bit of a number that gates real money. The convention is the element at sorted index `(EpochLength−1)/2` — one real sample, never an interpolation.
- **The burst valve's two floors are the specification, not an approximation of one.** `floor(floor(base×excess/2T)×excess/2T)` — where `base` is the producer's subsidy share plus the block's fees — is not the same integer as the combined division `floor(base×excess²/(2T)²)` in general; the two-step form is chosen because `(2T)²` can exceed 64 bits once T has grown for decades and `u256.MulDiv64`'s divisor is a `uint64`. An implementation computing the exact single division diverges from this one on some inputs. **`spec/vectors/064-burst-forfeiture-where-two-floors-are-not-one-division` is one such input, committed**: a valid block inside the band at a seeded `T` where the two forms differ by one drop, whose only certificate is dropped so that the block's whole `burned` figure is the forfeiture itself. The sentence that stood here before it — that no golden vector reaches the valve and that `core/fold/elastic_ceiling_test.go` is therefore the only thing holding the rounding — was wrong in both halves, and the second half was wrong before the vector existed: `TestBurstValveAtGenesisParameters` pins that the band is *reachable* under stock parameters and asserts no forfeited amount at all, so the single-division mutant leaves `core/fold` entirely green. What did hold the rounding is `sim`'s differential against `sim/refold`, which states the two floors independently and kills that mutant in three tests — and which holds this tree's two folds to each other, never a second implementation.
- **Citation dedupe is structural, and the narrowing that buys it has a cost.** A citation must share the citing block's grandparent (C2) and name its parent's height (C1), so the window is exactly **one block** and there is nothing to deduplicate across blocks. Whitepaper §8.1 says "recent competing headers", which is wider, and the difference is not cosmetic: **a one-block window undercounts exactly when the network is unhealthy.** A proposer at height H has roughly one block interval to have heard about a competitor at H−1; if propagation is slower than that — precisely the condition the health gate exists to detect — the competitor is never citable, the epoch reads as healthy, and growth is permitted when it should be withheld. **The gate therefore fails *permissive* under slow propagation**, the opposite of the direction §8.1 asks it to lean. The alternative is a W-block window, which restores detection but requires a bounded, prunable, reorg-safe cited-id set in consensus state — a second seen-set — for a signal nothing in Era 0 yet produces. Widening it is the first thing to revisit if the health gate is ever load-bearing rather than latent.

## 9. Native operations (Era 0 program set)

`Program` is a tagged union. Each op deterministically derives its full, canonicalized read/write set (V3). All value motion is guarded deltas.

**`TRANSFER { moves: [(asset_id, src, dst, amount)] }`** — derivation merges per-slot: for each debited slot, one `GUARD_GE(total)` + one `DELTA_SUB(total)`; for each credited slot, one `DELTA_ADD(total)` (R1-M1). Derivation **rejects** a certificate in which one balance slot is both debited and credited, along with zero-amount and self-directed moves (I1-M1): netting a routed transfer would erase the `DELTA_SUB` that V4 derives debit authorisation from, letting a route move an intermediary's balance without the intermediary's signature. Routing is two certificates with ascending `Seq`. Debit sigs per §6; each debited `0x01` address carries its `MARK_SPENT`. `dst` may be a fresh cell (a tip *is* a transfer to a fresh or pure-credit cell; no separate op). Native coin is `asset_id = 0`. Derivation also **whitelists `asset_id` itself**, to the all-zero native id or a `0x03` asset address and nothing else: the id is hashed into the balance slot's word, so an unvalidated 32-byte field would be an attacker-chosen consensus slot key that no rule asserted named an asset. It is the same whitelist V9 gives the *holder* half of a slot, which V9 cannot extend to the asset half because that half is a hash. It does not claim the asset exists — an unissued `0x03` id still derives an empty cell and still skips.

**`ISSUE { issuer, cap, decimals, symbol_hash, minter_pubkey }`** — permissionless. `asset_addr = 0x03 ‖ blake3("zcd/addr/v1" ‖ 0x03 ‖ chain_id ‖ issuer ‖ seq)[:31]`, and V4 requires a signature by the key hashing to `issuer`. Deriving from the certificate id instead is circular: the id commits to the writes, and the writes name the address (I1-C1). Re-using a `seq` re-derives the same address, and the write-once `EXACT` read below makes the duplicate skip against the issuer's own earlier certificate. `SET`s the immutable metadata words (`cap`, `decimals`, `symbol`, `minter`) together, in the one certificate the `cap` read's write-once lock permits. **There is no per-word guard on `decimals`, `symbol` or `minter` individually**; each is write-once only as a *consequence* of sharing that certificate with the guarded `cap` write, so an implementation that later added a fifth metadata word or relaxed the `cap` read would lose their immutability silently, with nothing else here to catch it. Emitting an asset costs only fees.

**`MINT { asset_id, dst, amount }`** — reads `EXACT(asset.cap) = C` and `EXACT(asset.minter) = M` (immutable ⇒ never stale), requires sig by `M` (immutable-cell authorization, §6), rejects `amount > C` at derivation (R1-M2), then `GUARD_LE(asset.minted, C − amount)`, `DELTA_ADD(asset.minted, amount)`, `DELTA_ADD(bal(dst,asset), amount)`. Supply caps hold under unlimited concurrent mints.

**`RETIRE { addrs: [addr] }`** — explicit `MARK_SPENT` on caller-owned one-shot addresses (privacy hygiene / state compaction without a spend).

That is the entire genesis instruction set, and it is closed: `TRANSFER`, `ISSUE`, `MINT`, `RETIRE`. Two namings the whitepaper (§11) now depends on: **a tip is not an operation** — it is a `TRANSFER` whose credit lands on a pure delta or a fresh one-shot cell, so the network's native verb spends no opcode of its own; and **`RETIRE` is not a sweep** — sweeping debits an address, and a debit already carries its mandatory `MARK_SPENT` (V6), while `RETIRE` burns an address *without* spending it, which is why it has no reads and cannot pay anybody. The last clause needs care, because F8b moves value on a `RETIRE` certificate that burns a funded address: the *program* is unchanged and still a pure write with no reads, and what F8b performs is a fold-level movement of the residual into the certificate's own `RefundTo` cell — the same cell settlement already credits — exempt from guards exactly as settlement is. What `RETIRE` still cannot do, and what the whitepaper's "moves no value" contrasts it with, is *spend*: it names no payee, takes no amount, and can send nothing anywhere its signer did not already declare as their own change address. Every later operation, `BOND` included, arrives with a later phase's ruleset (§17).

**Theorem (poisoning immunity, R1-N1, scoped by I1-H3).** *In Era 0, no third party can cause another signer's certificate to be billed, except by burning the authority of an address that certificate writes to.* The exception is narrow and structural: a write to an address in the spent registry must fail (R1-C3-iii), and a failed write is a billed skip — so a payee who retires a one-shot address after handing it out bills the payer. One-shot addresses are generated fresh per payment received, so the window is empty under the default wallet pattern, and the payer's skip fee is burned rather than paid to anyone.

Proof sketch: billable skips require a failed guard or overflow at commit. TRANSFER balances carry only `GUARD_GE` — third-party *credits* strictly help a ≥-guard, and debits require the owner's signature; MINT's `EXACT` reads target immutable cells; ISSUE writes only cells derived from its own address derivation; RETIRE touches only owner cells; overflow would require two balances of one asset to sum past 2^256, and they cannot — an asset's supply is bounded by `minted ≤ cap ≤ 2^256−1` (MINT rejects `amount > cap` and its `GUARD_LE` holds `minted ≤ cap − amount`), so all balances of an asset partition a total that is itself below 2^256, and balances of different assets never share a slot. The bound is the capped, per-asset supply, not a limit on any single slot: under `cap = u256.Max` one slot can hold ~2^256−1, yet no second unit of that asset can exist to overflow a credit onto it. That partition is not left as an argument: `TestAssetSupplyEqualsMintedOverFoldedState` states it over folded state — it enumerates every balance cell of an asset after a fold, sums them, and requires the sum to equal the asset's `minted` cell with `minted ≤ cap` — which is the same invariant `moveResidual`'s untestable carry-past-2^256 branch rests on, and `TestMaxCapSupplyBoundsEveryCreditBelowOverflow` drives it to the `cap = u256.Max` boundary. Hence every billed skip is self-inflicted or a genuine mint-cap race among willing minters. EXACT-read poisoning becomes possible only with the cEVM in Phase 1 — exactly where bonded co-signers exist to price and absorb it.

The theorem is pinned by the griefing suite (§18) and must survive every op-set change. It has a **fourth** closure property, because the first three were not enough: lemmas 1–3 reason over *derived write sets*, and the burn rule's first design was a staging rule with no new write — all three green, theorem false. `TestLemmaNoUnsignedCreditChangesAnOutcome` asks the question the theorem actually makes, by running the fold. **Stated as a constraint on future rules: no fold rule's verdict may read a cell a stranger can credit.** That is the form the `BOND` note (§17) needs, and the form the cEVM will need.

## 10. Deposits, billing, and the drop rule

`SKIP_FEE` is a **protocol constant** in `spec/params.json` (R1-H1) — skip pricing is anti-spam, not fine resource pricing; constancy is what makes the deposit ceiling statelessly checkable and deposits small. Fee ceiling per certificate: `ceil(c) = max(SKIP_FEE, seq_bid_max(c) + par_bid_max(c))` (V5). The deposit reserves `ceil`; settlement charges actuals and refunds the remainder to `RefundTo` *within the same fold step*, so a user's liquidity is locked for exactly one certificate lifetime, never longer.

**The billing law, restated as the audit target:** one signature, at most one bill, never at a position its signer could not avoid. Mechanics: billed skips mark seen (F6/F7); seen, expired, and under-bid certificates are unincludable (B1–B4); drops bill nothing. The griefing suite (§18) exists to break this law and must fail to.

**Why DROPPED exists and is not billed:** a deposit can be valid at mempool admission and gone by commit (the depositor spent it in between). There is nothing to charge. The certificate touches no state, is not marked seen, and is free to resubmit once funded. That much is the design and it is not in question. **What follows is the two-sided accounting of what it costs, because the one-sided version this paragraph used to carry is the substantive defect the final pre-launch audit found, and it does not survive.**

**The send side.** (a) Relay policy — nodes only gossip certificates whose deposits cover at their local tip, so unfunded spam does not propagate free; (b) miner rationality — a DROPPED cert pays zero, so block builders (who hold state and can dry-run the fold over their own candidate block, cheaply, by design) exclude them. **Both of these are send-side defences and neither binds a producer.** A block producer does not relay these certificates, it *includes* them; and "the producer forgoes fee revenue" prices the producer's own choice, not the cost that choice imposes on anybody else. Citing them against a producer is a category error, and it was this document's.

**The receive side, which is the cost that is actually paid.** Every node that receives the block pays its full bandwidth and, before any state is touched, one strict Ed25519 verification per signature the block declares — B0 runs `validity.Check` over every certificate. The producer pays zero for that. It is amplification-free (bounded by the block's own ceilings), creates no state, and causes no consensus split, which is why it is an accepted risk rather than a defect; it is *not* free to the network, and the sentence that used to end "burning their own block space and forfeiting fee revenue" stopped exactly one term short of saying so.

**What bounds it is `B18`, the per-block signature ceiling** (§8, `max_sigs_per_block_genesis`) — checked before any signature is verified, so it bounds the work rather than reporting it. At the genesis value a fully drop-stuffed block costs each receiver at most 6,000 strict verifications, about 4.4 core-seconds against a 30-second interval, and that product no longer grows when the byte ceilings grow. **`V5`'s upper bound on `Deposit.Amount` (§7) is not what bounds this**, and adding it did not close the class: the attack works identically with `Amount = 1` from an unfunded fresh key, because the primitive is "a deterministic DROP costs the producer nothing" and the declared amount is not part of it. `V5`'s bound is there because a consensus-valid object declaring more coin than can exist is an absurdity the cheap gate should refuse, and it was taken before the freeze because after it the fold cannot move.

**What is deferred, explicitly.** Charging at `F3` — making the failed state check billable so the producer pays for what receivers verify — touches the billing law and the conservation identity, was not analysed by the audit, and is deferred to a post-launch hard fork, to be taken up only if testnet or mainnet measurement shows producers stuffing in practice.

**Why skip fees are 100% burned:** if skip fees paid the miner, a miner could deliberately assemble blocks to harvest other people's deposits. Burning removes the direct reward; B1–B4 remove the manufactured-skip vectors entirely; what remains billable (STALE/OVERFLOW) is risk the signer took knowingly. Miners are paid by emission plus par-gas tips of *applied* certificates, aligning them with maximizing application.

## 11. Mempool and admission

Admission = V1..V8 (stateless, and batchable in principle though nothing batches them today) **plus** local, non-consensus checks: deposit covers at tip, per-underwriter in-flight caps, minimum fee bids, TTL within `[now+2, now+TTL_MAX]`. The mempool indexes by `cert_id`, by deposit cell (to re-check cheaply on new blocks), by `(underwriter, Seq)` (to relay dependent chains in order), and by fee density for block building. On each new block: evict committed/expired ids, re-admit reorged certificates, re-screen deposits touched by the block. The validity pipeline lives in `node/verify`, in two implementations that both answer "are these certificates valid" for a batch and return one verdict per input, positionally aligned: `Sequential`, which exists to be the thing the concurrent one is compared against, and `Pool`, a worker pool handing certificates out by atomic index rather than in contiguous chunks, because the cost of checking one varies by the number of signatures it carries and a static split strands workers behind the expensive chunk. There is no `Verifier` interface: one was written and removed, because an interface with no consumer is a guess about a future call site rather than a seam.

The seam is the point. *What* the predicate is, is consensus and lives in `core/validity`, single-threaded and free of anything that could make two nodes disagree. *How fast a node evaluates it* is scheduling, and scheduling is where goroutines, batching and eventually a GPU belong. Batch signature verification and, in Phase 1, cEVM re-execution slot in here without a line changing in `core/`. `TestPoolAgreesWithSequential` pins order-independence by comparison rather than by argument, over a batch deliberately mixing valid and invalid certificates so that dropped results cannot hide behind all-nil.

**No hot path uses it yet, and the reason is more interesting than a to-do.** A batch verifier needs a batch, and Era-0 traffic does not produce one: certificates arrive *singly* over gossip and singly at mempool admission. The one natural batch is a block's certificates — and that check lives inside `core/fold.CheckBlockRules`, which cannot import `node/`, and which re-verifies even work the caller already did, deliberately: a fold that trusts its caller is a fold with an attack surface. So the pool is an instrument rather than plumbing — it is what the whitepaper's §15 verification figures are measured with — and it holds no exemption from `sim/wiring`'s unreferenced-export guard.

## 12. Blocks, proof-of-work, and fork choice

- **PoW:** `pow_seed = blake3("zcd/pow/v1" ‖ ssz(header with nonce zeroed))`, computed once per candidate block; the work function runs over the 43-byte **hashing blob** described below, once per attempt (I1-M5). RandomX at M3, re-keyed every `RANDOMX_KEY_INTERVAL = 2048` blocks with a `RANDOMX_KEY_LAG = 64` block shift of the boundary; a BLAKE3 development engine stands in behind the same interface until then, keyed identically so the schedule is exercised by every devnet and every test. **The key is `blake3("zcd/pow-key/v1" ‖ le64(chain_id) ‖ le64(seed_epoch))`, derived from the header's own height — not, as upstream RandomX does, from a key block's hash**; it keeps `CheckWork` a *total* function of a header's bytes, and §21 has the full entry with its cost and reversal trigger. **`seed_epoch(H)` is `0` for `H < INTERVAL + LAG` and `(H - LAG) / INTERVAL` above it**, so the key changes at heights congruent to `LAG` modulo `INTERVAL` and every epoch is exactly `INTERVAL` blocks wide; `Validate` pins `LAG < INTERVAL`, without which the expression skips epochs instead of shifting the boundary. A block header MUST declare that value in `PoW.SeedEpoch` (B0b) — the field is redundant with the height by construction, and pinning it is what stops it being 64 bits of free grinding space inside the proof-of-work seed. That rule lives in `core/fold` rather than beside the target check, because it is pure header arithmetic and therefore gets golden-vector coverage and path-independence for free, which the target rule had to be argued into. **Cited headers are exempt and that exemption is normative** ([spec/wire](spec/wire.md) §9 rule 7): a citation's `PoW.SeedEpoch` stays unconstrained, its work is checked against the key *its own height* implies, and a citation may therefore be a header that would be invalid as a block. **Genesis carries no proof of work** (I1-L1): solving block 0 would make it unreproducible without the miner's nonce, and a competing genesis is a different network rather than a fork.

  **The value compared against the target is the COMMITMENT, not the RandomX digest, and this is normative.** The work check is

  ```
  commitment = blake2b-256(pow_input ‖ pow_hash)
  le256(commitment) ≤ Target
  ```

  where `pow_hash` is the full RandomX digest, carried in the header, and `blake2b-256` is unkeyed BLAKE2b with a 32-byte output. A verifier MUST also check that `pow_hash` is in fact the digest of this header's own blob under the height's key; the two halves are separable and the separation is the point (below).

  **This follows the miner rather than choosing.** rx/2 sets `Tweak_V2_COMMITMENT` unconditionally — `RandomX_ConfigurationMoneroV2`'s constructor sets it, `RxAlgo::base()` returns that configuration for every `RX_V2` job, and no pool-protocol field, flag or configuration turns it off — and under it stock XMRig filters shares on the commitment. `CpuWorker.cpp` calls `randomx_calculate_commitment(prev_job, size, m_hash, m_hash)`, which writes its output **over `m_hash` in place**, so the buffer the target test reads twelve lines later holds the commitment while the one named `m_commitment` holds the raw digest. **The names are inverted at every layer, the Stratum wire fields included:** the field named `result` carries the commitment and the field named `commitment` carries the hash. A chain that compared the raw digest under rx/2 would be evaluating a number no miner filters on, and stock XMRig would discard the nonces that win and submit the ones that lose — a healthy reported hashrate with every share refused, which is the silent failure [decisions/xmrig](decisions/xmrig.md) exists to prevent.

  **What the commitment buys, and it is why the header grew 32 bytes.** Forming the commitment costs a BLAKE3 over the header plus a BLAKE2b over 75 bytes — about a microsecond — against roughly 55 ms for a light-mode RandomX verify. So a header whose commitment misses the target is refused at a millionth of the price, and the paths where that matters are the ones an attacker aims: cited headers, flood handling, light rejection. A passing commitment still required its author to produce the digest inside it, so the cheap path defers the expensive check behind a proof of work rather than skipping it; a forged `pow_hash` costs a full search to construct and is refused by the identity half regardless. `pow_seed` zeroes `pow_hash` along with `Nonce`, without which the seed would be a function of itself.

  **The little-endian rule is unchanged and still normative**, now applied to the commitment: `le256` reads byte 0 as the least significant byte. This is the one place in the protocol that departs from the big-endian convention every other 256-bit value here follows — a cell value, a target, accumulated work are all numbers somebody encoded, and their wire form is 32 big-endian bytes. A digest is not: it is 32 opaque bytes out of the work function, so which end is most significant is a convention the rule must *choose*, and the choice is made to match the producer. RandomX is a Monero-family work function, and the entire Monero-family ecosystem — XMRig, every pool, every proxy — reads its digest little-endian, comparing the last eight bytes as an LE `uint64` against a compact target. The two conventions read **opposite ends** of the digest, and the ends are independent, so no proxy or pool can translate between them: under a big-endian rule a share a stock miner finds is uniform noise to the node, and vice versa. The rule's difficulty is unaffected — a digest is uniform, so either reading lands at or below a given target with the same probability — and what changes is which nonces win, and therefore who can mine at all. An implementation that reads it big-endian does not merely fork; it is unmineable by every miner that exists.

  **A consequence to record, because a component outside consensus depends on it:** under the little-endian rule a 64-bit Stratum job target is a clean truncation of the 256-bit consensus target, `t64 = max(1, floor((TARGET + 1) / 2^192))`. The bytes that truncation keeps are exactly the bytes XMRig compares — the last eight of the commitment, read as an LE `uint64`, which is the same window and the same end as under rx/0; what moved is which 32 bytes it is a window into — so every share found under `t64` satisfies the full 256-bit check up to a boundary sliver one part in `2^64` wide — and a node re-verifies every submitted share against the full rule regardless. Under a big-endian rule no such truncation exists at all. This relationship is stated here rather than in the endpoint that uses it because it is a property of the consensus rule: if the rule ever changed back, the truncation would stop being sound and the endpoint would be silently wrong (`core/pow.TestAStratumJobTargetIsACleanTruncation` is the executable form).

- **The hashing blob (§12).** The work function is evaluated over exactly 43 bytes, and the layout is normative:

  ```
  offset  0..31   pow_seed     blake3("zcd/pow/v1" ‖ ssz(header with Nonce zeroed))
  offset 32..38   seven bytes  reserved — MUST be zero
  offset 39..42   le32(nonce)  the searched nonce
  ```

  **The offset is not a design choice.** Stock XMRig writes a four-byte little-endian nonce at byte 39 of whatever blob it is handed for `rx/0`, because that is where the nonce sits in Monero's block-hashing blob; the offset is compiled into the miner and no pool-protocol field moves it. A chain that wants unmodified XMRig pointed at it therefore takes 39 or ships a forked miner. **Shipping a forked miner was the alternative and it was rejected** ([decisions/xmrig](decisions/xmrig.md)): the trust and rebasing costs are the ordinary objections, but the one that decides it is that a big-endian target has no clean 64-bit truncation, so the mismatch does not stay inside consensus — it leaks into every pool, proxy and dashboard that ever speaks to this chain, permanently, while the miner fork's own cost is at least in principle temporary. The seven reserved bytes exist only because 32 and 39 are seven apart. **43 is not merely permitted by XMRig, it is XMRig's floor:** `Job::setBlob` refuses any blob shorter than `nonceOffset() + nonceSize()`, which for the RandomX family is 39 + 4, so this chain's blob is the smallest one stock XMRig will accept and there is nothing to trim. **One consequence for whatever serves jobs, recorded here because it is a property of the blob rather than of the endpoint:** `Job::setBlob` also reads the four bytes at 39 as it loads them, and a *non-zero* nonce in a served blob silently puts the miner into nicehash mode, where `nonceMask()` narrows the search from 32 bits to 24. A job blob MUST therefore carry a zero nonce — which it does, since the nonce is the field the miner is being asked to find.

  **The zero-pad is a consensus rule and it binds implementations rather than blocks.** No header field can reach bytes 32..38 — they are written by the blob constructor and derived from nothing — so there is no block a node could receive that violates the rule and no fold rule that could reject one. It is stated here because that is precisely what makes it dangerous to leave unstated: an implementation that filled the gap with a nonce's high bytes, a version byte, or an uninitialised buffer computes a different digest for the same header and forks on its first block, and no corpus of *blocks* can catch it. Pinning the gap at zero also keeps it from later becoming a place to put a field, which would be grinding space that `pow_seed`'s zeroing does not reach. `core/types`' `TestTheReservedBytesAreZero` is this tree's executable hold, and it reaches only this tree. What makes the rule binding on a second implementation is a cross-check against the miner rather than a golden vector over blocks — the corpus in `spec/vectors` folds blocks and a block cannot express this gap, so no vector there ever could — and that cross-check now exists: `core/pow/randomx`'s `TestTheBlobThisTreeBuildsIsTheBlobXMRigSearches` assembles the 43 bytes a second time from XMRig's own published offsets, importing no constant from `core/types`, and requires the two byte strings to be identical. Its companions carry the digest convention the same way: a share XMRig's own test accepts must satisfy `CheckWork`, one it rejects must not, and the solver must find the same set of nonces a stock miner finds. The mutations those tests were confirmed to fail under are listed in the file, including the one they do **not** catch and where it is caught instead.

  **The seed schedule did not change, and what it is worth is easiest to say in the miner's own vocabulary.** `KeyFor(height)` is exactly a Stratum `seed_hash`: the 32-byte value a pool sends with a job and a miner uses to key its cache, never deriving it and never needing to. So the schedule needs no new field, no new message and no miner-side change — a pool reads the height, computes the key, and puts it in the job. **What is unusual is that the next epoch's key is derivable arbitrarily far ahead**, because it is a function of height alone. Upstream RandomX keys from a key block's *hash*, so the next key is unknowable until that block is mined and is revised by any reorg across it; every dataset rebuild is therefore a surprise, arriving when a block arrives, and a pool cannot warm a cache for a key it cannot yet name. Here every participant — node, pool, miner — can compute the key for any future height and build its cache whenever it is idle. That is the integration advantage, and it is why the boundary stall this tree measured (8–11 s of a node verifying nothing, at every key rotation) was removable by prefetch at all: `core/pow/randomx`'s package comment records the 24.8 ms warm figure against 574.9 ms cold, and notes that under upstream's schedule the same prefetch would depend on which branch wins. The cost side of the trade is not hidden — a height-derived key is one fewer thing binding the proof to chain history — and §21 carries the full entry with its reversal trigger.

  **`PoW` is `{Nonce u32, ExtraNonce u32, SeedEpoch u64}`** — 16 bytes, so the seal split is invisible to the wire. **`HeaderSize` is 260**: it was 228 until the header gained the 32-byte `pow_hash` the commitment rule needs, which is the one field this change added and the price it was worth paying (above). A 512-header response is 133,120 bytes, still far under the wire ceilings. `pow_seed` zeroes **`Nonce` and `pow_hash`, and nothing else**. The two zeroings are there for opposite reasons. `pow_hash` is zeroed because the seed is hashed to make the blob and the blob is hashed to make `pow_hash`, so leaving it in the preimage would make the seed a function of itself — no value would satisfy it and no header could ever be valid. `ExtraNonce` is *not* zeroed: it stays inside the preimage, so every value of it is a distinct seed and therefore a disjoint 2^32 nonce space. That is what lets a pool serve stock miners — one `ExtraNonce` per connection or per job gives each miner a search space no other miner is walking. Monero pools obtain the same separation by varying `tx_extra` in the coinbase transaction; this chain has no coinbase transaction to vary, so the separation has to be a header field. **Nothing in consensus constrains `ExtraNonce`**, deliberately: it is 32 bits of grinding space a miner already has for free by iterating `Nonce`, so pinning it would remove a pool's only means of sharding work while removing no grinding capability at all. A solo miner sets it to `0` and loses nothing — 2^32 nonces per (template, `ExtraNonce`) pair is ample at a 30-second target, and a template refresh re-rolls the seed anyway.

- **Difficulty:** LWMA over the last 90 blocks, targeting 30 s. The ratio is normalised against the window's **average** declared target — canonical Zawy LWMA — not against its last target. Normalising against the last target feeds each correction back onto the rule's own previous output, leaving the loop only marginally stable (dominant pole |z| ≈ 0.9993, ~1,500-block memory): it does not diverge on its own, but it integrates proof of work's exponentially distributed solve-time noise almost without forgetting it, turning log(target) into a random walk several bits wide — and mainnet has only 12 bits of headroom between `GENESIS_TARGET` (2^238) and `MAX_TARGET` (2^250), so that walk crossed it within a few hundred blocks on a **fully honest** chain. Averaging moves the pole to |z| ≈ 0.9785 and the spread to a stable 0.15 bits; the loop keeps non-zero DC gain, as it must to track hashrate at all, and simply no longer amplifies its own noise (`core/pow/honest_chain_poisson_test.go`). Each solve time is a **signed** quantity, clamped symmetrically to ±(`TARGET_BLOCK_SECONDS`×`DIFFICULTY_CLAMP_FACTOR`) = ±480 s on mainnet (F-PARAM-3). **It must be signed:** the only lower bound on `Header.Time` is the median of the last 11 blocks, not the parent's own time, so a miner may legally backdate a block it wins — and flooring that block's negative interval at zero keeps the inflated positive interval its backdating donates to the *next* block while discarding the compensating charge, which leaves the controller with no fixed point at all for any manipulated share strictly between 6.25 % and 93.75 % (`core/pow/pow_test.go`).

  The clamp above bounds each block's target to at most ±`DIFFICULTY_CLAMP_FACTOR` of the *immediately preceding block's* target — applied fresh on every block, **not** once per `DIFFICULTY_WINDOW` (F-PARAM-2; §21 records why the code's reading is the one that stands). The upper half *was* provably redundant while the ratio was applied to the last target (R2-POW-5), and that proof does not survive the average-target normalisation: mean and last can diverge, so a window whose about-to-age-out headers declare much larger targets can push a neutral ratio past `last×DIFFICULTY_CLAMP_FACTOR` (`core/pow/upper_clamp_test.go`). The lower half was never redundant: it is what turns a non-positive weighted sum into the actual floor on how much a single block may harden. **The target is additionally clamped, absolutely, to `[1, MAX_TARGET]`** — `2^250` on mainnet, `2^251` on devnet, both in `spec/params.json` and both committed by the consensus root. This bound is normative and an implementation that omits it computes a different target from the first block where the relative clamp would have gone past it, because **the relative clamp bounds the *step*, not the destination**: it is a ratio against a value itself free to move, so sustained upward pressure multiplies the target every block and 256-bit saturating arithmetic delivers it to `2^256 − 1` rather than failing — where every hash satisfies the target and `BlockWork` returns 1 for every header, so accumulated work is a block count and fork choice picks whoever emits headers fastest. From `GENESIS_TARGET` that state is 2^18 away, about 4.5 clamp steps. `Validate` requires `GENESIS_TARGET ≤ MAX_TARGET < 2^255`, the second bound being exactly where block work collapses to one (F-PARAM-1).
- **Time rules (R1-H2):** validity requires `Header.Time >` median of the last 11 blocks. The future side is **not** a validity rule: blocks timestamped beyond `FTL = 180 s` of local clock are *withheld* — queued and re-evaluated as the clock advances — never rejected. Wall clocks must not fork the network's view of validity.
  - **The producer side is a separate rule and it is one-sided: a miner never declares a time it has not reached** (`node/miner.blockTime`). The median-past rule fixes the earliest timestamp the next block may carry; until the local clock passes that floor the miner refuses to build rather than dating a header forward to satisfy it. This is a *policy* on what this node produces and not a validity rule — nothing rejects a future-dated block, and a network of nodes that ignored it would still converge — but its absence is not a small thing. The miner used to clamp instead, and before a network's genesis the floor **is** `genesis_time`, so an honest operator who started early got a private chain dated into the future: peers withheld it and then dropped it past the withhold horizon, and because `NextTarget` reads *declared* solve times, intervals pinned near zero against a 30 s goal hardened the target by the per-block clamp every block with no feedback from real time. The refusal costs nothing a real network wants and removes that whole class from a launch.

  **What the backward direction permits, stated.** `FTL` is the stated bound on the forward direction; the backward one had none written down, and what stood in for it was a measured degradation curve, which is a statement about one attacker rather than a bound. The bound is derivable from the rule alone. **It bounds a rate and not a depth, and that is the whole of it: dating a block deeper buys depth, not rate — and the rate is what `NextTarget` integrates.**

  - **Depth: no constant bounds it in validity, and propagation charges for it in wall time.** `Header.Time` is never compared against its *parent's*, only against the median, so a block may legally be dated arbitrarily far below its parent. The depth available is exactly `parent.Time − MedianTime`, and since the future side is a withhold rather than a validity rule, nothing in *consensus* bounds the parent's own timestamp from above either. **What bounds the depth is the withhold path, not the rule:** a forward-dated parent is queued rather than relayed until the local clock passes `Time − FTL`, sync truncates a header range at the first header the local clock cannot reach, and past the one-hour withhold horizon it is dropped by every peer instead of held. So a deeper backdate is bought with wall-clock wait, second for second, and a chain built that way propagates no faster than a clock. Legal at every step, and not free.
  - **Rate: bounded, and the holder pays only for the headers the honest minority does not supply.** `MedianTime` is **non-decreasing** under R1-H2 — of the 11 headers in the window at least 6 are at or above the median; dropping the oldest leaves at least 5, and the new header is strictly above the old median by the rule, restoring the count to 6, which puts the new median at or above the old one. Raising it therefore takes `floor(MEDIAN_TIME_BLOCKS/2)+1 = 6` headers above the old value — **but a holder of `h` of the 11 supplies only `h − 5` of those six, because the `11 − h` honest headers in the window are already above the old median.** So the declared clock advances **one second per `h − floor(M/2)` headers the holder produces**, which per second of real time is `h / ((h − floor(M/2)) · M · TARGET_BLOCK_SECONDS)`. The two ends of that range are a factor of `(floor(M/2)+1)² / M = 3.27` apart and must not be quoted for each other: **at the threshold, six of eleven, it is one second per *one* header it produces — a 55× compression on mainnet; at total capture, eleven of eleven, one second per six — 180×.** The infimum of one second per six headers is reached **only** by a producer that makes every one of them.
  - **The threshold is a count of headers, not a share of hashrate, and it is sharp.** At five of eleven the declared clock tracks real time exactly; at six of eleven it runs at 1/55 of real time. Against a **fixed** honest hashrate — the model that isolates the timestamp rule from the controller — five of eleven leaves the target within a factor of two of genesis, while six of eleven drives the weighted accumulator non-positive on most blocks, fires the relative floor, and takes the target down to the absolute floor at `1`. Against a hashrate that **feels** the target — the model in which the attack costs its own author wall time, and a different run — the expected block interval passes 100× the goal inside a few hundred blocks. The two models answer different questions and neither number transfers to the other.
  - **It is a liveness degradation and not a kill**, and that is asserted rather than assumed: the floor is absolute rather than attacker-chosen, and once the producer stops, the chain returns to within 1.1× the goal in a bounded number of honest blocks without operator action. What that recovery costs is *wall time* rather than blocks, because each of those blocks takes as long as the damaged target says it takes. Six of every eleven headers is a sustained majority of block production, and a stochastic miner at 54.5 % holds the window only about 63 % of the time — so this is a majority attack whose interest is that it is cheap to sustain, not that it is available to a minority.

    Beyond the derived rate formula and the `3.27` that separates its two ends, both of which are checked against the measurement at every `h`, the quantities above are bounds the tests assert rather than figures typed here: the exact block counts and hours are printed by `core/pow/median_bound_test.go` when it runs, and this paragraph deliberately quotes none of them.

  Each clause is pinned in `core/pow/median_bound_test.go`, on all three parameter sets where the clause is about the rule rather than about mainnet's numbers. What a producer *below* the threshold costs the chain is a different question with a different kind of answer, and it is measured rather than derived, in `core/pow/backdate_sweep_test.go`.

  **What enforces each half, and where** (neither half is redundant: without the lower bound a backdated block splits the network by ingress path, and without the upper bound a forward-dated one drives the LWMA to its floor). The lower bound is checked in `node/sync.ValidateHeaders` for every header of a range, in `node/p2p.Engine.OnBlock` for a gossiped block that extends the tip, and again when a branch is adopted through fork choice against the same preceding-window construction (`node/chain.validateBranchDifficultyLocked`) — by then `depthOf` has established that the ancestor names a block on *this* chain within the undo horizon, which is exactly the ancestor window the rule needs. **Both rules are therefore path-independent.** What is deliberately *not* re-derived there is the proof of work itself: every block reaching `ConsiderBranch` had its own work checked at admission, so re-evaluating it would cost a hash per block for a fact the package can already assume — a cost decision, and the one that hardens under RandomX rather than softening.

  The future side is the withhold queue in `node/p2p/withhold.go`: a gossiped block dated past FTL is queued rather than judged, keyed by id, released when the local clock passes `Time - FTL` by a one-second tick, and only then judged and — if accepted — relayed. It is bounded (64 blocks, 8 MiB) and evicts the block that matures *last*, deterministically, so a flood of far-future blocks cannot displace a near-future one; past a one-hour horizon a block is dropped rather than queued, because "never rejected" cannot mean "retained for a period the sender chooses". A future-dated block scores its sender **nothing** — neither useful nor invalid — because whether it is early is a fact about the receiver's clock. On the sync path the same bound truncates a header range at the first header the local clock cannot reach, checked **after** version, height, linkage, target, work and the median, so a header carrying no proof of work is refused as garbage rather than laundered into "nothing to do this pass". The clock lives in `node/p2p.Engine.Now` and `node/sync.Clock` and nowhere below them: `node/chain`, `core/fold` and `core/pow` remain clockless, and `pow.IsTooFarAhead` takes `now` as an argument precisely so that consensus never reads one.
- **What the FTL bound does and does not buy.** It closes the *downward* collapse and only that: the unbounded push drove the median arbitrarily forward, flooring every honest timestamp at `median + 1` and dividing the target by the clamp factor every block until the chain was unmineable, and with the bound in place the same attack reaches a worst real block interval of about 53 s on mainnet against roughly 48 years unbounded. **The mirror direction used to survive it**, and the mechanism is kept because it is what makes the bound legible: a miner dating every block it wins at exactly `now + FTL − 1` is never withheld, never scored and perfectly legal, and under the floor-at-zero accumulator its donation was cumulative rather than once per window, leaving an equilibrium only for a manipulated share **`p < goal / FTL`**. That threshold scales with `TARGET_BLOCK_SECONDS`, so a faster network is proportionally more exposed to the identical rule — and it was never a safe margin either, since it assumes away both the exponential dispersion of real solve times and any attacker spacing other than the minimum-variance one.

  **Both halves are now closed, by two separate changes, and which does what matters.** Signing the accumulator removes the attacker's free ratchet; **normalising against the window average, and that is what stabilises the controller against ordinary Poisson dispersion rather than against an attacker** — under the old rule an honest chain with no attacker at all reached `MAX_TARGET` in roughly two thirds of long mainnet runs. `sim/timestamp_test.go` drives the real rule across shares from 1 % to 50 % on both parameter sets and reaches `MAX_TARGET` at none of them; restoring the floor-at-zero fails all three of that file's tests. **That file drives the FORWARD direction only** — its `push` is a `uint64` added to the real clock, so it cannot backdate at all — **and `MAX_TARGET` is the runaway direction's witness, not the freeze's**. The backward direction is driven in `core/pow/pow_test.go`'s interleaved-backdating test and, against the median rule rather than a fixed offset, in `core/pow/backdate_sweep_test.go` and `core/pow/median_bound_test.go`. An earlier revision of this sentence said "in both directions" and it was reading the file's two *outcome* columns — worst interval and best interval — as two attackers. **`MAX_TARGET` remains the backstop of last resort, and a chain pinned at `2^250` is compromised, not safe** — `BlockWork` is 63 for every header there and fork choice degenerates toward a block count.
- **Fork choice:** greatest accumulated work. Undo horizon `UNDO_DEPTH = 1024` blocks; deeper reorgs require resync (accepted for Era 0 — wallets and exchanges should treat depth ≪ 1024 as practical finality; Phase-1 checkpoints make this moot).

  ### Launch checkpoints

  **The honest scope, first.** No checkpoint stops a hashrate majority from winning the *live tip* going forward, and nothing below claims to. What these layers do is make history rewrite **against joining nodes** impossible past the pinned heights — which is the privilege-the-early-network property the launch era needs, and nothing more.

  The launch era is CPU-mined by design (§14; the whitepaper accepts that RandomX invites botnets), so a young chain's cumulative work is small in absolute terms. An attacker who arrives in week two does not have to outrace the honest tip: the cheaper theft is to mine a heavier chain **from genesis** in private and feed it to everyone who joins later. The early network keeps its chain; every new node adopts the attacker's. **`undo_depth` is no help there, and that is the whole of the gap** — it defends a tip, and a node with no history has no tip. The uncovered case is exactly the first sync from genesis, and a return after an outage longer than the undo horizon.

  Three layers, in the order of how much they ask you to trust:

  1. **`min_chain_work`** — a cumulative-work floor, refreshed every release: a chain that arrives at the floor's height carrying less than the floor is not the network's chain. It names no block id and cannot decide between two chains that both clear it, which is why it is the primary layer. Bitcoin Core's `nMinimumChainWork`, and it is **paired with the height it is measured at** here for an implementation reason worth stating: Bitcoin evaluates it against a peer's complete header chain, downloaded before any block is requested, while `node/sync` is batch-interleaved — so a bare "total work must exceed W" would refuse a fresh node's first batch and every batch after it, because a chain that is not allowed to grow can never reach a floor. Pairing value with height puts the refusal where it belongs and leaves a chain still below that height unjudged.
  2. **Hard-coded `(height, block_id)` checkpoints** — from the first patch release onward; a sync candidate that contradicts a pin is refused outright. Precedent: Bitcoin since July 2010, and Monero, Litecoin and Zcash ship them today, refreshed per release.
  3. **`undo_depth`** — already implemented, and it is the tip-side layer of the same story rather than a separate mechanism.

  **Schedule:** v1.0.0 none (the enforcement ships with empty data — a defence added later is a defence nothing has ever run); v1.0.1 (~day 3) height 2,880; v1.0.2 (~day 10) height 20,160; v1.0.3 (~day 31) heights 40,320 and 86,400; monthly thereafter. **Never pin a block younger than 2,880 blocks (24 h)** — one `epoch_length`, and 2.8× `undo_depth`, so anything old enough to be pinned is a block no honest node would reorg away in any case. **Sunset at height 1,051,200 (one year):** past it no new pin is added and `min_chain_work` alone carries the floor. `node/checkpoints.Validate` refuses a table that breaks the sunset, and `MaxPinnableHeight` is the age rule as a function a release step calls (docs/RELEASE.md).

  **None of this enters `ConsensusRoot()`, and that constraint is load-bearing.** Checkpoints are client release policy, not chain parameters: they live in `spec/checkpoints.json`, which the params blake3 does not cover, their types live in `node/checkpoints` rather than in `core/`, and the file is announced under its own hash. If editing a checkpoint could move the parameter hash, every routine release would derive a different genesis id and fork the network — `node/checkpoints`'s `TestCheckpointDataDoesNotEnterTheConsensusRoot` pins the boundary three ways so that moving a field across it fails a test rather than a network.

  **Enforced in `node/sync.Admit` only**, after a candidate has won on work and before a single body is requested for it. It does not need to exist on the gossip path: a gossiped branch is bounded by `undo_depth`, a pin is at least 2,880 blocks old, so a gossiped branch can never reach far enough back to cross one — which is the same 24-hour rule paying for a second thing.

  **Refused, not scored.** Every other sync refusal charges the peer; these two deliberately do not. The rule a contradicting peer broke is *this client's release policy*, not a rule of the protocol, so a checkpoint shipped wrong would otherwise ban the honest network from every node that took the release — an editing mistake turned into a partition. A node that had already followed the wrong chain below the highest pin stops there and stays stopped: it cannot reorg back past `undo_depth`, and it must be resynced from an empty data directory. That is the intended outcome — stuck and saying so beats following an attacker's history — so the refusal names the height, the pinned id and the offered id, the active table is printed at startup, and `/status` carries `min_chain_work`, `min_chain_work_height`, `checkpoint_count`, `checkpoint_height`, `checkpoint_id` and `checkpoint_sunset_height`.

  `/status` also carries **`chain_work`**, the accumulated work of that node's own canonical chain up to `height`, decimal. It is what makes layer 1 refreshable at all: `min_chain_work` is a number a release engineer has to *measure*, and this is the only surface it can be read from — the release step (docs/RELEASE.md) takes the `(height, chain_work)` pair out of one `/status` response and cross-checks it against a second node, the same discipline the pinned block ids get. Enforcement whose value no release can obtain is a layer that is switched off, so the reporting side is part of the defence rather than operator convenience.

  **Deliberately excluded: rolling/automatic checkpoints at the tip** (the Bitcoin ABC 10-block auto-finalization pattern). Under a network partition both sides auto-finalize their own branch and the partition becomes permanent. `undo_depth` stays the only tip-side rule; human-published, release-carried pins with a 24-hour minimum age cannot create that split, because anything they pin is already unanimous.

  **Related exposure, since it is the same question asked from the other side:** `coinbase_maturity = 100` (50 min) sits against `undo_depth` 1,024 (~8.5 h), so a miner's reward is spendable ten times sooner than it is safe from reorg. That is what drives the confirmation-depth guidance of **100 / 1,024 / 2,880** — spendable, past the undo horizon, and past the age at which a block can be checkpointed at all.
- **Block validity** = header rules + bodies present and matching `CertRoot` and `CitesRoot` + B0–B18 (§8) + `ApplyBlock` returns no error. A citation's proof of work is checked outside `ApplyBlock` entirely, alongside the header's own — `core/fold` cannot import a `pow.Engine` (P4), so this is the one piece of block validity that does not live behind `ApplyBlock` returning no error.
- **Assembly (miner):** pick by fee density under the ceilings — seq gas, par gas, bytes, all functions of `T` (§15) — respecting `(underwriter, Seq)` order, dry-run the fold once over the candidate (§10), drop the drops, fill `Cites` and `CitesRoot`, seal, solve. **`Cites` is always empty in this release.** An empty list is always valid — the health gate only ever *withholds growth* against an empty signal, never decay or the floor — but it does mean this miner never itself supplies whitepaper §8.1's health signal. Gathering genuine competing headers is unimplemented; the citation *rules* (§8) and their proof-of-work check are complete and apply the moment any producer starts filling the field.

## 13. Networking

TCP with standard-library TLS 1.3 and Ed25519 peer identities, flood gossip with a seen-cache, and request/response for blocks, headers and peers. The decision not to take libp2p — and the conditions that reverse it — are in [decisions/networking](decisions/networking.md); **the normative protocol is [spec/wire](spec/wire.md)**, written so that a second implementation, or libp2p, can replace `node/p2p` without a fork.

- **Certificates** gossip as full bodies (~350–850 B for native ops); a node validates (V-rules) before re-propagating — invalid certs score the peer down.
- **Blocks** relay **hash-first**: header + ordered cert-id list. **Header PoW is verified before any body fetch** (R1-M3), so ghost announcements cost real work; receivers then reconstruct from mempool and fetch only missing bodies (`getcerts`), compact-block style. Peers that fail to serve bodies for blocks they announced are scored down. Propagation latency is thereby decoupled from block contents. `Cites` (§8.1) rides with the body fetch, not the announcement — `CitesRoot` in the header is what the announcement already commits to — and a cited header's own proof of work is checked once the body arrives, alongside the block's (§12).
- **Sync:** headers-first. A header sequence is validated link by link — parent, work, and **the declared target against the one the LWMA rule computes from the preceding window** — before a single body is requested, which is what makes accumulated work a fact rather than a claim (R4-H1). Bodies are then fetched forward along a chain that has already won, and folded. Body availability is consensus (a block without retrievable bodies is not valid), so serving bodies for the recent window is mandatory peer behavior; deep-history serving is incentivized by default-on archival until state-sync ships (post-genesis roadmap).
- **Relay policy** (non-consensus, uniform defaults): deposit-covered-at-tip, fee floor, per-peer rate limits. A relay node needs *zero state* to filter structurally: V-rules from bytes; the deposit screen is the only tip-dependent check.

## 14. Storage

An in-tree write-ahead log plus periodic snapshots (`node/storage`; ~830 lines, standard library only) — not Pebble, which the original decisions log named; the reversal is in §21 and [adversarial/I2](adversarial/I2.md). One key-value namespace, partitioned by one-byte key prefixes rather than column families: `h/` (headers), `b/` (block bodies), `c/` (cells: slot → value), `s/` (spent registry, append-only), `n/` (seen: id → ttl), `u/` (undo: block id → pair list), `i/` (height → block id), `m/` (fixed metadata keys). The fold runs against an **in-memory hot overlay** over the `c/` prefix with write-back at block commit — the design target is the full hot set in RAM and the fold never blocking on disk reads for warm slots. Pruning: `seen` by TTL (F10), `undo` beyond `UNDO_DEPTH`, and cell *values* under spent addresses beyond `UNDO_DEPTH` — **registry entries are never pruned** (§6; R1-C3/L4). Both `seen` (F10) and `undo` (`pruneUndoLocked`) prune one block later than the provably tight floor: the tight bound and a bound wrong by one are otherwise separated by zero, and one block of slack costs nothing. The epoch state root is maintained incrementally from the dirty set, not recomputed from scratch: `core/state` caches the canonical key order, the leaf hash of every cell and registry entry, and the internal merkle nodes of both subtrees. **The value is unchanged** — the definition is still §8's F14, and `core/state` proves the cache reproduces it bit for bit.

**Incremental does not mean sublinear, and the difference is a consensus-shape fact rather than an implementation detail.** The leaves are a canonically *sorted list*, so inserting a registry entry moves the position of every leaf after it and invalidates every cached node covering them; and the capacity is `nextPow2` of the live count, so crossing a power of two re-shapes the whole tree. Only the **hashing** is proportional to the dirty set. Around it, every root still rebuilds the two key/leaf arrays in full whenever any key is dirty and still compares every leaf slot against the tree it is holding — both Θ(N) — so **no block is cheaper than a full pass over the live state**, and no cache can change that without changing what the root *is* (a position-stable sparse merkle tree keyed by slot would be incremental in the strong sense — and a different value, therefore a hard fork).

Measured in `core/state/root_bench_test.go`, which regenerates every figure; the shapes matter more than the numbers. **A single new cell or a single `RETIRE` costs Θ(N)** — roughly 7–8× better than from scratch, against the 28–73× the overwrite-only shape shows. So an ordinary payment that creates a slot is already on the slow path, and **an attacker buys the slow path for one `RETIRE`**: 700 sequential gas out of a 4,000,000 ceiling (§15), or 0.0175 % of a block. Even the overwrite-only shape is not proportional to the dirty set — a *constant* 200 writes costs tens of times more as the state grows a hundredfold, which is the Θ(N) leaf scan showing through. And the registry is never pruned, so the Θ(N) term only grows: the same open problem as the ~33 B per entry, seen from the CPU side.

**The cache is also RAM, in a process that already holds everything** (`BenchmarkRootCacheMemory`): **147–164 B of added resident memory per live entry**, worst just above a power of two, since the figure tracks `nextPow2` slack. Stated next to the ~33 B per entry deliberately — if 33 B/entry of permanent *disk* is the protocol's declared open problem, then 147–164 B/entry of *RAM* is the same problem with a larger constant, and it compounds with the unevicted undo logs and block bodies. Resident consensus state nearly triples at 100k entries and doubles at 1M: the price of the CPU figures above, and a trade rather than a free win.

**Go maps do not shrink, so every map in a long-lived consensus process is sized to its high-water mark** — and unlike the two dirty sets, `s.cells` and `s.seen` are driven by workload rather than by restart: 200,000 cells drained to zero (a delete, which one-shot addresses do by design) left ~26 MB resident with no live cell, and 200,000 `seen` entries pruned by TTL left ~12 MB with `SeenCount() == 0`, both for the process lifetime. `core/state` therefore keeps a high-water mark per map and rebuilds the map when the live population falls below a quarter of it, **re-basing the mark to the new size** (`maybeShrinkCells`, `maybeShrinkSeen`, `shrinkDivisor` = 4, `shrinkFloor` = 1024); both figures go to ~0. The dirty sets use the same rule and are reset rather than `clear`ed, because `chain.load` replays the whole state through `Set` and `MarkSpent` at startup, so a set cleared in place would be sized to the whole state from the first restart onward. `s.spent` has no counterpart: registry entries are never pruned, so it only grows.

Four things about that rule, none obvious, all pinned by tests in `core/state`:

- **It costs nothing on the fold's hot path** — two `len` comparisons on `Set`'s delete branch, below the noise floor of the benchmark that measures it; on the `seen` side it is free by construction, since `PruneSeen` is already Θ(live) and already sorts.
- **It is amortised O(1), and re-basing the mark is what makes it so.** After a rebuild the mark becomes the live count, so re-arming requires the map to grow fourfold again, and an adversary who oscillates across the trigger pays one rebuild and then nothing. Measured over three shapes, two of them built to break exactly this, every one sits well under the amortised bound of 1.0 entry copied per `Set` — and the worst is one of the two adversarial shapes, at a 24× margin, which is the result; a zero there would invite the question of what had not been measured.
- **The `seen` half makes retention track the *live* set rather than the *peak***, which is precisely the property that was broken. It fires whenever the inclusion rate falls, and does **not** fire while the rate is sustained, because a sustained-rate chain genuinely has that many live entries and retaining their buckets is correct rather than a leak. Recovery therefore does not require the chain to go idle, only for the rate to fall. The `cells` case has no such caveat, because a drained cell is a *deleted* map entry under zero-is-absence (whitepaper §4).
- **The instrument that certifies the rule had to observe the re-basing line directly**, by the map changing identity rather than by watching the mark step downward: the derived version reported a perfect `0.000` copies per `Set` under exactly the mutation that makes the rule pathological, because removing the re-base removes the downward steps the counter was reading. That is the mirror CONTRIBUTING names — an instrument deriving its signal from the state the bug corrupts inherits the bug's blindness, and fails in the reassuring direction. `TestSeenShrinkIsAmortisedConstant` asserts the rebuild count directly, which is the property: *one collapse, one rebuild*.

None of this can reach a consensus value. The marks are hints: a rebuilt map holds exactly the same key-value pairs, and every consumer of map iteration in `core/state` either sorts first or writes into another map — so the only thing a rebuild can change is Go's internal iteration order, which no consensus value depends on. `TestRootIsInvariantToTheShrinkSchedule` asserts that against a witness rather than leaving it as an argument.

## 15. Fees and emission (Era 0 parameters)

Two independent EIP-1559-style markets, each with its own per-block ceiling, target, and base fee that steps by `deviation / target / BaseFeeMaxChangeDenominator`. **F12b clamps its sequential input at `2T`**, and the clamp is load-bearing rather than tidy: a block may carry up to `4T` under §8.1's burst valve, so an unclamped upward step would reach **+37.5 %** while the downward step stayed bounded at −12.5 % by an empty block — an asymmetry that ratchets the fee upward under alternating full and empty blocks. With the clamp the step is back inside ±12.5 %, so R2-H1's `SeqMax` safety margin stands as derived. **Consequence, stated so it is not rediscovered as a bug:** the burst band is priced by F11 and invisible to F12b, so `2T` is the ceiling the fee market steers toward and `4T` is a per-block relief valve that buys passage without repricing the market for everyone — what §8.1 means by "genuine surges buy passage immediately". The epoch controller is deliberately left unclamped: it reads `median_applied` and is *supposed* to see a real surge. The rejected alternative — reprice bursting through a second forfeiture on miner tips instead — is argued in §21, and the reason it fails is general enough to state here: **any deterrent priced in forfeited producer revenue is bounded by what the block credits that producer, and a self-dealing proposer sets that to zero.** `core/fold/elastic_ceiling_test.go`'s `TestBurstDoesNotRatchetTheBaseFee` pins both halves and fails without the clamp.

**The two base fees are consensus state**: cells under the `0x00` address, initialised at genesis from `spec/params.json` and updated by the fold at F12b (I1-H1). B4 is evaluated against the values in state *before* the block, which is the only reading under which a proposer can know in advance what it may include. **Sequential gas** meters fold work: per read check, per write, per registry insert, per seen-insert. **Parallel gas** meters verification work: per signature, per byte, per program-derivation unit. **Three gas quantities, three jobs (R2-H2)** — "gas accounting" means three different things in three different rules, and an implementation that conflates any two is wrong:

| Quantity | Counts | Bounds / drives |
|---|---|---|
| **Included gas** | the declared gas of *every* certificate in the block, whatever its outcome | the per-block ceilings `SeqGasLimit(T)`/`SeqGasBurst(T)` and `ParGasLimit(T)` — they bound physical work, and a skip still costs a verifier its signature checks and the fold its guard evaluations |
| **Applied gas** | the declared gas of the certificates that **APPLIED** | the base-fee update at F12b, and nothing else |
| **Block bytes** | the encoded size of every included certificate, drops included — they occupy the block | `BlockByteLimit(T)` |

**The sequential ceiling is elastic (whitepaper §8.1), and this section fixes the constants; §8 (F2b, B5/B6, F11) specifies the mechanism.** `T`, the sequential target, is consensus state from block 0 (`types.SeqGasTargetSlot`, §6), not a `spec/params.json` constant — `SeqGasTargetGenesis` names only its initial value and its permanent floor. Every ceiling below is derived from `T` and moves as `T` does:

```
SeqGasLimit(T)   = 2T                       // the soft ceiling: B5's forfeiture threshold
SeqGasBurst(T)   = 4T                       // the hard bound: B5's validity threshold
ParGasLimit(T)   = ParGasRatio × 2T         // a fixed multiple of the sequential ceiling (B6)
ParGasTarget(T)  = ParGasRatio × T          // F12b's parallel-market target
T                   = min(the epoch controller's output,                    SeqGasCapacity)
MaxCertsPerBlock(T) = min(MaxCertsPerBlockGenesis × T / SeqGasTargetGenesis, CertListCapacity)
MaxSigsPerBlock(T)  =     MaxSigsPerBlockGenesis  × T / SeqGasTargetGenesis   // B18; no clamp
BlockByteLimit(T)   = min(BlockByteLimitGenesis   × T / SeqGasTargetGenesis, BlockByteCapacity)
```

**`MaxSigsPerBlock` has no capacity clamp, and the absence is the rule rather than an omission.** The other two are clamped because a real structural bound exists behind each — `CertListCapacity` fixes `CertRoot`'s merkle width and `BlockByteCapacity` fixes what a network message can carry — and nothing plays either role for a signature count: a block's signatures are a property of its certificates, not a merkleised list of their own. A clamp invented for symmetry would be inert at every shipped set, and this document's own precedent is that **inert is worse than absent, because it reads as covered**. Both implementations saturate instead, at the point where the scaled ceiling stops fitting a `uint64` — above any signature count a block can carry, so the saturated ceiling refuses exactly what a representable one would.

**The table above is defined for `T ≤ SeqGasCapacity` and for nothing else, and that domain is a statement rather than an omission.** `T` is the value the table's own first line produces — already clamped — so a larger `T` is not an input left unhandled; it is an input this document says cannot exist. Four independent facts close it, and a second implementation should confirm all four rather than any one, because each alone is a line somebody could change: a parameter set with `seq_gas_capacity < seq_gas_target_genesis` is refused at load; F2b applies the capacity clamp **before** the genesis floor, so the controller's output never exceeds the capacity; height 0 writes `SeqGasTargetGenesis` into the target cell and nothing else does at that height; and the golden corpus's generator writes `T` at exactly two places, both *below* `SeqGasTargetGenesis`. **Above that domain this section fixes nothing, and it withholds the choice uniformly.** Read as written, `MaxCertsPerBlock` and `BlockByteLimit` scale `T` first and take the `min` afterwards, so substituting a larger argument yields output-clamping and `core/params` is a faithful reading rather than a defect — but **it does not follow that a second implementation owes the same behaviour**: `core/params/naive` refuses such a `T` outright and is equally conformant, and `core/params/ceilings_differential_test.go` cannot separate them, because both implementations would have to move together. Fixing a convention over the empty part would be an answer nobody chose, in a consensus document, where a later reader would take it for a reachable rule.

**Neither `min` in the table can take its second branch, for any parameter set `Validate` accepts, and that is now the strong claim rather than the narrow one.** The byte half is the pairing argument, restated below: `Validate` pairs `block_byte_capacity` to `seq_gas_capacity` by exact 128-bit cross-multiplication, so `BlockByteLimit(SeqGasCapacity)` *is* `BlockByteCapacity` and never more. The count half is the same argument with one deliberate difference. `Validate` now also requires

```
cert_list_capacity × seq_gas_target_genesis  ≥  max_certs_per_block_genesis × seq_gas_capacity
```

again in exact 128-bit arithmetic, which says precisely that `MaxCertsPerBlockGenesis × T / SeqGasTargetGenesis` cannot exceed `CertListCapacity` anywhere in `T ≤ SeqGasCapacity`. **The relation is `≥` and not `==`, and that is the one place the two clamps are not identical.** `block_byte_capacity` is re-pinned at era boundaries against measured propagation, so pinning it to the genesis ratio costs nothing that cannot be repaired later; `CertListCapacity` is frozen for the life of the chain (it fixes `CertRoot`'s merkle depth — see below), so it is deliberately oversized once, at genesis, for the *end* of §8.1's curve, and an equality would forbid exactly the headroom that sizing exists to buy. The count side used to be bounded only from **below**, at `≥ MaxCertsPerBlockGenesis`, and a legal parameter set could put the count clamp strictly *inside* the domain — at `cert_list_capacity` = 12,799 the `min` fired at `T` = 5,120,000, and at 4,000 it fired at `T` = 1,600,400, both values the mainnet controller reaches. No shipped value moved: the rule demands 12,800 at the mainnet and testnet genesis ratio against a shipped 2²⁵, and 820 at devnet's.

**One consequence of that rule is a bound on era policy, and it is the only place a `Validate` check constrains a future re-pin.** An era boundary raises `seq_gas_capacity` with `block_byte_capacity` at the fixed genesis ratio ([decisions/capacity-eras](decisions/capacity-eras.md)); `cert_list_capacity` cannot follow, because it is frozen. So the check above is what a re-pin set must still satisfy, and it stops being satisfiable once the scaled count ceiling would meet the frozen 2²⁵ — a factor of about 2,621 above the shipped mainnet capacity. That is the wall the capacity was sized against in the first place, now stated as a refusal at the moment such a set would be chosen rather than as a number in a note.

**The four unclamped ceilings — `SeqGasLimit`, `SeqGasBurst`, `ParGasLimit`, `ParGasTarget` — fall under the same silence, and they make plainer why it is the right one.** They carry no `min` at all, so there is no output to clamp and not even a notation to extend, and the overflow argument below is *conditioned* on `T ≤ SeqGasCapacity` and says nothing outside it. Above the domain this document does not choose between wrapping, saturating and refusing: `core/params` wraps, `core/params/naive` refuses, and neither is a defect. Reading that silence as deliberate is the point — for all seven ceilings the quantity that would reach past the wall does not exist.

**All three ceilings are clamped against a second, static bound, and each clamp answers a different question.** `CertListCapacity` fixes `CertRoot`'s merkle depth (§5), which cannot move with height without changing what every earlier `CertRoot` commits to — which is also why it alone is sized at genesis for the *end* of §8.1's curve rather than for the launch network (2²⁵; the padding is virtual, so the headroom costs tree depth and nothing else). `BlockByteCapacity` answers a cruder question: a block consensus calls valid must still be one the transport can move, so the bound is `MaxBlockChunks × BlockChunkBytes` ([spec/wire](spec/wire.md) §5.1), and it is this capacity, with `SeqGasCapacity` at the fixed genesis ratio, that an era boundary re-pins against measured propagation ([decisions/capacity-eras](decisions/capacity-eras.md)).

**Neither capacity is defensive tidiness, and the two failures they close are different.** With no byte capacity at all the chain outruns its transport permanently, on a healthy network, in about 620 epochs — because §8's EIP-1559 base fee steers *applied* gas toward `T`, so `2·median_applied` lands near `2T`, the growth clamp binds every epoch, and `T` rises at its maximum rate whenever the fee market is merely working, not only under attack. The failure is the bad kind: not a rejected block but a block every node agrees is valid and no node can transmit, unrepairable after genesis without a hard fork (`TestBlockByteCapacityFitsChunkedTransfer` is the only place the consensus number and the transport numbers meet). **What holds that bound in the shipped design is `SeqGasCapacity`, not the `min` inside `BlockByteLimit`.** `Validate` pairs the two capacities by exact cross-multiplication, so `BlockByteLimitGenesis × SeqGasCapacity / SeqGasTargetGenesis` *is* `BlockByteCapacity` — 2,500,000 × 5,120,000 / 1,600,000 = 8,000,000 on all three shipped networks, testnet and devnet included since the respin put them back on mainnet's gas schedule (they reached the same 8,000,000 through 2,500,000 × 6,400,000 / 2,000,000 before it) — and `T ≤ SeqGasCapacity`, so the byte ceiling is already bounded before the `min` is consulted and that `min` cannot take its second branch for any parameter set `Validate` accepts. `BlockByteCapacity`'s job is to name the transport wall and fix the pairing point; the pairing and the clamp are one mechanism written twice, which is why relaxing the pairing to an inequality would silently arm the clamp and start `BlockByteLimit` returning values the elastic-ceiling reasoning does not expect. **`SeqGasCapacity` closes a subtler one as well:** with bytes pinned and `T` still free, `T` climbs until `2·median ≤ T` — to `T = 2G` for `G` the most sequential gas a full block can physically hold — where F12b's base-fee target sits at twice anything a block can reach, a physically full block reports `applied/target = 0.50` *forever*, the base fee decays to its resting point (measured: 1000 → 15 over 3,000 full blocks), and block space rations purely by priority tip with no burn: the permanent auction §8.1 calls unreachable, and the end of §14.2's congestion deflation. **The 0.50 is exact and independent of gas density**, because `T`'s fixed point is `2·median` by construction while the base fee's is `applied = T` — two controllers whose fixed points cannot both hold, each correct alone, which is why nobody noticed.

`SeqGasCapacity` introduces no new economic assumption: it preserves the ratio the genesis parameters already chose — `SeqGasCapacity / SeqGasTargetGenesis == BlockByteCapacity / BlockByteLimitGenesis`, so 5,120,000 against 8,000,000 bytes — which makes gas and bytes reach their walls together and the terminal state *exactly* as well calibrated as block 0, checked in `Validate` and pinned by `TestSeqGasCapacityPairsWithTheByteCeiling`. Whether **genesis** is well calibrated was a separate, pre-existing question, and **it is answered** by moving `SeqGasTargetGenesis` from 2,000,000 to 1,600,000: the break-even is now 0.64 sequential gas per byte *of block* against a plain transfer's 0.704, so a byte-full block of ordinary payments applies 1.0999 of the target and raises the base fee instead of lowering it. It could not be left on the [testnet measurement list](decisions/testnet-measurements.md), for the reason that list gives for what belongs on it: the number is in the consensus root, so a testnet carrying a different one measures a different chain. It also disposes of an overflow question in one line: `SeqGasBurst(T) = 4T` and `ParGasLimit(T)` are plain `uint64` multiplications and `T ≤ SeqGasCapacity`, so every quantity derived from `T` is bounded by construction. That replaces an earlier argument that was worse than merely long — that `T` is self-limiting once its consumers are pinned. Every step of that is true and the conclusion is the bug: `T` does self-limit, at `2G`, which is precisely the state where the fee markets stop pricing (I6-C2). **Safety was being argued from the same property that made the system fail**; a bound you can point at beats a bound you have to argue for.

**Constants (genesis, illustrative; the values live in `spec/params.json`):** `CeilingGrowthDivisor` (Γ) = 512 — T grows by at most `T/Γ` per epoch of full, healthy blocks, compounding to at most a doubling per year of full blocks; `CeilingDecayDivisor` (Δ) = 1024 — T shrinks by at most `T/Δ` per idle epoch, and never below `SeqGasTargetGenesis`; `HealthGateBps` = 200 (2 %) — the epoch's cited-competing-header rate, above which growth (never decay, never the floor) is withheld for the epoch; `MaxCitesPerBlock` = 4; `CertListCapacity` = 33,554,432.

Three decisions this document had to make that the paper's §8.1 does not itself pin down, recorded here and in §21:

1. **All three block ceilings scale with `T`, not sequential gas alone.** At genesis, `MaxCertsPerBlockGenesis`, `BlockByteLimitGenesis` and `SeqGasTargetGenesis` bind close enough together that scaling only the gas ceiling would make the other two the *real* limit after about one doubling, and elasticity would be decorative past that point. **A measurement replaced that estimate, and it corrects the picture in two directions.** First, be exact about which bound rejects: `checkBlockRules` rejects a block only above `SeqGasBurst(T) = 4T`, never at `2T`, so the *rejecting* ceilings are count, bytes, `4T` sequential gas and parallel gas — `2T` is F11's forfeiture threshold, a price on a revenue-maximising producer rather than a rule. Second, swept over 98 shapes covering the whole Era-0 shape space, all `wallet.Builder` output and validity-clean, the rejecting ceilings split that space into **three** classes with no ties: **count** binds for the two 558 B shapes at the encoding floor, **gas** binds for 38, and **bytes** binds for the other 58; nothing is parallel-bound, and under the `2T` soft threshold the gas class widens to 76 of the 98. **The gas class is new at these parameters and is the concrete form of B5 becoming reachable**: at the superseded `T₀` = 2,000,000 the `4T` bound demanded 3.2 sequential gas per byte of block against a densest achievable 2.8937, so the class was empty and no block could be refused by B5 at all; at 1,600,000 it demands 2.56 and 38 already-built shapes clear it. None of that widens the count rule's job, which is still the floor and only the floor: without it a minimum-size flood would be bounded at 4,447 by bytes and 8,000 by `4T` gas instead of 4,000 (`core/fold/cert_budget_test.go`).
2. **The burst valve's forfeiture falls on the producer's share of the subsidy alone, never the treasury's.** Bursting is the producer's choice; the treasury is computed from the unreduced subsidy before F11 evaluates the valve. Total issuance still falls when a block bursts, so it remains a permanent shortfall against `C` (§14.2), exactly the shape of a coinbase burned under I1-M2.
3. **The health gate ships with citations, not as a later addition.** A ceiling rule is genesis-frozen consensus (P6): `Header.CitesRoot` and `Block.Cites` (§5) cannot be added after launch without a hard fork, so the health signal's carrier is built into the encoding from block 0 even though nothing in Era 0 yet gathers citations to fill it (§12's `Assembly` note).

Applied gas alone drives the base fees because a skip is a *failed attempt* to use the chain, not evidence of demand for it. Were included gas to drive them, a griefer would have a constant-cost lever: stuff blocks with self-conflicting certificates — self-inflicted, so the billing law is untouched — at `SKIP_FEE` each, and price everyone else's certificates upward. `SKIP_FEE` is a constant (R1-H1), so the attack's cost does not rise with the damage it does.

**Each market has a maximum and a priority (R2-H1).** The base-fee portion of each is burned; the priority — clamped to whatever headroom the base fee leaves under the maximum — is paid to the miner, and only on certificates that apply (I1-H2). Three properties depend on this split. Burning the base fee keeps it a *measurement* of demand rather than a *lever*: a base fee that reached the miner could be inflated for free by self-stuffing. Tipping on both markets is what gives the scarce resource a price at all — with only a parallel tip, a revenue-maximising builder allocates sequential capacity by verification demand and sells the ordering it cannot auction on chain. And splitting the offer into a maximum and a priority stops a signer paying for its own safety margin: B4 forces a certificate to name a price above the base fee for its whole TTL window, and a single-field bid would charge that margin in full whenever the certificate happened to be included early. The full argument, the six revenue lines and the rejected alternatives on both sides are in [adversarial/H2-economics](adversarial/H2-economics.md). Fee-market drift can strand a signed certificate (re-sign with a higher bid), but can never bill it. **`gas_par_per_sig` has never been repriced against V2's torsion check**, which added roughly 10.8× to the valid verification path (§3, §21), so the parallel market under-prices a signature against what it now costs to check.

**Emission (whitepaper §14.2).** The rate is constant within an epoch and decays once per epoch by exact integer arithmetic (I1-L2):

```
E(0) = GENESIS_EMISSION
E(n) = max(TAIL_EMISSION, E(n−1) − E(n−1)/EMISSION_DECAY_DIVISOR)
```

No floats and no table to get wrong. `emission(0) = 0`: the genesis block pays no coinbase at all, because there is no miner to pay and a reproducible genesis must not credit an address.

Genesis values: `GENESIS_EMISSION = 21 ZCD`/block, `EMISSION_DECAY_DIVISOR = 1054`, `TAIL_EMISSION = 0.33 ZCD`/block, over a 2,880-block epoch. These compound to a yearly factor of 0.70702 — the emission rate **halves every two years**, exactly rather than approximately: `E(730) = 10.50230028 ZCD` against `E(0) = 21 ZCD`. The formula falls below the tail at epoch **4,376** (height **12,602,880**, ≈ year 12), where `core/params.buildEmissionTable`'s 4,377-entry walk ends, so the decaying arm runs over epochs 0 through **4,375** and sums to `C` = **62,744,838.47 ZCD**, of which **62,744,817.47 is actually issued** — the difference is the genesis block's 21, which pays no coinbase. **The closed form `EPOCH_LENGTH × E(0) × EMISSION_DECAY_DIVISOR` = 63,745,920 ZCD is an upper bound on `C` and not its value**: it sums the infinite geometric decay, while the schedule is finite, floors at every step and stops at the tail, so it overshoots by 1.60 %. It is recorded as a bound because it used to be quoted as the value. **`C` is what the schedule *sums to*, not a cap it guarantees**: the schedule is a pure function of height and never consults what was actually paid, so a coinbase burned under I1-M2 is a permanent shortfall rather than a debt the curve repays. Deciding otherwise would require the fold to carry `issued` as consensus state; it does not, because the Era-2 ramp is a redivision between PoW and PoS and never a reduction (whitepaper §14).

**The subsidy is split 97/3 (whitepaper §14.1).** `TREASURY_SHARE_BPS = 300` of every subsidy is credited to the treasury cell at F11 and the remainder pays consensus; the split is on the subsidy only and never on fees. In Era 0 the producer takes the whole 97 %, and keeps taking it through Phase 1's instruction-set heights; the 77/20 subdivision between producer and checkpoint attesters begins only when the finality overlay activates on its stake condition (§17), because before that there are no attesters to pay. All four constants live in `spec/params.json` and enter the consensus root, so any of them moves the genesis id.

`COINBASE_MATURITY = 100`. Note the launch dynamic this implies: for the first ~100 blocks only miners can fund deposits, so the chain's first users are necessarily its miners — "mine to play" (R1-L3).

## 16. Repository and package architecture

```
zycord/
  spec/                 params.json, golden vectors (JSON), test-vector schema   ← THE PROTOCOL
  core/                 consensus-critical; standard library only (P4)
    types/  crypto/  fold/  validity/  pow/  state/ (interfaces + hot overlay)
    pow/randomx/          the mainnet engine: vendored C++, cgo, behind a build tag
  node/                 mempool/  p2p/  storage/  rpc/  miner/  sync/  verify/
  wallet/               key mgmt, cert builders (reference; not consensus)
  sim/                  adversarial simulator, fuzz harnesses, differential runner
  cmd/                  zycordd, zcd (cli)
  docs/                 this file, whitepaper, adversarial reviews, CONTRIBUTING, SECURITY
```

Dependency arrows point inward only: `node → core`, `wallet → core`, never the reverse, and nothing inside `core/` reaches outside `core/` and the standard library. **One exception, named and enforced:** `core/pow/randomx` is the only cgo in the tree and holds the vendored RandomX. It compiles only under the `randomx` build tag, so every build without the tag — including `make build` and `go test ./...` — is still standard-library-only and needs no C toolchain. `make check-imports` scans for `import "C"` outside that one directory, because the third-party check greps module paths and cgo has none, which left the rule enforced by nobody until it was added. `make check-imports` is what CI actually runs: no outward arrow from `core/` or `node/`, and no third-party import inside either. It does not check the narrower, package-by-package graph within `core/` — today `core/fold` also imports `core/params`, `core/state`, `core/u256` and `core/validity`, and `core/validity` also imports `core/params` and `core/u256`, both wider than `core/types` and `core/crypto` alone, and neither is a CI violation. CODEOWNERS marks `core/` and `spec/` as the high-review zone (consensus changes need vectors + simulator runs before human review is even scheduled); `node/`, `wallet/`, `docs/` are the low-barrier zone where contributors are grown.

## 17. Phase gating

Activation constants in `spec/params.json` (`H1_BOND`, `H1_VM`, `H2_POS`), compiled per release. **Two kinds of gate, and the difference is load-bearing (whitepaper §14).** Era 1's *instruction set* activates by height, in the order the parameters already encode: `H1_BOND` turns on the `BOND` operation, `H1_VM` turns on underwriter and sequencer registration and the cEVM, and `Validate` enforces `H1_VM ≥ H1_BOND`. Era 1's *finality overlay* activates on a **state condition** instead — bonded stake ≥ 1 % of supply, sustained for `K` epochs — because stake cannot be measured before the operation that creates it exists. That is the whole reason `BOND` is not a genesis operation: moving the trigger past the operation costs two ordered heights, where moving the operation back to genesis would have cost a fifth opcode in the one era with no co-signers to absorb its failures (P7, §9's theorem).

A state-gated activation is a different animal from a height and must be built like one:

- **It is consensus state.** Bonded stake is an accumulator cell; "sustained for `K` epochs" is a latch evaluated at epoch boundaries, and both live in the state root or they are not consensus.
- **It must be a one-way ratchet, and reorg-safe.** If a reorg could retract a `BOND` and retroactively un-satisfy the condition, every block accepted under the overlay would become invalid — the worst failure mode this codebase has. `K` is not yet a `spec/params.json` field, because the overlay is deliberately absent from the genesis binary (P7); it exists only as whitepaper §13's illustrative `K = 14` epochs. That value already closes the reorg-safety question, and the coincidence is worth naming rather than relying on silently: 14 epochs is 40,320 blocks, roughly 39× `UNDO_DEPTH`, so the earliest epoch the latch would read is far below any reorg the node will ever perform. **`K` was chosen to stop activation on trivial stake; it also happens to be what makes the latch safe.** Whoever adds `K` when Era 1 ships must check any departure from that value against `UNDO_DEPTH`, not only against the economics.
- **It must be measured over completed epochs only**, never over the epoch in progress, for the same reason F14 computes the state root at boundaries.

- `Underwriter` — Era 0 ships `SelfInsured` only; Phase 1 adds `CoSigned` (bond registry cells, equivocation-proof verification, skip billing against bonds) at `H1_VM`, and the forced queue with leases + scheduled application (the fold gains F-rules; old vectors must replay bit-identically below `H1`). B1–B4 already protect bonds from manufactured billing, so the co-signer inherits the billing law for free. Co-signing goes live before the overlay does; the gap is deliberate, and it is a market-honesty question rather than a consensus one, because a bond prices skips and never reorgs.
- `Bond` — absent in Era 0 by design. Phase 1 adds the `BOND` operation at `H1_BOND`: value moves from a balance into a bonded cell with a consensus-visible withdrawal delay, activating *before* registration so stake can accumulate toward the overlay condition while nothing yet consumes it. **Design constraint carried over from I1-H3: whatever the credit rules on a bonded cell turn out to be, they must not let a party other than the cell's own key move it**, or the attribution theorem gains a fourth case — and unlike the third, this one would sit on a cell with a time-dependent read.
- `Finality` — Era 0 ships `WorkDepth`; Phase 1 adds `FFGOverlay` (checkpoint votes every 32 blocks by bonded validators) **at overlay activation, not at a height**, and with it the subdivision of F11's producer share into 77/20 between producer and attesters. Between `H1_VM` and activation the split stays 97/3: there are no attesters to pay, and paying a share to nobody would either burn issuance or hand it to the producer under a name that does not match what it is. The treasury's 3 % is unchanged by that split and by every later one.
- `Treasury` — Era 0 ships accrual only (F11, §6). Phase 2 adds the debit path: a certificate carrying 3-of-5 signatures over a key set **pinned by hard fork**, plus rotation with delay `R`. Neither the key set nor any spend rule may appear in an Era-0 or Era-1 release, because a seal that exists in the binary before the fork that authorises it is not a seal (P3, P7).
- `Program` — Era 0 ships `NativeOps`; Phase 1 adds `CEVM` behind the same `derive/verify` contract, plus the pre-deployed delta-first standard library. The cEVM reintroduces mutable EXACT reads, ending the §9 theorem's scope — co-signer pricing is the designed absorber, and the griefing suite gains cEVM scenarios then.
- `Shielded` (**Era S**, whitepaper §12) — confidential payments: hidden amounts in Pedersen commitments, one-time stealth recipient addresses, a range-proof verifier, the hidden-cell kind of §6, the third-party-guard ban, and a shielded-pool slot whose guarded delta bounds what a verifier break can cost. Absent from every release until it is proposable, per P7. Three things set it apart from every other entry here:

  **Its trigger is a checklist — a third kind of gate.** Heights are facts a node measures; sustained stake is consensus state a node evaluates; a verifier's readiness is neither, so it cannot be encoded as a constant or a cell at all. What activates the era is a hard fork operators adopt, proposable only once it can cite: co-signed underwriting live (shielded traffic cannot ride self-insurance without the public deposit cell re-linking what the stealth address unlinked); the verifier and its batch path published with at least two independent audits, findings and remediations public; the full rail run on a public testnet with adversarial participation for ≥ `K` epochs; and golden vectors for the verifier committed to `spec/`. The form matters more than the items: this network has no emergency response team, so the checklist exists to make a community that cannot maintain a consensus verifier discover that *before* activation rather than after a break.

  **It is not purely additive, and it is the only phase here that is not.** Hidden-cell typing and the ban on third-party guards against hidden balances change how F6 and F7 treat a class of slot — genesis-critical surface, the code P1 calls sacred. The closing rule of this section still holds (no `0x04` cell exists below the activation height, so every historical vector replays bit-identically) but that is weaker than it sounds: it says the *past* is safe and says nothing about the diff. So the era is a hard fork reviewed as a consensus-critical change rather than an activation flag, and **the touched guard path needs its own vectors on both sides of the height.**

  **It is the first consensus-critical cryptography outside `core/crypto`, and P4 has no answer for it yet.** A range-proof verifier's arithmetic is not standard-library code, and it is the one piece of this era whose bug is unbounded in the way P1 means. Whether it is vendored, written in-tree, or the era is not shipped is a decision that belongs before the era is proposable, not in the pull request that introduces it.

  Four questions the whitepaper leaves open and this document inherits rather than answers: whether the rail carries only the native coin or §9 assets too (a single generator commits to a scalar, not to an `(asset, value)` pair); whether `RETIRE` acts on shielded cells (if it does, value leaves the pool without a public unshield and the pool slot becomes an upper bound rather than an equality); where the encrypted `(v, r)` lives (certificate body, and seed-only wallet restore dies when bodies are pruned; or cell value, and it costs state per output); and whether an underwriter can charge inside the certificate in public value.

Rule: a new phase may add rules and record types; it may never alter the meaning of an existing vector below its activation height. `sim/` replays the full historical vector suite against every candidate release.

## 18. Testing and verification strategy

- **Golden vectors** (`spec/vectors/`): every F-rule, B-rule, and V-rule has positive/negative cases as `(pre-state, block) → (post-state | invalid, outcomes, fees)` JSON. The vector suite is the compatibility contract for independent implementations.
- **The griefing suite** (pins R1-C1/C2/C3 and the §9 theorem): re-inclusion of applied and skipped certs (must be invalid blocks), expired inclusion, under-bid inclusion, same-signer dependent chains under proposer shuffling (must commit in Seq order), deposit-from-one-shot with MARK_SPENT + RefundTo cycles (no stranded or double-billed funds — asserted of the whole burned cell, not only of the remainder), one-shot-funded `ISSUE` end to end (F-VAL-5), a burned remainder reported as burned (F-FOLD-1), third-party credit storms against pending TRANSFERs (zero billed skips), mint-cap boundary races (only willing minters billed).
- **Property-based:** fold determinism under proposer-order permutation (canonical sort must erase it); delta commutativity; ABA tolerance; conservation (Σ value invariant minus burns minus emission, including deposits in flight, the coinbase maturity ring, and the treasury cell — the treasury is issuance that has been credited, so a conservation check that omits it reports every block as creating value).
- **Differential:** a deliberately naive second fold implementation (`sim/refold`, written for obviousness, not speed) fuzzed against `core/fold` — divergence is a release blocker. The epoch state root doubles as a production-time differential guard between nodes.
- **Adversarial simulator (`sim/`):** skip storms, deposit-drain races, drop-stuffing miners, reorg torture (deep forks, TTL-boundary re-inclusion, seen/registry undo), timestamp manipulation vs LWMA — **forward-dating only** here, driven against the real `pow.NextTarget` and observed in both directions the *target* can move (`sim/timestamp_test.go`, whose `push` is a `uint64` added to the real clock and therefore cannot backdate at all; the backward direction is in `core/pow`, and calling this file "both directions" was a false coverage claim, since corrected; the withhold **queue** is covered in `node/p2p/withhold_test.go` and `node/sync`, not here), eclipse-lite relay scenarios. Scenario configs are committed; runs are reproducible by seed.
- **Fuzzing:** SSZ decoders, program derivation (including merge canonicalization), guard arithmetic — continuous, corpus committed.
- **Sync test:** full replay from genesis reproduces every epoch state root on a machine profile documented in `docs/` (the decentralization budget, stated and tracked).
- **Concurrency, deliberately:** every component more than one goroutine touches has a test that *is* concurrent, in the shape the process actually uses. `-race` on a single-goroutine suite measures nothing and reports success — see [concurrency](adversarial/concurrency.md). Consensus-state access rules are machine-checked rather than reviewed: the borrowed reference `chain.Read` lends panics if used after its callback, in every build; re-entering the chain panics in builds carrying `-tags zcdguard`.
- **The chaos soak (`sim/chaos`):** real `zycordd` processes over real sockets behind a proxy injecting latency, jitter, loss, severed connections and partitions, with nodes killed by `SIGKILL` at random. Two regimes, because they ask different questions: convergence after the chaos stops (one chain, one tip, one state root), and — under mining that never stops — agreement about history below the reorg horizon, sampled throughout rather than at the end. Every run asserts it reached an epoch boundary and that its nodes were built with the state guard armed, because a soak that did neither proves much less than it looks like. This is the surface that found the data race the entire `-race` suite missed.

## 19. Genesis procedure

Genesis is a reproducible artifact, not a ceremony: `zcd genesis --params spec/params.json` emits the genesis block (empty state, beacon cells initialized, empty spent registry, no allocations of any kind) and its id. The announced launch commits, weeks in advance, to: the code tag, the params hash, the genesis id, and the launch height/time. Anyone can rebuild all four. There is nothing else to trust.

**Whoever executes the parameter freeze reads the release checklist's freeze item first**, and re-verifies at the freeze commit the four ratified figures — the `seq_gas_target_genesis` floor, the `seq_gas_capacity` ratio, `health_gate_bps` and `epoch_length` — then closes it citing that commit. The step, the values and why the record stays open until the freeze are the [RELEASE.md §8](RELEASE.md) checklist item; it is stated once there rather than twice, because a figure copied into a second place is a figure that can drift.

It is two findings. The **charged** half — headers the work check refuses — is bounded and tight (`TestAHeightVaryingFloodIsBoundedInEpochsToo`); what is missing is the aggregate over Sybil identities, which is what M3.5 is for. Every fix direction proposed at the time was eliminated with evidence, in [I7](adversarial/I7.md) and [sync](adversarial/sync.md) §6.1.

  **The price has since been built, and one line of that reasoning is struck rather than quietly deleted because it was wrong:** the price does **not** need the work engine to answer *"do you hold this key"* — that answer is an LRU, so it moves with whatever traffic ran most recently, the attacker's included, and a budget sized by it would be one the sender sets. The price is charged instead against the key epochs this node is itself working in (its tip's and the next one), which are facts this node owns, with a **per-identity budget** refilled at `randomx_key_interval × target_block_seconds`, refused **before** the work check and unscored. **Keyed on the sender's Ed25519 identity, it is the per-identity rate limit that was asked for:** the budget survives disconnect rather than being dropped by `forgetPeer`, so an identity cannot re-buy it for the cost of a TLS handshake, and the scoring the number was derived from is keyed on that same identity and its ban is permanent. A keypair is free, so the per-identity budget does not bound the aggregate over identities on its own; a **node-wide ceiling** over all of them — `DefaultMaxUnheldKeyEpochsPerNode`, sized from the connection set — caps the node's total never-held key-epoch evaluations independently of how many identities a sender mints.

Its parameters mirror mainnet's — the only configuration in which [testnet-measurements](decisions/testnet-measurements.md) §1 transfers — and a RandomX network's genesis target must be sized against a measurement of the engine rather than guessed. What it inherits from I7-H4's aggregate is now the charged half alone: the charged half's Sybil count, which is the input the scoring magnitudes have never had (`-20` against `-100` was chosen when an invalid header cost microseconds under the BLAKE3 stand-in and it now costs 15–55 ms). The uncharged half is no longer M3.5's to supply: it is now priced per identity under a node-wide ceiling that bounds the total over identities directly, rather than leaving it to the handshake rate against `MaxInbound`, `perSource` and the `/16` rule.
- **M4 — Adversaries.** Public attack-net with bounty pool (community-funded), external review of `core/`, reproducible-build attestation by independent parties, continuous fuzz farm.
- **M5 — Genesis.** Parameter freeze, vector freeze, v1.0 tag, announced launch, block 0 mined by whoever gets there first. **Three gates, all genesis-frozen and none repairable afterwards.** A fourth is recorded as closed rather than dropped: the base fee's asymmetric step, discharged by F12b's `2T` clamp (§15, §21), which puts the maximum upward step at +12.5 %, symmetric with the −12.5 % an empty block gives — the condition that gate named for itself.
  - **The miner gathers and cites real competing headers**, or the decision to ship without it is made explicitly rather than by default. Nothing is unsound without it — an empty `Cites` list is always valid — but the health gate is then decoration: a ceiling that can only ever grow, because nothing ever reports it unhealthy, is not the gate whitepaper §8.1 describes. This matters more than it reads: the gate is the *only* mechanism the paper gives for keeping capacity inside what propagation carries, and `BlockByteCapacity` (§15) is now the sole backstop holding growth short of the transport's bound.
  - **The genesis gas/byte calibration is decided — and it is decided in the file, not only in principle.** The break-even is `seq_gas_target_genesis / block_byte_limit_genesis`, in sequential gas per byte **of block**, and the density has to be measured in the same unit or the two do not compose: a plain transfer is 600 gas in 852 bytes of block (848 of body plus its SSZ offset) = **0.704**. At the superseded 2,000,000 the break-even was 0.8, a byte-full block of ordinary payments was 2,933 certificates applying 1,759,800 gas — **0.880** of target — and it pushed the sequential base fee *down*, so congestion of the network's commonest transaction never priced at any `T`. The two levers were `block_byte_limit_genesis` up to ≈2.84 MB or `seq_gas_target_genesis` down to ≈1.76 M, and the second was taken, past its own break-even to **1,600,000** for margin: the break-even is **0.64**, 9.1 % under the measured 0.704, and the same block now applies **1.0999** of target and raises the fee. 1,700,000 was rejected at 3.5 % of margin, because these densities have already moved ~1 % twice under re-derivation and the number has no repair path after block 0. The [measurement list](decisions/testnet-measurements.md) now *validates* this rather than deciding it.
  - **The transport's chunked-transfer bound and `BlockByteCapacity` are sized together. The transport half is now sized and recorded; the consensus half is not, which is why this gate stays open.** `BlockChunkBytes` stays at 4 MiB, above the genesis ceiling so a launch block is one chunk and a capacity block is two; `MaxBlockChunks` drops from an inherited 256 to **4**, since at 256 the transport admitted a claimed transfer of 1 GiB, **134.2×** what consensus can ever call a valid block — and a bound above what the block rules can produce is not headroom, it is unreachable state a peer can still make this node account for. The pairing is pinned in **both** directions by `TestBlockByteCapacityFitsChunkedTransfer` over every parameter set `spec/` embeds — **the capacity must fit under the transport ceiling, and the transport ceiling must not exceed twice the chunks a capacity block needs** — so an era re-pin has to raise the transport constants in the same release instead of finding the headroom already sitting there. **`BlockByteCapacity` itself is still the inherited 8,000,000**, retained on a comparison with a data-availability network carrying 8 MB per 6 seconds in production — 2.1 Mbit/s sustained at a 30-second interval here, conservative by roughly 5× **in byte rate**. **Whether that comparison lets the testnet's bandwidth distribution *confirm* the pairing rather than *set* it is disputed and reserved to the owner, and is not answered here in either direction** — a DA network's nodes carry opaque blobs, while a node here must carry *and* fold, verify and write every byte. Both sides are on the [measurement list](decisions/testnet-measurements.md) §1. Until it is decided the value is a genesis-frozen number retained on an argument under challenge, which is what a gate is for.

## 21. Decisions log

Each entry gives the decision, the one thing that would reopen it, and a rejected alternative only where the rejected option is tempting enough that somebody will propose it again. Measurements live in the tests and decision documents named beside them.

**The dependency rule.** A dependency is weighed against **auditability**, not only against maintenance and cgo: the trust case for Zycord is that there is very little to read, and each transitive module is a supply-chain surface the project cannot afford. It cuts both ways, and has — storage in-tree ([I2-C1](adversarial/I2.md)), networking in-tree ([decisions/networking](decisions/networking.md)), Argon2id bought from `golang.org/x/crypto` because passphrase stretching is exactly the kind of primitive not to hand-roll. Reopen conditions are measured rather than rhetorical: [decisions/testnet-measurements](decisions/testnet-measurements.md).

- **A burn is address-scoped, so the rule that guards it is an *effect*, not a verdict** — `MARK_SPENT` kills every cell under an address while every derived guard names one slot, so four certificate shapes could burn an address while accounting for only part of it. F8b moves the residual to the certificate's own `RefundTo` **after** the outcome is decided, and **delivers or leaves it alone, never destroying it**. Both properties were learned from designs that broke them: a rule that *refuses* the burn makes its verdict a function of a balance a stranger can raise with an unsigned credit (§5's forbidden fourth case), and destroying an undeliverable *asset* residual into the block's native burn accumulator broke the conservation identity, letting anyone build a stateless-valid certificate that invalidated every block carrying it. **The general rule to carry into Phase 1: no fold rule's verdict may read a cell a stranger can credit.** Argument, measurements and rejected alternatives: [decisions/one-shot-burn-scope](decisions/one-shot-burn-scope.md).
- **Ed25519 over secp256k1** — batch verification is available to the scheme, non-malleable *when canonical encodings are enforced*, simpler constant-time implementations. The qualifier is not pedantry: non-malleability is a property of verifiers that reject unreduced scalars, several popular implementations do not, and V2 makes rejection a consensus rule rather than an assumption about somebody's library.
- **The certificate id excludes `Sigs`; the block's cert root covers them** — the id names an authorization and many exemplars may carry it, because an Ed25519 signature is a randomized demonstration whose nonce no verifier can constrain (measured before the fix: one signed transfer of 100,000,000 drops moved 200,000,000 in a block). Rejected alternative: key the seen set on the body root instead — the smaller diff in `core/` and the larger diff overall, since the id is also the mempool key, the gossip dedupe key, the miner's tiebreak, the RPC handle and the wallet's idempotency key. **Rejected alternative, and the dangerous one: signatures out of the id with `CertRoot` left over ids.** An id-keyed root commits to no particular signature bytes, so two bodies carrying different valid signatures over the same authorizations share a block id — and swapping an exemplar is *free*, since `CertRoot` is inside the proof-of-work preimage and an id-keyed root would not invalidate the work. **That is an equivocation primitive at zero cost.**
- **V2's point rules: cofactorless + explicit torsion rejection, not ZIP-215** — either keep RFC 8032's cofactorless equation and refuse the inputs batch and single verification disagree on, or adopt ZIP-215, which defines the disagreement away. The first was chosen, and **ZIP-215 is not available to this protocol at any price**: it buys agreement by *deliberately accepting non-canonical encodings*, and a rule that admits encodings other implementations refuse is a consensus split on a certificate neither side can call invalid. Cost: one scalar multiplication by `L` per verification, ~10.8× on the valid path. Vendoring a point library would remove most of it without reopening this, and P4 would have to be widened to admit one (§3).
- **The rules are computed, never tabulated** — the defect being fixed was a nine-entry blocklist missing five accepted encodings, two of which decode to the identity and verify every well-formed signature. It was missing them because *nothing makes a literal fail when it is short*: two review rounds counted the same table and got two different wrong answers. `[8]A == identity` and `[L]A == identity` cannot be short.
- **`R` gets the encoding rule and nothing else** — torsion on `R` is *entailed* by cofactorless verification and is not re-tested (`TestCofactorlessVerificationIsPinned` asserts the entailment against the standard library, which does not promise it). Low order on `R` is not redundant but **wrong**: the only low-order point in the prime-order subgroup is the identity, so testing it rejects exactly `R = identity`, a zero-nonce signature RFC 8032 accepts — the cofactor question with the sign flipped, the same chain split from the other side. **Strictness is only a virtue where the spec licenses it.**
- **BLAKE3 over SHA-256/keccak** — line-rate hashing for relay and an efficiently parallel epoch root; behind an interface and frozen at genesis.
- **SSZ over RLP/protobuf/custom** — canonical-by-construction encoding plus free merkleization; custom encodings are where consensus bugs are born.
- **~~Pebble~~ → an in-tree write-ahead log (I2-C1)** — twenty-six modules including a telemetry SDK, to answer a requirement one sentence long. Reopen when state size rather than correctness is the binding constraint.
- **The RandomX key comes from the height, not from a key block's hash** — `key = blake3("zcd/pow-key/v1" ‖ le64(chain_id) ‖ le64(seed_epoch))`, the only place this tree parts company with upstream's own schedule. **What it buys:** `pow.CheckWork` stays a *total* function of a header's bytes, so a header whose ancestry a node does not hold still has checkable work — orphan admission, announcement scoring, the work-verdict cache and whitepaper §3's stateless-verification claim all rest on that — and it removes a grinding vector upstream admits, where the miner *of* a key block grinds its own hash to set the next epoch's key. **What it costs, and this is the part not to lose:** every key of every epoch is known from genesis, which **breaks the key-unpredictability premise upstream assumes**. Dataset precomputation is not the concern (it is symmetric and improves liveness at a boundary); **long-horizon offline specialisation** is, and it is part of RandomX's ASIC-resistance argument. Acceptable only because proof of work here has an expiry date, so **the risk grows with the length of the PoW-to-PoS ramp and lengthening the ramp reopens this decision.** The reversal trigger is *evidence of specialised hardware*, not a calendar review.
- **RandomX v1.2.3, not v1.2.1** — the version usually named as "the one Monero runs" generates wrong ARM64 and RISC-V code for `ISUB_R` when `src == dst` and `imm == 0x80000000`, because negating −2^31 does not fit in an `int32`. An ARM machine computes a **different hash from an x86 one for the same header**: a chain split along CPU architecture, invisible until two populations exist. Fixed in v1.2.2; v2.0 does not carry the fix and v2.0.1 does, applied independently — which is why ancestry is not proof and the source had to be read. v2 is a different hash function, weighed and not taken: it answers the same specialisation pressure the entry above names, with far less production exposure.
- **The vendored tree is byte-identical and must not be patched** — auditing the work function is then a `diff` against tevador's tag rather than a review of somebody's copy. It also closes a trap invisible without it: **Go's build cache hashes the files in a package directory and does not see into subdirectories**, so editing the vendored C++ rebuilds nothing and every test measures the code you replaced — four mutations of the ARM64 code generator, including deleting the ISUB_R fix, reported green before this was understood. `vendor.sh` writes the tree hash into a package-level Go file, which is what makes the cache correct; `TestVendoredTreeMatchesPinned` catches a hand edit.
- **~~libp2p~~ → TCP with standard-library TLS 1.3** — 141 modules for six problems, and the amplification problem gossipsub exists to solve is structurally weaker here because a certificate is checkable from its bytes. The security-critical part is still bought rather than built: `crypto/tls`, not a hand-rolled Noise handshake. [spec/wire](spec/wire.md) specifies the protocol independently, so libp2p can replace `node/p2p` without a fork ([decisions/networking](decisions/networking.md)).
- **LWMA over Bitcoin-style retarget** — 2016-block windows are a death trap for young chains under hashrate tourism; LWMA responds in ~an hour.
- **`MAX_TARGET`: the target has an absolute ceiling, not only a relative one (F-PARAM-1)** — a per-block clamp bounds the step and not the destination, and with saturating 256-bit arithmetic the destination is `2^256 − 1`, where proof of work is a tautology and fork choice is a block count. That is unrecoverable after genesis; running at minimum difficulty is not. Rejected alternative: derive the ceiling from `GENESIS_TARGET` — it hides a consensus constant inside an arithmetic relation a second implementer has to rediscover. Rejected alternative: a compile-time constant in `core/pow` — it would not enter the consensus root, so two nodes could disagree about it and still share a network id, the silent fork R3-1 exists to prevent. The value is policy inside a hard bound, and `Validate` refuses anything at or above `2^255`.
- **Signed solve-time accumulation, not a floor at zero (F-PARAM-3)** — with `max(0, t_i − t_{i-1})` a miner could legally backdate a block it wins, since the only lower bound on `Header.Time` is the 11-block median: that block's interval floored to zero while the next block's was inflated by the same amount and clamped only at the top, so the donation was uncancelled and strictly profitable, and past a 6.25 % manipulated share the controller had no fixed point at all. **Every LWMA reference implementation surveyed reaches the same conclusion independently** — zawy12's `difficulty-algorithms` names this exact exploit ("if ST<0 then ST=0 ... allows unlimited block production") and its real-world instance (Graft Network, 2018). Rejected alternative: a consensus rule that `Header.Time > parent.Time` — broader than the arithmetic needs, and it interacts with the deliberate FTL withhold-not-reject decision. **What that rejection costs is now written down rather than left implicit:** without it, nothing bounds how far below its parent a block may be dated, and the only bound in the backward direction is on the *rate* at which declared time advances — the R1-H2 entry above states it and `core/pow/median_bound_test.go` pins it. Rejected alternative: clamping the negative side at `-FutureTimeLimitSeconds` — a node-layer threshold applied to this function's *input* on some ingress paths only, where `maxSolve` applies uniformly whatever path fed it a header.
- **The relative clamp is per block, and the documentation is what moved (F-PARAM-2)** — this document previously read "±16× per window"; the code has always clamped against the *immediately preceding block's* target, applied fresh every block. The choice is the code's for three reasons: a sliding LWMA has no periodic retarget boundary for a window-level clamp to anchor to, so the candidate is a novel mechanism rather than a bug fix; no surveyed LWMA-family implementation layers one on the per-sample clamp, and Zcash's Digishield-family DAA clamps the *aggregate timespan ratio*, a different quantity; and a second clamp is not free, since Bitcoin Cash's 2017 moving-average retarget produced a daily oscillation precisely from discrete-window retargeting effects, which is what motivated ASERT — and this project already chose LWMA over a period-retarget design for that class of reason.
- **The epoch state root is maintained from a dirty set, and the root's *definition* is untouched** — §14 asserted this as fact while `core/state` rehashed the whole state every block; the code moved to meet the document. Rejected alternative: compute the root only at F14 — `metaStateRoot` has a second consumer, `chain.load`'s M1-G3 integrity check, which would then run on ~1 restart in 2,880, and M1-G3 is already nearly blind. Rejected alternative: an in-place update path for blocks whose writes all land on existing slots — 72 ms → 25 ms at n=1M, rejected because it buys a constant factor on the *only* regime an attacker can deny, at the cost of a second write path through the leaf arrays in the consensus zone. Rejected alternative: a position-stable sparse merkle tree keyed by slot — incremental in the strong sense, and a different root value, therefore a hard fork rather than an optimisation.
- **Single-billing via block validity (R1-C1)** — billed skips mark seen; expired/seen/under-bid certificates invalidate the block. Rejected alternative: billing those outcomes, which is miner-manufactured griefing of deposits now and of Phase-1 bonds later.
- **Explicit `Seq` in Era 0 (R1-C2)** — hash-ordered same-signer certificates break the default wallet pattern.
- **Explicit MARK_SPENT + fold-level billing + RefundTo (R1-C3)** — implicit spent-on-debit created unresolvable ordering with refunds. Rejected alternative: forbidding one-shot deposit cells by wallet convention (unenforceable).
- **The deposit cell's `MARK_SPENT` belongs to derivation, not to V6 alone (F-VAL-5)** — V6 demanded it for every one-shot deposit cell while derivation produced it only for a `TRANSFER` whose deposit cell was also a move source, so the rules were jointly unsatisfiable everywhere else and a wallet holding funds only under one-shot addresses could build no `ISSUE` or `MINT` at all. **The scope of whitepaper §4's "a signature from its key moves it to spent, permanently" is *declaration*, not settlement:** F8 commits declared writes only on the APPLIED path, so a certificate whose deposit is debited at F3 and which then skips at F6 leaves its one-shot deposit cell debited and unburned, free to fund another certificate. That is pre-existing and benign — the skip is billed, the id is marked seen, no third party can force it — but the argument for this rule is that a valid certificate must *declare* the burn, not that the ledger guarantees one per debit.
- **Refunds and credits may not target an address the certificate itself burns (F-FOLD-1)** — F8 commits a certificate's `MARK_SPENT`s before F9 settles, so such a refund is destroyed at settlement and reported as an ordinary refund; the rule covers any address in the certificate's own write set, and V6 carries it for `DELTA_ADD` credits. Rejected alternative: having settle distinguish "burned by this certificate" from "burned earlier" — the registry does not record which certificate burned an address, and making it do so would put certificate identity into permanent consensus state to solve a problem a stateless rule already solves.
- **A one-shot deposit cell is swept, not sipped (F-VAL-5, wallet)** — whatever the reservation did not take is stranded under a spent cell, and no stateless rule knows a balance, so the discipline lives in `wallet.SweepDeposit` and is pinned by a griefing test asserting the burned cell ends empty. Accepted cost: value under a one-shot address in *other* assets is unreachable from an `ISSUE`/`MINT`/`RETIRE` that burns it, so a wallet must sweep them with a `TRANSFER` first.
- **Permanent spent registry; values prune, bits don't (R1-C3/L4)** — address resurrection breaks the one-shot invariant and silently burns payments to dead addresses. Accepted cost: ~33 B/one-shot address forever; accumulator compaction is future research, shared with all nullifier-set designs.
- **Constant SKIP_FEE (R1-H1)** — market-priced skip fees make deposit ceilings unbounded over the TTL window.
- **FTL withhold, not reject (R1-H2)** — wall clocks must not fork validity.
- **The withhold queue retains one representation of a block, so its byte bound is exact rather than estimated** — `MaxBytes` is the whole of its memory argument ([spec/wire](spec/wire.md) §9 rule 8), and it counted the delivered frame while retaining a decoded `*types.Block` beside it, so a full 8 MiB queue held about 16.5 MiB. **Rejected alternatives: count an estimate of the decoded block as well, or keep it and raise `MaxBytes`.** The same objection kills each, and it is the general one: **the expansion multiplier is content-dependent and therefore the sender's to choose** — an estimate calibrated on ordinary blocks under-counts the adversarial shape by about a third, and one calibrated on the adversarial shape shrinks the effective queue for everyone. The same reasoning makes the copy `make`+`copy` rather than `append([]byte(nil), raw...)`, which sizes through the allocator's size classes and retains up to 25 % capacity the bound does not count.
- **Bid ≥ base fee as block validity (R1-H3)** — fee drift may strand a certificate, never bill it.
- **Skip fees burned, not paid to miners** — removes the residual harvesting incentive even for the skips that remain billable.
- **DROPPED as a silent, unseen non-event** — billing an unfunded deposit is impossible by definition. **The accounting is two-sided and §10 now states it that way:** the relay and miner-rationality defences are *send-side* and do not bind a producer, who includes rather than relays; what a producer can do for free is fill its own block to every ceiling with certificates that deterministically DROP, and every receiving node pays the bandwidth and one strict Ed25519 verification per declared signature. The primitive is amplification-free, creates no state and splits no chain, which is why it is accepted; it is not free to the network. **What bounds the receive side is `B18`, the per-block signature ceiling** — 6,000 verifications, ~4.4 core-seconds per 30-second interval, checked before any signature is verified and no longer growing with the byte ceilings. **`V5`'s new upper bound on `Deposit.Amount` is not that bound and does not close this class:** the attack works identically with `Amount = 1` from an unfunded fresh key. It was taken anyway, before the freeze, because a consensus-valid object declaring more coin than can exist at that height is an absurdity the stateless gate should refuse and the fold could still move. Rejected alternative: block-invalidity on drops, which would force proposers to be stateful *in consensus* for a marginal spam gain. Rejected alternative: bounding it in relay policy — send-side, and therefore the same non-answer to a producer that the old note's defences were. **Deferred, explicitly:** charging at `F3` so the producer pays for what receivers verify — it moves the billing law and the conservation identity, was never analysed, and is post-launch hard-fork work to be taken up only on measurement showing producers stuffing in practice.
- **No lease scheduler in Era 0** — with no co-signers there is nothing to defend, and unreachable consensus code is unauditable risk (P7).
- **uint256 cell values** — cEVM alignment outweighs the space savings of uint128; deltas carry unsigned magnitude + direction to keep arithmetic rules trivially auditable.
- **State root each epoch, not each block** — per-block merkleization taxes the fold for a property Era 0 doesn't sell.
- **Conservative genesis ceilings (R1-M4)** — 4 k certs/block at launch; a young network's fork rate is its scarcest resource.
- **The elastic sequential ceiling implemented rather than left as v0.7's declared divergence** — the epoch controller is reorg-sensitive consensus state, built like §17's sustained-stake latch (a cell, a boundary-only evaluation, full undo-log coverage), and the health gate's header field was added as a genesis-frozen encoding change rather than deferred, because a field added after launch cannot backfill blocks that already exist.
- **All three block ceilings scale with T, not sequential gas alone** — the measurement is in §15 decision 1. Rejected alternative: scale only `SeqGasLimit`, matching the paper's literal text — a ceiling that stops moving after one doubling is not the mechanism the paper is arguing for.
- **`max_certs_per_block_genesis = 4000` against a 2.5 MB byte ceiling is calibration, not accident** — a count ceiling exists to bound a flood of *minimum-size* certificates, the case the byte ceiling is cheapest for and therefore bounds worst. Swept over 98 shapes under the `4T` bound `checkBlockRules` actually rejects on, 4,000 binds for exactly the two 558 B floor shapes and for none of the other 96; without it that flood would be bounded at 4,447 by bytes and 8,000 by `4T` gas. **Utilisation is not constant in `T`**, because the two ceilings floor independently — a sweep stepping by a round number samples only exact divisions and reports the wrong interval, which is how an earlier revision of this entry got it wrong. **Rejected alternative: raise it.** 4,449 is the first value inert at every reachable `T`, since 4,448 becomes violable at `T` = 1,687,410 and at 41.74 % of the 3,520,001 reachable values — and **inert is worse than absent, because it reads as covered.** (Not an argument from the maximal growth ladder, which an earlier revision used and got wrong: `T ← T + T/512` steps *over* the violable band at rung 28, and its first violable rung is 77.) Rejected alternative: lower it toward the payment shape — below 2,933 the count ceiling cuts the byte-bound capacity of ordinary payments. 4,000 sits strictly inside `[2933, 4447]` at `T₀`, and both edges now fail the build (`core/fold/cert_budget_test.go`).
- **The burst valve is denominated in `producer subsidy share + block fees`, and the `2T` bound is restored at F12b's *input*** — the mismatch was real and exact: the forfeiture was priced in the producer's subsidy share, which decays on §14.2's schedule to ~1.6 % of its genesis value, while `2T` grows under the epoch controller, so the break-even priority tip for a full burst fell from 636.56 drops/gas at genesis to 10.00 at the tail. The deterrent shrank while the opportunity grew. **It was a unit mismatch, not a mis-sized penalty**, and it is fixed by re-denominating the base rather than by re-tuning the number: a deterrent §8.1 presents as "a standing property" has to be priced in something that tracks the benefit it prices, and `subsidy + fees` is the smallest base that does. At genesis it changes almost nothing — fees are near zero, so the operating point stays the 1,273-versus-1,000 drops/gas margin the audit confirmed works — and at the tail it tracks exactly the revenue a permanently bursting producer is playing for. The reasoning is EIP-1559's: align what a producer stands to lose with the unit manipulation would actually earn. **Rejected alternatives:** accept the decay and document it (that terminal default is "every rational producer bursts to `4T` on every block, forever", which is not a state a mechanism called load bearing may end in); scale the base by height or by an era schedule (a consensus discontinuity nothing else in the design carries); raise the genesis forfeiture to cover the tail (it costs legitimate genesis burst capacity to fix a tail problem).

  **This is one quadratic with a wider base, and it is NOT the second forfeiture that was rejected.** A *separate* quadratic charge on the block's miner tips, on top of the subsidy one, was implemented, measured and rejected on four counts, and the record stands because three of them still apply to any future proposal of that shape. (1) §8.1 says "forfeiting *producer* subsidy quadratically", and the sentence offered as authority for taxing tips ends "never by scarcity", which is the sentence saying the producer is *not* paid by that line — so a second charge needed a spec change and this re-denomination is one, taken deliberately and written into §8.1 rather than read into it. (2) Neither shape fixes what the F12b input clamp is about: a bursting block steps the base fee identically with and without it, because both `NextBaseFee` and the controller's sample are keyed on `SeqGasApplied` — which is why the clamp below exists and is not replaced by any of this. (3) **The general statement, which survives untouched and must not be read as repaired:** a block credits its producer exactly two things — the subsidy, fixed by `Emission(height)`, and tips, chosen by the producer — so any deterrent priced in forfeited revenue is bounded by what the block credits, and **no repricing inside the forfeiture calculation survives a self-dealing producer**. A proposer whose burst-region certificates declare `priority = 0`, authoring its own filler traffic, still forfeits only a decayed subsidy. What the re-denomination buys is the *paying* producer, the one bursting because the burst-band gas is worth money to somebody; it buys nothing against the one who is not paid at all. (4) The fourth count was that with tips forfeited a `4T` block pays its producer zero however valuable the traffic, and that **is** now true at exactly `4T` — accepted, because that is the hard bound B5 rejects above and buying passage *to* it was never the mechanism's promise. Below it the valve stays monotone: the reward is `(1 − (excess/2T)²) × (subsidy + fees)`, strictly decreasing in the burst and strictly increasing in the fees, so a genuine surge still buys passage into the band. The non-monotonicity in included gas that killed the second-forfeiture design was a property of adding a second term, not of widening the base.

  **The treasury is not a party to it, and that clause is preserved exactly.** §8.1 computes the treasury share on the *unreduced* subsidy and never forfeits it (§14.1 fixes the split so that the remainder pays consensus); the base is the producer's own subsidy remainder plus the producer's own fee income, because bursting is the producer's choice. `Validate` refuses `treasury_share_bps ≥ 10000` for the neighbouring reason. **Honest caveat, on the record:** no long-running economic simulation of the fee market exists, so coupling the valve to fees is reasoned rather than simulated. What makes the risk acceptable is that the genesis operating point does not move — the coupling only becomes active in the regime where the alternative is a decorative valve.

  **On the downstream claim — that sustained bursting walks `T` to the structural walls — the arithmetic says the epoch controller is safe left unclamped, and the correction is load bearing for everything above.** `NextSeqGasTarget` clamps growth to `hi = t + t/Γ` *before* comparing against `2×median`, so a proposer sustaining `4T` applied moves `T` by exactly `T/Γ` per epoch, byte-identical to what an ordinary full `2T` block already moves it — and not marginally, since an ordinary full block is already **3.99×** past the point where the clamp binds and walking `T` to `SeqGasCapacity` takes 597 epochs either way. **The scenario the re-denomination is priced against is therefore bursting to `4T` every block against a hard-clamped controller, not runaway growth**, and no restatement of this decision may drop that. Clamping the epoch controller too would make it blind to genuine surges, the one thing §8.1 asks it not to be. **The parallel market is left unclamped because it has no burst band at all**, so a parallel clamp would be dead code. If a griefing-only scenario is later shown to walk `T` to the walls, the next mechanism is outside the forfeiture calculation entirely — a block-validity minimum-tip rule for the burst region, which would need checking against the same self-dealing loophole count (3) names.

- **`BlockByteCapacity`: the elastic byte ceiling is clamped to what a network message can carry** — unclamped it crosses the transport's bound in roughly 620 epochs of ordinary healthy operation, and the result is a block every node calls valid and no node can send, unrepairable after genesis without a hard fork. **Rejected alternative: raise the transport limit instead** — that is a propagation and DoS decision, not a bookkeeping one, and the safe direction is to make consensus never ask the transport for more than it agreed to carry. *Amended:* blocks travel as chunks, so the bound moved to `MaxBlockChunks × BlockChunkBytes` and the era re-pin goes through `TestBlockByteCapacityFitsChunkedTransfer` ([decisions/capacity-eras](decisions/capacity-eras.md)).
- **`CertListCapacity` is a separate, static bound — not the dynamic certificate-count ceiling** — the old `MaxCertsPerBlock` constant did two jobs (SSZ/merkle structural capacity, and the policy ceiling block rules enforce) and §8.1 makes only the second move. The split was forced by `ssz.Merkleize`'s contract: it panics on a list longer than its capacity, and a capacity that changed with height would make one certificate list hash to different `CertRoot`s at different heights. The same split was applied to citations, and the same panic-ordering hazard was caught on both count checks before the roots are computed (§8) — found by the vector generator attempting the naive construction.
- **The block decode bound was loosened and is deliberately left that way** — `types.UnmarshalBlock` bounds the certificate list by `CertListCapacity` rather than the old fixed 4,000, because a block must still decode once `T` has grown; and `node/p2p.OnBlock` decodes *before* `pow.CheckWork`. The concern is bounded by the frame limit, is SSZ parsing rather than signature verification, and decays: the multiplier `frame ÷ BlockByteLimit(T)` is **3.36× today and 1.05×** once `T` reaches the byte clamp at 5,120,000. **What rules the obvious fix out is the false-positive direction, and it is the general trap:** a pre-decode `len(raw) > BlockByteLimit(T)` check must read `T` from the node's own tip, and a node that is behind holds a *stale, smaller* `T`, so it would reject and score down honest peers serving current blocks at exactly the moment it depends on them — a late joiner 168 blocks behind once reached `min_score -104` and banned a peer while catching up ([I4](adversarial/I4.md)). **The state-free variant is already priced by the decay curve:** checking against `BlockByteCapacity` needs no state and buys exactly 1.05× permanently, because that *is* what `BlockByteLimit(T)` converges to. A version that drops without scoring would be safe and is the shape to revisit if the multiplier ever stops shrinking.
- **The health gate ships with citations from block 0, not after** — `Header.CitesRoot` cannot be added to the wire format after launch without a hard fork, so the carrier had to exist even though no miner in this release fills it. Rejected alternative: ship the elastic ceiling and add citations in a later era — a *ceiling* is exactly the kind of consensus rule this document's own precedent treats as unaddable after the fact, unlike a feature that only adds capability.
- **A one-block citation window, narrower than whitepaper §8.1's "recent"** — it makes duplicate citations structurally impossible and needs no cited-id set in state, but it undercounts competitors exactly when propagation is slow, so the gate fails *permissive* in the regime it exists to catch (§8). Rejected alternative: a W-block window with a bounded, prunable, reorg-safe cited-id set — the correct mechanism, and disproportionate machinery for a signal no Era-0 miner yet emits. **The honest position is that the gate is latent rather than load-bearing, and widening the window is a prerequisite to relying on it, not an optimisation of it.**
- **An invalid golden vector pins the rule id, never the reason string, and its block breaks exactly one rule** — a corpus that records only the verdict cannot tell an implementation that applies the rule from one that rejected the same block for something else: with B4's sequential clause deleted from `core/fold`, `028-invalid-cap-below-base` still satisfied every condition the runner applied, because the block then reached F9 and tripped a conservation assertion. Rejected alternative: compare `expect.reason` — that freezes English into a consensus surface. Rejected alternative: rule-pin only the exposed vectors — the exposure is a property of the *format*, not of a vector. Rejected alternative: specify the order rules are evaluated in — that converts an implementation detail into consensus. **The consequence to hold:** a conservation assertion is deliberately nameless (`fold.Rule` answers `""`), so `spec/gen` refuses to write a vector whose rejection came from a backstop rather than from a rule.
- **The vector format records a params *name*, and that is a trap for whoever writes the next vector** — "mainnet"/"devnet" is resolved back to the canonical, unmodified parameter set at conformance time (`spec.ParamsFor`), so a vector generated against a locally tightened `SeqGasTargetGenesis` is silently replayed against different numbers and fails for a reason unrelated to what it tests. Discovered by generating exactly such a vector and watching the suite reject it. Where the epoch controller's arithmetic is exercisable under real parameters it *is* golden vectors (`017`–`020`), as are a valid citation and its seven invalidity conditions (`034`–`041`). **The burst valve is the exception, on corpus cost rather than the params-name problem:** the cheapest block crossing `2T` under stock `mainnet` numbers is 284 `RETIRE` certificates each retiring the sixteen addresses `max_sigs` allows — 11,300 sequential gas in 3,933 bytes each, for 3,209,200 in a 1.12 MB block — and the vector carrying it would weigh about 3.0 MB of JSON against the 633 kB the 38-vector corpus then weighed. (It was 354 certificates and 4,000,200 gas at the superseded `T₀`; the per-certificate figures did not move, because the gas schedule did not. The vector sizes are scaled from that measurement rather than re-measured, and nothing pins them.) So the *stock-parameter* block stays a Go test (`TestBurstValveAtGenesisParameters`), which is the measurement of that cost and is all it was ever asked to be. **The consequence recorded here for a second implementation — that the corpus does not hold it to the burst valve's arithmetic at all — is retired.** The cost argument is entirely about `T = T₀`, and `T` is not a parameter: it is read from a pre-state cell, which a vector carries and `spec.ParamsFor` never overwrites, so the params-name trap above does not apply to it. At a seeded `T` one certificate of the same family already crosses `2T`, and `spec/vectors/064-burst-forfeiture-where-two-floors-are-not-one-division` reaches the valve in 14 kB rather than megabytes (§8).
- **A priority tip in both markets, base fees burned (I1-H2)** — the scarce resource must carry the ordering signal, and a base fee that reached the miner could be inflated for free. Rejected alternatives: leaving the sequential market unpriced (it becomes an off-chain auction); paying the miner the base fees (free self-stuffing); tipping on skips (recreates the harvesting incentive R1-C1 closed).
- **A two-field bid: maximum and priority per market (R2-H1)** — B4 plus a 240-block TTL plus ±12.5 % drift forces every signer to carry a safety margin, and pay-your-bid charges that margin in full on early inclusion. Accepted cost: the deposit reserves against the maximum. Rejected alternatives: pay-your-bid; relaxing B4 (reintroduces R1-H3 exactly); shortening `TTL_MAX` (a latency parameter bent to paper over a fee bug).
- **Applied gas drives the base fee; included gas bounds the ceilings (R2-H2)** — otherwise `SKIP_FEE`, a constant, buys an unbounded upward push on everyone else's fees.
- **Conservation assertions invalidate a block, never the process (R2-M1)** — rejected alternatives: `panic` (halts a node that could keep serving other branches); saturation (erodes the very invariant that proves the case unreachable).
- **Strictly increasing, not merely sorted (R2-M2)** — enforced at decode for reads, writes, signatures and retire lists. Equal neighbours would give one state transition two encodings and therefore two ids, which the seen set cannot close over.
- **Every numeric parameter is positive, with no exceptions (R2-S3)** — checked by walking the struct, so a parameter added later is covered without anybody remembering to cover it.
- **Asset addresses from `(chain_id, issuer, seq)` (I1-C1)** — the certificate-id derivation is circular and unimplementable. Rejected alternative: a certificate id that does not commit to the writes, which the seen set cannot tolerate.
- **Coinbase maturity as a fixed-size ring (I1-C2)** — "a V-rule on spends" cannot work against fungible balances. Rejected alternative: a claim operation, which grows the Era-0 instruction set for a purely mechanical need.
- **Emission stays a pure function of height; the fold does not track `issued`** — the whitepaper's remaining-supply form and the per-epoch recurrence describe the *same* geometric curve and differ only when the amount actually paid falls below the schedule, which it cannot, because the Era-2 ramp redivides the subsidy rather than reducing it. Accepted cost: a coinbase burned under I1-M2 is a permanent shortfall against `C`. Rejected alternative: `issued` as consensus state — it makes every reward a function of state, and turns a burn into a deferral, which is not what a burn should mean.
- **The treasury share is taken at F11, before the maturity ring** — the floor goes to the treasury and the remainder to the producer, so integer division cannot create or destroy a drop; it does not pass through the ring, because maturity exists to make a reorg-able reward unspendable and a cell with no debit path is already unspendable by everyone forever. Rejected alternatives: crediting through the ring (buys nothing); taking the share from fees as well (the base fee is a measurement of demand and a burn is what keeps it one); rounding in the producer's favour (the floor keeps the treasury's claim a ceiling rather than a surprise).
- **Reservations are subject to the spent registry (I1-C3)** — otherwise the fold's answer depends on each node's pruning schedule.
- **Minimal signature sets (I1-M4)** — one state transition, one canonical form, one id.
- **Host-less Go module path** — this repository claims no organisation, domain, or vanity import path. Clone it anywhere. Reproducible builds and the vectors are the identity of the protocol; a hosting provider is not.
