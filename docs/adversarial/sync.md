# Zycord — The sync adversary

**Status:** R5-M1. Written as an analysis of a coordinated liar; found a liveness bug that needs no coordination at all. Fixed, pinned by tests, mutation-checked.

Sync is where a node with no chain asks strangers for one. Every other adversarial surface in this project is about what a node will *accept*; this one is also about what a node can be prevented from *hearing*, and those turn out to have very different defences.

---

## 1. The two questions, kept apart

**Safety:** can a peer make this node accept a chain that is not the heaviest valid one?

**Liveness:** can a peer stop this node from reaching the heaviest valid one?

Zycord's design answers the first structurally and answered the second not at all. Keeping them apart matters because the first answer is so strong that it is easy to mistake it for both.

## 2. Safety: what re-derivation actually buys

A syncing node re-derives everything. In `ValidateHeaders` ([node/sync/sync.go](../../node/sync/sync.go)), for every header in sequence:

- the version is known;
- the height is contiguous with the anchor;
- the parent linkage matches the previous header's id;
- **the declared target equals the target `pow.NextTarget` computes from the preceding window** — this is the load-bearing one;
- the proof of work meets that target;
- the timestamp exceeds the median of its predecessors.

Then in `Fetch`, every body must hash to the header it was requested for.

What that gives, precisely: **accumulated work is a fact rather than a claim.** A peer that declares an easy target to inflate its apparent work fails at the fourth check, before a single body is requested, at the cost of one recomputation. A peer that serves a different block than the one asked for fails at the body check. There is no trusted snapshot, no checkpoint, and no fast path — `Run` folds every block from an ancestor this node already has.

So a swarm of any size **cannot**:

- make this node adopt a chain with less work than its own;
- make it adopt a chain whose blocks do not satisfy the difficulty rule;
- make it accept state it did not compute itself;
- make it hold unbounded memory on their behalf (the orphan pool is bounded by count, bytes and height distance — R4-H1).

That boundary is real and it does not depend on how many identities the attacker has. It is worth stating plainly because everything below is about the other question.

## 3. Liveness: the bug this analysis found

The sync driver chose its peer with an argmax over claimed height:

```go
for _, t := range e.tips {
    if t.Dial == "" || t.Height <= own { continue }
    if !found || t.Height > best.Height { best, found = t, true }
}
```

Three things were wrong with it, and together they are worse than any of them alone.

**It ranked unverified claims.** `t.Height` comes from a handshake or a block announcement. Nothing checks it — nothing *can* check it, because verifying a height means having the headers, which is what sync is for. So the peer that claims the most is chosen, and claiming is free.

**A liar therefore wins every round, forever.** A peer advertising height 2³⁰ is the maximum on every tick. `syncLoop` had no fallback, no exclusion and no cooldown, so the honest peer holding the real chain was never asked. Not asked less often — **never asked**.

**And the failure is silent.** Trace what the liar does: `SyncFrom` dials, handshakes, and `runOnce` asks for headers from `ch.Height()+1`. The liar returns an empty list. `runOnce` returns `&Result{}, nil` — no error. `Run` sees nothing adopted and returns. `SyncFrom` returns `nil`. **No error is logged and no score is charged.** Every three seconds, forever, the node performs a complete handshake with the peer that is preventing it from syncing, and records nothing.

This needs no coordination. **One peer, one lie, and a node never syncs again.** The coordinated case only makes it survive that peer being banned — which it would not have been, because nothing was scoring it.

It also cannot be routed around by gossip. A node far behind receives announcements whose parents it lacks; those become orphans, and the orphan pool's height window (`HeightWindow: 128`) refuses anything further from its tip than that. A node held at height 5 while the network is at 500 is refusing every announcement it receives, correctly, and waiting for a sync that will never be attempted against anyone useful.

## 4. The fix: rotation, not ranking

Peer selection is now **least-recently-tried first**, with claimed height only breaking ties among equally-stale candidates. The property this creates:

> **No candidate is asked while another current candidate has been waiting longer** — where a peer waits from its last turn, or from its entry into the rotation if it has not yet had one.

Stated over the **live** candidate set rather than a fixed one, and that distinction is load-bearing rather than pedantry: read over a fixed set the guarantee is satisfied *vacuously* by a set that grows every round, so it returns *compliant* for the starvation §6.1 measures and *violated* for the corrected rotation. Over a set that stays put it is a strict round-robin — one turn per candidate per `len(candidates)` rounds — which is the cycle every cost model below leans on.

This is the right shape because it never has to decide whether a claim is true. Ranking must trust the number it ranks by; rotation does not. A liar can still waste one round trip per rotation — bounded, unavoidable, and cheap — but it cannot own the rotation, and a calibrated lie (claiming just enough to look plausible) buys exactly as little as an absurd one.

**The rotation's memory is bounded by the connection set.** `NextSyncPeer` keeps one sequence number per rotation key and prunes on every selection, because addresses come and go and the map would otherwise grow for the whole life of a process meant to run for months. The bound is *liveness* rather than a cap or a timeout: a cap needs a number and invites eviction pressure, and a timeout is a clock this node would have to defend. It was originally the live **candidate** set, on the argument that "an address that is not a candidate is one this node has no reason to remember having asked" — which lived in `NextSyncPeer`'s own comment and, until the fix below, nowhere in this file, though §6.1 and §7 both cited *this section* for it. That argument names the wrong reason: the map does not record who was asked, it orders who is asked **next**, and that reason survives a lapse in candidacy. It is now the live **tip** set — every peer this node holds a connection to, candidate or not — which keeps the liveness shape and moves the bound off an unpriced grant (candidacy, §6.1) onto a priced one (admission):

    len(syncTried) <= len(Engine.tips) <= len(Node.conns)
                  <= MaxInbound + 2 * MaxOutbound = 48

(A display line rather than a blockquote deliberately: §7 refers to "**the blockquote**" in §4 when it names the two non-equivalent statements of the rotation guarantee, and a second blockquote here would stop that definite article resolving uniquely.)

`MaxInbound + 2 × MaxOutbound` and not `MaxInbound + MaxOutbound`, because `Node.register`'s capacity gate is inbound-only and `topUp` bounds outbound separately.

**The two links hold for different reasons and are not equally exact, so they are stated apart rather than read off one line.** The first is exact by construction: `NextSyncPeer` takes the candidate list and the prune's liveness set from **one** acquisition of the engine's lock (`syncRotationView`), so every key the seeding loop enters is already in the set the prune keeps, and what the map holds after a selection is a subset of the tip set that selection read. Under **two** acquisitions they are two snapshots: a key that was a candidate at the first read and whose tip was gone by the second is pruned and then seeded straight back in, so the retained set is bounded by the **union** of the two — twice this figure and not this figure. No single-threaded test separates one acquisition from two, because a single-threaded caller gets the same tips from either, so this half is established by construction and pinned at the seam by `TestTheRotationPrunesAgainstASetThatContainsEveryKeyItSeeds` rather than by any rotation outcome. The second link is exact **at rest**: see the teardown-ordering residual in §7.

**The middle link is a choke point and a key, not a list of function names**, since an enumeration of spellings is never a property. `Engine` never lets the `tips` map escape — it is never returned, assigned away or passed as an argument, so nothing outside the package can insert into it and any new write has to be written where the same census sees it. Every write keys on the `peerAddr` given to `Engine.Handle`, which has exactly one non-test caller and passes `conn.Addr` — the string `register` has already stored in `Node.conns`. So `keys(Engine.tips) ⊆ keys(Node.conns)` by construction, and `forgetPeer` removes the entry on `unregister`.

Two supporting repairs:

- **`SyncCandidates` skips banned peers.** The ban list existed and the path that decided who to talk to never consulted it, so a peer's score was computed and then discarded by the same code that computed it.
- **Four more lies now cost score.** `ErrNotContiguous`, `ErrBrokenLinkage`, `ErrBadTime` and `ErrBadVersion` were free; only forged targets and bad work were charged. Every one of them is a peer describing a chain that cannot exist, and [wire.md §10](../spec/wire.md) says so.

**A third, later repair — a whole-attempt deadline — bounds a round trip's wall-clock cost, not just its count.** Rotation bounds how *often* a peer is asked — one turn per cycle, by §4's guarantee above — and says nothing about how long any one "ask" may take. `await`'s own per-read tolerance (sixteen unsolicited messages at twenty seconds each, 320s) governs *one request* — but `extendToCover` can issue several header round trips and `Fetch` one body round trip per header, so a peer that answers every individual request just inside its own 320s budget, forever, could hold `syncLoop` — single-threaded, one attempt at a time — hostage for as long as it kept doing that, with no per-read deadline ever firing to say so. §7 named this and left it unbuilt; it no longer is.

`SyncFrom` now runs under a `context.WithTimeout` set to `Node.SyncAttemptTimeout` (ten minutes by default), enforced by two mechanisms that cover each other. First, every per-operation deadline inside the attempt — `SyncFrom`'s handshake read and write, `connSource.await`'s reset on each loop iteration, and each `get-headers`/`get-block` write — is clamped to the attempt's absolute deadline (`clampDeadline`), so a per-operation reset can never re-extend past the budget: once the attempt deadline has passed, the next deadline computation lands in the past and the operation fails immediately. Second, a watcher goroutine closes the connection outright the moment the timeout — or the node's own shutdown, `n.quit` — fires first, whichever is sooner, which interrupts an operation *already parked* rather than only bounding the next one to start.

For the timeout the two are **redundant**, and this is measured rather than assumed: mutating out either one alone still leaves a stalling peer bounded, and only mutating out both together unbounds the attempt, at which point it runs to `await`'s own twenty-second per-read window. Neither should be described as the enforcement. The asymmetry that does exist is shutdown: `n.quit` reaches only the watcher, never the clamp, so a build with the clamp alone stays bounded on timeout but hangs `Node.Stop` behind a stalling peer. Ten minutes is sized off real volumes rather than guessed: `block_byte_capacity` (spec/params.json) is the largest body any attempt can legitimately be asked to hold, and the sustained-bandwidth floors this project has already committed to (docs/decisions/testnet-measurements.md: ~0.7 Mbit/s at the genesis byte ceiling, ~2.1 Mbit/s at the structural one) buy on the order of twenty maximally-sized blocks inside that window — several batches of real progress on an honest, merely slow, link, with room to spare past `await`'s own 320s single-request tolerance. The full derivation, and the Bitcoin Core / go-ethereum precedent for "minutes, not hours" on the same class of decision, are in `syncAttemptTimeout`'s doc comment (node/p2p/syncdriver.go).

The expiry is deliberately unscored. It reaches `SyncPenalty` exactly like a severed socket does (the transport-fault exemption in the table below), because a peer that never answers is not distinguishable, at the point a penalty would be charged, from an honest one on a slow link — it is only rotated away from, which `NextSyncPeer` already does for any peer just tried, timeout or not.

The same fix closes a second, unrelated-looking gap. `syncLoop`'s goroutine holds an `n.wg` entry for as long as `SyncFrom` runs, and `SyncFrom`'s own connection was never one `Node.Stop`'s teardown closed — it is a dedicated, ephemeral socket the call opens itself, not a registered gossip connection — so a stuck attempt used to be able to hang a clean shutdown indefinitely, and still could after the accept-lifecycle fixes: those bounded the *inbound* handshake and reply paths, not `syncLoop`'s own *outbound* dial-and-read. Watching `n.quit` alongside the timeout means `Stop` now interrupts a stuck attempt directly.

## 5. What each defence carries

| Damage | Carried by |
|---|---|
| Accepting a false chain | Re-derivation in `ValidateHeaders` (§2). Complete. |
| Unbounded memory from unattached blocks | Orphan bounds — count, bytes, height window (R4-H1). |
| One peer monopolising sync attention | **Rotation** (§4). This was carried by nothing. |
| A Sybil range filling the peer set | `SelectDiverse` — one `/16` fills one outbound slot. |
| One source filling inbound slots | The per-source inbound bound in `Listener`. |
| Starting from an attacker-chosen peer set | The persisted peer store. |
| Wasted round trips per rotation | Nothing, and nothing should. It is O(candidates) per cycle and the alternative is trusting a claim — each round trip's own wall-clock cost is now bounded too by the whole-attempt deadline, so the total is O(candidates) × a fixed ceiling rather than O(candidates) × however long a peer cares to stall. |

**Not carried by anything, and named rather than implied:** a node whose *entire* candidate set is hostile. Rotation guarantees it reaches every candidate; it cannot manufacture an honest one. That is an eclipse, it is what `SelectDiverse` and the persisted store exist to make expensive, and no amount of sync logic substitutes for them.

## 6. Rejected alternatives

- **Rank by claimed work instead of claimed height.** Rejected: identical failure, better disguise. Work is exactly as unverifiable as height at selection time — verifying it is what sync does *after* choosing — so this swaps one unchecked number for another and makes the reasoning harder to follow.
- **Require a minimum score before a peer is a sync candidate.** Rejected as backwards: a new peer has no score, so this preferentially trusts peers this node has already talked to, which is an eclipse amplifier. Scoring belongs after evidence, not before it.
- **Sync from several peers in parallel and prefer whoever answers first.** Rejected as premature and possibly wrong. It costs N connections per round, it rewards whoever can answer fastest — which an attacker controls and an honest peer on a home connection does not — and the problem it solves (latency to first sync) is not one anybody has measured. Reopen with testnet data.
- **Cool down a peer that adopted nothing, by score.** Rejected: adopting nothing is normal. An honest peer one block ahead whose block already arrived by gossip adopts nothing every time. Penalising it would score honest peers down for being well-connected. Rotation handles the same case without a moral judgement, which is why it is a rotation and not a penalty.
- **Trust the first peer to serve a valid header chain and stick with it.** Rejected: it re-creates the bug with an extra step. Whoever answers first becomes permanent, and answering first is cheap for an attacker who serves a valid-but-stale prefix.

### 6.1 Free candidacy through `OffersUnknown`

Sync candidacy through `PeerTip.OffersUnknown` is obtainable for one hash. `OnBlockAnnounce` checks work with `pow.CheckWork`, which compares the header hash against **`h.Target`, the announcer's own declared target**; re-deriving the real target needs the ancestors, and deciding before fetching those is the entire point of hash-first relay, so only the `OnBlock` body path re-derives. That is R4-H1, and `recordAnnounce`'s doc comment has always named it. A header declaring `MaxTarget` with an empty exemplar list and a matching `CertRoot` therefore passes version, non-zero height, the exemplar ceiling, `work.Check` and `certRoot`, is not canonical, and refreshes `OffersUnknown`.

**The grant is not priced, and three ways of pricing it were rejected.** All three were rejected on the same test: what does the attacker actually spend today, and does the change move that number?

- **Bound the accepted `h.Target` by something checkable without ancestors** — refuse a target looser than our own tip's, or than the loosest within `undo_depth`. This is the only one of the three that would move the cost from one hash to real work, and it is rejected because its failure mode lands on the node it would hurt most. Difficulty may legitimately *fall*, so a node whose tip is old cannot bound the network's current target from below; it would refuse honest announcements precisely while far behind, which is the state candidacy exists to escape. That re-creates the fork-holder starvation §5 names, with a new mechanism, and it puts a consensus-adjacent rule on a relay path that by construction has no ancestor context to evaluate it in.
- **Cap `OffersUnknown` refreshes per peer per window.** Rejected as already implemented, by `offersUnknownWindow` itself. Candidacy is decided by a *rolling* staleness test — `time.Since(t.OffersUnknown) > offersUnknownWindow` — not by fixed windows, so a refresh does not top up a bucket that empties on a boundary; it restarts the clock, and candidacy runs 30 s from the **most recent** refresh. That is why a second refresh inside 30 s of the last one buys the sender nothing it did not already have: a cap can only reduce the refresh rate to one per window, which is the rate the window already makes worth using. It removes no cost from anybody.
- **Enter future-dated ids into a separate short-lived seen set**, so one forged header cannot refresh a tip forever on the path that deliberately keeps ids out of `seenBlocks` (this subsection's first amplifier). Rejected because the amplifier is not one. Holding candidacy costs **one message per `offersUnknownWindow` per connection on both paths**; the dedup on the accepted path does not stop that, it only forces the message to carry a *fresh* header. So the future-dated path saves an attacker the hash and not the message — across a day, 2879 SHA-256 evaluations it would not have noticed paying. Sizing a defence against that is sizing it against a cost that does not exist. That rejected defence would also add a table an attacker fills for free at `CostFree`, since any bounded set is walked past by minting one more id than it holds.

  **The 2879-SHA-256 sentence above is priced in the wrong engine, and the key-epoch budget below is the repricing.** The hash the future-dated path saves the attacker is `pow.CheckWork`, which under `randomx-v1` is keyed by `pow.KeyFor(h.Height, p)` — a height the sender chooses. At a height whose epoch this node does not hold it is a 256 MiB allocation and an Argon2 fill — about **0.55 s**, from `core/pow/randomx`'s `BenchmarkInitCache` and the 574.9 ms cold reading `randomx.go` records — not a SHA-256 evaluation; 2879 of those is roughly **twenty-six minutes** of CPU per connection per day, and that rate is a floor rather than a ceiling, because one message per window is what *candidacy* needs and nothing obliges the attacker to stop there. `ScoreFutureBlock = 0` and the deliberate absence from `seenBlocks` are still right for the reasons given above — this is not an argument for charging the future-dated path, it is an argument that the cost it saves is no longer negligible, which is what the rejection rested on. Tracked in [I7-H4](I7.md).

  **The key-epoch budget is priced per connection, and it changed neither of the two things this subsection defends.** The declared target is still accepted — the first rejected pricing above stands — and `ScoreFutureBlock`, the `seenBlocks` omission and the `offersUnknownWindow` rolling test are all untouched, so the second and third rejections stand too. What was added is a fourth kind of price that none of the three considered: a per-connection budget over the **key epochs** an announcement forces, rather than over the candidacy it refreshes. An announcement whose key epoch is outside the two this node is itself working in — its tip's, and the next one — costs one of `MaxUnheldKeyEpochsPerPeer` credits, refilled one per `randomx_key_interval x target_block_seconds`; past that it is refused at `CostBudgeted` **before** `work.Check`, unscored and unremembered. So the twenty-six minutes of Argon2 per connection per day above becomes, per connection, `MaxUnheldKeyEpochsPerPeer` key initialisations per epoch period and a hash for everything else — and the 2879 messages a day still buy candidacy exactly as this subsection says they do, because the refusal deliberately still runs `recordAnnounce`. **Free candidacy is therefore unchanged, and that is on purpose**: dropping the record instead would stop a node that is behind from refreshing the candidacy of the peers it needs to climb back, which is the failure that reverted I7-H4's tip-window guard. The residual that leaves is one chain lookup per over-budget announcement, unpaid — cheaper than the hash it replaces, and the same absence of a per-connection message rate limit. **The other residual is the axis: the budget is per connection and dies with it, so the twenty-six minutes a day above is per connection per day and one identity re-buys it for a TLS handshake.** That is a reduction in the rate and not a bound on the total, and this subsection's arithmetic should be read with the multiplier in it.

  **That first residual — the unpaid chain lookup — was looked at on its own, and the answer is that nothing is done about it.** Stated as a decision rather than left as an inference from this subsection. An over-budget connection reaches, per message and unpaid, `Chain.Height()`, `Chain.Params().UndoDepth`, one `Chain.CanonicalHeader` index lookup and one `types.Header.ID()` hash, on top of the announcement's own unmarshal. The one narrowing considered was a **partial refresh** — keep the `Height` write and skip the `CanonicalHeader` lookup that sets `OffersUnknown` — and it is rejected on two grounds. It removes a fraction rather than the residual: the height read, the params read, the hash and the unmarshal all stay, the index lookup is the cheapest of the four, and what bounds the aggregate is the connection set and a per-connection message rate limit that does not exist yet, either way. And it would take a signal that is not always redundant: `syncCandidatesLocked` drops a peer only when it is behind by height AND by claimed work AND its `OffersUnknown` has gone stale, so for a peer that is *ahead* the height alone carries candidacy, but for a peer holding a **heavier branch that ends below this node's tip** — the fork-holder §5 names — `OffersUnknown` is the only thing that makes it a candidate at all — and whether such a branch falls outside the two working key epochs is `undo_depth` against `randomx_key_interval`, 1024 against 512 on testnet, so it is reachable by ordinary parameters. Free candidacy through this path therefore stays free, as the three refusals above already have it. **What reopens it is a measurement and not an argument**: a per-connection message rate limit, which subsumes this residual along with the ones it shares a bound with, or testnet evidence that the lookup is reachable at a rate the connection set does not already cap.

**What was changed instead is what candidacy buys.** This subsection scores the impact as rotation dilution, and dilution is the right description of the steady state. It was not the right description of the transient: `NextSyncPeer` read the zero time for a rotation key it did not know, so a newly-appeared peer sorted ahead of every peer already in the rotation. A rotation key is not scarce — it is the advertised address, or the connection address for a peer that cannot be dialled — and §4's prune deliberately forgets any key that stops being a candidate, so an identity appearing under a fresh key was never-tried on **every** round. Measured on this rotation before the change: two honest peers, one fresh identity per round, twenty rounds, honest peers reached **twice**. That is starvation, and it is a stronger claim than dilution.

Note this **does** contradict §4's guarantee as it now stands: a candidate placed at the front on the round it appears is asked while candidates that have been waiting longer are not. It did *not* contradict the wording §4 carried at the time — "no peer is asked twice until every other candidate has been asked once" is about a *fixed* candidate set, and a set that grows every round satisfies it while starving. That gap is what the live-set restatement of the guarantee closed.

That sentence was challenged during review and **it survived a measurement**, which is worth recording because the challenge was that the amendment *restores* §4 rather than departing from it. Encoding the blockquote **as it then read** literally and running it over a regime where a candidate arrives every round: pre-fix the trace is `[n0, n1, … n11]` — both honest peers never asked once in twelve rounds, total starvation — and the blockquote **holds**, *vacuously*, because there is always a fresher never-asked newcomer to prefer. Post-fix the trace is a healthy round-robin with newcomers queueing, and the blockquote is **violated**. So as it then read it returned "compliant" for the broken regime and "violated" for the correct one, and "the amendment restores §4" would be false in the reading a future reader would check. The reframing was dropped. **§4 also stated its guarantee twice in non-equivalent forms, settled since**, which is why two reviewers measuring the same lever reached opposite verdicts — each had faithfully encoded a different sentence. The amendment was therefore a policy change rather than a bug fix against the invariant as §4 then stated it, and against the restated one it is both: **a candidate seen for the first time is placed at the back of the rotation rather than at the front**, so appearing cannot preempt a peer that has been waiting longer. A genuinely new honest peer now waits at most one cycle (`len(candidates) * SyncInterval`) before its first turn, which is the accepted cost and the safe direction.

Two candidates first seen on the *same* round share one sequence number, so they are placed at the back together and §4's height tie-break still orders them against each other. That is a second, separable claim: numbering each newcomer individually would satisfy "a newcomer does not preempt" just as well, while handing first-round order to `SyncCandidates`' map iteration rather than to the claimed height the policy names.

The order is kept as a **sequence number rather than a wall-clock stamp**, and that is load-bearing rather than tidiness. Written against `time.Now()` the change regressed both existing rotation tests, because the rotation needs a *strict* order over "who has waited longest" and a clock's resolution is a platform detail: on a coarse clock the stamp `MarkSyncTried` writes can compare **equal** to the seed written microseconds earlier, every candidate ties, and the height tie-break decides every round — which is argmax over an unverified claim, the exact starvation this file's §4 replaced, reappearing as a property of the clock rather than of the policy. It would have been invisible on a fine-grained clock and load-bearing on a coarse one. A counter cannot tie unless the policy means it to, and here it means it to in exactly one place: every candidate first seen on the same round shares one sequence number, so they are placed at the back together and §4's "claimed height breaks ties among equally-stale candidates" still applies among them. On the first round every candidate is new, they all tie, and the rotation starts exactly where it did before.

**Minting identities is not required, and that is the sharper form of the bug.** Candidacy only has to be cheap to *drop and regain*: the prune forgets, and the old code re-entered at the front. Driven with a ban/unban on a **single fixed address** — no identities minted, one rotation key reused, only the candidacy flapping — the flapper took **28 of 30** rounds from three equal honest peers (1 and 1 to two of them), and **0 of 30** after the change, with the honest peers at 15 and 15. So the bug is not that a rotation key is cheap to mint; it is that re-entry was cheap, and a cheap key is only one of the ways to buy it.

**Residual, stated as a cost and not as a closure:** free candidacy is unchanged, and dilution is unchanged. An attacker holding *k* concurrent connections still takes roughly *k/(k+h)* of the rounds. That residual is carried by the defences in §5 that bound concurrent connections — the per-source inbound bound in `Listener`, and `SelectDiverse` for outbound — and not by anything in this file. The change removes the transient in which it took **all** of them.

**Superseded by the tip-set prune, and kept in place because it is the derivation that justifies that fix — do not cite it as current behaviour.** Everything from here to the end of this subsection describes the rotation when its memory was pruned on **candidacy**. The prune is now bounded by the tip set (§4), so a lapse on a connection that stays up costs a peer no position and the condition below no longer gates service. What replaces it is stated after the tables.

**The one-cycle wait was paid on every entry to the candidate set, not only the first.** Seeding is keyed on a key being absent from the rotation's memory, and the prune drops any key that stops being a candidate, so the two loops compose: a peer that lapses out of candidacy and returns is seeded again. For a continuously-ahead peer that is once, ever. For a peer whose candidacy rests on `OffersUnknown` alone it is once per lapse.

That makes the safety a **condition, and the condition has three terms, not two**:

> `len(candidates) × SyncInterval ≤ offersUnknownWindow`

The window decides how many rounds such a peer is *present* for — 30 s against a `SyncInterval` of 3 s is about ten — and it is *not* re-seeded during them, because seeding fires only for an absent key. The **cycle** decides how many rounds it must *wait*, and that is `len(candidates)`, not a constant. It is served only when the second fits inside the first, so at the shipped constants **the candidate set has to stay at or under ten**.

An earlier version of this paragraph said *"it needs to win one round in ten, which rotation gives it"* and **dropped `len(candidates)` on the floor**: rotation gives it one round in `len(candidates)`, and ten is the number of rounds *available*, not the number of candidates.

**The boundary is sharp to the integer, and it was pinned rather than estimated.** A peer present for 10 rounds per lapse (the window divided by the interval) against otherwise-continuous candidates, counting the lapse periods in which it was served at all, over 60 periods and two duty cycles:

| `len(candidates)` | 6 | 8 | 9 | **10** | **11** | 12 |
|---|---|---|---|---|---|---|
| periods served (1 round absent) | 60 | 60 | 60 | **60** | **1** | 1 |
| periods served (5 rounds absent) | 60 | 60 | 60 | **60** | **1** | 1 |

**The cliff is between 10 and 11**, reproduced on three independent harnesses at 60 periods per point, in **every** claim position. At 10 the peer is served in *every* period; at 11 it is served at most once and never again.

**The condition is derived, not fitted.** The first-hit round is exactly `len(candidates) − 1` — measured 5, 7, 8 and 9 at `len` 6, 8, 9 and 10 — because a candidate seeded at the back waits for every other candidate to take its turn. Service therefore requires

> `len(candidates) − 1 ≤ live_rounds − 1`,  i.e.  `len(candidates) × SyncInterval ≤ offersUnknownWindow`

which is the shipped condition, arrived at from the mechanism rather than by curve-fitting the table above.

**That at-most-one hit is a first-window artefact, and it depends on the peer's claimed position — the row for 11 and 12 is not a flat figure.** During the first window every candidate still carries the initial shared seed, so the rotation reaches ten of them before any re-seeding happens, and the lapser takes its single turn *iff it places in that first ten*. Twenty trials per claim position at `len` = 11:

| lapser's claim | served | at which round | later periods |
|---|---|---|---|
| **top** | 20/20 | round 0, always | 0 hits in 240 |
| **equal** | 16/20 | rounds 2–9, map-order | 0 hits in 240 |
| **bottom** | **0/20** | never reached | 0 hits in 240 |

**A bottom-claiming peer gets no turn at all** — not one turn and then starvation, but starvation from the first round: all ten window slots go to higher claims first, and by the time it would be reached, re-seeding has begun and it is permanently behind. That is the cliff in miniature, and it is the case this file should lead with: an adversarial document that says "it is served once" **understates the harm** for the peer with the weakest claim, which is exactly the shorter-but-heavier fork-holder §5 cares about.

Note the equal-claim case involves **no tie-break at all** — it lands by map order among candidates tied on both seed and height. The earlier description here, "the tie-break on claimed height hands it one turn", was true only of a top-claiming peer, and worse, it **promised a turn that a bottom-claiming peer never receives**.

**And "map order" is not a uniform shuffle, which is why the equal-claim rate is 0.77 and not 10/11 = 0.91.** Go randomises the *starting* bucket and offset and then walks buckets in order, so an iteration is a randomised rotation over a fixed bucket layout, not a uniform permutation. Measured directly on an 11-key map of these very addresses, 200 000 iterations, recording where one fixed key lands:

| position | 0 | 1–5 | 6 | 7–10 |
|---|---|---|---|---|
| frequency | **0.188** | ≈0.062 each | **0.250** | ≈0.062 each |
| uniform would be | 0.091 | 0.091 | 0.091 | 0.091 |

Two positions carry nearly half the mass. The shortfall replicates at scale — 1370 trials give 0.767 against a naive-uniform 0.909, `z = −18.3` — so it is a property of the runtime's iteration order, not a fluke and not a defect in the rotation. The rotation itself is exonerated directly: distinct peers served per full cycle is 100/100 at sizes 8, 11 and 12, so §4's one-turn-per-cycle guarantee and the cycle-length arithmetic above are sound.

**This is the argument for the shared sequence number rather than a caveat against it.** All candidates first seen on one round share one number precisely so that map order does not decide who is asked first — and the measurement shows map order is not merely arbitrary but *strongly biased*, with two positions taking half the mass. A per-candidate seed would hand first-round ordering to that bias. `TestCandidatesFirstSeenOnOneRoundShareOnePlaceInTheRotation` is what stops it.

A candidate set above ten is ordinary, so this is reachable rather than theoretical.

The margin narrows if either constant is tuned toward the other, and mainnet's `target_block_seconds` is already **exactly equal** to the window (30 s), so such a peer sits on the staleness boundary by construction. The starvation measured above needs candidacy to lapse faster than the rotation ticks, which is an extreme driven deliberately and not a production condition.

**What replaces the condition.** With the prune bounded by the tip set, a peer whose candidacy lapses while its socket stays up keeps its sequence number, so it is selected on the first round it is present after every other candidate has taken a turn. The wait is `len(candidates)` rounds plus however long it happens to be absent when its turn arrives — bounded in **rounds by the cycle**, with no term in `offersUnknownWindow` at all, so the bound survives any parameter set rather than only the shipped one. For a peer whose socket stays up, the condition is not weakened but **removed**: no candidate-set size stops service. **That is scoped to a peer whose socket stays up, and the scope is not decoration** — a peer whose connection is torn down and takes longer than one `SyncInterval` to return has a starvation regime of its own, at a different constant, quantified in §7. Saying flatly that no such size exists would be the same false universal this fix exists to repair, one clause along. Measured over 330 rounds at incumbent counts 4, 8, 10, 11, 12, 20 and 40 — straddling the pinned boundary on both sides — the longest gap between services stayed inside `len(candidates) + period` at every point. The same instrument on the pre-fix rule reports **zero** services from `len(candidates) = 11` upward, which is the boundary the table above pins.

**And the cost is stated rather than implied.** Retention buys a *disconnected* peer nothing: the tip goes with the connection (`forgetPeer`), so the retained set never exceeds the live tip set that selection read — **exactly**, and the reason is the single acquisition rather than the absent union: the prune's liveness set and the candidate list the seeding loop re-enters come from one read of `Engine.tips` (§4), so the seeding cannot put back a key the prune dropped. Deleting the union changed which sequence number a peer whose tip vanished mid-call receives, and no key set at all — and the peak is bounded by the same admission caps that already bound `Engine.tips` and `Node.conns` (§4). What it does grant is that an attacker's *k* connections now hold *k* rotation positions across their own lapses instead of forfeiting them — the same *k* as the dilution residual above, and it grants nothing new, because a peer that is served is moved to the back in the same call. `TestADisconnectedPeerLosesItsPlaceInTheRotation` and `TestTheRotationRemembersNoMoreKeysThanTheNodeHoldsTips` separate the retention from the bound; neither is implied by the lapse test, which a retain-everything rule would pass identically. `TestTheRotationPrunesAgainstASetThatContainsEveryKeyItSeeds` pins the subset relation that exactness rests on, at the seam, with both non-vacuity halves asserted: there has to be a candidate for the check to range over, and the key set has to be strictly wider than the candidate list or a set built from the candidates themselves would satisfy it.


## 7. What is still open

**Sync candidacy is still free (§6.1).** Nothing on the announce path can price it without the ancestors, and the three ways of pricing it that were considered were each rejected for a stated reason. What is bounded is what it buys.

**The two residuals §6.1 banks separately do not compose additively — they share a term.** `len(candidates)` in §6.1's re-entry condition is the *same k* as the dilution residual: every attacker connection is a candidate. So inflating the candidate set does two things at once — it takes `k/(k+h)` of the rounds, **and** it stretches the rotation's cycle past `offersUnknownWindow`.

**It was a cliff, not a slope** — served in every lapse period at `len(candidates) = 10`, and effectively never at 11 (§6.1 has the pinned boundary and the two duty cycles). Not a gradient in service quality: one side of a single integer was full service, the other starvation. **Closed** by rebinding the prune from the candidate set to the tip set (§4); the paragraphs below are kept because the diagnosis is what makes the fix legible, and each says what survives it.

The defect in the prose this replaces, stated as a diagnosis because it is more useful to a future reader than the corrected inequality alone: **the sentence conflated two different tens — rotation gives one round in `len(candidates)`, and ten is the number of rounds *available in the window*, not the number of candidates.** It read as true to everyone who checked it because the two tens coincide at the set sizes every test uses. Past the cliff such a peer never reaches the front before lapsing, is re-seeded to the back on re-entry, and is **starved permanently rather than delayed** — the "at most one cycle" bound stops holding because a cycle stops fitting inside the window.

The sharpest way to state it: **candidacy was unpriced (§6.1), and the unpriced grant funded the mechanism that broke the bound the fix relied on.** Two residuals that read as independent when listed apart, and multiplied when read together.

**That is the sentence the fix acts on, and it decides the fix's shape rather than merely motivating one.** The defect was never that the memory was bounded — it has to be — but that it was bounded by the one quantity in the system that costs nothing to move. Rebinding it to the tip set leaves the bound a liveness bound, needing no number and no clock, while making the thing that inflates it the thing admission already prices. **Candidacy stays free (§6.1's three refusals stand); what it can no longer buy is the erasure of somebody else's position.**

**Three things this is not, because the correction is easy to over-apply:**

- **Not a regression.** Before the fix that same lapsing peer *preempted everything* — that is §6.1's own finding. The trade is forced: the mechanism that let a lapsing honest peer jump the queue is identically the one that let an attacker own the rotation. In no regime that matters is this worse than `main`.
- **Not a broad population.** Anything ahead by height or by claimed work is *continuously* a candidate and never lapses, so it is untouched. Only a peer ahead on neither — holding candidacy solely through `OffersUnknown`, i.e. an equal-or-lighter side branch — is exposed, and those are the lowest-value sync targets in the set.
- **Not a reason to price candidacy.** The three refusals in §6.1 stand.

It is still the **fork-holder shape from the other side**: §5's findings are about a fork-holder never *becoming* a candidate; this is about one becoming a candidate and never being *reached*. `k` is bounded by the carriers §5 names — the per-source inbound bound in `Listener`, `SelectDiverse` for outbound — and by nothing in this file. A candidate set above ten is ordinary, so the condition is reachable **without an attacker at all**, which makes it worth measuring on the M3 testnet where a real candidate-set size is observable rather than assumed.

**It was reachable on `main`, independently of anything in §6.1, and that was not a hypothetical about a future candidate set.** `Node.MaxInbound` is **32** and `MaxOutbound` **8** (`node/p2p/node.go`), and `Node.register`'s capacity gate is inbound-only, so admission admits up to `MaxInbound + 2 × MaxOutbound` = **48** connections against a cliff at eleven candidates. The justification for admitting undialable inbound peers to candidacy — `node/p2p/syncdriver.go`, in the "why this is not a new eclipse surface" block — reads:

> What a liar can do is waste attention, and rotation bounds that: least-recently-tried selection means one round trip per candidate per rotation, and the number of inbound candidates is capped by `MaxInbound`

Stated precisely, because the loose version overclaims: **that arithmetic is correct.** One round trip per candidate per rotation, capped at 32, does bound what a liar costs this node. What the sentence also carries, implicitly, is that *rotation reaches every candidate* — and past `len(candidates) = 10` that premise fails for any candidate whose candidacy lapses, at a cap sitting more than three times beyond it. (**That "more than three times" is against the 32 the shipped sentence names, not against the 48 derived above** — the two figures are different quantities and both are correct: 32 is `MaxInbound`, which is what the sentence cites, and 48 is the whole connection set, which is what actually bounds the candidate count. Recomputing the ratio against 48 gives a different and also-true number, which is exactly why the roles are labelled here rather than left to a reader.) So the bound on the **attacker's cost** holds; the bound on an **honest lapsing peer being reached** does not, and only the first is written down.

That was the term missing from the shipped justification, and it is the same audit question this file keeps running into: the prose credits a mechanism, and the arithmetic has no term for it.

**The tip-set prune makes that sentence true rather than annotating it.** With the prune bounded by the tip set, rotation does reach every candidate whose connection is up, so the connection cap is the bound the paragraph always claimed it was — one round trip per candidate per cycle, at most `MaxInbound + 2 × MaxOutbound` = 48 per cycle. The service-rate term is now written into that paragraph beside the cap, because a reader checking the claim needs both: **a cap on the set size bounds the attacker's cost per cycle and says nothing on its own about whether any given candidate is reached within one.**

**The fix is in, and the option taken is not one of the five that were sketched.** A grace period bounds memory by time, which is a clock this node would have to defend, and needs a number whose derivation cannot survive parameter sets that decouple `offersUnknownWindow` from `SyncInterval`. A bounded LRU needs a cap and invites the eviction-pressure shape this codebase has met elsewhere. "Do not seed a returning key to the back" is the property wanted, not a mechanism, and reduces to one of the other two. Leaving it and bounding *k* leaves a reachable no-adversary starvation of exactly the fork-holder §5 exists to reach. Widening the window or shortening the interval moves a constant that mainnet's `target_block_seconds` is already equal to. **What was done instead is to keep the prune's shape and change only which liveness set it is bounded by** — candidate set to tip set (§4) — which needs no number, no clock and no cap, and prices the retention against admission rather than against candidacy.

**What the tip-set prune does not close, stated separately so no one of them stands for the others:**

- **A peer that disconnects re-enters at the back, and that has a cliff of its own with the same shape as the one this issue closed — stated with its arithmetic, because the qualitative version reads as smaller than it is.** The prune drops a key when its tip goes, so position survives a lapse but not a teardown. `Listener.charge` admits an inbound connection into a per-source slot first and a *reserve* slot otherwise, by arrival order within an address group and not by purpose, and `Node.probationLoop` closes a reserve slot once `DefaultInboundProbation` (90 s) has passed, on a 15 s sweep — so a reserve-charged connection lives **90–105 s**, by design. The worst-case cycle after this fix is `len(candidates) × SyncInterval ≤ 48 × 3 s = 144 s`, and **105 < 144**, so such a peer cannot survive one cycle at a saturated table. The boundary has the identical form to §6.1's, with `DefaultInboundProbation` where `offersUnknownWindow` was, and admission allows 48 against it — **reachable with no attacker**, one constant along. Three separations, because merging them over-claims: it is **pre-existing and unchanged by the fix** (before it a dropped tip removed the key by the candidate route too); its **population is different** — not confined to `OffersUnknown`-only peers, since after the fix every peer's position depends on connection lifetime, but requiring a reserve slot; and at a saturated table roughly two in five inbound connections are reserve-charged, so the population is not exotic. **It is also gated on reconnect latency, which is a real narrowing and not a softening:** the prune runs only inside `NextSyncPeer`, once per `SyncInterval`, so a peer that returns inside one round is never observed absent and keeps its place. Measured over 990 rounds with the subject continuously ahead by height (so no candidacy lapse is involved at all): with the reconnect completing inside one `SyncInterval` there is **no cliff at all** — the prune never observes the peer absent, it keeps its stamp, and service decays smoothly to fair share, 20/990 at `len` = 48. With the reconnect taking one round or more the key is pruned, the wait restarts, and the cliff is sharp at `len(candidates) ≤ DefaultInboundProbation / SyncInterval` = **30** — 31/990 at `len` = 30 against **0 or 1 in 990 at `len` = 31, depending on a startup tie-break**. The two values in that second cell turn on the round-0 tie-break, when every candidate still shares the seed sequence number: the subject takes **one** turn it never regains when it wins that tie and none when it does not, with **no ongoing service past the cliff either way**, which is the claim the cell carries. The `len` = 30 cell beside it is **tie-break-invariant**, measured by moving that one variable and holding everything else fixed. **The gate is binary and not linear.** The boundary is unmoved at absences of 1, 2, 3, 5, 10 and 20 rounds, because absence does not consume the presence budget: the peer needs `len(candidates)` consecutive present rounds *inside one connection*, and one reserve connection supplies `DefaultInboundProbation / SyncInterval` of them however long the gap before it was. Lengthening the absence changes only how many services it collects over the run (**31, 31, 30, 28, 25, 20 at those six absences, all at `len` = 30**), never whether it is served at all. The `len` is stated because the sequence is a function of it, and so is the same round-0 tie-break the cliff cell turns on: an independent model of the stamp algebra reproduces the column above when the subject loses that tie and 33, 32, 31, 29, 26, 21 when it wins. The 30 is presence and not a period: `DefaultInboundProbation` bounds the *connection's* lifetime, and the reconnect happens after that connection is already closed, so the gap is additional to those rounds rather than inside them. A model that folds the gap into the 30 pins the boundary one lower for each absent round and is measuring a shorter connection than the constant describes — which is the reading to check first if this figure is ever re-derived and comes out different. The reconnect latency the gate turns on is unmeasured on a real network. **No code change is requested here and none is made.**
- **A peer with no advertised address is keyed by its connection address**, which changes on every reconnect, so for that population "lapse" and "disconnect" are the same event and the fix reaches only the first. The population that keeps a stable key across a socket is exactly the population the peer store can re-reach, which is the peer store's line and not this one.
- **Dilution is unchanged.** An attacker holding *k* connections still takes roughly *k/(k+h)* of the rounds, carried by the §5 defences. What changed is that *k* no longer converts a share into a starvation.
- **The FIRST link of §4's chain is exact against the snapshot the last NON-EMPTY selection read, and against the live map it is not an at-rest bound at all — quiescence does not close it.** In the measured rows below the node is **quiescent** — no teardown in flight, no selection running, nothing racing anything — and the inequality is still false. It closes at the next **non-empty** selection, not when the system comes to rest. The middle link genuinely *is* at rest, because its window is two adjacent statements inside `unregister`; that asymmetry is why one predicate cannot serve both links, and why this is a residual distinct from that one. `NextSyncPeer` releases `e.mu` when `syncRotationView` returns and only then takes `n.mu`, so a `forgetPeer` that **completes** any time between those two points deletes a tip the snapshot still carries, after which `len(syncTried) ≤ len(Engine.tips)` is false against the live map **until the next selection that has a candidate — which is unbounded while the node has none**, since `NextSyncPeer` takes the empty-candidate early return **before** `n.mu` and **before the prune**. Driven single-threaded: seeded `keys=3 tips=3`; after **fifty** consecutive empty selections `keys=3 tips=0`; after one selection that *has* a candidate, `keys=1 tips=1` — the third row being the arm that shows the gate is candidacy rather than elapsed calls. **The population is any node with no current candidate, and its common member is a node that is simply caught up — every peer still connected, every tip live, none of them ahead.** That is where a healthy node spends most of its life, and it is wider than the lost-its-peers case, which is a special case of it: the prune is gated on the **candidate list**, not on connectivity. Measured single-threaded with only one peer dropping, so two tips stay live: seeded `keys=3 tips=3`; after the node mines past every peer and their `OffersUnknown` goes stale, **fifty** consecutive selections leave `keys=3 tips=2` — a dead key sitting beside two live ones on a fully peered node; one **fresh** connection arriving ahead restores `keys=3 tips=3`, the prune having run and dropped it. (A fresh connection is required: `Handle` refuses a second handshake on a connection it already holds. The peers claim minimal work, because candidacy is height **or** work and a peer claiming more work than this node has never stops being a candidate.) Pinned by `TestACaughtUpNodeWithEveryPeerConnectedStillSkipsThePrune`, and the falsifier is stated there: if that middle row came back with keys equal to tips, this sentence is wrong. **Unbounded in time is not unbounded in size, and the term that makes that a mechanism rather than an observation is this: the seeding loop is *also* below the early return.** With no candidates nothing is added either, so `syncTried` is **frozen, not growing** — it holds whatever the last non-empty selection left. So the duration lands entirely on the set relation and leaves the cardinality untouched: the 48 is bounded by the snapshot that last selection read, however long the node then sits without candidates. Stated because *"unbounded in time"* invites a reader to assume the size, and here it must not. **It does not depend on `unregister`'s lock order at all**: were `unregister` to hold `n.mu` across both of its statements, `NextSyncPeer` would block at `n.mu` with its snapshot already taken, `forgetPeer` would run during that hold, and the prune would still proceed against a stale set — same window, same outcome. So **reordering the teardown does not close this one**; closing it needs `e.mu` held across the prune, which nests the node's lock inside the engine's, and this path deliberately reads outside `n.mu` precisely to avoid introducing that nesting. **That remedy is named, not priced**: nobody here has enumerated `Node.mu`'s acquisition sites for the reverse nesting, so the sentence describes what the fix would create and is **not** a claim that it would be safe. Since this residual is named rather than fixed, nothing rests on it — recorded so it is not read as vetted. **And unlike the middle link's, this window needs no concurrency whatever — it is demonstrated, not merely argued.** The prune is **lazy**: it runs only inside `NextSyncPeer`, so an ordinary sequential teardown between two selections exhibits it on one goroutine. Driven single-threaded: three candidates and one selection give `keys=3 tips=3`; two `forgetPeer` calls with **no** further selection give `keys=3 tips=1`; one further selection restores `keys=1 tips=1` — which is what establishes the cause as the prune's **per-selection cadence** rather than the teardown itself. The `-race` caveat below belongs to the **middle** link, where the question really is an ordering one, and not here. The **48 is unaffected as an at-rest bound** — the qualifier `syncdriver.go` already puts on the chain, and the middle-link residual is why it is needed; a snapshot of `Engine.tips` is bounded by the admission caps, and as a **cardinality** it survives between selections because `MarkSyncTried` only rewrites a key the snapshot already held — **which is a fact about the one non-test caller it has today, not a structural guarantee.** `MarkSyncTried` is exported and takes an arbitrary address, so a second production caller passing a key with no tip would falsify the between-selections half while leaving the per-selection bound intact. That makes the call-graph residual below **load-bearing for this sentence rather than merely informational**, and nothing in the type system guards it. **Named, not fixed.**
- **The middle link of §4's chain is exact at rest rather than at every instant, and that is pre-existing and unchanged by the fix.** `unregister` deletes from `Node.conns` under `n.mu`, releases it, and only then calls `Engine.forgetPeer`, so between those two statements a tip outlives the connection entry it was admitted against and `len(Engine.tips) ≤ len(Node.conns)` is momentarily false. Creation is the safe way round: the tip is written by `Handle`, which `serve` reaches only after `register` has stored the connection. This is an **ordering read off the source, not an interleaving anyone has driven** — the race detector needs cgo and the machine this was measured on has none, so no claim is made in either direction about how often it happens. It belongs to `unregister`'s lock order rather than to this rule, `NextSyncPeer` cannot close it from where it stands, and closing it means reordering a teardown against a discipline that deliberately releases `n.mu` before touching the engine. **Named, not fixed.**
- **Nothing here is measured on a real network.** The cliff, its closure and the memory bound are all measured on the rotation in isolation. The M3 testnet is still where a real candidate-set size becomes observable rather than assumed.

**§4's own guarantee used to be stated twice in non-equivalent forms, and it is settled at one.** The arithmetic above depends on which one holds: the blockquote's strong form is what "one turn per cycle" needs, and the weaker "not asked twice running" that the same section carried six lines later would not have supported it. What survives is the blockquote's, restated over the **live** candidate set rather than a fixed one, because the fixed-set reading returns *compliant* for the starvation regimes §6.1 measures and *violated* for the corrected rotation — so it could not distinguish the two, which is what let two reviewers of the same lever reach opposite verdicts. Docs-only, no behaviour changed, and every cycle-length claim in this file now rests on one sentence.

**The rotation has no notion of progress.** A peer that serves a valid but perpetually stale chain is asked again on every cycle and costs a round trip each time. Bounded and harmless at this scale; worth revisiting if a testnet shows rotations dominated by peers that never help.

**`await`'s per-read tolerance (sixteen unsolicited messages at twenty seconds each) is still a guess, even though the whole-attempt deadline built on top of it (§4) is not.** Nothing argues for sixteen specifically, only that it cannot be zero, because a peer's gossip loop legitimately pushes announcements down the sync connection. Bounding the sum was the load-bearing gap; the per-request tolerance inside it is a smaller, separate question worth its own measurement.

**Nothing measures how often rotation actually rescues a node**, because on an honest network it never has to. The property is pinned by unit tests; its value under a real hostile peer set is unmeasured, and the M3 testnet is where that changes.

The three deadline tests do the same, and for a reason this section should record rather than assume: as first written, all three passed with the entire fix disabled by mutation (`clampDeadline` neutered, the watcher's `conn.Close()` removed), because none of them reached the deadline at all. Two used a "stalling" peer whose handler returned after one `Receive` and so closed the connection, handing the victim `EOF` at ~3ms; the third drove junk fast enough that `await`'s own sixteen-frame counter ended the attempt in ~20ms, measured by raising the budget to sixty seconds and watching the elapsed time not move. Each now asserts its setup — the stalling peer really stays parked and silent, the candidate really is a candidate, the junk really is slower than the frame counter — and each now fails when the fix is mutated out, the first at exactly 20.007s, which is `await`'s own per-read window and therefore the unbounded behaviour §4 describes.
