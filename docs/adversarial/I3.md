# Zycord — Implementation Findings I3

**Scope:** M2 — fork choice, the reorg edges, mempool eviction, and the network layer: `node/p2p`, plus the R3-1 binding of the genesis id to every consensus parameter.

**Persona:** the implementer in a Byzantine environment. M0 asked whether the spec survives a compiler. M1 asked whether the node survives an operating system. M2 asks whether the network survives *other participants who are trying* — and the failure modes are partition, equivocation, eclipse and amplification, none of which a compiler or a differential fold can see.

---

## HIGH

### I3-H1 — A node judging blocks one at a time can never adopt a longer fork ✅ *found by the partition test*

**Problem.** The first working version of the block handler judged each arriving block on its own: extend the tip, or hand it to fork choice as a one-block branch. Every test passed except the one that mattered, and it failed in a way worth reading carefully.

A competing branch is heavier than what it replaces **only in total.** Each block on it, considered alone, loses on accumulated work — the first block of a four-block branch is one block of work against the two it would displace, so it is rejected; and once it is rejected the second cannot attach, and so on. A node in that state does not merely converge slowly. **It never converges at all**: it sits on its own branch permanently, and a partition that heals at the network layer stays partitioned at the consensus layer.

This is the worst kind of bug the milestone could contain — invisible in isolation, invisible under test until two nodes actually disagree, and fatal to the property M2 exists to establish.

**Fix.** The engine holds blocks that do not extend the tip, walks back through them to a block the chain already has, and offers the assembled branch to fork choice as a unit. The walk is bounded by the number of held blocks, so a peer cannot make it run long by sending fabricated parents.

**Found by** `TestNetworkConvergesAfterPartition`, which is the first test in the repository that required two nodes to disagree before it could say anything.

The walk is still how a branch reaches fork choice — `node/chain.ConsiderBranch`, assembled from the blocks `node/p2p` holds that do not extend the tip — and what bounds the holding is no longer this document's to state: [spec/wire.md §9](../spec/wire.md) makes that pool normative, requiring it to be bounded by count, by total bytes and by height distance from the tip, and its declared work to be treated as meaningless (R4-H1).

### I3-H2 — Mempool eviction, reclassified from deferral to blocker ✅ *see [mempool.md](mempool.md)*

M1 deferred this with an accurate description — "a full pool refusing arrivals rather than displacing worse-paying ones is the wrong shape under real congestion" — and an inaccurate severity. Without a network it is a wart. With one it is a **censorship vector**: flood the pool to capacity at minimum priority and legitimate high-priority certificates are refused at the door, which inverts the fee market exactly when it is supposed to be resolving contention.

Fixed by price-eviction on **sequential priority** — the scarce resource; ranking by parallel tip would re-import R2-H2's error one layer up — with a bump requirement, a per-sender quota and hysteresis against churn, and tail-only eviction so a dependent `Seq` chain is never given a hole. The design, the attack and five rejected alternatives are in [mempool.md](mempool.md).

Two of the six tests failed on first run, and both failures were informative rather than incidental: the fill loop tripped the bump rule (correct behaviour, wrong test), and with a twenty-slot pool the hysteresis gap was **one** — which is not hysteresis, it is eviction on every arrival, which is the thrashing the gap exists to prevent. The parameters had to get large enough for the property to exist before the test could observe it.

## MEDIUM

### I3-M1 — `ConsiderBranch` could leave a node on neither chain ✅

The first version, on encountering an invalid block part-way through a branch, re-applied the original blocks — without first rolling back the branch blocks that had already applied. The result was neither the old chain nor the new one, which is worse than either: a chain nobody else has, produced by a *rejection* path.

Fixed by unwinding to the common ancestor before restoring. Found by `TestInvalidBranchLeavesTheChainIntact`, which exists because "all-or-nothing" is easy to write and easy to get wrong in the error path specifically — the path nothing exercises unless a test insists.

### I3-M2 — Accumulated work needed a 256-by-256 division ✅

Work is `2^256 / (target + 1)`, and both operands are 256-bit. Implemented as bitwise long division, deliberately the plainest possible version: it runs once per header during fork choice, and a subtly wrong division here silently selects the wrong chain, which is the one failure mode fork choice must not have.

Two properties are worth stating because a test tried to assert something stronger and was wrong to. Halving the target doubles the work **up to the floor**, which costs at most one unit at each compared point; and at targets above roughly `2^255` the floor swallows the difference entirely, so every such target costs "one hash". Both are standard, harmless — real targets live near `2^238` — and worth knowing before someone reads the arithmetic and thinks it is broken.

The second property stopped being a curiosity and became a parameter invariant, which is where it is owned now: [ARCHITECTURE §12](../ARCHITECTURE.md) requires `MAX_TARGET < 2^255` (F-PARAM-1) for exactly the reason given above — past that bound every header is worth the same one unit and fork choice degenerates into a block count.

### I3-M3 — The on-disk format needed a version ✅ *M2 review*

A format with no version field is a migration that can only be performed with a flag day, and a node that silently misreads an older file is corruption by the route no checksum catches: the bytes are well-formed and the *interpretation* is wrong. The log record magic and the snapshot magic now carry a version byte, and an unknown one is refused rather than guessed at — reported as its own error, not as corruption, because a file from another version may be perfectly intact.

### I3-M4 — Eclipse resistance is three separate mechanisms ✅

Not one. Outbound **address diversity** (one `/16` fills one slot, so a Sybil range counts once), **bounded inbound per source** (one origin cannot crowd out the inbound slots), and a **persisted peer store** (a node that rebooted into a blank slate would accept whatever peer set it was handed next, which is exactly when an eclipse is cheapest). Each is cheap now and expensive to retrofit, and each is separately testable.

All three are live — `SelectDiverse`, the per-source inbound bound, and the persisted `PeerStore` — and the account that owns them now is [decisions/networking.md §11](../decisions/networking.md), which is about what each bound does at the *moment it binds* rather than about the numbers, and which adds the bound this finding did not have: address diversity prices the addresses an attacker owns, and nothing here priced the ones it merely claims.

## LOW / NOTES

- **I3-L1 — Gossip validates before forwarding, always.** The spam firewall works because a certificate is checkable from its bytes with no state at all — the design's central property, doing load-bearing work at the network layer. An invalid certificate costs one signature check and scores its sender down. ✅
- **I3-L2 — An announcement must match its own certificate root.** An id list that does not produce the root the header commits to describes a block that does not exist, and that is checkable from the announcement alone, before any body is fetched. ✅
- **I3-L3 — Work is checked before bodies (R1-M3).** A ghost announcement costs the announcer real work rather than costing every receiver a fetch. ✅
- **I3-L4 — TLS certificates use fixed dates, not relative ones.** A certificate valid "from now" would make clock skew able to prevent connections, which is R1-H2's principle — wall clocks must not partition the network — applied outside consensus. (The first version used a year beyond what ASN.1 `GeneralizedTime` can represent, which the transport test caught immediately.) ✅
- **I3-L5 — `InsecureSkipVerify` is correct here and deserves the comment it has.** There is no certificate authority in this system and nothing for one to attest. Authentication is `VerifyPeerCertificate` extracting the peer's Ed25519 key, which *is* the identity. A reader who sees the flag and not the reason should be alarmed; that is why the reason is next to it. ✅
- **I3-L6 — Not-better, unknown-ancestor and beyond-horizon earn no peer penalty.** A peer on another branch is not misbehaving, and a reorg past the undo horizon is a node-operator event rather than a peer's fault. Scoring things that are not misbehaviour is how a network partitions itself. ✅

## Confidence

Flagged for the R4 reader. As predicted, the unforced choices are concentrated in adversarial-environment policy, where "reasonable" hides more than in any earlier milestone.

- **Every peer-scoring number is invented.** `-20` for an invalid message, `-50` for a protocol violation, `-100` to ban, a ceiling of `+100`. The *shape* is defended — bounded goodwill so a long-lived peer cannot bank credit and spend it on an attack; no penalty for honest disagreement — but the magnitudes are not derived from anything, and the ratio between "invalid message" and "ban" is a guess at how many mistakes a peer should get.
- **Eclipse parameters likewise.** `/16` as the diversity group is the conventional proxy for "one entity", and it is wrong in both directions: a single `/16` can hold several unrelated operators, and one operator can hold many `/16`s. Three inbound connections per source group is a number with no evidence behind it.
- **Flood gossip has an unmeasured ceiling.** [networking.md §5](../decisions/networking.md) states it as "comfortable into the low thousands of nodes", which is an estimate from message sizes and block time, not a measurement. It is the reopen condition most likely to fire and the one nobody has data for.
- **NAT traversal is simply absent**, and the decision document says so. For a network whose stated demographic is laptop miners, this is the most uncomfortable thing in this milestone. The mitigation — enough publicly-reachable nodes, as Bitcoin has — is real but is an assumption about a network that does not exist yet.
- **The in-process network harness is not a network.** It delivers messages by an explicit schedule, which makes partition, heal and eclipse deterministic and reproducible — genuinely better than driving sockets for *those* properties. But it does not exercise concurrency, latency, reordering, connection churn, or partial writes, and a class of bug lives exactly there. The transport has its own tests; the two have not been run against each other under load.
- **Equal-work ties resolve to first-seen, and that is a choice with consequences.** It rewards propagation speed, which is intended, and it advantages a well-connected miner, which is not something to pretend otherwise about. `TestEqualWorkKeepsTheIncumbent` pins the behaviour; nobody has modelled the MEV implications.

**Disposition.** All ✅ implemented and covered. The network suite runs partition-and-heal convergence, invalid-flood non-amplification, ghost announcements, cross-network handshake refusal, address-diverse selection and peer-store persistence. Fork choice covers work-versus-height, the equal-work tie, the undo horizon, the epoch-boundary reorg and the failed-branch restore.

Not done in this milestone, and named rather than left implicit: **sync is the block-replay path only** — headers-first with backward proof-of-work verification is designed (the message set carries it) but the driving loop is not written, so a node joins by replaying blocks in order rather than by validating headers first. That is M2-G5's remaining half and it belongs at the top of the next milestone, before the testnet meets anybody.
