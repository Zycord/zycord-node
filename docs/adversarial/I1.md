# Zycord — Implementation Findings I1

**Scope:** the M0 implementation of architecture spec v0.2 — `core/types`, `core/crypto`, `core/ssz`, `core/u256`, `core/params`, `core/state`, `core/validity`, `core/fold`, `core/pow`, plus the golden vectors and the differential fold.

**Persona:** the literal-minded implementer. Every finding below is a place where the spec, read exactly as written, could not be implemented — or could be implemented in two ways that disagree. Each lists the problem, the resolution taken, and whether it is a spec bug (the spec changes), a spec gap (the spec gains a rule), or a scope refinement (the spec was right and the code is narrower than it needed to be).

The architecture doc's §0 rule applies in reverse here: where the implementation teaches us the spec was wrong, the spec changes — loudly, in public, before genesis.

---

## CRITICAL

### I1-C1 — The asset address derivation is circular ✅ *spec bug*

**Problem.** Spec §9 defines `asset_addr = 0x03 ‖ blake3("zcd/addr/v1" ‖ 0x03 ‖ cert_id)[:31]`, and §4 defines `cert_id = blake3("zcd/cert/v1" ‖ ssz(certificate))`. The certificate commits to its own write set, and an `ISSUE` certificate's writes are cells *under the asset address*. The address therefore depends on a hash of a structure that contains the address. No `ISSUE` certificate can be constructed.

**Impact.** Total for the operation: `ISSUE` is unimplementable as specified, and with it the entire asset layer.

**Fix.** Derive from data that exists before the writes do:

```
asset_addr = 0x03 ‖ blake3("zcd/addr/v1" ‖ 0x03 ‖ chain_id ‖ issuer ‖ seq)[:31]
```

`ISSUE` gains an explicit `Issuer` field, and V4 requires a signature by the key hashing to it. Uniqueness is preserved per issuer per `Seq`; re-using a `Seq` re-derives the same address, and the write-once `EXACT` read that `ISSUE` carries then makes the duplicate skip against the issuer's own earlier certificate — self-inflicted, which is the only kind of skip Era 0 permits (§9's theorem is untouched).

Rejected alternative: computing the id over a body root that excludes the writes. That would make the certificate id not commit to the writes, which the seen set cannot tolerate.

### I1-C2 — Coinbase maturity cannot be a V-rule ✅ *spec bug*

**Problem.** Spec §8 F12 says *"coinbase spendable only after COINBASE_MATURITY (V-rule on spends)"*. V-rules are stateless by construction, and balances are fungible: no function of a certificate's bytes can distinguish a coin mined two blocks ago from one mined two years ago. As written, maturity is unenforceable.

**Impact.** Either maturity is silently dropped — and a reorg can unwind a coinbase whose children have already been spent — or the V-rules stop being stateless, which is the load-bearing property of the whole design.

**Fix.** Maturity becomes a fold-level mechanism: a **fixed-size maturity ring** of `COINBASE_MATURITY` entries under the protocol address, two cells each (payout address, amount). At height `H` the fold reads the entry at index `H mod maturity` — which is always the one written at `H − maturity` — credits it to the payee's spendable balance, and overwrites it with this block's reward. O(1), needs no history, and the whole reward — emission plus the tips of **both** markets — matures together. (The original wording here said "parallel-market tips", which predated I1-H2 giving the sequential market a tip at all. A miner paid some tips instantly while the rest matured would reintroduce exactly the reorg asymmetry the ring exists to remove.)

A reward whose payout address has burned its authority in the meantime is burned rather than written into a cell nobody can read (see I1-M2).

### I1-C3 — A reservation must respect the spent registry ✅ *spec gap*

**Problem.** Spec §6 says billing operations *"bypass spent checks and guards — with the single exception of the reservation's own `GUARD_GE`"*. Spec §14 says pruning *"may delete cell values under spent addresses beyond `UNDO_DEPTH`"*. Together these are a determinism hazard: a deposit cell under a spent address reads as its old balance on a node that has not pruned yet, and as zero on a node that has. The same block then yields `DROPPED` on one node and `APPLIED` on another.

**Impact.** A consensus split whose trigger is each node's pruning schedule — that is, unreproducible and un-debuggable.

**Fix.** F3 refuses to reserve from a deposit cell whose address is in the spent registry; the outcome is `DROPPED`. Pruning is then always safe, because nothing in the fold can ever read a prunable value. The exemption in §6 narrows to: *billing bypasses guards and the registry at the **destination**, never at the source.*

Pinned by `TestSpentAddressCannotFundADeposit` in the griefing suite.

## HIGH

### I1-H1 — The base fees have no home in state ✅ *spec gap*

**Problem.** Spec §15 specifies two EIP-1559 markets with per-block base fees, and B4 makes *"bid ≥ the block's base fee"* a block-validity rule — but the spec never says where a base fee lives, when it updates, or what it is at height 0. A rule that every node must evaluate identically needs a value every node derives identically.

**Fix.** The two base fees are ordinary consensus state: cells under the protocol address, written by the fold. Genesis initialises them from `spec/params.json`; every later block updates them from its own gas usage after the certificates have run (a new rule, **F12b**). B4 is evaluated against the values in state *before* the block, which is the only reading under which a proposer can know in advance which certificates it may include.

Both cells are live and normative text owns the rule now: [ARCHITECTURE §15](../ARCHITECTURE.md) names them as consensus state under the `0x00` address and cites this finding for F12b. Two things landed on top of it and neither is visible from the wording above. *"Its own gas usage"* was never defined here and the wrong reading is a cheap market lever, so R2-H2 split it into three quantities of which only **applied** gas drives F12b; and F12b's sequential input is clamped at `2T`, because §8.1's burst valve lets a block carry up to `4T` and an unclamped step would ratchet the fee upward.

### I1-H2 — The sequential market has no priority tip ✅ *resolved — see [H2-economics](H2-economics.md)*

**Problem.** Spec F11 credits *"Σ(par tips)"* to the miner and burns *"all base fees and all skip fees"*. Sequential tips are not mentioned. Implemented literally, a sequential bid above the base fee is never charged, so the bid is a *maximum* that keeps a certificate includable as the market drifts — not a payment for priority.

The consequence is worth stating plainly: **the scarce resource has no priority signal.** Sequential capacity clears by base fee alone, while a miner's only revenue-maximising lever is the parallel tip — which prices the abundant resource. That is backwards from how the two markets are motivated in §8.

**Resolution.** Not deferred: an incentive frozen into genesis is a fork, not a parameter. Both markets now charge the full bid; the base portion of each is burned and the excess is a priority tip paid to the miner **on applied certificates only**. Base fees stay burned, because a base fee that reached the miner could be inflated for free by self-stuffing. The full analysis — all six revenue lines, the rejected alternatives, and why an unpriced scarce resource becomes an off-chain auction rather than a free one — is in [H2-economics](H2-economics.md).

Two things fell out of the fix worth recording. V5's ceiling formula already assumed the sequential bid was charged in full, so the deposit ceiling is now *tight* rather than permanently over-reserved — evidence the specification intended this and only F11 failed to say where the money went. And the "no profit from skips" constraint holds more strongly than before: a builder is no longer indifferent to skips but actively against them, since a skipped certificate consumes ceiling space and pays nothing.

### I1-H3 — Every billed skip is self-inflicted, *except at a burned destination* ⚠ *scope refinement of R1-N1*

**Problem.** R1-N1 states the poisoning-immunity theorem over the read side: `TRANSFER` guards are `GUARD_GE`, so third-party credits cannot falsify them; `MINT`'s `EXACT` reads target immutable cells. It does not consider the **write** side. A write to an address in the spent registry must fail — that is what the permanent registry is *for* (R1-C3-iii: a payment to a dead address must be loud, not a silent burn) — and a failed write is a billed `SKIPPED_STALE`.

So: if Alice signs a transfer to Bob's one-shot address and Bob retires that address before Alice's certificate commits, **Alice is billed a skip fee she did not cause**.

**Assessment.** The window is narrow. One-shot addresses are generated fresh per payment received, so an address a payer has been handed is one the payee has no reason to retire; and the payee gains nothing but the payer's skip fee, which is burned rather than paid to anyone. But it is a genuine third-party-triggered bill, and the theorem's statement must say so.

**Resolution.** The theorem is restated as a case split rather than as prose with an asterisk, because a theorem with a fuzzy exception gives false confidence:

> **Theorem (Era-0 billing attribution).** Let `C` be a certificate whose committed outcome is a billed skip. Then exactly one of:
> 1. **Self** — the failing read or write is under an address whose key is in `C`'s own signature set;
> 2. **Mint race** — the failure is the `GUARD_LE` on an asset's `minted` cell, whose only movers are certificates signed by that asset's declared minter, which is in `C`'s signature set;
> 3. **Destination burn** — the failure is a write to an address `A` that `C` *credits*, where `A` is one-shot and `A`'s own key holder burned it after `C` was signed.
>
> No party unnamed by `C` can cause `C` to be billed.
>
> ⚠ *The one-shot burn decision added a fourth closure property, and the reason is worth reading before the next rule is written. The three below reason over **derived write sets** — which writes a program emits, and which of them need a signature. That is the right question for a rule expressed as a write and blind to a rule expressed anywhere else. That decision's first design refused to burn an address whose cell was not empty: a staging condition, no new write, all three properties green, and any stranger able to bill a signature with one drop of dust (measured at a 9.3:1 cost ratio in the attacker's favour). `TestLemmaNoUnsignedCreditChangesAnOutcome` asks the question over **outcomes**, by running the fold. Stated as a constraint on future rules: **no fold rule's verdict may read a cell a stranger can credit.***

The earlier draft of this carve-out said the burner must be "a party `C` already authorised to co-sign". **That was wrong** and is corrected here: the burner never co-signs `C`. It is the holder of an address `C` names as a *destination* — the payee, who supplies no signature at all. The bound is not shared authorship, it is *being named*.

Three closure properties make case 3 the only carve-out, and all three are tested mechanically rather than by inspection (`core/fold/theorem_test.go`):

- **Only one-shot addresses can ever be burned.** `RETIRE` rejects any address that is not version `0x01`, and `TRANSFER` emits a `MARK_SPENT` only for a debited `0x01` source. The registry can therefore never contain a `0x02` address — so a payee who publishes a *persistent* address has no grief surface whatsoever, which makes the carve-out avoidable by wallet policy rather than merely rare.
- **Burning an address requires its own key.** V4 requires a signature matching any `MARK_SPENT` target. Without this the carve-out would widen into an unrestricted grief and this would be a critical finding.
- **Credits are the only unsigned writes.** Every other write to a user address — `DELTA_SUB`, `SET`, `MARK_SPENT` — already requires that address's signature, which collapses it into case 1. Checked over the whole Era-0 program set, so adding an operation that breaks the property fails the test.

**Bounded, demonstrated.** `TestCarveOutIsLimitedToNamedDestinations` commits, in one block, a certificate that names the burned address and an independent one that does not: the first is billed, the second applies. If an independent certificate could ever be caught, this would be critical rather than high, and that test is where it would surface.

**Amplification, as a formula rather than a constant.** One `RETIRE` may burn up to `MAX_RETIRE_ADDRS` addresses, so the leverage a malicious payee gets for the cost of one certificate is

```
leverage = MAX_RETIRE_ADDRS × (concurrent payers per address)
```

The second factor is the one that matters, and it is set by wallet policy rather than by the protocol: about **1** under the rule that an address is used for exactly one expected payment, and **unbounded** without it — a published, reused one-shot address can have any number of payments in flight. That is why the rule is a deliverable ([WALLET.md](../WALLET.md)) and not folklore. Nobody profits either way: the skip fees are burned, not paid, and the payers keep their funds. It is a nuisance with leverage, not a theft.

**A good-faith variant, with no malice at all.** A payee *sweeps* a one-shot address it was paid on. Sweeping debits the address, which marks it spent — and a second payment already in flight to that address now skips. Same case, same mechanism, nobody at fault. The same wallet rule covers it, stated from the other side: **an address, once paid, is dead for payers too.**

**Rejected alternatives.** Letting a credit to a burned address succeed silently restores exactly the silent-burn bug R1-C3-iii closed, and costs the payer the whole payment rather than a fee. Reporting it as `DROPPED` instead of a skip makes the certificate un-seen and therefore infinitely resubmittable — free mempool spam. Neither is better than a loud, cheap, burned failure.

## MEDIUM

### I1-M1 — A slot both debited and credited by one `TRANSFER` ✅ *spec gap*

**Problem.** R1-M1 requires derivation to merge all debits and credits per slot into *"one guard + one delta"*. For a routed transfer (A→B, B→C for equal amounts) the merged delta on B nets to zero, or changes sign. Debit authorisation (V4) is derived from the *write set*, so a netted-away `DELTA_SUB` means B's authority is used without B's signature being required.

**Fix.** Derivation rejects any `TRANSFER` in which one balance slot is both debited and credited. The merge is then trivially unambiguous — a slot is either all-debits (`GUARD_GE` + `DELTA_SUB`) or all-credits (`DELTA_ADD`) — and V4 stays derivable from the write set alone. Routing is expressed as two certificates with ascending `Seq`, which the fold already orders correctly.

Derivation also rejects zero-amount moves and self-moves, for the same reason: they have no canonical merged form.

### I1-M2 — Settling into a burned refund cell ✅ *spec gap*

**Problem.** `RefundTo` exists so that a refund never targets a cell the certificate burns (R1-C3-i). It does not prevent `RefundTo` naming an address that was *already* burned by an earlier certificate. Crediting it would write value into a cell nobody can ever read.

**Fix.** Settlement checks the registry at the destination: a remainder owed to a spent address is **burned**, deterministically, and counted in the block's burn total. The same rule applies to a maturing coinbase whose payout address was retired in the meantime (I1-C2). Consistent with I1-C3: billing bypasses the registry at the source, never at the destination.

### I1-M3 — The undo log must carry seen-set removals ✅ *spec gap*

**Problem.** Spec F15 logs *"(slot, old_value) pairs for every touched slot — and registry additions"*. F10 also *prunes* seen entries. A block that prunes an entry and is later undone leaves the seen set permanently short, so a certificate that had already been billed becomes includable again — the exact re-billing R1-C1 closed, reachable through a reorg instead of through a proposer.

**Fix.** The undo log records both seen additions and seen *removals*. `UndoBlock` restores both. Pinned by `TestUndoIsExact` and `TestReorgBillsExactlyOnce`.

### I1-M4 — Signature-set minimality ✅ *spec gap*

**Problem.** V4 as written requires every write that needs a signature to have one. It does not forbid signatures that authorise nothing. A certificate carrying a superfluous signature is a different certificate — different bytes, different id — expressing the identical state transition. Two canonical forms for one transition means the seen set does not close over it.

**Fix.** V4 requires the signature set to be exactly the required set: every required address or key is satisfied, and every signature satisfies at least one requirement.

### I1-M5 — The proof-of-work input needs the nonce in it ✅ *spec bug*

**Problem.** Spec §12 says the work function runs over `blake3("zcd/pow/v1" ‖ ssz(header sans PoW.Nonce))`. Taken literally the nonce does not enter the input, so no amount of nonce iteration changes the result and mining is impossible.

**Fix.** Read as the midstate optimisation it clearly intends:

```
pow_seed  = blake3("zcd/pow/v1" ‖ ssz(header with nonce zeroed))   # once per candidate
pow_input = pow_seed ‖ le64(nonce)                                   # once per attempt
```

### I1-M6 — The beacon's entropy source ✅ *spec gap*

**Problem.** §6 defines `beacon.entropy` as *"16 bytes of the previous epoch-boundary block id"*. Producing that at height `H` requires the id of the block at `H − EPOCH_LENGTH`, which is not available to a fold over one block against one state without adding a history cell.

**Fix.** The entropy is taken from `Header.ParentID` — the last block of the epoch that just ended, which is available and is at least as fresh. The R1-L1 caveat is unchanged and unchanged in force: this value is proof-of-work output, it is miner-grindable, and it is unfit for high-value lotteries until a verifiable random function arrives in Phase 2.

## LOW / NOTES

- **I1-L1 — Genesis carries no proof of work.** Solving block 0 would make it unreproducible without the miner's nonce, which defeats `zcd genesis`. A competing genesis is a different network, not a fork, so there is nothing a genesis nonce protects. Height 0 is exempt from the work check; every later block is not. ✅
- **I1-L2 — Emission is a per-epoch integer decay.** "×0.8 per year" is realised as `E(n) = E(n−1) − E(n−1)/1637` per epoch, floored at the tail. No floats, no tables to get wrong, and the compounded yearly factor is 0.8001. The genesis block pays no coinbase at all. ✅
- **I1-L3 — The base fee's resting point is not the floor.** The decrease step is proportional and integer-divided, so it rounds to zero once the fee falls below the change denominator, leaving the practical resting point at a small constant rather than `MIN_BASE_FEE`. This matches EIP-1559 and is deterministic. The increase step is deliberately asymmetric — it always moves by at least one unit — so a chain at its resting point cannot be congested for free. ✅
- **I1-L4 — Stranded remainders under a burned one-shot.** A certificate that debits a one-shot address burns it, and whatever balance is left under that address is unreachable forever. This is correct behaviour and a wallet obligation: sweep the whole cell. Worth an explicit warning in the wallet UX at M1. ⚠ *The warning this note asked for exists now: `zcd wallet sweep` prints the exact numbers and requires a typed confirmation before an irreversible one-shot sweep submits (docs/WALLET.md rule 1) — added once it was found that the number being confirmed could itself come from a single, unaudited node.* ⚠ *The "correct behaviour" half was overturned: F8b now moves whatever a burn would have stranded into the certificate's own `RefundTo` cell, so the native remainder is returned to the certificate's own refund address rather than destroyed — and where it cannot be returned, it is left in place rather than destroyed. The obligation survives for assets the certificate does not name, which no rule can reach — see [decisions/one-shot-burn-scope.md](../decisions/one-shot-burn-scope.md).*
- **I1-L5 — The epoch state root is recomputed, not maintained.** `core/state` rebuilds the root from the sorted cell set. That is the right choice for M0, where the root's *definition* is what matters and a differential implementation must be able to reproduce it obviously. Incremental maintenance from the per-epoch dirty set is an M1 storage concern and must produce the identical value. ✅
- **I1-L6 — The seen set is not in the state root.** It is prunable, fully determined by recent history, and held by every full node anyway for B3. Committing it would tie the root to the pruning schedule. ✅
- **I1-L8 — `SKIPPED_OVERFLOW` is unreachable in Era 0.** For any asset, the sum of all balances equals its `minted` cell, which a `GUARD_LE` holds at or below the cap; for the native coin the sum equals the total emitted, which no physical amount of time brings near 2^256. So no credit can overflow and no guarded debit can underflow. The outcome and its code path are kept — "unreachable" is a property of today's operation set, not of the fold, and the cEVM will change it — but no vector exercises it and none can. Stated so that a future reader does not mistake the gap for an oversight. ✅
- **I1-L9 — Fold-level credits saturate rather than fail.** ✅ *superseded by [R2-M1](R2.md).* The objection to a panic was right and the instrument was wrong: `ApplyBlock` already reports block-invalidity, so an impossible arithmetic condition returns exactly that. A block that trips it is rejected and the node keeps serving other branches; if every block trips it the node halts loudly, which is the right failure mode for money. There is also a self-referential reason: the I1-L8 unreachability proof rests on conservation, and saturation is precisely a conservation-violating operation — it would have eroded the invariant that proves it cannot run.
- **I1-L10 — `Seq` is neither unique nor contiguous per signer.** Nothing requires it, and it needs nothing: the fold only needs a total order. The one visible consequence is that two `ISSUE` certificates from one signer at one `Seq` derive the same asset address, where the write-once cap read resolves it — the first applies, the second skips against its author's own earlier certificate. Deliberate, and pinned by the `issue-same-seq-collision` vector. ✅
- **I1-L11 — `coinbase_maturity` was unvalidated.** The maturity ring is indexed by height modulo its size, so a parameter file with `coinbase_maturity: 0` divided by zero inside the fold on every block. Found while confirming I1-C2; now rejected at load time with the other parameter invariants. ✅
- **I1-L7 — In Era 0, V3 subsumes V4, V6 and V7.** Derivation pins the read and write sets of all four native operations exactly, so no certificate that passes V3 can violate the others. They are implemented and tested directly anyway: they are what will do the work when the cEVM makes write sets open-ended, and a rule first written under pressure is a rule written badly. ✅

## Confidence

Flagged for the R2 reader, per the review's request to surface the ones I was *not* confident about rather than only the ones I resolved:

- **I1-M6 (beacon entropy from `ParentID`)** — flagged as the least forced choice here, and [R2](R2.md) ratified it as a decision with a reason the original draft had missed: a block one whole epoch back is *known an epoch in advance*, which maximises the prediction window for anything that consumes the value, while `ParentID` is revealed only at the boundary. Not merely the available reading — the better one. Now recorded with that rationale in normative §6. R1-L1's grindability caveat applies to both equally and stands verbatim.
- **I1-L3 (base-fee resting point)** — the practical floor is the change denominator, not `MIN_BASE_FEE`, because the decrease step is integer-divided. This matches EIP-1559 and is deterministic, but it means `MIN_BASE_FEE` as a parameter is not the number it appears to be. Now carried as a note inside `params.json` itself, so a parameter editor meets the trap where the parameter is (R2-S4).
- **I1-L9 (saturating fold-level credits)** — resolved by R2-M1; the flag was right and the fix was better than the one proposed here.
- **I1-H3** — resolved above, but it is the finding whose *statement* went through the most revisions, and the one where an incorrect framing survived a draft. Worth a second reader on the case split specifically.

Everything else in this document I am confident is forced: the alternative either fails to compile, fails to be deterministic, or reintroduces a finding R1 already closed.

**Disposition.** All ✅ findings are implemented and covered by golden vectors, the griefing suite, or both. I1-H2 is resolved rather than deferred ([H2-economics](H2-economics.md)). The remaining ⚠ items — I1-L4 (stranded remainders under a burned one-shot, a wallet obligation) and I1-L9 (saturating fold-level credits) — are documented in-spec rather than hidden, and neither is a consensus risk.
