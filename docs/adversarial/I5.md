# Zycord — Implementation Findings I5

**Scope:** the R5 gates — mechanizing `Read`'s two rules (R5-G2), the long soak and its continuous-contention regime (R5-G1), and the coordinated-lie sync analysis (R5-M1).

**Persona:** the implementer auditing his own instruments. I4 found three green things that were measuring nothing and named the standing question — *what would this look like if it were measuring nothing?* R5 asked it deliberately, of the fixes as well as the code. It found four more. Two of them were in work delivered this milestone, one was in a metric that had been decorative since M1, and one was a liveness bug that needed no adversary at all.

---

## HIGH

### I5-H1 — One peer, one lie, and a node never syncs again ✅ *found by asking the R5-M1 question*

**Problem.** R5-M1 asked for an analysis of a *coordinated* liar against the sync trigger. The analysis found that coordination is unnecessary.

Peer selection was an argmax over claimed height:

```go
if !found || t.Height > best.Height { best, found = t, true }
```

`t.Height` arrives in a handshake or a block announcement and nothing checks it — nothing *can*, because verifying a height means having the headers, which is what sync is for. So a peer advertising height 2³⁰ is the maximum on every tick, forever. `syncLoop` had no fallback, no exclusion and no cooldown, so the honest peer holding the real chain was **never asked**.

And the failure was silent. The liar answers the header request with an empty list; `runOnce` returns `&Result{}, nil`; `SyncFrom` returns `nil`. **No error logged, no score charged.** Every three seconds, forever, the node completes a handshake with the peer preventing it from syncing and records nothing. Gossip cannot route around it either: a node held far behind refuses every announcement it receives, correctly, because the orphan height window rejects blocks more than 128 from its tip.

The safety boundary held throughout — re-derivation means nothing false is ever *accepted*. That is precisely why this survived: the property the design is proudest of is about what a node believes, and this is about what a node can be prevented from hearing.

**Fix.** Selection is now **least-recently-tried first**, claimed height breaking ties only among equally-stale candidates. The property:

> No peer is asked twice until every other candidate has been asked once.

It is the right shape because it never decides whether a claim is true — ranking must trust the number it ranks by, rotation need not. A liar still costs one round trip per rotation; it cannot own the rotation, and a calibrated lie buys exactly as little as an absurd one. Plus two repairs: `SyncCandidates` skips banned peers (the ban list existed and the path choosing who to talk to never consulted it), and four more ways to lie now cost score (`ErrNotContiguous`, `ErrBrokenLinkage`, `ErrBadTime`, `ErrBadVersion` were free).

Full analysis, including what each defence carries and five rejected alternatives: [sync.md](sync.md).

### I5-H2 — `deepest_reorg` had been structurally zero since M1 ✅ *found by a check that depended on it*

**Problem.** The continuous-contention check validates its history horizon against the deepest reorg any node actually performed, so that the depth constant is answerable to measurement rather than to taste. The first run reported **`deepest observed reorg: 0`** after 21 partitions and 8 kills.

That is not a credible number, and it was not a number at all. `Metrics.ObserveReorg` existed, was correct, and **was never called from anywhere**. `/metrics` had reported `deepest_reorg: 0` since M1, through every fork and every partition.

Worse on inspection: the whole metrics surface was fed from exactly one place, the miner's loop. `blocks_applied` counted only *locally mined* blocks — a non-mining node reported zero forever and a mining node did not count the blocks it received. And the test covering it called `ObserveBlock` itself and then asserted the endpoint reported what the test had just supplied. **The only caller of the recording function was the test for the recording function.**

A metric that cannot be non-zero is the observability form of a test that cannot fail, and validating a constant against one is not validation.

**Fix.** Counters moved to `node/chain`, where every accepted block passes through `Apply` or `ConsiderBranch` and there is no fourth door. Reorg events and depth are recorded after the commit lands, so they describe what a node did rather than what it attempted; extending the tip explicitly does not count as a reorg, or the deepest-reorg number drowns in zeroes. The dead writers are deleted rather than left pointing at fields nobody reads. The RPC test no longer feeds the metric it checks.

Added while there: `blocks_rejected`, because a block the fold refuses was previously recorded nowhere — the gossip path logged it only if the peer's score crossed a threshold — which made "no node violated the billing law" checkable only by scraping for a line that usually was not written.

### I5-H3 — The continuous-contention check would have measured nothing ✅ *caught by its own guard, before it ran*

**Problem.** The check compares history below a reorg horizon. Its first run reported: *"the history checker made no comparisons at all (max height 12, horizon depth 16)"* — the default 25-second soak never reaches a horizon, so zero heights were ever compared.

Had that guard not been written first, the test would have passed. Green, fast, and asserting nothing — I4-H3 verbatim, one milestone later, in the code written to prevent it.

**Fix.** The guard was written first and it fired, which is the finding. Three more were added around it: the check fails if it compared fewer than ten heights; it fails if the verified watermark falls far behind the network (the failure mode where one stalled node freezes the compared height below the fork point, so hours of "agreement" are agreement about a prefix nobody disputes); and the horizon depth is checked against both its derivation and the deepest reorg actually observed.

The variant runs only when a duration is asked for, and **the skip message says what is going untested** — a skip that reads like a pass is the same failure as a green test that measures nothing.

## MEDIUM

### I5-M1 — The watchdog would have been blind in exactly the wrong place ✅

**Problem.** The obvious way to enforce rule 2 (`Read` must not re-enter the chain) is a watchdog on lock acquisition: reentrancy deadlocks, so time it out and panic. Before building it I measured Go's `RWMutex` directly:

| Sequence, same goroutine | Result |
|---|---|
| `RLock` → `Lock` (Read then Apply) | **always blocks** |
| `RLock` → `RLock` (Read then Read), no writer queued | **succeeds** |
| `RLock` → `RLock`, writer queued | **blocks** |

The middle row kills the design. A nested `Read` succeeds in a quiet test suite and deadlocks in production the moment a writer queues behind it: correct-looking, load-dependent, invisible to the tests that exist. That is this project's signature bug, and a watchdog is blind to it precisely there.

Confirmed afterwards in the real codebase: with the reentrancy check mutated out, the nested `Read` in `TestReentrantReadIsCaught` neither panicked nor deadlocked. It simply returned.

**Fix.** Detection before the lock is taken, via a goroutine-scoped set of chains currently under `Read` — a located panic with the offending frame on the stack, instead of a process that stops answering. Keyed by `(goroutine, chain)` rather than by goroutine, because in-process multi-node tests run several chains and `chainA.Read(func(){ chainB.Apply(…) })` is not reentrancy. A guard with false positives is a guard somebody switches off.

### I5-M2 — A guard armed only in test builds proves almost nothing ✅

**Problem.** The first cut put both rules behind `//go:build race || zcdguard`. But the chaos soak builds its nodes with plain `go build`, and releases ship untagged — so the answer to *"if the guard is armed only under `-race`, what has the long soak proven?"* was: that eight hand-written call sites do not retain a reference, a fact readable by grepping. **Zero executions of the guard would ever have coincided with the concurrency the guard is about.**

**Fix.** Split by cost, not by convenience. Rule 1 — the borrow-lifetime check — is **always on, in every build**, because it is nearly free: measured at **+17.5 ns and one 4-byte allocation per `Read`**, and flat, since a ten-access `Read` costs the same +14.5 ns as a one-access one. Rule 2 needs the goroutine's identity, costs ~3 µs, and stays behind `-tags zcdguard` (and `-race`, so CI gets it free). The soak builds its binaries with the tag — not with `-race`, which slows a node enough to distort the timing a soak exists to measure.

And armed-ness is now observable: a build tag that does not match a constraint is silently ignored by the toolchain, so a typo would produce a run that looks exactly like a guarded one. `zycordd` logs `state_guard=on|off`; the soak reads it back before any chaos starts and fails if it says `off`.

### I5-M3 — The guard knows about one lock ✅

**Problem.** Rule 2 reasons about `chain.mu` alone. Six call sites establish the order `chain.mu` → `pool.mu`, and a future `pool.mu` → `chain.mu` path would be an ABBA deadlock that the guard certifies as clean and `-race` cannot see either, since a lock-order inversion is not a data race.

**Fix.** What makes the inversion impossible is that the mempool cannot reach the chain: it takes state as a parameter and holds no reference. That was true and was an accident nobody was defending. It is now an import rule in `make check-imports` — `node/mempool` must not depend on `node/chain`, `p2p`, `sync`, `rpc` or `miner`; `node/storage` on nothing at all. The lock order is enforced by the thing that cannot forget it.

### I5-M4 — The horizon depth was a number with no argument behind it ✅

**Problem.** The contention check needs a depth below which history is treated as settled. Sixteen, chosen because it seemed enough.

**Fix.** Derived, then validated twice. Derived as `max(epochLength, ceil(3 · maxIsolation / targetBlockSeconds))` bounded above by `undoDepth/4` — the first term keeps a state root behind every settled height, the second is how far the chain moves while the harness has a node cut off, and the bound keeps it inside the undo horizon. Validated against the derivation, so that shortening a partition or changing the block time makes the constant fail rather than silently stop being derived from them. Validated again against the deepest reorg actually observed, which is the check that would have been meaningless before I5-H2.

### I5-M5 — R5's own ban filter turned normal competition into a ban ✅ *found by adversarially reviewing R5*

**Problem.** `SyncCandidates` skipping banned peers (I5-H1) was correct in isolation and dangerous in context, because the scoring underneath it was wrong in two places.

A block that does not extend the tip and does not win on work — which is *every* block a competing miner produces, on every node, constantly — went through fork choice and could reach `ScoreInvalidMessage`. And `Chain.Apply` returns `ErrWrongParent` when the tip moves between the engine's parent check and the write lock inside `Apply`, the same race the miner sees as `ErrStaleTemplate`; that was charged too. Five of either bans a peer at `-100`.

Before R5 that was a bad but bounded mistake: a banned peer was disconnected. After R5 a ban also removes a peer from sync candidacy, so **the node would have taught itself to stop syncing from whoever was fastest at telling it things** — the best-connected, most useful peers first. A defence against a liar became an attack on honest peers, by composition with code neither change touched.

**Fix.** Not-better, unknown-ancestor and beyond-horizon were already exempt; `ErrWrongParent` now is too, and the block falls through to fork choice rather than being dropped, since it still describes a branch.

The general lesson, which is why this is written up rather than fixed quietly: **a filter is only as good as the signal it filters on.** Adding the ban check made the score load-bearing for the first time, and nothing had audited what the score actually meant.

### I5-M6b — The counters reset on the event they exist to survive ✅

**Problem.** `Stats` lived in memory. The soak kills nodes at random, so `deepest_reorg` and `blocks_rejected` reported only what had happened since the last crash — and the checks built on them (the history horizon validated against the deepest observed reorg; the assertion that no block was refused by the fold) are asserted in exactly those runs. A metric that resets on the event it is meant to describe is measuring uptime.

**Fix.** The counters ride the same storage batch as everything else (M1-G1: everything one block changes lands in one batch, or none of it does).

Writing the test found a second bug immediately: `writeHead` encoded the counters *before* `recordBlock` and `recordReorg` ran, so the persisted values were permanently one commit stale. The recorders are now pure functions returning the next value — the version that goes to disk is computed before the commit, and memory is updated only after it lands, so the two agree whether or not it did. Mutating in place had made keeping them together impossible.

### I5-M6 — Every address-keyed defence was attacker-controlled ✅

**Problem.** The sync rotation, the persisted peer store and the ban filter are all keyed on a peer's self-declared `ListenAddr`. Nothing stopped a peer sending `Hello` repeatedly on one connection with a fresh address each time — minting an identity that has never been tried, so it wins the rotation on every tick. **The rotation was defeated by rotating the key**, and each repeat added another entry to the peer store.

**Fix.** Two, deliberately overlapping. One handshake per connection — a second is a protocol violation, because there is nothing a second one could legitimately say. And the dialable address is **pinned by the first handshake and never rewritten**, so even a future change that relaxed the first rule cannot silently reopen the hole. Either alone closes it; together they mean the property does not depend on one line staying where it is.

The first attempt at this used "is there an entry for this connection?" as the evidence of a handshake, which is wrong: a block announcement creates an entry too, and a peer may legitimately announce before it says hello. That version disconnected honest peers for sending their own first `Hello`. It needed an explicit flag, and a test for the ordering.

Related, and fixed with it: gossip scores the *connection* address while candidacy filtered on the *advertised* one, so an inbound peer's misbehaviour never reached the ban filter at all. Both are now checked. And a peer at the ban threshold could previously shed the ban by re-advertising, since the ban is keyed on the same string — closed by the same pinning.

**The test that could not fail.** `TestSyncSelectionRotatesRatherThanRanking` records each peer's handshake once and rotates over a candidate set frozen for the test's lifetime. Under that assumption the rotation is unbreakable *by construction* — the test cannot distinguish "rotation over stable identities" from "rotation over identities the adversary reissues", which is the only distinction that matters. It was structurally incapable of failing against the attack it was written to prove impossible: the standing question, answered "like success", inside the fix for the previous instance of the standing question.

`TestRotationSurvivesAnIdentityThatKeepsChanging` is the test that can fail. With the pinning mutated out it reports honest peers reached **0 of 20** ticks while one socket mints twenty identities.

### I5-H4 — Two branches of equal height never resolved ✅ *found by a 20-minute soak, after the heartbeat made it visible*

**Problem.** Fork choice decides by accumulated work. Sync candidacy decided by height. Those two agree almost always, and disagree exactly where it matters: **an equal-height branch can be strictly heavier**, because targets differ, and a node gated on height alone will never ask about it.

A 20-minute soak ended with node b at height 537 on one tip and nodes c and d at height 537 on another. Every one of them reported `ahead_peers=0` — no peer ahead — for a full hour. Nothing was broken. Nothing was going to fix itself. The only thing that could break the tie was a new block from the one still-mining node, and it was mining slowly for an unrelated reason (below).

This is a liveness failure of the same family as I5-H1, from the opposite direction: there the trigger was too permissive about who to ask, here it was too narrow about when to ask at all.

**Fix.** A peer is a candidate if it claims more height **or** more work. Claimed work is no more verifiable than claimed height, and that is fine for the same reason — this only decides who is worth a round trip, and every claim is re-derived from the difficulty rule before a body is fetched. What it buys is that the trigger now agrees with the rule that actually decides: a node that chooses branches by work should ask about branches by work.

`TestAnEqualHeightHeavierBranchIsASyncCandidate` pins it, and pins the other side too — an equal-height, *equal*-work peer must not be chased, or every node spends a round trip per tick on every peer that agrees with it.

### I5-H5 — A non-mining node logged nothing, ever ✅

**Problem.** Every log line in `zycordd` came from the mining loop. So a node that was not mining — which is most nodes, and every miner between blocks — produced **no output at all**. A 45-minute soak ended with three nodes stuck and two minutes of complete silence in their logs, and there was no way to tell from outside whether they were disconnected, unable to sync, or simply not trying. Those have entirely different causes and were, at the time, indistinguishable.

That is also the situation of an operator whose node has stopped following the chain at three in the morning.

**Fix.** One status line every fifteen seconds: height, tip, peers, inbound and outbound separately, whether it is listening, how many peers it believes are ahead, mempool size, and the chain counters. Reachability is reported apart from peer count because the two fail differently — a node with peers and no inbound is unreachable while looking healthy — and `ahead_peers` because "behind with candidates it is not syncing from" is a different fault from "behind with no candidates".

I5-H4 was found by reading `ahead_peers=0` on three nodes that were visibly disagreeing. It was not findable before.

### I5-H6 — Submitted certificates were never relayed ✅ *found by the first soak that carried real load*

**Problem.** `/submit` validated a certificate, admitted it to the local mempool, and stopped. It did not gossip it.

On a network that is mostly non-mining nodes — which is every network — a user's transaction therefore sat in the mempool of whichever node they happened to submit to, until its TTL expired, while the node reported it accepted. Locally it had been.

The first soak run with real load submitted 27 certificates, had all 27 accepted, and saw exactly **1** included in a block. After relaying: 16.

This is the clearest possible vindication of R6-G2. A soak that mines empty blocks cannot find it, no unit test had a reason to look, and it breaks the single most common thing a user does.

**Fix.** Relay after admission — the same rule gossip already follows: nothing is forwarded before it has been validated. `TestSubmittedCertificatesAreRelayed` asserts both halves, because a handler that broadcast unconditionally would pass the first and turn the RPC into an amplifier for anything anyone posts at it.

### I5-H7 — A permanent dedup cache censoring a valid certificate, network-wide, forever ✅ *found by the R7 §2 audit*

**Problem.** `seenCerts` in the gossip engine: written once, never pruned, never bounded, and consulted **before** the mempool. So the trigger was permanent while every reason behind it was transient.

A certificate is evicted from the pool when the base fee rises past its bid, or when its deposit stops covering. Both are consensus state, so the eviction fires on **every node simultaneously, by construction** — the pool even sorts its eviction list to guarantee it. Base fees then come back down (`NextBaseFee` subtracts as readily as it adds), and the fold would apply the certificate again.

It could never return. Every peer dropped the re-offer at the seen check before consulting its pool; `AnnounceCertificate` has exactly one caller and there is no rebroadcast loop; and direct resubmission was answered `{"accepted": true}` and then silently discarded by every peer that had ever seen it. Permanent censorship of a valid certificate, no error anywhere, no crash — the third instance of R7's trigger-vs-rule pattern and the most consequential, because it censors *users* rather than stalling *nodes*.

The cache was also redundant except in the harmful case: `Pool.Add` already rejects duplicates (`ErrAlreadyPooled`, `ErrAlreadyCommitted`), so the only thing `seenCerts` uniquely refused was what the pool had since dropped.

**Fix.** The cache is gone. Deduplication now asks the two places that actually know and are both bounded: the pool (what it is holding) and the chain's seen-set (what has been committed, pruned by TTL). A certificate in neither is re-evaluated, which costs exactly what an unseen certificate costs — so it is no cheaper to attack with than the traffic that already exists. The unbounded per-certificate memory leak went with it.

### I5-H8 — The equal-height fix was inert on the connections that matter ✅

**Problem.** I5-H4 made a peer a sync candidate if it claimed more *work*. `PeerTip.Work` is written once, at the handshake, and gossip cannot honestly update it — an announcement carries a header, not a chain. As both nodes advance, the frozen number stops exceeding ours and candidacy-by-work switches itself off.

The 30-minute soak passed with the fix in place, and that is the uncomfortable part: 115 kills and 215 partitions churn connections constantly, so handshakes were never stale. **The fix worked in the environment that tested it and not in the one that ships.** The unit test could not see it either — it constructs `PeerTip` directly and never ages a connection.

**Fix.** The signal that survives is an announcement this node cannot place: the peer demonstrably holds a block we do not, at a height where it matters, and paid proof of work to say so. It is refreshed by gossip rather than frozen at the handshake, and it is a fact about what was shown rather than a claim about what is held. Bounded by a short window so a peer stops being a candidate once it has nothing new. Both halves are tested — announcing a block we *already have* must not make a peer a candidate, or every peer would be one on every block.

### I5-H9 — Catching up was one wager, and the odds fell as the gap grew ✅ *found by arming the property before diagnosing it*

**Problem.** `sync.Fetch` downloaded every body in a candidate and then applied one branch. A severed link on body 579 of 581 discarded 578 blocks that had already crossed the wire, and the next attempt re-requested all 581. Nothing anywhere retained a header, a body, or the fork point the backward walk had found.

That makes catching up an all-or-nothing wager on one connection surviving a round trip per block — and the size of the wager is the size of the gap. P(arriving on a given attempt) falls as the node falls further behind, monotonically, while the network keeps moving. There is a threshold beyond which a node is stranded permanently, and it crosses it silently: `peers=3`, `banned=0`, `blocks_rejected=0`, `ahead_peers=3`. It knows it is behind, it knows who is ahead, and it cannot close the gap.

That is exactly the ten-hour observation this investigation opened with — node `d` at height 581 while the network reached 5,702, with 166 sync attempts ending in EOF.

**How it was found, which matters more than the finding.** The standing hypothesis was that `extendToCover` accumulated across a dying connection, and it was explicitly flagged as a poor place to start. Starting instead from the property — **a sync attempt that dies partway through must leave the node further along than it started** — and arming it produced a scenario in which the node reached height **0** across 200 severed connections. The hypothesis was about the wrong function: `extendToCover` accumulates headers, and headers were never the expensive half.

**Fix, and it is two mechanisms because these are two cases.**

A candidate that *extends* the tip is landed a piece at a time: every prefix of it is a strict improvement on work, so applying one can never leave this node on a chain nobody has. The prefix is committed before the failure is reported, and the happy path still commits one batch and costs one fsync.

A candidate that *replaces* blocks cannot be landed early — a partial branch loses to the tip it would displace, correctly — so its progress is kept by not re-fetching. `BodyCache` retains bodies across attempts, and it lives on the `Node` rather than on the connection, because the connection is the thing that keeps dying.

Two, and not one, because of `storage-fault-scored`: a fix covering the first case passes a catch-up test, reads as complete, and leaves a node on a minority branch exactly as stranded as before. Both cases have their own scenario and both scenarios were watched failing first.

**What it does not fix.** The cache is memory. A node killed mid-catch-up loses it and re-fetches, so a deep reorg is still atomic across a process restart — and the soak kills nodes constantly. Making it durable means keeping non-canonical blocks in the block store, which is a schema change: `switchTo` deletes a block the moment it leaves the chain. The alternative considered and rejected was rolling back to the common ancestor on the strength of the validated headers alone, then catching up by extension. It is durable and it collapses the second case into the first — but it abandons this node's branch before the replacement is secured, on evidence that is proof of work rather than proof of availability, and that is a fork-choice policy change rather than a sync fix. Named here rather than left to look unconsidered.

### I5-H10 — The guard against charging a peer for our own packet loss was defeated by one verb ✅

**Problem.** `connSource.Body` marks its own failures with `ErrTransport`, and the sync driver declines to score them: *a peer must not be charged for this node's packet loss.* The guard reads correctly and was merged one commit before this session.

It could never fire. `sync.Fetch` wrapped the inner error with `%v` instead of `%w`, so the sentinel was flattened into a string and `errors.Is(err, ErrTransport)` was false at the only site that asks. Every severed body fetch charged the serving peer `ScoreUnservedBody` (−10).

The consequence is a ratchet with no release. Nothing decays a score; the +1 for a useful sync is awarded only on the whole-round success a lossy link prevents; ten severances reach the ban threshold; and a banned peer is dropped from sync candidacy. So the node that pays for the network's faults is the node that cannot catch up — and the more blocks it needs, the more body round trips it makes, and the faster it bans the peers that could serve it. It compounds I5-H9 rather than duplicating it.

**Fix.** `%w`, and the classification given a name — `SyncPenalty` — because an unnamed policy decision inlined in a loop is one nothing can observe.

**The test was vacuous on its first draft, and mutation found it.** It constructed the wrapped error by hand and asserted on the classification, and it *passed with the `%v` restored*, because it was measuring its own string formatting rather than the code's. It now takes the error from `sync.Run`. A test of an error classification has to classify an error the system actually produced — which is I4's standing question arriving in a new costume, and it was caught only because every fix in this milestone is mutation-checked (I5-L9).

### I5-H11 — Every sync-driven reorg dropped its certificates, and the code that would have said so was unreachable ✅

**Problem.** `Result.Undone` carries the blocks a reorg removed so the caller can return their certificates to the mempool — the chain cannot do it itself, because `node/mempool` must stay unreachable from `node/chain` and that import is what fixes the lock order. `runOnce` filled the field. `Run` copied `Adopted`, `From`, `Applied` and `To`, and left `Undone` nil.

So `SyncFrom`'s readmission branch — `if len(res.Undone) > 0` — was dead code for every sync-driven reorg there has ever been. A user whose certificate was confirmed and then reorged out by a sync would watch it vanish from the chain and from every mempool at the same moment.

This is the defect 5ed12c7 fixed for the gossip path, still open on the sync path, and it is the *third* time in this project a correct piece has been reachable from nowhere (`node/sync` in I4-H2, `mempool.Readmit` in I5, this). The wiring check (I5-L8) does not catch it: `Undone` is referenced, by the branch that can never be entered.

**Fix.** `Run` merges each pass's result, including `Undone`, and merges *before* deciding on the error — a pass that landed blocks and then hit a severed link returns both, and the blocks are on disk either way. `SyncFrom` readmits on any pass that undid anything, not only on a clean whole-round success. Pinned by a test that checks every block past the fork is reported.

### I5-H12 — A refused inbound connection was invisible from both ends ✅ *armed as an instrument rather than as a hypothesis*

**Problem.** `Listener.Accept` closes an over-budget connection before the TLS handshake and logs nothing. At the dialer it is a bare EOF; at the listening node it is no event at all.

So the two candidate explanations for a stranded node's 166 EOF sync attempts — a severed link and a refused accept — were **the same observation**, from either end. The previous session refuted the probation-window explanation by checking for a log line that exists; it could not refute or confirm this one, because the evidence does not exist to be checked.

The arithmetic makes it worth seeing. Every peer reaches a soak node through that node's chaos proxy, so every inbound connection arrives from 127.0.0.1 and the whole network shares one address group — deliberately, since that is the CGNAT case the whitepaper's population lives in, and `assertOneAddressGroup` states it as a precondition. `perSource` (3) held slots and `DefaultInboundReserve` (2) reserve slots are therefore shared by *every* peer at once: at most two peers in a group can be catching up simultaneously, however many there are. With three peers that want to, one is refused.

**Fix — an instrument, and deliberately not an alarm.** The listener counts refusals; `refused_in` joins the heartbeat. A refusal is the eclipse defence working exactly as designed, and a check that fires for a benign reason is noise with authority. It becomes a signal only read beside the sync failures at the other end, and that pairing is now possible where before it was not.

**It fired on its first real run.** A 25-second soak — the short one `make ci` executes — recorded `refused_in=1` on one miner. So refusals are not hypothetical at this topology, and they happen inside half a minute; a ten-hour run has ~1,400 times the opportunity. That is an observation and not yet a cause, and the difference is the whole discipline: what it establishes is that the mechanism is live, which is exactly what could not be established before.

**This does not claim to be the cause of anything.** Dimension (b) was a correlation with a sample size of one node. Reading says what is genuinely asymmetric about an outbound-only node — it advertises no dialable address, so no peer can dial it, add it to a peer store, or sync *from* it; the sync path is a one-way valve at that node — but none of that explains a node that pulls and fails. The reserve sizing is a §2 tunable and stays untouched: `DefaultInboundReserve = 2` and `DefaultInboundProbation = 90s` remain invented numbers, now with a counter that can tell a future run whether they bind.

### I5-H13 — The soak reported a setting as a defect ✅ *found by running it*

**Problem.** `make ci` runs the soak at its 25-second default. The load driver waits `(coinbase_maturity + 2) x target_block_seconds` — 60 seconds on the soak parameters — before its first attempt, because until a mining reward matures there is nothing on this chain that can pay for anything. So the driver never woke up, and the billing-law check duly failed the run for having submitted nothing.

The check is right and stays: a run in which nothing was included satisfies "no double billing" perfectly, which is the shape of every instrument this project has caught measuring nothing. What was wrong is that it could not distinguish **"this run was too short to have load"** from **"load was attempted and nothing landed"**. The first is a setting; the second is a defect; and reporting a setting as a defect is how a suite teaches its readers to skim failures — the same cost `assertBalancesAgree` charged.

Whether it failed depended on how fast the network converged, so it presented as flaky. A red build is not flaky; it is a build nobody has understood yet.

**Fix.** The driver records whether it ever reached its first attempt — measured, not derived from a warm-up recomputed in a second place, because two copies of one number drift. A run too short to have load now says NOT RUN and says why. A run that had load and submitted nothing still fails.

### I5-H14 — `sync-no-onblock`: the node that catches up and then cannot mine ✅ *drained, because I5-H9 made it reachable*

**Problem.** `Pool.OnBlock` is the only thing that removes committed certificates from the pool. The gossip path calls it; the sync path never did. `Candidates()` returns the pool unfiltered and `Select` takes no state, so a node that caught up by sync assembled its next block from a pool still holding certificates the chain it had just adopted already committed — and B3 makes re-inclusion block-invalid. The node catches up and then cannot produce a block.

It was masked by gossip density: a synced node applies a gossiped block within seconds and *that* path clears the pool before the miner's next tick. Zero occurrences of `candidate block is invalid` in any run.

**Why it was drained now rather than in turn.** It is reachable only where the sync window is long — a node whose only catch-up route is sync — which is exactly the node I5-H9 exists to rescue. Fixing the stranding and leaving this would have converted a node that could not catch up into a node that catches up and then mines invalid blocks. A fix that creates the conditions for a known defect owns that defect.

Armed first, and it fired with the predicted words: `miner: candidate block is invalid: fold: invalid block: certificate 0 has already been committed`. This is the first of the four drain-queue candidates to be *observed* rather than read.

**Fix.** `Pool.Rescreen(state, tipHeight)` — the screen `OnBlock` already ran, without naming a block. It is a function of state rather than of blocks: a committed certificate is dropped because `s.Seen(id)` is true, which is B3's own rule, so one pass covers a catch-up of any length. `SyncFrom` readmits and then re-screens, in that order, which is the order the gossip path already uses and for the same reason.

**The test drives `SyncFrom` over a real socket, and that is not incidental.** The defect is a missing call, not a wrong computation, so a test driving `sync.Run` directly would exercise the sync package and prove nothing about whether anything calls what it needs to. Mutation then found a *second* uncovered call the same way: deleting the driver's `Pool.Readmit` left every test green, because I5-H11's test pins the sync package's report and nothing pinned the driver acting on it. Both are covered now, both mutation-proven.

### I5-H15 — One unauthenticated message, no proof of work, and the node is gone ✅ *found by reviewing outside the diff*

**Problem.** `UnmarshalAnnounce` bounds a block announcement's id list by `MaxAnnouncedCerts` — 100,000, a transport ceiling with nothing to do with consensus. `OnBlockAnnounce` then handed that list to `certRoot`, which merkleises against `max_certs_per_block`: 256 on devnet, 4,000 on mainnet. `ssz.Merkleize` **panics** when handed more chunks than its limit, and that is right for `core/` — inside the consensus zone an oversized list is a caller's bug, not an input. It was a caller's bug, and `p2p` was the caller.

Nothing on the peer message path recovers. A panic in a per-peer goroutine is the whole process.

And it was free. `pow.CheckWork` returns nil immediately for height 0 — correct, genesis carries no work — so a genesis-height header walks past the work check at no cost. One TCP connection, one handshake, one small message, repeatable against every node on the network. A chain with no admin keys has no answer to that after launch.

**Fix, and it is two because they close different doors.** An announcement claiming more certificates than a block may hold is describing a block that cannot exist, and is refused as a lie and scored. Separately, a genesis-height announcement is refused outright: every node already has genesis, so such an announcement can never be useful, and the only party with a reason to send one is a party looking for a free path past the work check — whatever lives downstream of it now or later.

**Where it came from.** Not the diff. This milestone did not touch `OnBlockAnnounce`. It surfaced from an adversarial review told to look at the *neighbours* of the changed code rather than only the change, which is the argument for scoping a review that way. It also survived every previous review of this file, and the fuzzers do not reach it: they fuzz the decoders, and the decoder here behaves correctly — the mismatch is between two limits that are each individually right.

**And the first version of its test was vacuous.** It used a height-0 header, so the genesis refusal caught the message before the count guard ever ran; with the count guard deleted the test still passed. Mutation found it. It now uses height 1 with a trivially easy target, so the message reaches the guard the test is named for and nothing else stops it first.

### I5-H16 — The retention I added turned a transient lie into a permanent one ✅ *found by an adversarial probe, and it is my own defect*

**Problem.** `Fetch` promised in its own doc comment that "each body must match the header it was requested for", and checked `blk.Header.ID() != id`. That proves the *header* is the header that was asked for. It says nothing about the certificates carried beneath it.

A peer can answer with the genuine header and a body it never had. The header id still matches. `types.UnmarshalBlock` does not verify the cert root; `p2p`'s cert-root check is on announcements, not on served bodies. The mismatch is caught by B1 inside `CheckBlockRules` — which runs in `ApplyBlock`, after the body has been accepted and after the cache has kept it.

Without a cache that cost a liar one wasted attempt. With the cache I added in I5-H9, the poisoned body is served from local memory to every subsequent attempt, against every peer, for the life of the process. **One malicious response and the node never syncs again** — strictly worse than having no retention at all. A fix that makes a node able to catch up while handing an attacker a way to stop it catching up forever is not an improvement.

**Fix.** `Fetch` now checks the binding the doc comment always claimed: the body's computed cert root against the root its header commits to. Retention became something *offered* rather than *taken* — a new `Retainer` interface, called only after both checks pass — so nothing unvalidated can reach a store that outlives the connection it came from. The mismatch is `ErrBodyUnavailable`, so the liar is scored, which it was not before: the old error came from the fold and matched no sentinel, so serving a poisoned body was free.

**No new crash surface**, checked rather than assumed: `CheckBlockRules` already called `ComputeCertRoot` on the same peer-supplied block, so this call touches the same data with the same function, only earlier. And a certificate with a nil program cannot come off the wire — `UnmarshalCertificate` builds the program or fails.

**Then the fix was wired to nothing, and an anti-vacuity guard caught it.** `runOnce` hands `Fetch` a `sourceFetcher`, not the caching source beneath it, so the `Retainer` assertion failed and nothing was ever retained. Every correctness test stayed green — a cache that never stores is indistinguishable from no cache except in how long catching up takes. What failed was the guard asserting that the first severed attempt retained *something*, which is the entire argument for writing those guards rather than inferring the mechanism from convergence.

### I5-H17 — The catch-up check compared nothing, 120 polls out of 120, and blamed the wrong node ✅ *the sixth instrument to measure nothing*

**Problem.** `waitForCatchUp` asks the right question — does the joiner hold the same history as everyone else, below the depth where the tip is still contested — and derived its comparison height from the **minimum height across every node**. One node far enough behind therefore put the settled height out of reach, the check declined, and it declined *every single time*: 120 polls, zero comparisons. The run then failed with `the late joiner never caught up to the network`.

The joiner had caught up. It went from 0 to **516** through 78 kills and 147 partitions, landed on the majority tip, and held `min_score=100` and `banned=0`. The node holding the check hostage was a fourth one that had diverged onto its own branch at height 240. The message named the wrong subject, and it named it in the exact words an engineer would act on.

This is the sixth entry in the table CONTRIBUTING keeps, and the most pointed: the rule it breaks — *compare only when the comparison is meaningful, and say why when you decline* — was written in this repository, about a check in this file, and is quoted two hundred lines above the code that broke it. Declining and then failing anyway is worse than either honest option, because the run produced a specific accusation from a measurement it never took.

**Fix.** The comparison height comes from the nodes that can actually be compared. Nodes below the horizon are excluded and reported rather than allowed to veto, and — the half that matters — a node still below it when the run ends is failed **as itself**, with its own message, because a node that cannot rejoin is the defect this regime exists to surface. Guarded against firing benignly: if *every* node is below the horizon the network is younger than the depth rather than anyone being behind, and that is logged, not failed.

**What it was hiding.** Exactly the thing this investigation set out to find. See I5-H18.

### I5-H18 — The reorg case is still open, and now it has been observed ⚠️ *confirmed, not fixed*

**Observation.** In the same 1x run, with the corrected reading: `a` and `b` at 516 on tip `c18ac9`, the late joiner at 516 on `c18ac9`, `c` at 509 on a contested sibling — and `d` at **240 on tip `6a080a`**, a branch nobody else held.

`d` is the outbound-only node, and it had been killed and restarted 17 times.

**This is I5-H9 half-fixed, and the half that is fixed is visible in the same run.** The late joiner traversed 516 blocks of chaos and arrived: that is the extension case, landed a piece at a time, exactly as intended. `d` diverged, and a divergence needs a **reorg** — the case that cannot be landed in pieces, because a partial branch loses to the tip it would replace. Its progress depends entirely on `BodyCache`, and `BodyCache` is memory, and `d` was killed seventeen times.

The handoff predicted this in as many words: *"A node killed mid-catch-up loses it and re-fetches, so a deep reorg is still atomic across a process restart — and the soak kills nodes constantly."* It is no longer a prediction.

**Re-run after mechanism B was fixed: `d` converged.** Same seed, same 78 kills and 147 partitions, the same 17 kills on `d` — and it performed a 128-block reorg onto the majority tip where before its deepest reorg was 1 and it sat 276 blocks behind. B was the mechanism that bit. A remains confirmed and open, with its severity revised down: kills alone did not strand a node once the bound was right.

**Written up with its evidence self-contained**, so it survives the logs that produced it. The write-up also named a **second candidate mechanism** found alongside it — `extendToCover` bounds the candidate by header *count* while `BetterThanTip` decides by *work*, so a candidate can stop growing one batch before it could have won, and lose silently. It is the cheaper of the two to arm and should be armed first.

**Not fixed here, deliberately.** The two candidate designs are both larger than a follow-up commit deserves:

- **Persist the retention.** Keep non-canonical blocks in the block store so a restart does not lose them. `switchTo` deletes a block the moment it leaves the chain, so this is a storage-schema change.
- **Roll back to the common ancestor** on the strength of the validated headers alone, then catch up by extension. Durable, and it collapses the reorg case into the extension case that already works — but it abandons this node's branch before the replacement is secured, on evidence that is proof of work rather than proof of availability. That is a fork-choice policy change wearing a sync fix's clothes and it wants its own review.

The second is the one I would take, and it should be taken deliberately rather than at the end of a long session in the region I have just been editing.

### I5-H19 — Proof of work was not checked on the path blocks actually arrive by ✅ *CRITICAL — found by the double-check review*

**Problem.** `pow.CheckWork` had exactly two call sites in the tree: `OnBlockAnnounce`, which checks an *announcement*, and `node/sync`, which checks headers it pulled. Neither is on the road a block body travels. `OnBlock` had none. `Chain.Apply` has none. `fold.CheckBlockRules` has none — the fold judges a block's *contents*, and nothing judged its cost.

A `KindBlock` message is unsolicited: `Node.serve` dispatches whatever arrives, so an attacker needs no announcement, no handshake, and no prior relationship.

**Reproduced.** One message carrying a real block with a single field changed — `Target = 1`, a target its hash cannot possibly meet — was **applied**, scored **+1 as a useful message**, and **relayed to every peer**.

The damage is not one bad block. Accumulated work is computed from the target a header *declares*, so that block claimed **2^255** work — more than any honest chain will ever reach. `ConsiderBranch` weighs branches by work, so after it lands **no honest branch can ever outweigh the tip again**: the node is permanently forked, pays the attacker's emission address, and has already forwarded the message to everyone it knows. Cost to the attacker: one TCP message and no proof of work at all.

**And the second half, armed separately.** Even with the hash checked against the declared target, a header may *declare* anything. Declaring `Target = 2^256-1` is solved in a handful of hashes and walks straight through. That is R4-H1 — the attack headers-first sync exists to remove — and it was removed there and nowhere else. Reproduced on real devnet parameters: the rule gives 2^248, the header declared 2^256-1, and the block was applied.

**Fix.** `pow.CheckWork` unconditionally in `OnBlock`, before anything is done with the block. And on the tip-extension branch, where the parent is by definition this node's tip, the declared target is recomputed with `pow.NextTarget` over `RecentHeaders` and must match. Both score `ScoreInvalidMessage`.

The rule check is deliberately **only** on that branch, and the limit is real rather than an oversight: the difficulty rule is a function of the preceding window, so it can be re-derived exactly when the ancestors are held. A block on another branch is an orphan judged later by fork choice, and re-deriving its target means validating headers against a chain this node does not have — which is what sync does and what gossip cannot. `spec/wire.md` §12 already records that asymmetry.

**Why every previous review missed it, and why the tests did.** Every p2p test drives blocks through announce → GetBlock → KindBlock, where `OnBlockAnnounce` happens to check the announced header — so the work check *appears* to be on the path. Nothing exercised the unsolicited `KindBlock`. And `node/sync`'s tests arm this exact adversary (`cheapChain`, `mineCheapChain`) and pass, which is the false reassurance in its purest form: **the rule was proven in the one package that implements it.**

**A mutation caught the first version of the test.** Its forged block declared `Target = 1`, which the *rule* check also rejects — so with `CheckWork` deleted the test still passed, and the guard that also covers the orphan path was not exercised by anything. It now declares the rule's own target with a nonce that does not solve it, so only `CheckWork` can catch it. Both guards are mutation-proven in isolation.

### I5-H20 — The reserve forgave squatters instead of evicting them ✅

**Problem.** The inbound reserve's justification is "a connection may exist, but may not persist": `ExpiredProbation` names connections past their window and `Node.probationLoop` closes them. But `expireProbationLocked` ran inside `Accept` on **every new inbound connection from the same address group**, and deleted the expired entry — freeing the reserve slot without closing anything.

The deadline map is the reaper's only record. Erasing an entry did not enforce the window, it *forgave* it: the connection stayed open, unclosable because nothing remembered it was overdue, and the slot it vacated was immediately available again.

A squatter only had to outlast its window until the next connection arrived from its own group — which, on a network where that group is dialling anyway, is at once. **One address group could hold unbounded persistent inbound connections**: the eclipse bound this defence exists to impose, dismantled by the bookkeeping written to enforce it.

`TestTheReserveDoesNotPersist` could not see it — it never dials again after the window passes, so the erasing path is never taken. The mechanism needed a *second* connection, and nothing had one.

**Fix.** An overdue connection keeps its record until it is actually closed, and `Release` is the only thing that frees a slot. A group that has filled its reserve with overdue connections waits for the reaper — at most one sweep — which is the delay "may not persist" is supposed to cost it.

### I5-H21 — The check I fixed for measuring nothing could still measure nothing ✅

Two vacuities in `waitForCatchUp`, both introduced by I5-H17's own fix and both found by re-reviewing it.

**The comparison height came from the joiner.** `lowest` started at the joiner's height and took the minimum across established nodes — so a joiner stalled arbitrarily far behind pulled the comparison height down to *its own* minus the horizon, agreed with everyone about ancient history, and was declared arrived. The only guard against that was `lateHeight > startHeight`: cross your start height by one block, stall forever, pass. The height now comes from the established network alone, and the joiner must have reached it.

**Zero comparisons read as unanimity.** `agree := true`, and every node in the loop can be skipped — excluded as a laggard, or erroring on its RPC. A poll where nobody answered fell through to `if agree` and returned "arrived" having compared nothing. It now counts what it actually compared and refuses to conclude from an empty set.

The first is the same defect as the balance check's, the second the same as the original I5-H17 — reappearing inside the fix for I5-H17, written in the same session by the same hand. *"Writing the rule down did not stop me breaking it in the next check I wrote"* is a comment already in this file, three hundred lines above.

### I5-H22 — Three more from the double-check, each armed by reading and closed ✅

**A body the fold rejected stayed in the cache.** `Retain` runs before the fold does — it has to, because retention exists for the case the fold cannot yet judge: a reorg whose branch is still incomplete. So a body can pass every check `Fetch` makes (header id, certificate root) and still be refused later as block-invalid — a header carrying real work over a certificate its signer never authorised, for instance. That body stayed retained and was served from local memory to every later attempt. I5-H16 through a second door, and the same permanent stall at the end of it. `Retainer` grew a `Forget`, and a fold rejection now purges the bodies it rejected.

**`ConsiderBranch` never checked that a branch was a chain.** Only the first block's parent was verified. `fold.ApplyBlock` takes no parent and cannot check linkage, and `switchTo` applies each block in turn setting the tip to whatever it claims — so an unlinked set would be applied as though it were a chain, leaving heights with holes and a state no fold ever produced from a real branch. Both callers happen to build linked branches today; that is an argument about callers, and this is an exported entry point on the consensus boundary. The invariant now lives where it is relied on.

**`PeerStore.SelectDiverse` read peer fields after releasing the lock.** It collected `*Peer` pointers under the read lock and then sorted and read `Score`, `Failures` and `Addr` through them afterwards, while `Adjust`, `MarkFailed` and `MarkConnected` write those same fields from the gossip and dial goroutines. An unsynchronised read of a peer's score deciding who this node dials — the eclipse defence choosing on a torn value, and the same shape as the consensus-state race this project already shipped once. It now snapshots the three fields it needs while the lock is held.

`-race` never caught it, and the reason is I5's oldest lesson: the race needs `Adjust` and `SelectDiverse` running concurrently, and no test does that. A tool observes only the executions it is given.

- **I5-L14 — the refusal counter earned its place on its first real run, and it points somewhere.** An accelerated late-joiner regime (`ZCD_SOAK_CHAOS=10`, twenty minutes) ended with every **listening** node converged at height 505 and both **non-listening** nodes stranded together at 246 on a minority tip. The listening nodes had recorded 81 refused inbound connections between them (24/40/17); the two stranded nodes had 377 sync failures between them, overwhelmingly `EOF`.

  Before `refused_in` existed those two facts were one indistinguishable symptom, which is precisely why the previous session could not decide between a refused accept and a severed link. They are now separate observations that can be laid side by side, and side by side they say: the nodes that could not get home are the nodes whose sync connections have to be *accepted* by somebody, and refusals were happening at the same time in the same network.

  **This is a correlation with real numbers behind it, and it is still a correlation.** Mechanical correlation plus a plausible reading is a hypothesis — that rule has been wrong four times in this project, twice on this exact question. What it justifies is arming the reserve specifically: a scenario in which a catching-up node's sync connection is refused because `DefaultInboundReserve` (2) is shared by an entire address group, and showing it cannot converge until that changes. It does **not** justify tuning the reserve on this data; it is a §2 number for the public testnet, and the harness is not the instrument that should set it (docs/decisions/testnet-measurements.md).

  Conditions, because a measurement is true about the conditions it was taken under: ten times the calibrated loss and severance rates, four miners plus one late joiner, every peer in one address group by construction, and a tree that predates I5-H16. The 1x run is the one that decides whether any of this survives at realistic rates. ✅ *observed, not diagnosed*
- **I5-L15 — the incremental landing was visible doing its job in that same run.** The stranded joiner's height climbed 233, 234, 237, 238, 239, 241, 244, 246 — small steps, each a severed attempt that landed what it had carried before dying, against 198 failures in the same window. Before I5-H9 every one of those attempts contributed nothing. That is the fix working in the regime it was written for, and it is also why the remaining failure is a *different* shape: what stalls now is a node needing a reorg, which is the case that cannot be landed a piece at a time and depends on retention instead. ✅ *observed*
- **I5-L12 — `extendToCover` re-validates its whole prefix every round, and the cost is quadratic in the gap. Measured, not fixed.** Each iteration builds `cand.Headers + more` and calls `ValidateHeaders` on all of it, so `pow.CheckWork` re-runs over every header already checked; `ancestorWindow` also re-reads the 91-block difficulty window from disk each time. Measured with a counting `pow.Engine`, against a chain the node must reorg onto:

  | divergent suffix | batch | header hashes | vs linear |
  |---|---|---|---|
  | 100 | 32 | 346 | 2.2x |
  | 200 | 32 | 926 | 3.6x |
  | 400 | 32 | 2,950 | 6.5x |
  | 400 | 128 | 1,222 | 2.7x |
  | 1,000 | 128 | 4,638 | 4.4x |

  Quadratic confirmed — the ratio roughly doubles as the suffix doubles at fixed batch. **Deliberately not fixed.** `need` is bounded by `undo_depth`, so at the shipping `syncBatch` of 128 and mainnet's `undo_depth` of 1024 the worst case is the 4.4x in the last row: a bounded constant on a rare path. Removing it means splitting the difficulty-rule loop so a batch can be validated against a carried-forward window — a refactor of the single most load-bearing check in the package (R4-H1), where a subtle window error weakens the check silently and passes every existing test. That trade does not favour the refactor today.

  **It may favour it after RandomX.** This measurement was taken with `pow.Dev`, one BLAKE3 pass. The same 4.4x under the mainnet engine is 4,638 RandomX evaluations where 1,054 would do, and RandomX is roughly three orders of magnitude more expensive per hash — seconds of CPU per sync attempt, spent exactly when a node is furthest behind and its attempt is most likely to be cut short. The number above is true about the conditions it was taken under; the condition that changes it is on the M3 list. ✅ *measured*
- **I5-L13 — A divergence past the undo horizon surfaces as an error on the sync path, and is logged.** `ErrBeyondUndoHorizon` was recorded as being swallowed into a `Verdict` on the gossip path with no other consumer. On the sync path it is not swallowed: it propagates out of `sync.Run` through `SyncFrom` to `syncLoop`, which logs it, and `SyncPenalty` matches none of its sentinels so no peer is charged for it. Nothing still *acts* on it — there is no resync trigger, which is the real point and remains open — but "silently" is too strong for this half, and a permanent partition would at least leave a line in a log that now survives the run. ✅ *observed while measuring I5-L12*
- **I5-L10 — Node logs now outlive the run that produced them.** They were written under `t.TempDir()`, which the framework deletes when the regime returns — so a ten-hour finding's entire record was erased a moment after the failure was reported, and the diagnosis was lost with it. They are now written outside the ephemeral tree in the first place rather than copied out at the end: a run killed by a CI timeout, an OOM or an operator's Ctrl-C never reaches its own cleanup, and those are the runs whose logs are worth most. A manifest beside them records the seed, the roles and the ports, because a directory of logs is only evidence if what it is a log *of* is written down next to it. ✅
- **I5-L11 — The standing hypothesis was wrong, and saying so is the point.** It named `extendToCover` — the previous session's fix — as the suspect, and flagged its own poor epistemic position for suspecting it. Arming the property instead of the hypothesis found the defect one layer down, in `Fetch`, which had never been touched. `extendToCover` accumulates headers; headers were never the expensive half. The instruction that produced the right answer was *arm the property, not the hypothesis*. ✅

## Confidence

Flagged for the R6 reader.

- **The standing question is now the most productive tool in the project, and that is not reassuring.** Asked deliberately, it found four more instruments measuring nothing — two of them in code written *this* milestone to prevent exactly that. I do not believe the list is complete. The class it belongs to has no upper bound I can see, and no method beyond continuing to ask.
- **The guard has never fired on a real violation**, only on the ones written to test it. Its value is entirely prospective, and prospective value is realised only in builds that carry it — which is the argument that made rule 1 always-on, and it is an argument, not evidence.
- **A static escape check was not built.** With rule 1 enforced at runtime in every build, a compile-time checker on the named type `chain.StateRef` is belt-and-braces: it would catch escapes earlier but cover strictly less (it cannot see through interfaces or across goroutines). Deliberately deferred, and named here rather than left to look like an oversight.
- **The soak's duration is still the weakest evidence in the project.** The gate asks for hours and then days. What has been run is measured in tens of minutes. The four-minute threshold bought the data race; the next threshold is unknown and the only way to find it is to extend the axis. Everything else in this document is better tested than this.
- **Continuous contention is checked at one depth, on one topology, at one chaos intensity.** Four nodes, three miners, one periphery node, partitions of 1–3 seconds. The invariant is right; the sample is small, and nothing here says what happens at forty nodes or under a partition that lasts an hour.
- **Rotation is unmeasured under a real hostile peer set.** The property is pinned by unit tests and never has to fire on an honest network. Whether it is *sufficient* — as opposed to necessary — against a peer set that is largely hostile is an eclipse question, and eclipse is carried by address diversity and the persisted store, both of whose parameters remain the invented numbers I3 flagged.
- **`SyncFrom` still has no absolute deadline.** Per-read deadlines exist; `await` tolerates up to sixteen unsolicited messages at twenty seconds each. The tolerance cannot be zero, because a peer's gossip loop legitimately pushes announcements down the sync connection — but sixteen is a guess and a whole-attempt bound is the right shape. Named in [sync.md](sync.md) §7, not built.
- **Peer-scoring magnitudes, `/16` diversity grouping, and equal-work-tie behaviour are unchanged from I3** and remain unmodelled. Repeated rather than dropped, because a confidence section that lists only new doubts implies the old ones were resolved.

**The qualifying soak, and what the extended axis found.** The 30-minute convergence regime passed on post-fix binaries: 115 kills, 215 partitions, four nodes converged at height 309 on one chain, one tip and one state root, 38 epoch boundaries crossed, and — for the first time — real economic load: **1428 certificates submitted, 1427 accepted, 1058 inclusions across 309 blocks with no certificate billed twice**. The single refusal was a connection reset from a node killed mid-submission.

The contention regime failed on that run, and failed correctly: its own fell-behind guard refused a result in which only 167 of 327 heights had been compared. The cause was the checker, not the chain — `sweep` aborted on the first unreachable node, and at 132 kills there is rarely a window where all four answer long enough to clear a backlog. It now proceeds on a quorum, records how many nodes each height was compared across, and asserts on that average, so a run that mostly reached two nodes cannot pass as one that reached four.

**And the extended axis produced a number worth carrying out of the harness.** The horizon depth was derived at 8 and set to 16 for margin. A contention run observed a reorg **43 blocks deep**. The derivation was not so much wrong as modelling the wrong thing — it assumes one isolation at a time, and this harness partitions or kills something every two seconds, so isolations compound and block production is bursty. The reassuring half is that the chain performed that 43-block reorg atomically, with no rejected block and no state-root disagreement — R4-M1 holding at five times the depth anything had previously exercised.

The margin needs stating carefully, because the first version of this paragraph got it wrong in the direction that matters. The soak derives its parameters from `params.devnet.json`, where `undo_depth` is **128**, so 43 leaves roughly 3x there. **Mainnet's `undo_depth` is 1024**, so against the parameter that actually ships the same observation leaves roughly 24x. Both numbers are worth having and only the second bears on genesis. It is a fact about the parameters rather than about this test, and it is on the [testnet measurement list](../decisions/testnet-measurements.md) as an irreversible-at-genesis choice — not tuned on harness data, which is more hostile than reality on one axis and far less on another.

**The regime the harness has never tested, which three findings now live in.**

Every soak starts four nodes at genesis together and applies short perturbations: kills lasting 300 ms, partitions of one to three seconds. So no node is ever more than a handful of blocks behind, and **long-distance catch-up has never been exercised** — a fresh node joining an established chain, or one returning from a partition long enough to fall outside the orphan height window.

Three findings live in exactly that shadow, and none was observed in any run because of it:

- **I4-H2** — sync was complete, tested, and driven by nothing. Only a node that needed to catch up would have noticed.
- **`SyncFrom` never re-screens the pool** — committed certificates stay pooled and B3 makes the next mined block invalid. Masked because gossip delivers a block within seconds and *that* path does re-screen; a node whose only catch-up route is sync has no such rescue.
- **The ban family** — a node more than 128 blocks behind charges `ScoreInvalidMessage` to every honest peer answering its own `GetBlock` request, and `ErrBodyUnavailable` laundered from a transport error charges another −10. Six blocks from ceiling to permanent ban. Unreachable unless a node is far behind.

That is three findings in one untested regime, which is the regime's own argument for existing. It wants its own scenario: a network that converges, and *then* a fresh or long-partitioned node attempting to join and catch up while the chaos continues. Bigger than any of the individual fixes, and it belongs beside the two soak regimes rather than inside either.

**Newly named, not fixed:**

- **The soak mines empty blocks.** No certificate is ever submitted to it, so the fold's billing law, the fee markets, the mempool and the skip/drop machinery are exercised by the unit suites and by `sim/`, and by the soak not at all. `blocks_rejected == 0` is therefore a true assertion about a network that never asked the question. Adding transaction load is the single highest-value change available to that harness, and it is the first thing to do before the multi-day run.
- **The long soak validates the tree it was built from.** Its binaries are compiled when the run starts, so fixes landed during a run are not in it. The run reported here covers the guard, the contention invariant and convergence; the peer-identity and readmission fixes below it are covered by unit tests and belong in the next long run.

**Disposition.** R5-G2 is met: both rules are machine-checked, rule 1 in every binary, rule 2 in the builds the soak uses, with armed-ness asserted and every check mutation-proven. R5-M1 is met and exceeded — it was supposed to be an analysis and it found a live bug, now fixed and pinned. R5-G1 is **partially met**: the continuous-contention regime exists, is non-vacuous by construction, and is green; the multi-hour and multi-day runs the gate actually asks for have not happened, and no amount of the rest substitutes for them.

That last sentence is the honest state of the M3 gate.
