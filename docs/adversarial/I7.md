# Zycord — Implementation Findings I7

**Scope:** M3 — binding real RandomX behind the `pow` interface, the key schedule the binding needs, and the consequences of a work function that costs three orders of magnitude more than the stand-in every earlier cost decision was made against.

**Persona:** the implementer whose *build* was lying. I5 audited its instruments and found four that reported success while measuring nothing. I6 found three defects by reading rather than running. This milestone found something one layer beneath both: **a test suite that was not compiling the code it was testing**, and reported green against a deliberately broken proof-of-work code generator four times running. Every finding below is downstream of that, either because it was hidden by it or because it was found once it lifted.

---

## I7-C1 — Go's build cache does not see the vendored C++, and nothing said so ✅ *fixed*

The RandomX sources live in `core/pow/randomx/upstream/` and are compiled through one-line shims in the package directory, because cgo compiles only the package directory and never a subdirectory. That arrangement is correct and it has a consequence nobody wrote down: **`cmd/go` hashes the files in the package directory to decide whether to rebuild, and `upstream/` is not one of them.**

Editing the vendored C++ therefore rebuilds nothing. `go test -count=1` does not help — it disables *result* caching, not *build* caching.

What that looked like from the inside, in order:

1. Reverting upstream's `ISUB_R` fix — the bug where an ARM64 machine computes a different hash from an x86 one — left every test green.
2. Corrupting `h_IADD_RS`, one of the most frequent instructions RandomX emits, left every test green.
3. A probe that dereferences a null pointer at the top of that handler left every test green.
4. Only then did the pattern become legible, and even then an early `#error` experiment on `go build` *had* failed, which made the mechanism look ruled out.

**The instrument was not the test. It was the build.** Nothing in the toolchain reports this; a stale object and a fresh one are indistinguishable from the outside.

**Fixed two ways, because one is not enough.** `vendor.sh` now generates `pinned.go`, a package-level file carrying the tag, the commit and a tree hash — so re-vendoring changes the package's own hash and the cache invalidates properly. And `TestVendoredTreeMatchesPinned` recomputes that tree hash in pure Go, **without the `randomx` build tag**, so a hand edit under `upstream/` fails the ordinary `go test ./...` on a machine with no C toolchain at all. The first fix handles the legitimate path; the second handles the one `vendor.sh` cannot see.

**The generalisable lesson:** a build system's dependency tracking is an instrument like any other, and the question I5 taught — *what would this look like if it were measuring nothing?* — applies to it. Here the answer was "exactly like success".

## I7-C2 — v1.2.1 splits the chain by CPU architecture ✅ *avoided*

The version colloquially named as "the one Monero runs" generates wrong ARM64 and RISC-V code for `ISUB_R` when `src == dst` and `imm == 0x80000000`, because negating −2^31 does not fit in an `int32`. An ARM machine and an x86 machine then compute **different hashes for the same header**.

That is not a performance bug. It is a consensus split along CPU architecture, invisible on any single machine and invisible until two populations exist.

Fixed upstream in v1.2.2. **v2.0 does not carry the fix either**; v2.0.1 does, applied independently rather than inherited — which is why `git merge-base` said one thing and reading the source said another, and why the source had to be read.

Pinned at **v1.2.3**. The cross-checks that would notice its return are `TestJITAgreesWithInterpreter` (generic, catches systematic codegen disagreement) and `TestTheISUBREdgeCase` (upstream's own targeted `(key, input)` pair, because the immediate is drawn from the program's bytes and a random sweep would need about ten million tries).

**A note on the targeted vector that cost an hour.** Upstream's test harness takes its key as `const char (&key)[N]` and calls `randomx_init_cache(cache, key, N - 1)` — the minus one drops the NUL of a string literal. This vector's key is not a literal, it is a `char[32]` of raw bytes, so the same helper keys the cache with the first **thirty-one** of them. Passing all 32 produces a perfectly stable, perfectly wrong digest that the JIT and the interpreter *agree on* — which is what makes the mistake easy to keep.

## I7-H1 — The cross-check compared the JIT with itself ✅ *fixed*

`randomx_get_flags()` returns what the platform offers, and on this machine that is `JIT | SECURE | HARD_AES`. The first `New()` OR'd `RANDOMX_FLAG_JIT` in when `Interpreted` was false and did **nothing** when it was true.

So `Interpreted` was a no-op, both engines ran the same configuration, and `TestJITAgreesWithInterpreter` compared the JIT against the JIT. A cross-check that cannot fail is worse than no cross-check, because it reads like one.

It now **clears** what the options turn off rather than setting what they turn on. The evidence that the axis is real is a ratio: the interpreted engine measures **10.7× slower**, which is what a JIT is for.

**Shape worth recognising:** the bug was writing the option in terms of what to *add* when the base value already contained it. Every "start from the platform's capabilities and apply the user's preferences" API has this failure mode.

## I7-H2 — Two diagnoses of the same devnet, both wrong ✅ *understood*

The acceptance run — a RandomX devnet crossing a key boundary — failed twice, and I misattributed it twice.

**First:** it stalled at height 9 and I called it a dataset rebuild at the key boundary. It was the **difficulty**. The fixture carried devnet's `genesis_target` of 2^248, about 256 hashes, sized for a work function that is one BLAKE3 pass. Under RandomX the first nine blocks were solved in milliseconds, the LWMA hardened by up to 16× per block, and the chain was unmineable within ten. The controller was working correctly against a fixture that lied to it.

**Second:** re-sized to 2^240, the node produced zero blocks in 200 seconds and I called it an anomaly with no cause. It had a cause and it was arithmetic. Fast mode measures **335 H/s aggregate** on this machine; 2^240 is 65,536 expected hashes; that is **196 seconds a block**. The target was wrong by a factor of forty, for the second time.

At 2^245 — about 2,048 hashes — the chain runs at roughly six seconds a block, and the acceptance run reaches height 73 with `applied=73, rejected=0, undone=0, reorgs=0` across eight key rotations.

**The operational finding, which belongs to whoever builds the public testnet:** sizing a RandomX network's genesis target requires *measuring the engine*. Getting it wrong does not produce slow blocks. It produces a chain that stops inside ten of them, and the symptom is a miner that looks idle.

**The methodological finding is about me.** Both wrong answers were plausible mechanisms reached by reasoning from a symptom. The right answer both times came from a measurement that took four minutes. I5's standing question has a corollary: *what number would distinguish these explanations, and how long would it take to get?*

## I7-H3 — Verification costs 55 ms, and several decisions were priced against 50 µs ✅ *acted on*

| | |
|---|---|
| verify, light mode, 1 goroutine | **18 H/s** (~55 ms per header) |
| mine, fast mode, 8 goroutines | 335 H/s aggregate |
| dataset init, 8 goroutines | ~7 s |
| dataset init, 1 goroutine | ~167 s |
| key rotation, observed on-chain | 8–11 s |

One machine (arm64). Orders of magnitude, not specifications.

Three things this reclassified, each measured rather than argued:

- **Hash-first relay verified every block's header twice** — once as an announcement, once when the body landed. Free against BLAKE3, ~55 ms per relayed block per node against RandomX. `verify.WorkWasChecked` closes it.
- **`extendToCover` was quadratic in the gap.** I5-L12 measured 4.4× linear, chose to keep it, and recorded that the trade *flips when RandomX lands*. Re-measured: **100 evaluations before, 30 after**, without touching the difficulty loop the original trade was protecting.
- **A flood of distinct invalid headers** — target copied from the rule so the cheap check passes, garbage nonce — buys **five headers, ~0.3 s of CPU, then a ban**. Self-limiting per identity. The aggregate is the Sybil question `decisions/testnet-measurements` §2 already carried, now with a CPU price per identity rather than only a connection slot.

**Both caches are sound only because the key comes from the height.** Under upstream's key-block schedule a verdict indexed by block id would serve one branch's answer to another. The decision recorded in ARCHITECTURE §21 has these as dividends, and they are what a reversal would cost.

## I7-M1 — The parallel miner had to be made deterministic by default ✅ *fixed*

A parallel nonce search returns whichever nonce a worker reaches first, so the miner is nondeterministic above one thread. F13 writes the parent id into state on **every** block (`PrevParentIDSlot`, for §8.1's citations), so two chains mined from identical content with different nonces have different state roots from the next block onward.

`node/chain`'s restart-equivalence test failed the moment the default became `GOMAXPROCS`, and it was right to. The zero value of `Miner.Threads` is now **one**; `cmd/zycordd` asks for cores explicitly.

**The general shape:** the zero value of a type used in tests should be the boring one. Defaulting to parallelism put nondeterminism in the path of every fixture that had no opinion about it.

## I7-M2 — The key-rotation stall ✅ *fixed*

A mining node rebuilds the ~2 GiB dataset when the key epoch changes, **under the engine lock**, so it also stops verifying for the duration. On the devnet timeline ordinary blocks arrived every 0.3–1 s and every boundary took 8–11 s, three times running.

At mainnet's 2048-block interval that is one pause roughly every seventeen hours: nothing to a miner, something to a node that depends on prompt verification.

The fix is available and cheap **here specifically**: because the key comes from the height, the next epoch's key is known long before the boundary, so the next *cache* can be built in the background while the current one is in use. Under upstream's schedule the same prefetch would depend on which branch wins.

*(That sentence said "cache and dataset" until I7-C4. It cannot be the dataset: there is one of them, so "building the next one in the background" is not a background build at all — it is an overwrite of the one in use. That is the defect, and it was written down here as a plan before it was written into the code.)*

**Fixed, and not by the fix I first reached for.** The instinct was to prefetch the dataset. Priced, that is 4 GiB held permanently to avoid a seven-second pause once every seventeen hours on mainnet — a bad trade for a chain whose pitch is the laptop you already have.

The actual defect was narrower and worse: the rebuild ran **under the engine lock**, so a node crossing a boundary stopped verifying the chain it already had. The rebuild has to happen; stopping verification does not. The build now runs outside the lock behind a per-key readiness gate, and `Prefetch` warms the next epoch's *cache* — cheap, and possible only because the key comes from the height.

Measured: 24.8 ms for a prefetched key against 574.9 ms cold, and hashing on the live key runs at 138% of its idle rate during a build (the build competes for CPU; it no longer blocks).

**And the first version of the test passed against the broken implementation.** Asserting "more than zero hashes completed during the build" was satisfied by the single hash already in flight when the lock was taken. It is now a ratio against a control window, with a 25% floor; the locked implementation reports 5% and fails with the cause in the message. That is three for this milestone — see I7-L1 — and this one was written *after* writing I7-L1.

## I7-C3 — Every third-party verification of a release would have failed ✅ *fixed*

Found while building the canonical container M3 now requires, and it is not a cgo defect at all — it was in the shipping, non-cgo build.

Go stamps `vcs.revision`, `vcs.time` and `vcs.modified` into any binary built inside a git work tree, and derives the module version from the commit rather than using `(devel)`. So **the same sources produce different binaries depending on whether a `.git` directory happens to sit beside them.** Measured: 2.2 MB of a 6.9 MB binary differing, from nothing but the presence of a directory.

Why that is fatal rather than untidy: [RELEASE](../RELEASE.md) §1 publishes the tree **without history**, so the released binary carries no stamp. Every verifier checks it from a **clone**, which has a `.git` and stamps *their* revision. The comparison fails for everybody, always — and a failed reproducible-build check does not look like a missing compiler flag. It looks like a compromised binary.

**And CI could not have caught it.** The `reproducible` job built twice in the same directory, which is invariant under both variables that mattered: the path and the presence of history. It was a check that could only fail if the compiler were nondeterministic.

Fixed with `-buildvcs=false`, which loses nothing — the version a user sees comes from `-X main.version`, explicit rather than inferred from how the source was obtained. `make repro` now exports the tree to two different paths and compares those against each other *and* against the working tree; `make repro-randomx` does the same for the cgo build. Mutation-checked: removing the flag fails `repro` at byte 377.

**The lesson is I7-C1's, one layer out.** That finding was a build system whose dependency tracking silently measured nothing. This is a *verification procedure* that silently measured nothing — same shape, and it had been green for the whole life of the project.

## I7-H4 — Eviction stranded a borrower, and the flood is thirty times what I measured

Both found by an external reviewer of this milestone, and the second only because the first made me look again.

### The deadlock ✅ *fixed*

`keyedFor` returned a `*keyed` and the caller borrowed a VM from it afterwards, outside every lock. Between those two moments another goroutine could evict that entry, and `release` drains the VM channel and destroys everything in it — so the borrower received from a drained, never-closed channel and **blocked forever**.

Reachable on an honest node at the production default of `Keys: 2`, which needs only three concurrent key epochs: the one being verified, the one the prefetcher is warming, and a third from a peer's header. Reproduced deterministically.

**Why the existing concurrency test missed it:** `TestConcurrentHashingIsSafe` used `Keys: 2` with exactly *two* distinct keys, so eviction never ran at all. The gap was the third key, not the concurrency — a test can be thoroughly concurrent and still never reach the state that matters.

**The first fix did not work, and that is the useful half.** Reference counting with a per-entry mutex, an `idle` channel, a `sync.Once` and a background releaser that *waited* for the count to fall — it passed without `-race` and still deadlocked with it: 21 of 24 hashes after ten minutes. Adding it also introduced two more deadlocks of the same family, both caught before commit (`Close` released entries without marking them, so it waited on a gate nobody closed; `Prefetch` took a reference it never returned).

Three attempts to derive the interleaving from the code failed. The table dump at the deadlock refuted the analysis outright: the two live entries showed `refs=0`, `evicted=false`, full VM pools — nobody using them — while six goroutines were blocked on entries already destroyed.

**So the mechanism was replaced rather than patched**, on the principle that a concurrency mechanism nobody can justify is one nobody should ship. What replaced it is one sentence:

> An entry's VMs are destroyed by whoever drops the last reference to it after it has left the table, and by nobody else.

Everything follows. Out of the table, no new reference can be taken, so the count only falls; whoever takes it to zero knows every borrowed VM is back, because a borrower returns its VM before dropping its reference; and that goroutine is the only one that can be there, so the destruction needs no lock and no waiting. `refs` moved under the engine lock — the same lock that adds and removes entries — which makes "no new reference after it leaves the table" true by construction rather than by argument. The per-entry mutex, the `idle` channel, the `sync.Once` and the background releaser are all gone.

The performance difference says the old design was wrong twice: **2–4 seconds under `-race`, against not finishing in 600.**

Mutation-checked in both directions, and both were needed: freeing on eviction without checking references deadlocks; the last put not freeing leaks 256 MiB per epoch.

### Unbounded concurrent cache builds ✅ *fixed*

Found while chasing a test that would not pass. Eighteen goroutines were inside `build` at once, each allocating a 256 MiB cache — about 4.6 GiB — because nothing bounded how many key epochs could be initialised simultaneously.

The test that produced it was unrealistic and was fixed. The property it exposed was not: the key comes from a header height **the peer chooses**, so this is the second dimension of the flood below — not just CPU, but concurrent allocation.

Bounded at `Keys`, on an argument that stands without an attacker: the table holds `Keys` entries, so a build beyond that is for an entry that will be evicted before anyone uses it. More than `Keys` is guaranteed waste either way, and the bound turns an unbounded memory amplification into a queue.

### The leak the tests could not see ✅ *fixed*

Freeing on eviction and freeing on the last reference are two different code paths, and only concurrency reaches the second. A first leak test hashed keys one at a time — with sequential use every entry has zero references by the time it is evicted, so eviction frees it directly and the mutated path never runs. It passed against the broken engine.

The engine also gained a `destroyed` counter, because **nothing else in the package can see a leak**: the table stays bounded, no hash blocks, no verdict changes, and it grows by 256 MiB per key epoch forever.

### The flood costs far more than I published ⬜ *open; the uncharged half is priced per connection but not yet bounded per identity*

The reviewer's finding sent me back to the ingress ordering, and the number I put in `decisions/testnet-measurements` §2 is wrong for the worst case.

I measured a flood of unique invalid headers at ~55 ms each — five per identity, ~0.3 s, then a ban. That is the cost **when every header sits in a key epoch the node already holds.** It does not have to. The key comes from the header's **height**, and an announcement's height is chosen by the sender, so headers at widely separated heights select epochs the node has never seen. A new epoch is a 256 MiB allocation and an Argon2 fill, and **that is the one figure in this entry that never had an instrument**: it was written as ~1.7 s, attributed to what `core/pow/randomx` publishes, and that package publishes 574.9 ms cold against 24.8 ms warm. Its own `BenchmarkInitCache` on an idle machine gives **552.9 ms**, and `BenchmarkVerify` **15.1 ms** — two independent readings agreeing on ~0.55 s for the epoch, against a 1.7 s that is three times either. Taken per machine, which is the only valid way to take it, the ratio is **22×** (randomx.go's pair) and **36×** (the benchmarks' pair), so *some thirty times a hash under a held key* survives as a summary and its two absolutes do not. The heading above stands. And the whole budget realises it: an identity that aims its heights at epoch *starts* spends every one of its five charged messages on an epoch this node does not hold — **5 never-held epochs, ~2.7 s of CPU against ~0.1 s**, where 8.5 s and 0.3 s were the same counts priced at the figures that had no instrument.

*(This paragraph also said "and five 256 MiB allocations per identity", meaning five at once. That half was wrong — allocation is admitted `Keys` at a time and a queued caller holds nothing — and is corrected immediately below, by measurement rather than by deletion, together with the sentence that first replaced it, which was wrong in the other direction. The ~30× CPU figure is not the wrong half: it survived, and it now has an instrument.)*

**Reviewed again, and the *shape* of the cost is not what this entry said.** A second adversarial pass — run because I7-C4 reworked the machinery the first pass had reviewed — proposed that the queued builds each hold a 256 MiB cache, so that one identity's five headers are five concurrent allocations and the aggregate OOM-kills a laptop. **That mechanism is wrong**, and the code says why plainly: `build` takes the `building` semaphore **before** `randomx_alloc_cache`, so a caller beyond the bound is parked holding nothing at all. Concurrent *allocation* is bounded globally at `Keys`, never per peer — pinned by `core/pow/randomx.TestConcurrentEpochDemandIsAdmittedKeysAtATime`, which puts **sixteen** goroutines on sixteen never-seen epochs — the ad-hoc probe's own arrangement, so that this entry no longer has to cite a probe that is in nobody's tree — and asserts the number ever inside the allocating region is exactly `Keys`: more is the amplification I7-H4 removed, fewer means the test never raced.

**And the sentence that would have replaced it is also wrong, which is the part this entry has to say out loud.** "The semaphore is taken before the allocation" bounds *allocation*; it does not bound *residency*, and an earlier draft of this paragraph slid from one to the other. The semaphore is released when `build` returns and the 256 MiB is not: it lives in the table entry until that entry is destroyed, and `evictLocked` frees an evicted entry only at `refs == 0` — otherwise its last `put` does. That is I7-H4's one invariant, it is correct, and it means **the table bound is not a memory bound**. Residency is `Keys` plus every entry evicted while a borrower still holds it. Residency has **three** terms and the table bound is only the first: the table's `Keys`; the builds still being *filled*, up to `Keys` more, because a cache is resident from `randomx_alloc_cache` and the Argon2 fill that makes it expensive comes after; and every entry evicted while a borrower still holds it. Measured in both regimes rather than argued — under demand, `TestConcurrentEpochDemandIsAdmittedKeysAtATime` reports **four caches, 1024 MiB, with `Keys: 2`**, twice the table bound; under one long-lived borrower, `TestAnEvictedEntryStillHeldKeepsItsCache` pins an entry, drives two more epochs through the same table and reports **three**. The reachable long-lived holder is `MineOn`, which keeps its reference across `initDataset` — ten to thirty seconds at a key boundary by this package's own reckoning — so two arriving epochs are exactly that sequence. The two terms compose, and the composition is the case a mining node actually reaches — a borrower pinned across the fill *while* peers keep announcing unheld epochs. Measured in the same test: **five caches, 1280 MiB**, which is the derived ceiling `2×Keys + holders` exactly. So on a mining node the resident total is the ~2.03 GiB dataset (`RANDOMX_DATASET_BASE_SIZE + EXTRA`) plus 1.25 GiB of caches plus 2 MiB of scratchpad per VM: **about 3.3 GiB**, and the holders term has no constant bounding it at all. `docs/RUNNING.md`'s "budget ~512 MiB for the engine alone" was the table bound read as a memory bound, and it is corrected there.

**What the refutation does and does not buy.** It buys the mechanism, which was the claim: a flood cannot make a cache appear per *parked* build, because a parked build holds nothing at all. It does not buy "memory is bounded at `Keys`", which nothing in this engine makes true and which the measured 1024 MiB under a two-entry table contradicts outright. The correction to the review is that the excess is bounded by `Keys` and by concurrent borrowers rather than scaling with how many peers demand epochs — a smaller number and a different mechanism, not the absence of one.

**What the same shape does establish is the cost that survives, and it is latency.** The builds are admitted `Keys` at a time and each takes ~0.55 s, so demand queues, and every honest header that needs a not-held epoch waits behind whatever is in front of it. The test above measures the shape — sixteen demands admitted two at a time — and the wall-clock figure is whatever the machine's Argon2 rate makes it; the 13.1 s and 790 MiB this entry used to quote are one laptop's readings, kept as an observation and load-bearing for nothing, because nothing in the tree reproduces them. So the residual is head-of-line delay on a `Keys`-wide gate, not memory exhaustion — a different exposure, with a different fix, and one that no longer argues for urgency on the grounds the review gave.

**And the recorded fix direction does not survive as stated.** Deriving the bound from the peer's handshake claim assumes the claim is worth something; `OnHello` accepts `Hello.Height` unvalidated and unbounded, so a peer that wants a wide window claims one. The bound would be sized by the attacker. Something real may still be built here — a rate over never-seen epochs, or a claim checked against elapsed time — but the one-line direction this entry carried is not it, and writing it down as though it were is how a plan becomes a fix nobody rechecks.

**The measured half is now a test, and measuring it revealed that it is a half.** `node/p2p.TestAHeightVaryingFloodIsBoundedInEpochsToo` walks the key schedule and reports 5 headers forcing **5 distinct epochs the node does not hold** before the ban — the budget in full, because the heights are aimed at epoch starts. For headers the work check **refuses**, the epoch count per identity is bounded by the same scoring budget as the message count, and the bound is **tight**: the test fails above the budget because the bound would have moved, and below it because the heights would have stopped forcing an epoch each.

**And that scope is the finding, not a caveat on it.** `pow.CheckWork` compares the digest against `h.Target` — *the header's own declared field* — and clamps it against nothing. At `Target = u256.Max` the check **passes**, having already evaluated the work function under `pow.KeyFor(h.Height, p)` at a height the sender chose; `OnBlockAnnounce` then returns `ScoreUsefulMessage` and `Forward: true`. So the epoch is forced before any verdict exists, and **`Header.Time` then decides whether anything ever charges for it.** Both variants measured on the merged tree, 50 announcements from one identity each:

| | epochs forced | charged at announce | forwarded | reaped as unserved | banned |
|---|---|---|---|---|---|
| present-dated | 50 | 0 | **50** | 50 | yes |
| future-dated | 50 | 0 | 0 | **0** | **no** |

The present-dated variant is the amplifier: `Forward: true`, so one message asks every peer of this node for the same epoch. It is not unbounded — the id enters `pending` and `ReapUnservedBodies` charges `ScoreUnservedBody` per unserved body — but that charge arrives one `PendingBodyTimeout` after the CPU was spent, so the bound is a minute of Argon2 late rather than a budget in front. The future-dated variant is the free one: `tooFarAhead` returns `CostFree` at `ScoreFutureBlock = 0` and enters the id into **neither** `seenBlocks` nor `pending`. Both of those are deliberate and both are right — charging would let a fast clock score down every honest relay (R1-H2), and marking it seen would dedupe the re-announcement that arrives once the clock catches up — and together they mean nothing charges, nothing dedupes, and ~27 s of Argon2 per fifty messages is repeatable without limit. The work check has already run: it is ordered before `tooFarAhead`, because a future-dated header must still prove work before this node spends anything further on it. Both variants were pinned as subtests of `node/p2p.TestAnAnnouncersOwnTargetForcesEpochsTheScoringNeverBounds`, which asserted the defect deliberately so that no document could cite the bounded pair as covering the class, and which said it would fail on the day somebody fixed it. **It did, and it is superseded by `node/p2p.TestAnAnnouncersOwnTargetBuysABoundedNumberOfKeyEpochs`**, which is the same arrangement asserting what it now costs — see the closure below.

**The uncharged half is priced — by a price rather than by any of the four eliminated directions — and the price is per connection rather than per identity, which is why this half is not yet closed.** The two rejected guards stay rejected: `h.Target` is still taken as declared, and there is still no window on the height. What is in front of the work check now is `Engine.spendKeyEpoch` — a per-connection budget of `MaxUnheldKeyEpochsPerPeer` announcements naming a key epoch outside the two this node is itself working in (its tip's, and the next one, which is where an honest peer announces for the whole interval it takes this node's tip to cross a boundary), refilled one per `randomx_key_interval × target_block_seconds`, which is the rate the honest chain enters new epochs. Past the budget the announcement is refused at `CostBudgeted`, **before** the work check, so the epoch is never built; the refusal is unscored, and the id is deliberately kept out of `seenBlocks`, so a node behind the chain neither bans the peers it depends on nor loses the re-announcement. The measured table above becomes, on the same fifty-message arrangement:

| | epochs forced | charged at announce | forwarded | refused unevaluated | banned |
|---|---|---|---|---|---|
| present-dated | **6** | 0 | **6** | 44 | no |
| future-dated | **6** | 0 | 0 | 44 | no |

Six and not five because the first height an attacker aims at an epoch start lands in `tipEpoch+1`, which is a working epoch and free by design; the other five are the budget. The two variants now cost the same, which is the sharpest statement of the fix: the price runs ahead of the work check and never consults `Header.Time`, so the free-forever variant stopped being free without `ScoreFutureBlock` or the `seenBlocks` omission changing at all — both were right and both are untouched.

**And the fix direction this entry recorded is not the one that was built, which is worth saying because this entry has already been wrong about a direction once.** It said the price "needs the work engine to answer *do you hold this key*". It does not, and asking would have been worse. The engine's key table is an LRU of `Keys` entries, so that answer is a function of whatever traffic ran most recently — the attacker's included — and an identity cycling two epochs of its own choosing would make an honest peer's announcements read as unheld; `CostClass`'s own documentation requires a budget "bounded independently of the sender's choices". It would also make `Forward` and `Score` depend on engine cache state, which is an argument rather than a rule already written: `pow.HotKeyEngine` says which internal representation an engine keeps warm "is not a consensus fact and must never be one" and closes "an engine that ignores this hint computes exactly the same digests, more slowly", so its line is about DIGESTS and an ingress verdict is not a consensus fact either way — same resource, different line, and its only non-trivial implementation is behind a build tag and a C toolchain, so nothing that ordinarily builds would exercise it. The header's height and this node's own tip answer the same question out of facts this node owns. What survives of the recorded direction is its shape and not its mechanism — this entry's own "*a rate over never-seen epochs*" is exactly what was built.

**The UNCHARGED half's aggregate now has a measurement.** That half had no instrument at all, which is why this entry and `decisions/testnet-measurements.md` §2 could only name three constants and say none had been measured. Six characterisation tests measure it in `node/p2p/keyepochaggregate_internal_test.go`, on devnet under `pow.Dev`. **Which half every figure belongs to is the first thing to say, because the two are priced in different currencies.** These counts are all on the declared-target path: the announcement declares `Target = u256.Max`, `pow.CheckWork` **passes**, the verdict is `ScoreUsefulMessage` and no ban is ever reachable — so the identity is free and the aggregate is bounded by address resources alone. What they report: the engine applies **nothing** across connections, so the aggregate is the per-connection budget times the connection set exactly. `Node.register`'s capacity gate is inbound-only, so that set has two figures rather than one: a saturated **inbound** table of 40 connections (`MaxInbound` 32 + `MaxOutbound` 8) holds **200** never-held key epochs at once, and this node's own `MaxOutbound` dialled connections are admitted above the gate on top of it — so the full concurrent set is **48** (`MaxInbound` + 2 × `MaxOutbound`, the product `engine.go` and `syncdriver.go` both already state for this set) and holds **240**. Filling the inbound table costs **8 address groups**, not 14: `acceptRaw` admits while `held[group] < perSource` **or** `probationary[group] < reserve`, both classes reach `register` and get their own budget, and `expireProbationLocked` reclaims nothing — so one `/16` holds `perSource + reserve` = **5** at once, measured by dialling the shipped listener rather than read off its field, and `node/p2p.TestTheReserveIsBounded` says the same next door. Holding the table *without re-handshaking* is the smaller, durable figure and costs **14** groups, since probationary connections are closed after `DefaultInboundProbation`. The outbound half is charged against no group in the **listener's** table, which is why the group price is stated against the inbound half — `SelectDialTargets` applies its own `/16` rule when this node picks those targets. Neither of the two currencies this tree already prices Sybils in is consulted by the price itself: 8 connections inside **one** `/16` buy the same 40 epochs as 8 across 8 of them, and the aggregate is byte-identical whether the peer store is empty or saturated from a single teller — so `SelectDiverse` and `SelectDialTargets` bound a different set entirely (which addresses this node **dials** or **serves**, never which connections arrive). And over time there is no ceiling at all: 4 rounds of a saturated inbound table force **800** epochs with the clock frozen — already more than three times what the whole concurrent set holds standing — for **two independent reasons** that the tests separate: a reconnect is a new map key, *and* `forgetPeer` deletes the entry, so even a sender returning on the address it left from finds a fresh budget. Deleting that `delete` leaves the first row passing and fails the second.

**The CHARGED half is still bounded per identity, and a Sybil count is still its missing input.** Measured in the same file, same harness, separated from the rows above by the declared target and nothing else: with the target the rule itself computes — the header the work check **refuses** — one identity spread across the whole 48-connection set forces **5** never-held epochs from score 0 and **10** from `ScoreCeiling`, and is `BannedKey` both times, against **240** and never banned on the uncharged path. `node.go` applies the verdict as `Peers.AdjustKey(conn.PeerKey, …)` and gates on `Peers.BannedKey`, so one ed25519 key carries one tally across every connection it holds — which is what that second, identity-keyed store was built for. **So §2's sentence naming a Sybil count as the missing input is correct for the half it is scoped to**, `ARCHITECTURE.md` §20's *“the charged half and its Sybil aggregate are unchanged and still M3.5's”* stands, and the aggregate for that half is this per-identity bound times a Sybil count. What has changed is that the *uncharged* half's aggregate is now a number rather than a question, and it does **not** wait on a Sybil count — one identity already reaches its totals for the price of handshakes, exactly as §2's own parenthesis already said of this half.

**What a bound on the uncharged half would need.** Keying the budget on the address group and letting it outlive the connection is the one shape that uses a currency the sender cannot mint — measured as a mutation, it takes the 800 above to 200 and the concurrent 200 to **40**. Its cost is that an honest peer sharing a `/16` with an attacker inherits a spent budget for up to one key-epoch period (17 h mainnet). Whether that is acceptable is the honest `/16` distribution, which is §2's own missing measurement, and a bounded table keyed on it needs an eviction rule that a sender minting groups cannot use as a lever — the failure `maxSkewGroups` already documents with a measurement next door. A per-key cap on concurrent connections was measured too and is **not** an answer to this: it takes one identity from 48 connections to 3, but a fresh keypair per connection leaves the aggregate at 240 untouched, so it bounds the per-identity multiplier and not the aggregate over identities. What is missing is the honest `/16` distribution, and that is why this half is carried rather than closed.

**What remains open here is the charged half and its aggregate over Sybil identities**, unchanged by the above — **and, in the uncharged half, the axis the price is keyed on.** The paragraph at the end of this entry asks for *"a rate limit over never-held epochs per identity"*, and what was built is per **connection**: the budget lives in `Engine.tips[peerAddr]` and `forgetPeer` drops it on disconnect, while an inbound peer's address is `ip:ephemeral_port` — the value `PeerStore.AdjustKey`'s own comment describes as *"a value the OS picks fresh on every reconnect, not the peer"*, which is why the SCORE was given a second, identity-keyed store. The score and the ban are therefore per identity and permanent; the epoch budget is per connection and re-bought for the cost of one TLS handshake. Measured with a frozen clock: one identity, eight reconnects, **40** never-held epochs against a derived budget of 5 (`node/p2p.TestOneIdentityRebuysTheKeyEpochBudgetByReconnecting`). So the rate an identity can force epochs at is no longer bounded by the message rate — two to three orders of magnitude better — but it is bounded by the handshake rate rather than by anything, and `CostClass`'s own requirement that *"the budget must itself be bounded independently of the sender's choices"* is not yet met on this axis. That axis — a budget bounded independently of the handshake rate — is what keeps this half open. Two further residuals of the fix are named where they belong rather than folded in: a flood of announcements *inside* the two working epochs is still bounded only by the unserved-body reaper on the present-dated path and by nothing at all on the future-dated one — a hash each rather than a key initialisation, about thirty times cheaper, and still unpriced; and an over-budget announcement now reaches `recordAnnounce` without paying even that hash, which is one chain lookup per message and the same absence of a price.

The announce path taking the announcer's own target is **deliberate and argued**: re-deriving the real target needs the ancestors, and deciding before fetching them is what hash-first relay is (`docs/adversarial/sync.md` §6.1, which rejected bounding `h.Target` because a node whose tip is old would refuse headers that are legitimately easier). What that argument priced was **one hash**. Nobody repriced it when one hash became a 256 MiB allocation and an Argon2 fill at a height the sender picks — and repricing it is exactly what this entry exists to do. Split out from the rest of this entry, because it is a different bound with a different shape: the charged half needs a tighter budget, this half needs a price where there is none. **And `adversarial/sync.md` §6.1 is the document this repricing lands on**, not just this one: it already describes the future-dated path exactly, and prices it at *“across a day, 2879 SHA-256 evaluations it would not have noticed paying”*. Under RandomX at heights the sender picks, those 2879 are 2879 never-held key epochs — at ~0.55 s each, about **twenty-six minutes** of Argon2 per connection per day — and the rate is a floor rather than a ceiling, because holding candidacy is what needs one message per window; nothing needs the attacker to stop there.

**I tried the obvious fix and reverted it, which is the part worth recording.** Refusing announcements whose height is outside the orphan pool's existing 128-block window, *before* the work check, closes the surface — and breaks catch-up. `TestCatchingUpDoesNotBanTheHonestPeersItDependsOn` says why in one line: *"the victim did not request the announced block"*. A node that is behind legitimately receives announcements far ahead and must act on them; refusing them trades a cost bug for a liveness bug, which is exactly the trade I5-M5 warns against.

That sentence stands. The one that followed it does not, and it is struck rather than quietly edited: *"the bound wants to come from what the peer claimed in its handshake — which is checked against accumulated work."* The claim is **not** checked against accumulated work before it could gate this path — `OnHello` records `Hello.Height` as given — so a window derived from it is a window the attacker sizes. Two wrong answers eliminated now, and the second one was mine, written as a direction rather than as a hypothesis and therefore never rechecked.

**A fourth direction exists, ships already, and is eliminated by arithmetic — which is worth more than the three eliminated by argument.** `OnBlock` bounds a declared target *without ancestors*: `ErrOrphanImplausible` refuses a header whose `Target` exceeds `plausibleCeiling(tip.Target, distance, DifficultyClampFactor)`, a pure function of the tip's target, the height distance and a consensus parameter — precisely the shape §6.1 said could not exist. It cannot bound this surface, and the reason is a division rather than a judgement: the ceiling multiplies by `difficulty_clamp_factor = 16` per block of distance, so from any tip target it saturates at `u256.Max` within **64 blocks**, while one key epoch is `randomx_key_interval` blocks — **2048** on mainnet, 512 on the public testnet. An attacker walking the key schedule steps a whole interval per message, so from the second message on it is past saturation by a factor of thirty-two, where the ceiling admits anything — and the code says so itself: *“at that range a node genuinely cannot tell without the ancestor headers.”* (The band below 64 is real and the exception is worth naming rather than rounding away: a *fresh* epoch can sit one block ahead when the tip is at a boundary. That is the one case `randomx_key_lag` already prefetches, and it is not a case an attacker can choose.) Verified rather than estimated: at `target = 1` saturation lands at distance exactly 64 and not 63, and at every shipped genesis target it lands between 2 and 5.

**Open, measured, and with four wrong answers eliminated — and larger than this entry first said, not smaller.** What is left to build is a bound that does not take the attacker's word for its own size, and it has to price the quantity that costs ~0.55 s rather than the message that costs 15–55 ms: a rate limit over never-held epochs per identity, applied to every announcement rather than only to refused ones, or a claimed height checked against what elapsed time makes possible. Shipping a guard that breaks catch-up to close a CPU cost would still be the wrong order, and §6.1 of `sync.md` has already rejected the obvious form of this one on exactly that ground, so the next attempt starts from the rejected list rather than from the idea.

**Carried out of M3, as a decision with reasons rather than a deferral, and tracked as two separate bounds rather than one milestone bullet:** the charged half's magnitudes, and the uncharged half — now priced per connection, see above, with the per-identity axis still open. Both belong to the ingress-cost class, whose second mechanism — *every refusal is priced* — is what they are missing. The charged half is bounded and tight and what remains of it is the aggregate over Sybil identities, which is what a public testnet exists to measure. The uncharged half is not an aggregate question at all and does not wait for one. §20's M3 bullet carries the argument for why neither blocks *this* milestone; being non-consensus is what makes carrying possible, and it is not the same as being small.

## I7-L2 — The window read that is fixed on reading, not on evidence ⬜ *read-verified, never observed*

`node/sync` built the difficulty window with one `BlockAt` per header — ninety-two lock acquisitions at mainnet's window, and ninety-two block bodies decoded to obtain ninety-two headers. A reorg landing between two acquisitions returns a window mixing two branches; `NextTarget` derives a target from the mixture; the honest peer whose header disagrees is scored down — and a ban also removes a peer from sync candidacy (I5-M5), so the node punishes its own race and loses a sync source for it.

Replaced with `Chain.HeadersEndingAt`, one acquisition, headers only.

**I could not make a test observe the torn read.** `TestTheDifficultyWindowIsOneSnapshot` drives real reorgs and the per-header form passes it, three attempts. Two earlier framings of the writer were tried and discarded, and both are recorded because each was a way of writing a test that *could not* fail: extending the chain only (a torn read across an extension is still a linked chain) and replacing the tip alone (depth one leaves every header below untouched). Depth three does put a parent change mid-window and the interleave is still too narrow to hit by chance.

So it stays **read-verified and never observed**, and that classification is not upgraded quietly. The wasted body decoding needs no such caveat.

## I7-L3 — The test two documents cite as measuring the flood measures its cheap half ✅ *fixed*

Found by the second adversarial pass, and it is I7-L1's pattern in the one place I would have sworn it was not: not a test that cannot fail, but a test that passes honestly while being cited for something it never touches.

`TestAUniqueInvalidHeaderFloodIsSelfLimiting` builds every header at `tip.Height+1`. Every one therefore lands in the key epoch the node already holds, and the test measures the ~55 ms case — which it says, in its own name and its own log line. The defect is not in the test. It is that `decisions/testnet-measurements` §2 cites it **twice** as the thing that "measures it and fails if the bound moves", in a paragraph whose whole subject is the *other* case: the height-varying one, at about thirty times the price, which had no test at all.

So the sentence a reader checks the claim against was true of the citation and false of the claim. That is worse than an untested property, because an untested property looks untested.

**And the assertion did not defend the number it was written for.** The guard read `sent > 16` while the comment above it, the log line below it and the prose in §2 all said five — `ScoreBanThreshold`/`ScoreInvalidMessage`. Sixteen is three times the budget: softening `ScoreInvalidMessage` to `-7` trebles what one identity buys, to fifteen, and the guard passed it. (`-6` buys seventeen and would have failed by one — the accident that stands between a slack assertion and a silent one, and worth recording because the first draft of this sentence used `-6` and was wrong about it.) Both tests now **derive** the budget from the two constants instead of restating it, so the assertion cannot drift from the comment beside it.

Fixed by writing the missing half — `TestAHeightVaryingFloodIsBoundedInEpochsToo`, which walks the key schedule so each header selects an epoch the engine must build, and reports 5 headers forcing 5 never-held epochs. **The first draft of it forced four, and the reason is worth more than the test.** It stepped by `RandomXKeyInterval` from `tip.Height+1`, on the reasoning that `SeedEpochFor` divides by the interval so one interval apart is one epoch apart. It does not: `SeedEpochFor` is `(height - RandomXKeyLag) / RandomXKeyInterval`, so the lag *shifts* the boundary and on devnet heights 1 and 65 both land in epoch 0 — which is also the epoch the node's own tip is in, so two of the five messages bought a cache the node already held and one of the four counted was never forced at all. Left alone it would have published ~20× where the attacker gets ~30×: an instrument reporting a *weaker* attack than the one available, in the entry that exists because an instrument reported the wrong thing. The heights are now the first height of each epoch, the count excludes any key the node already holds, and the assertion is an equality against the scoring budget rather than a ceiling under it. Mutation-checked in three directions, control passing: reverting to the interval step fails on *"one of the epochs charged for is the epoch this node's own tip is in"*, removing that guard fails on *"forced only 4 never-held epochs against a budget of 5"*, and removing the scoring lets one identity force **500** and fails on the ban.

**The lesson is about citations rather than tests.** This project mutation-checks its instruments and does not check the sentences that cite them. A document is an instrument too: §2 reported a bound it had not measured, in the voice of a test that had.

## I7-L4 — The two paths that swallow the error `hashRaw` panics on ✅ *counted*, ⬜ *not yet visible*

Found by the second adversarial pass. `keyedFor` returns the same error to three callers and they treat it three ways, and only two of the three are written down anywhere.

`hashRaw` **panics**: a work verdict this node cannot compute is not a verdict, and answering anyway is consensus-fatal. `Prefetch` and `MineOn` take the identical error from the identical call and carry on, and both are right to — a warm that did not land only means the later real hash pays the build it was meant to save, and a miner without a dataset mines light rather than not at all (`TestLightAndFastAgree` is why that is a slowdown and not a divergence).

The asymmetry is deliberate. What it costs is that both silent paths degrade under exactly the memory pressure that will make the next verify panic, so the first symptom anyone meets is the panic, with the minutes of declining prefetches that predicted it recorded nowhere. Nothing else in the package can see them: the table stays bounded, no hash blocks, no verdict changes, and the node simply gets slower — the same blind spot `destroyed` exists for.

`warmFailed` counts them — strictly, it counts *observations* of them: `keyedFor` hands the same error to every goroutine waiting on the same entry, so one failed allocation three prefetches were waiting for counts three, which measures lost warming rather than failed allocations. And **that is all it does, which this entry says rather than implies.** It is package-internal. No log line carries it, no `/metrics` field reports it and no RPC exposes it, so an operator is exactly as blind as before; what has changed is that the quantity now exists for something to read. Making it reach an operator is the observability gap — *"no log, no metric, no RPC field"* for this engine's internals as a class — and it is that work rather than this counter. Recording the counter as though it had closed the operator gap would be I7-L3's defect in the entry that files it.

Its non-zero case has **no test**, because nothing in this package can force a 256 MiB allocation to fail. The zero case is asserted (`TestPrefetchReturnsItsReference`), and that assertion is weak by construction — it catches a counter that fires on the happy path, and a counter never incremented at all would pass it just as well. Nor does the counter see the commoner way a warm fails to pay off: one that BUILT and was evicted before the real hash arrived, which is no error on any path and is governed by the LRU bound instead. Classified as I7-L2 classifies its own: read-verified, never observed.

## I7-C4 — A mining node sealed 1112 blocks under the next epoch's key, and nothing local noticed ✅ *fixed*

Found by running the public testnet parameter set on a VPS — not by a test — and reproduced on a second machine and a second architecture.

**The symptom.** About a minute after the chain passed height `randomx_key_lag`, a mining node began producing blocks that every other node rejects, permanently. On the testnet VPS heights 1–69 are valid and **70–1181 are invalid**: 1112 blocks, every one of them. The producing node's `/status`, `/network`, `/metrics` and block log all looked healthy throughout, and the explorer indexed all 1181 blocks with `roots_agree: true` — because it replays the *fold*, and the fold never evaluates work. The only visible failure was on somebody else's machine: `sync: a header does not meet its declared target`. A verifying node was unaffected and was the thing that detected it.

**The mechanism.** There is one ~2 GiB dataset. `build()` filled it for whichever key it happened to be initialising, and every VM in the key table had been created with `FULL_MEM`, so they all read that one buffer. **Initialising any second key therefore repointed hashing for the first**, with nobody having passed anything wrong: the miner handed in the correct key, the rule handed in the correct key, and the engine answered from the wrong data. Blocks sealed *during* a refill satisfied their target under neither key; blocks sealed after it satisfied it under the next epoch's.

`prefetchLoop` supplied the second key on a timer, and far earlier than anyone reading it would think. `next := height + RandomXKeyInterval` reads as "one interval ahead"; because `SeedEpochFor` shifts the boundary forward by the lag, it crosses into the next epoch as soon as the chain reaches height **`lag`** — 64 on mainnet and on the testnet both. So a node one minute old, 64 blocks in, warmed a key nothing would need for another 512 blocks (2048 on mainnet), and the engine took the miner with it.

**Three things were wrong, and any one of them alone would have kept this off a chain.**

1. **The dataset was in the key table.** It is now outside it: verification runs light out of each key's own 256 MiB cache, the dataset holds exactly one key, and `MineOn` — announced by `pow.NewSolver`, so a miner gets it by mining — is its only writer. A stale binding can now cost speed and nothing else, because light and fast compute the same function. That property was already asserted (`TestLightAndFastAgree`) and is now load-bearing.
2. **The prefetch warmed an epoch a full interval early.** It now asks for `height + RandomXKeyLag`: the next epoch's key over exactly the last `lag` blocks before the boundary, which is the window in which the next block might be the one that needs it.

   **And a second mismatch under that one, in the units.** `lag` is a distance in **blocks**; `prefetchLoop`'s period is a distance in **seconds**; nothing related them. Where the window is shorter than the period the loop can step over it and the boundary is crossed with nothing warmed. I7-M2's own end-to-end run was on such a set — a devnet-sized RandomX schedule, `interval` 64, `lag` 8, 5 s blocks, so a 40 s window against a 60 s period — and its own log shows the miss: the first boundary paid a 14 s pause for a cache nothing had warmed, the second paid 9 s for one that had.

   The repair is in the **rate**, not the distance, and the first attempt got that backwards. Widening the lead until three asks fit works on paper and is wrong twice: the lag is the slack the schedule itself defines, so `height + lag` says exactly what it means, and a wider lead only holds one of the engine's two key-table slots for longer. Worse, a widened lead has to be capped at one interval — and on every parameter set where `interval × target_block_seconds < 3 × period` the cap wins and the guarantee it was added for silently does not hold. A sweep of 648 `Validate`-accepted `(interval, lag, target_block_seconds)` combinations found **120 of them, 18.5%,** in exactly that state. `prefetchPeriodFor` instead asks often enough for the window the schedule already has, which is a property of the arithmetic rather than of the three networks somebody listed, and the test sweeps rather than lists.

   Mainnet and the public testnet reach none of this: 64 blocks of lag at 30 s is a 32-minute window, so the 60 s period already fits 32 asks.
3. **Nothing re-checked the work of a block this node mined itself.** `MineOneWhile` now runs `pow.CheckWork` on the sealed header between `SealWhile` and `Chain.Apply` — one hash against a block that cost thousands — and refuses with `ErrSealDoesNotVerify`. It does not catch a uniformly wrong engine, since `Try` and `CheckWork` both go through `Engine.Hash`; it catches an engine whose answer *moves* between the seal and the check, which is the first poisoned block of the 1112 and the one that ends the run instead of starting it.

**What the existing tests could not see, and why.** `TestTheSolverAgreesWithCheckWork` exists precisely to catch "a miner producing headers its own network rejects", and it cannot see this: both sides were correct, both asked the same engine, and the engine answered for the wrong key. `TestLightAndFastAgree` used one key. `TestConcurrentHashingIsSafe` used two keys and no dataset. **Nothing in the suite ever held a dataset and a second key at the same time** — I7-H4's lesson in a different room, where the gap was the third key and here it is the second key *plus* full memory.

**The generalisable lesson, and it is about an interface.** `pow.Engine.Hash` takes the key as a parameter, and its comment says why in as many words: an engine that held its own key "would make the digest depend on the order calls arrive in, which for a value shared between the miner, the gossip path and the sync path is a data race wearing an interface's clothes." The parameter was honoured at the interface and betrayed one layer beneath it. **A signature that forbids hidden state does not remove hidden state; it only removes the place a reader would look for it.**

## I7-H5 — RandomX's W^X switch is per-thread, and a Go program does not pick its threads ✅ *fixed*

Found by the tests written for I7-C4. `TestTheDatasetFollowsTheMiner` died with `SIGBUS ... signal arrived during cgo execution` on the third dataset rebuild of a full-suite run, with the fault address equal to the program counter — an *instruction fetch* from a page the thread was not allowed to execute.

On macOS (`USE_PTHREAD_JIT_WP`) RandomX allocates its code buffers with `MAP_JIT`, where W^X is `pthread_jit_write_protect_np`: **a per-thread mode, not a page permission**. Two facts meet.

- `allocMemoryPages` ends by putting the calling thread into WRITE mode, so the compiler can fill the buffer it just returned. Nothing puts it back. Every `randomx_create_vm` and every `randomx_alloc_cache` leaves its thread that way.
- Every hashing path sets EXECUTE mode itself before running code — `CompiledVm::run` does it under `RANDOMX_FLAG_SECURE`. **`randomx_init_dataset` does not**, and it executes the JIT-compiled dataset-init function.

So a thread left in write mode cannot fill a dataset. In C that is nearly unreachable: a program fills the dataset on threads it made for the purpose. In Go the fill workers get whatever OS threads the runtime has lying around.

**Which calls actually leave a thread poisoned is narrower than "anything that touched RandomX", and that distinction is the one this entry got wrong at first.** `randomx_init_cache` ends in `JitCompiler::enableExecution` (`dataset.cpp`), and so does `CompiledLightVm::setCache` under `RANDOMX_FLAG_SECURE`, so a thread that built a key-table entry ends *executable*. The two that end in write mode are a `randomx_create_vm` over a **dataset** — `CompiledVm` has no cache to set, so nothing follows the `JitCompiler` constructor's `allocMemoryPages` — and a `randomx_alloc_cache` whose goroutine migrates to another thread before `randomx_init_cache` runs. That is why the poisoned threads are few, why the crash showed up once in hundreds of fills, and why the first attempt at a regression test for it **passed with the guard removed**: it let `MineOn` build the cache on the pinned thread, and `setCache` had put that thread back into execute mode before the fill ever started.

**Latent before this change and rare; the I7-C4 fix made it routine.** The fill used to sit immediately after `randomx_init_cache` in `build()`, so the *calling* thread was in execute mode and any worker that landed on it was safe. Moving the fill into `MineOn` moved it next to `New`'s full-memory VM creation instead — the one loop that reliably leaves a thread unable to execute.

Fixed on the executing side, in a `zycord_init_dataset` shim: set execute mode, then fill, **in one cgo call** — the only construct that pins a goroutine to a thread for the duration. Setting the mode after each allocation instead would leave the invariant one unwrapped upstream call away from false, and a Go worker cannot know in advance where it will run.

**Observed once in the wild, then reproduced deterministically — and the second half is a correction of the first.** The fix landed saying "removing the guard and re-running the same tests does not bring the SIGBUS back", classified honestly as unreproducible under I7-L2's rule. That was true of the tests as written and false of the defect. A test cannot control which OS thread the Go runtime hands a fill worker; it can control **its own**. Three things make it certain:

- `runtime.LockOSThread` pins the test goroutine;
- the engine is built **on that thread**, and it is `New`'s fast-VM loop that poisons it. Not everything does: `randomx_init_cache` ends in `enableExecution` unconditionally, and so does `CompiledLightVm::setCache` under `RANDOMX_FLAG_SECURE` — which `randomx_get_flags` sets on every platform that needs W^X — so a thread that built a key-table entry ends *executable*. A `randomx_create_vm` over a **dataset** does not: `CompiledVm` has no cache to set, so nothing follows the `JitCompiler` constructor's `allocMemoryPages`;
- `initDataset` takes its first share on the calling goroutine rather than spawning a worker for every share and idling, so the fill lands on the pinned thread. The cache is warmed through `Prefetch`, off that thread, so nothing rebuilds it back into execute mode in between.

That is `TestAFillSurvivesTheThreadThatCreatedTheVMs`. With the `pthread_jit_write_protect_np` call removed from `zycord_init_dataset` it is `SIGBUS ... sigcode=1 addr=<PC>`, `[syscall, locked to thread]`, every run, on darwin/arm64 (go1.26.2, macOS 15). With the guard it passes. On linux/amd64 it cannot fail — there is no `MAP_JIT` and the guard compiles to nothing — and it still asserts the same sentence: a fill completes on the thread that created the virtual machines.

**The lesson is the one worth keeping.** "Not reproducible" was a statement about the harness, offered as a statement about the defect. The mechanism was read out of four lines of `virtual_memory.c` and was never in doubt; what was missing was the one degree of freedom the test already had.

It is not the shutdown crash reported alongside I7-C4; that one is a use-after-free on shutdown, and `Close` now takes the dataset lock every hasher holds, so a release waits for the hashes already inside. They are the same family only in the sense that matters here: **C-side state whose validity depends on which thread arrives, in a language whose whole proposition is that you do not think about that.**

## I7-H6 — One signal, five receivers: `zycordd` ignored `SIGTERM` four times in five ✅ *fixed*

Found while checking the one thing I7-M2 declined to claim — that the shutdown `SIGSEGV` reported alongside I7-C4 is closed as a side effect of `Close` taking the dataset lock. It is; and on the way to measuring it, the node turned out not to shut down at all most of the time.

**The mechanism is one sentence about Go.** `signal.Notify` writes each signal to a channel, and **a channel is a queue, not a broadcast**: the value goes to exactly one receiver. `cmd/zycordd` handed the same `chan os.Signal` to five places that all wanted to know — `main`, `mineLoop`, the abandon predicate inside it, `prefetchLoop` and `heartbeat` — so a `SIGTERM` woke one of the five and the other four continued. Whether the process exited depended entirely on which one won the receive.

**Measured, five runs, `zycordd --devnet --mine`, `SIGTERM` at six seconds, fifteen seconds to exit: one exited, four kept producing blocks** and had to be `SIGKILL`ed. After the fix, eight of eight exited, each logging `shutting down` exactly once. `stopOnSignal` turns the one delivered signal into a closed channel, which every receiver sees and none consumes.

It is also the sentence to re-read in that report: *"the miner also stopped on SIGTERM without the SIGSEGV, once."* The word doing the work there is **once**, and it was reporting this defect rather than the absence of the other one.

**And the other one is now claimed.** `Close` takes the dataset lock every hasher holds for read, so a release waits for the calls already inside instead of freeing ~2 GiB under them. Measured on a RandomX devnet (`spec/params.devnet.json` with `pow_engine` set to `randomx-v1`), ten runs, timing the signal and the exit **from `exec`** rather than timing the wait — which is the version of this experiment that can tell the two hypotheses apart:

| `SIGTERM` at | 1.08 | 1.08 | 2.13 | 2.08 | 3.14 | 3.09 | 4.14 | 4.07 | 5.12 | 5.09 |
|---|---|---|---|---|---|---|---|---|---|---|
| **exits at** | 5.57 | 5.84 | 5.56 | 5.72 | 5.64 | 5.92 | 6.64 | 6.12 | 5.81 | 5.99 |

The **exit instant does not move** — 5.56 to 6.64 s, a spread that is the fill's own run-to-run variation — while the wait falls from 4.5 s to 0.7 s. A release racing the hashes exits promptly on every row; one waiting for a fixed event exits at that event, and the second row is that event. No `SIGSEGV` in any run.

*(An earlier draft of this entry reported the WAIT times — 6.0/3.5/2.7/1.6/1.3 s — and called them "the fill's remainder and nothing else". They were not: `t + wait` came out anywhere between 5.5 and 7.0 s, which no single fill length explains. The measurement was fine and the frame was wrong, and the frame is the part a reader checks. Timing from `exec` fixes it, because the claim is about a fixed instant and only that measurement can see one.)*

A stop that lands during a key change costs that wait, and `docs/RUNNING.md` now says so — with the escape: the first signal is handed back to the operating system with `signal.Stop`, so a second `^C` kills the process at once (exit at 1.8 s, `rc=143`) instead of vanishing. Without that call `signal.Notify` stays registered for the life of the process and every later signal did nothing at all, which is a poor thing to discover during the one pause in which an operator reaches for it.

**The generalisable lesson is a small one and it has teeth.** Five receivers on one channel is not a concurrency subtlety; it is the documented semantics, read past because the code *looked* like a broadcast. What made it survive is that the failure is invisible from inside: the node that ignores the signal logs nothing, and the operator who presses `^C` twice never learns that the first one did nothing.
