# Zycord — Implementation Findings I4

**Scope:** the M2 completion batch and the M3 gate — headers-first sync and its driver, crash-atomic reorgs (R4-M1), the orphan pool bounds (R4-H1), the chaos soak against real processes, and the four §1 follow-ups.

**Persona:** the implementer who no longer trusts the test suite. M0 asked whether the spec survives a compiler; M1, whether the node survives an operating system; M2, whether the network survives other participants. M3's question is narrower and more uncomfortable: **whether the things that report success are measuring anything.** Two of this milestone's three most serious findings were green tests and a green tool.

---

## HIGH

### I4-H1 — `chain.Chain` had no lock, and `-race` said it was fine ✅ *found by the chaos soak*

**Problem.** The chain holds consensus state, tip and height. A running node touches it from the miner, from one goroutine per peer, from the sync driver and from every RPC request — with no synchronisation at all.

This is not a stale-read bug. The miner's `Assemble` read the base fees, then computed the epoch state root; a gossiped block landing between those two reads produced a header committing to a root derived from **a mixture of two chains**. No fold anywhere reproduces such a root, so the block is invalid on every node including its author.

Three things made it much worse than one bad block. State roots are checked only at epoch boundaries, so detection is dozens of blocks late. The error names height 64 when nothing was wrong at height 64. And it needs real concurrency to appear at all.

**Why it survived the whole suite.** `go test -race ./...` passed cleanly, always, everywhere — because every test drove the chain from a single goroutine. The race detector observes actual memory accesses; concurrency no test creates is invisible to it, and it reports that invisibility as success. **We read a passing tool as evidence and it was evidence of nothing.**

**Fix.** An `RWMutex` guarding state, height and tip *together* — one value in three fields. The accessor returning `*state.State` was **removed** rather than locked, since no lock inside an accessor protects the pointer after it returns; it is replaced by `Read(fn)` (callback under the read lock, making the safe window syntactic) and `Snapshot()` (a detached clone for callers that hold state across long work). The miner assembles against a snapshot and `Apply` re-checks the parent under the write lock: **optimistic assembly, validated commit**. Removing rather than deprecating was deliberate — the compiler then forces every call site to be revisited, which is the one review step that cannot be skipped.

Full write-up, including the audit of the other three concurrent surfaces: [concurrency.md](concurrency.md). `make ci` now runs `make race`.

### I4-H2 — The sync package was complete, tested, and driven by nothing ✅ *found by the chaos soak*

**Problem.** `node/sync` validates header chains against the difficulty rule, fetches bodies only along a winning chain, and has its own test suite including a forged-target adversary. Nothing called it.

The consequence is not slow sync, it is **no sync**. A node learns only about blocks gossiped after it connected: a fresh node stays at height zero forever, and two nodes that diverged never fetch the ancestors they are missing, so a healed network stays forked. The soak's fourth node sat at height 0 for the entire run with a log four lines long.

Every piece worked. Nothing connected them, and no unit test can see that, because a unit test's subject is a piece.

**Fix.** A sync driver in `p2p.Node`: peers' advertised heights are tracked from the handshake *and refreshed from every block announcement* (a handshake is one sample taken when the connection opened, and connections outlive it by hours), and a loop syncs from whichever peer claims the most height. Height is the trigger and work is the verdict — using work as the trigger would be circular, since verifying it needs the headers the node does not have yet.

Sync runs on a **dedicated connection** rather than sharing the gossip loop. Request/response interleaved with unsolicited gossip needs correlation ids and a state machine; a separate connection needs neither, and costs one socket per round.

*Amended.* The two paragraphs above describe the driver as it was built, and the mechanism has moved twice since — neither a defect found here, both this fix being overtaken.

**Selection is no longer by claimed height.** It is least-recently-tried first, with height breaking ties only among equally-stale candidates, because an argmax over unverified claims is a starvation vector: a single peer saying it is at height one billion is the maximum on every tick, forever, and the honest peer holding the real chain is never asked. The replacement landed with the R5-M1 sync analysis — `node/p2p/syncdriver.go:432-438` for why the candidate list is returned unranked, `:501-512` for the rule that replaced the ranking, which is the same doc comment that change wrote. A later change altered the *seeding* of that rotation, not the ranking: a candidate first seen on a given round takes a share of the rotation rather than the front of it.

**The dedicated connection is no longer unconditional.** A peer advertising no listen address cannot be dialled, so sync against it runs over the gossip connection that peer opened — and that path pays exactly the state machine *this fix declined*: one outstanding request per connection, and a frame claimed only when it could answer it (the dispatch in `syncOnce`, `node/p2p/syncdriver.go:576-583`; `syncOverGossip` at `:1301`; `headersAnswer` and `chunkAnswers` at `:1465` and `:1482`). The same premise is retracted in [spec/wire.md §12](../spec/wire.md).

The finding itself is left as it was written. A finding edited to match the tree it describes stops being evidence of what the review actually found, which is the whole of what a review record is for; what it owed a reader is the link it did not carry, written once rather than re-swept on every behaviour change ([CONTRIBUTING.md](../../CONTRIBUTING.md), "Node zone"). Full write-up of the adversary this driver faces, and of the selection rule that replaced the one above: [sync.md §4](sync.md).

### I4-H3 — The soak converged one block short of the only check that mattered ✅

**Problem.** After I4-H1 was fixed, the four-minute soak passed: four nodes, one chain, one tip, one state root. It had converged at **height 63**, against devnet's epoch length of **64**.

The epoch state root is the only mechanism that detects two nodes agreeing on a chain while holding different state. That run never reached one. Neither did the four-minute run *before* the fix — it failed for a different reason and its state-root error came from a node that had synced further. And the 25-second default run reaches height 11, so in normal CI the check had never once executed.

A green soak was standing for a test that was switched off.

**Fix.** The soak runs on its own parameter set with `epoch_length: 8`, so the check runs repeatedly inside the default 25 seconds. `assertSoakCrossedABoundary` fails the run outright if it did not reach a boundary, with a message that says so rather than letting the result stand. A different parameter set is a different genesis is a different network id (R3-1), so soak nodes cannot reach a devnet node — correct, and free.

The guard was then mutated to prove it fires. The first attempt did not: the boundary requirement was *also* encoded in the convergence loop, so a too-short soak failed as "did not converge" and the guard was unreachable. One requirement, one place — the convergence loop no longer knows about epochs.

`assertSoakCrossedABoundary` is still the guard, and what it enforces has since stopped being a property of one test: the release checklist gates a tag on the soak having crossed at least one epoch boundary, "a run that did neither proves much less than it appears to" ([RELEASE.md §8](../RELEASE.md)).

## MEDIUM

### I4-M1 — The reorg path had never crossed an epoch boundary ✅

`TestReorgAcrossEpochBoundary` exercises `Rollback` across a boundary. Nothing exercised `ConsiderBranch` across one — which is the path every real reorg and every sync takes — because the branch builder `buildBranch` **refuses** to cross a boundary, with a `t.Fatalf` explaining that a hand-built header cannot produce a folded state root.

That refusal was correct and it made the gap invisible: the helper's limitation read as a note about the helper. `TestConsiderBranchAcrossEpochBoundary` now mines the branch on a second node so its roots are real, and asserts the reorging node lands on the branch's state root exactly, in memory and on disk. It passed on the first run — the path was correct — but "correct and untested" and "correct and tested" are different claims and only one of them was true.

That test is still live, and it is catalogued with the rest of the consensus-state coverage in [concurrency.md §7](concurrency.md).

### I4-M2 — The soak was routing around its own chaos ✅

Nodes advertised the address they bound. The soak put a chaos proxy in front of each node and bootstrapped through the proxies — but peer exchange then propagated the *direct* addresses, so within a few rounds most connections bypassed the proxies entirely. The test was applying latency, loss and partitions to a shrinking fraction of the traffic while reporting that it had applied them to all of it.

The fix is a real feature rather than a test fixture: `--advertise`, which is what any node behind a forwarded port, a proxy or a container actually needs — the address peers can reach is routinely not the one the process binds. The soak binds the real port and advertises the proxy.

`--advertise` outlived the fixture that motivated it and is normative now: [spec/wire.md §4](../spec/wire.md) requires an implementation to provide a way to advertise an address different from the bind address, and to advertise empty when the node accepts no inbound connections.

### I4-M3 — Losing a mining race was logged as a failure ✅

`MineOne` assembles, seals, then applies. A gossiped block arriving in between makes `Apply` fail with `ErrWrongParent`. On a live network every miner loses this race constantly, and the node logged each one as `mining: chain: block does not extend the tip`. A node reporting healthy competition as a fault is a node whose logs nobody can read during an incident — and the noise hid the state-root errors underneath it.

Now `ErrStaleTemplate`, distinguished from real errors, and the mine loop rebuilds immediately on the new tip instead of idling out the interval.

`ErrStaleTemplate` is live and it is the visible half of the optimistic-assembly/validated-commit rule I4-H1's lock created, so [concurrency.md §5](concurrency.md) is what owns it now.

### I4-M4 — A too-permissive orphan pool prices a victim's memory (R4-H1) ✅

Blocks that do not attach cannot have their declared target checked, because the difficulty rule needs the preceding window and an orphan by definition lacks it. An attacker declares a trivial target, produces structurally-valid blocks at negligible cost, and fills the pool; declared accumulated work is forgeable by the same route, so work-based eviction does not close it.

Bounded three ways — block count, total bytes, and height distance from the tip — plus a target-plausibility ceiling derived from the tip's target and the claimed distance, with eviction by height distance. The real answer is headers-first, which removes the need to hold unverifiable blocks at all; the bounds are what makes the orphan pool safe as an *optimisation* rather than a liability.

The bounds are live and they are normative rather than this document's to state: [spec/wire.md §9](../spec/wire.md) requires an orphan pool to be bounded by count, by total bytes and by height distance from the tip, and to treat no declared work as meaningful; §10.3 prices the refusal as `Budgeted` against R4-H1.

## LOW / NOTES

- **I4-L1 — Peer keys are derived from nothing.** `ed25519.GenerateKey(crypto/rand)`, no KDF, no shared seed, no domain-separation tag — because there is no derivation to separate. Worth stating explicitly precisely because it is invisible in the code: nothing says "do not derive this from the wallet", it simply does not. The node process holds no wallet key at all (M1-G4), so there would be nothing to derive from. ✅
- **I4-L2 — The peer key is ephemeral, and the cost is real.** Regenerated every start, never written to disk. Sessions cannot be correlated by key, which is the point; peer *reputation* cannot survive a restart either, which is the price. Rotation is a restart. If a future release persists it for long-lived reputation, that trade must be made deliberately. ✅
- **I4-L3 — The gossip scale ladder is written down.** Rung 0 (flood, where the implementation is), rung 1 (announce-request for certificate bodies — designed, not built, ~25× off the dominant term), rung 2 (degree management), rung 3 (a mesh, which is where the libp2p reopen condition should be revisited rather than extended). A ceiling with no stated way past it is a trap. [networking.md §9](../decisions/networking.md) ✅
- **I4-L4 — Reachability is now measurable.** `/network` reports listening, inbound and outbound counts. `listening: true, inbound: 0` after a few minutes means the port is not actually reachable — which looks healthy in every other view. The aggregate is the first reopen condition in the networking decision, and it is now measured rather than assumed. ✅
- **I4-L5 — The wire protocol has its own specification.** [spec/wire.md](../spec/wire.md), written so a second implementation can be built from it alone. It carries the inverted authority rule: where it and the code disagree, **the document is wrong** — consensus is defined by the spec, the network by what peers accept. `ARCHITECTURE.md` §13 still described a libp2p host with gossipsub topics; corrected. ✅
- **I4-L6 — The mempool's per-sender quota is not the Sybil defence.** Identities are free; the quota bounds one identity. The defence is the **deposit screen against the current tip**, which in Era 0 denominates the cost of flooding in proof of work. Now stated in [mempool.md §2.5](mempool.md) and pinned by a test whose mutation shows 90 free identities entering the pool without it. ✅
- **I4-L7 — A storage test asserted a property the store never had.** The first version checked that two `Get` calls for two keys written by one batch always agree. It failed, and the store was right: every *single* read is atomic against a commit, but two calls are two reads. Cross-call consistency is the caller's job, which is what `chain.Read` is for. Recorded because it is the same rule from the other side — "this failed" is not "this is broken". ✅

## Confidence

Flagged for the R5 reader. The pattern in this milestone is different from earlier ones and worth naming: the unforced choices are no longer the main risk. **The main risk is instruments that report success without measuring.**

- **Three green things were meaningless.** `-race` across the whole suite (single-goroutine tests), the chaos soak (never reached an epoch boundary), and `buildBranch`'s refusal to cross a boundary (read as a helper limitation, was a coverage hole). Each was visible for the asking and none of them was asked. I do not believe this list is complete, and I have no method for finding the rest of it beyond continuing to ask "what would this look like if it were measuring nothing?"
- **The chain lock is coarse and deliberately so.** Every cell read takes the lock every block application holds. At Era 0 volumes this is irrelevant and an obviously-correct lock beats a fast one, but it is a scaling limit, and it should be measured on the M3 testnet rather than optimised on instinct.
- **`Read` has a discipline the compiler cannot enforce.** The state pointer must not escape the callback, and the callback must not re-enter the chain (the lock is not reentrant — it would deadlock). Both are documented at the definition. A future change that violates the first re-creates I4-H1 exactly.
- **The sync driver's peer selection is a heuristic with no adversarial analysis.** It syncs from whichever peer claims the greatest height. A peer that lies about its height wastes one round trip and is scored down, and everything it says is re-derived — so the damage is bounded — but "bounded" is not the same as "modelled", and nobody has thought about a swarm that lies in a coordinated way to steer whom a node talks to. *Amended, and amended rather than deleted: this is a forward list, so a stale still-open item is a wrong instruction rather than a dated one.* The analysis this entry asks for exists — [sync.md](sync.md), written against the coordinated liar it names — and it found something stronger than an unmodelled heuristic: ranking by an unverifiable claim is a **starvation** vector, so the damage was not bounded in the direction that mattered. Selection has been least-recently-tried rotation since the change that created [sync.md](sync.md), one day after this document was written and never reflected here (`node/p2p/syncdriver.go:501-512`) — which yields *no peer is asked twice until every other candidate has been asked once* without deciding whether any claim is true. The swarm question is answered as free candidacy and rotation dilution in [sync.md §6.1](sync.md); what is still open is its §7.
- **The soak's parameters are invented.** 15 ms latency, 35 ms jitter, 0.1% drop, 0.05% sever, three miners, one periphery node, a 2-second chaos tick. They produce a network that breaks and heals often enough to be interesting, which is the only justification. Nothing here is derived from a measurement of a real network, because there is no real network yet.
- **The soak's convergence question is well-posed only because mining is stopped on all but one node afterwards.** Three miners racing produce a contested tip almost continuously, so "do all nodes agree right now" would be asking whether four processes were sampled between blocks; stopping *all* of them is wrong too, since two branches of equal work stay forked forever, correctly. One miner makes convergence a property. This is a defensible choice and it is still a choice, and it means the soak does not test convergence *under continuing contention*.
- **Nothing here has run for hours.** The longest run is minutes. The review asked for a soak run "for hours" and that has not happened; the bug found at four minutes is a direct argument that duration buys findings, and the next duration threshold is unknown.
- **Equal-work ties, peer scoring magnitudes, and `/16` diversity grouping are unchanged from I3** and remain unmodelled. They are repeated here rather than dropped, because a confidence section that only lists new doubts implies the old ones were resolved.

**Disposition.** All ✅ implemented and covered. The M3 gate — headers-first sync, validated against the difficulty rule before any body is fetched — is met and driven. Reorgs are one atomic commit and are tested across an epoch boundary. The chaos soak runs real processes over hostile sockets and asserts one chain, one tip, one state root, past a boundary, with no local invariant violation.

Named rather than left implicit: **the soak has not been run for hours**, and **`Read`'s two rules are enforced by review alone**. Both belong in front of the R5 reader before a public testnet, not after it.
