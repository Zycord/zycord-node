# Zycord — Implementation Findings I6

**Scope:** implementing whitepaper §8.1, the elastic sequential ceiling — the epoch controller, the burst valve, the cited-competing-header health signal, and the block ceilings that stopped being constants.

**Persona:** the implementer read by someone else. I5 audited its own instruments and found four that reported success while measuring nothing. This milestone kept the habit and hit its limit: **three of the four defects here were found by reading, not by running**, and the fourth was found by a second reviewer reading the same diff. The project's strongest automated guard — a second, deliberately naive fold fuzzed against the first — was structurally blind to one of them, for a reason worth naming rather than filing.

One of the four is not a bug in code at all. It is a false technical claim, written confidently, replicated into normative documentation, and used as the stated foundation of an architecture decision. No test could ever have caught it. In a repository whose credibility *is* its review trail, that is the finding that says something about the method rather than about the ceiling.

## CRITICAL

### I6-C1 — The elastic byte ceiling outgrows the frame that carries it ✅ *found by a second reviewer reading the diff*

**Problem.** §8.1 makes the sequential target `T` a function of measured demand. This implementation scaled all three block ceilings with it — certificates, sequential/parallel gas, and bytes — and clamped only the first:

```go
MaxCertsPerBlock(T) = min(genesis × T / T₀, CertListCapacity)   // clamped
BlockByteLimit(T)   =     genesis × T / T₀                       // unbounded
```

The spec text made a virtue of it: *"`BlockByteLimit(T)` has no such structural ceiling to clamp against — byte size is not merkleised — so it scales without a second bound."* That sentence is true about merkleisation and wrong about everything else. `node/p2p` frames a block as a single `KindBlock` message carrying `ssz(Block)`, and `MaxMessageBytes = 8 << 20` is enforced on send (`Frame`) and receive (`ReadFrame`) alike.

Computed with the exact integer recurrence, the crossing is at **epoch 621 — about 1.70 years**: `T = 6,717,828`, byte ceiling `8,397,285`, frame cap `8,388,608`.

**Why it is not a slow-burning edge case.** The two controllers over `T` have different fixed points, and nobody noticed because each is correct alone. §8's EIP-1559 base fee steers *applied* gas toward `T`; the epoch controller sets `T ← clamp(2·median_applied, …)`. At the fee market's own equilibrium `median ≈ T`, so `2·median ≈ 2T`, the growth clamp binds **every epoch**, and `T` rises at its maximum rate whenever the fee market is merely working. No attack, no unusual load — a healthy busy chain walks into it.

**Why it is the worst class of failure.** Not a rejected block. A block every node agrees is valid and no node can transmit: the producer holds it on its own chain, and nobody can fetch it. Consensus-frozen at genesis, unfixable afterwards by anything short of a hard fork.

**Fix.** `block_byte_capacity` (8,000,000), a static consensus bound in the same shape as `cert_list_capacity`, with `BlockByteLimit(T)` clamped to it and `Validate` requiring capacity ≥ genesis. The transport half of the pair cannot be checked from `core/` — consensus must not import the node — so `TestBlockByteCapacityFitsAFrame` in `node/p2p` is the single place the two numbers meet, and raising either now has to pass through it. `TestElasticCeilingsAreStructurallyBounded` drives 20,000 epochs of maximum growth and asserts both clamps hold, with an anti-vacuity check that growth actually reached them.

**A second bug closed itself.** `SeqGasBurst(T) = 4T` and `ParGasLimit(T)` are plain `uint64` multiplications with no overflow check. With both consumers of `T` pinned, the applied gas a block can physically hold is bounded, so `2·median` stops exceeding `T` and growth halts far below anything that could overflow. `T` is self-limiting once its consumers are — but only once they are.

The clamp is live and the pairing test is still the single place the two numbers meet, but *which* two numbers has changed and [decisions/capacity-eras.md](../decisions/capacity-eras.md) owns that now. Blocks travel as chunks ([spec/wire.md §5.1](../spec/wire.md)), so `MaxMessageBytes` bounds a message and `MaxBlockChunks × BlockChunkBytes` bounds a block; the pairing test is `TestBlockByteCapacityFitsChunkedTransfer` rather than the `…FitsAFrame` named above. The decision that followed is the one this finding could not reach: the byte capacity was load-bearing in the wrong layer, so raising consensus capacity required a transport change, and each structural capacity is now classified by what re-pinning it costs.

## HIGH

### I6-H1 — The burst forfeiture was value the conservation identity lost ✅ *found by self-review, invisible to the differential*

**Problem.** The burst valve reduces what the block pays its producer when it runs over the soft ceiling — the subsidy share alone when this was written, the subsidy share plus the block's fees since the base was re-denominated:

```go
producer = producer.SatSub(forfeit)   // and nothing else
```

Conservation in this codebase is stated against the **schedule**, not against what was actually credited:

```
supply_after == supply_before + Emission(height) − burned
```

`Emission(height)` is what §14.2's curve says the height pays. A forfeit that reduced the credit without registering in `res.Burned` therefore left exactly its own value unaccounted for on every bursting block. Reproduced: **226,333,333 drops** missing, matching the forfeit to the unit.

The precedent was already in the same function and was not followed. I1-M2's burned coinbase — a coinbase owed to an address that burned its authority — is "a permanent shortfall against `C`" and *is* added to `res.Burned`. A forfeited subsidy is the same shape and needed the same line.

**Why neither guard saw it.** Two independent reasons, and the second is the interesting one:

- `TestConservation` builds its block under stock devnet parameters, where nothing comes near `2T`. The identity was checked, thoroughly, on blocks that never burst.
- **`sim/refold` mirrored the omission.** The differential fold exists to disagree with `core/fold`; here it agreed, because the same author wrote the same missing line into both within an hour of each other. Two implementations that share a *trick* share its bugs — the package doc says exactly this — and it turns out two implementations that share an *author's blind spot* share that too. The fuzzer ran clean over eight seeds and a long run, and was correct to: both sides computed the same wrong number.

**Fix.** The forfeit is added to `res.Burned` in both folds. `TestBurstForfeitureIsConserved` checks the identity against a block that actually bursts, with an anti-vacuity guard that the forfeit is non-zero. `Result.Burned`'s doc comment now says why a shortfall against the schedule and a burn of paid-out value have to be accounted identically.

**What it costs to state honestly:** a differential is a guard against *implementation* divergence, never against a shared misreading of the specification. It answers "do these two agree" and never "are they both right". Nothing in this repository currently answers the second question except a person reading the whitepaper next to the code.

The forfeit is still burned in both folds, and the valve it belongs to is owned by [ARCHITECTURE §15](../ARCHITECTURE.md) now: the burst band is priced by F11 and invisible to F12b, so `2T` is what the fee market steers toward and `4T` is a per-block relief valve. §21 records why repricing the burst through a *second* forfeiture on miner tips was rejected, and the reason bears on this finding directly — any deterrent priced in forfeited producer revenue is bounded by what the block credits that producer, and a self-dealing proposer sets that to zero.

### I6-H2 — The benchmarks were broken and `make ci` could not tell ✅ *found by self-review*

**Problem.** `benchBlock` builds its state by hand rather than by folding block 0, seeding the protocol cells the fold expects to find:

```go
s.Set(types.SeqBaseFeeSlot(), p.InitialSeqBaseFee)
s.Set(types.ParBaseFeeSlot(), p.InitialParBaseFee)
// and, as of §8.1, the sequential target — which nothing added
```

That list grew by one and nothing updated it. An absent cell reads as zero, so every ceiling derived from `T` collapsed, and the block was rejected with:

```
fold: invalid block: 100 certificates exceeds the ceiling of 0
```

Misleading rather than subtle: the message names the certificate count, and the defect is a missing target three layers away. The block also never set `CitesRoot`.

**Why CI stayed green.** Benchmarks do not run under `go test`; they need `-bench`. `make ci` runs the full suite, the race detector, the `zcdguard` build and the differential, and none of them execute a benchmark. So the measurements **whitepaper §15 quotes as the project's central throughput claim** could not be reproduced from the tree that CI called clean, and `docs/RELEASE.md`'s requirement that "every figure traces to a benchmark in the source tree" had quietly stopped being satisfiable.

**Fix.** The seed and the root, plus a comment naming the failure mode so the next cell added to that list meets it. Repo-wide `go test -run XXX -bench . -benchtime 1x` now passes; the fold's throughput is unchanged by §8.1 (~838k–917k slot-ops/s on the review machine, against the 960k the paper reports from its own hardware).

**And the instrument this asked for is now built.** `make bench-smoke` runs one iteration of every benchmark in the tree and is part of `make ci`. It is a smoke check, not a measurement: it answers "do these still execute", which is the question a green CI was silently answering wrong. Mutation-proven in the manner this repository expects — with the missing seed removed the target fails, with it restored it passes — because a guard nobody watched fail is a guard nobody knows works.

`bench-smoke` is still in `make ci`, and the requirement it defends is owned by [RELEASE.md §8](../RELEASE.md): every figure in whitepaper §15 traces to a named benchmark in the tagged tree, each measured in its own process — the checklist has since added that last clause, because one transcript read top to bottom publishes the later benchmarks slower than they are.

## MEDIUM

### I6-M1 — A false technical claim, written confidently, replicated into normative documentation ✅ *found by a second reviewer*

**Problem.** Citation proof-of-work is checked in `node/`, not in the fold. The reason given, in three places:

> `core/fold` cannot import a `pow.Engine` without inverting the dependency graph every other package respects (P4).

This is false, and one command settles it:

```
$ go list -deps zycord/core/pow | grep zycord
zycord/core/crypto/blake3   zycord/core/crypto   zycord/core/u256
zycord/core/params          zycord/core/ssz      zycord/core/types
```

`core/pow` imports only other `core/` packages. `core/fold → core/pow` creates no cycle and violates no principle. The claim was invented, stated as fact, and then used as the justification for where a consensus check lives.

It reached three files — `core/fold/blockrules.go`, `node/p2p/engine.go`, and `docs/ARCHITECTURE.md` §8 — of which the last is normative for implementers. (The first account of this finding said five files and "§8 and §12"; both were overcounts, corrected here, since a finding about imprecise confident claims should not be filed imprecisely.)

**The decision it justified was right anyway, for a reason nobody had written down.** Proof of work is memory-hard *by design* — RandomX at M3, milliseconds per evaluation — and §3's whole claim is that the one sequential stage is a loop over memory with no cryptography in it. Up to `MaxCitesPerBlock` work evaluations per block inside the fold would cost more than everything else the fold does, in the one place the design has no budget. That argument is stronger than the invented one and was available the entire time.

**Why this is the finding worth keeping.** The other three are bugs that a tool could catch with the right instrument: run benchmarks in CI; test conservation under a bursting block; clamp what scales. This one is not reachable by any test. It was a false statement about the codebase's own structure, asserted with the same confidence as the true statements around it, propagated by copy into a document that tells independent implementers what the protocol is. The only instrument that finds it is somebody checking a claim that sounded authoritative — which is the argument for the review trail existing at all, made from the inside.

**Fix.** All three corrected to the real reason. And the gap the false reason had been papering over is now closed properly: citation work is **consensus** (cited headers feed the health gate, which moves `T`), the golden vectors cannot express it — they scope the fold, and the fold checks no work at all, the block's own PoW included — so it is specified normatively in [spec/wire](../spec/wire.md) §9 rule 7, and `spec/README.md` now states what the corpus deliberately does not cover and where the rest lives. `spec/README` also no longer calls `wire.md` flatly "not consensus", which it no longer entirely is.

### I6-M2 — Two panic-ordering hazards, caught by the vector generator ✅ *found while building the corpus*

**Problem.** `ssz.Merkleize` **panics** rather than erroring on a list longer than its capacity — deliberately, because inside the consensus zone an oversized list is a caller's bug, not an input. The citation count was checked *after* `ComputeCitesRoot`, so a block carrying more citations than the capacity crashed the process instead of being rejected.

It surfaced because writing the golden vector for "too many citations" required constructing exactly that block, and the generator died. The identical ordering already existed, correctly, for certificates — `len(b.Certs) > ceiling` runs before `ComputeCertRoot` — and the new code did not copy it.

**Fix.** The count check moved ahead of the root computation in both folds. The scenario turned out to be unexpressible as a golden vector at all — the bytes cannot be produced without tripping the same panic, and `types.UnmarshalBlock` rejects an over-capacity encoding before block rules ever run — so it is `TestUnmarshalBlockRejectsTooManyCites` in `core/types` instead, pinned at the boundary that actually enforces it.

**The generalisable half:** building the vector corpus and the specification in the same pass, rather than one after the other, is what found this. A corpus written afterwards would have skipped the scenario it could not express.

## The pattern, and what the instruments could not see

Four defects. **Three were found by reading and one by a tool.** That ratio is the finding.

Ranked by what would have caught each:

| Defect | Caught by | Cheapest instrument that *would* have caught it |
|---|---|---|
| I6-C1 byte ceiling | a second reader | a test asserting every derived ceiling is bounded — now exists |
| I6-H1 conservation | self-review | conservation checked on a *bursting* block — now exists |
| I6-H2 benchmarks | self-review | `-bench . -benchtime 1x` in CI — now `make bench-smoke` |
| I6-M1 false claim | a second reader | **none** |

The differential deserves its own line, because its silence here was not a failure and should not be read as one. It compares two folds and reports divergence; it cannot report agreement on a misread specification, and I6-H1 was exactly that. Its blind spot is co-authorship: it is strongest against implementation slips and weakest against whatever the author believed wrongly while writing both sides. That is not a reason to trust it less — it is a reason to know which question it answers.

**Also fixed, and named here because the review that found them is the point:**

- **I6-C2 — the byte clamp turned both fee markets off at the terminal state.** ✅ *fixed.* Found by a third reviewer, and it is the other half of I6-C1: clamping the *derived* ceilings rather than `T` stops the partition but leaves `T` climbing until `2·median ≤ T`, i.e. `T = 2G` for `G` the most sequential gas an 8 MB block can hold. There the base-fee target is `2G` and applied gas can never exceed `G`, so a physically full block reports `applied/target = 0.50` **forever** and the base fee decays to its resting point — measured, 1000 → 15 over 3,000 permanently-full blocks. Block space then rations purely by priority tip with no burn: the permanent auction §8.1 calls unreachable, and the end of the congestion deflation §14.2 assumes. The 0.50 is exact and density-independent, because `T`'s fixed point is `2·median` by construction while the base fee's is `applied = T` — two controllers whose fixed points cannot both hold, which nobody noticed because each is correct alone. Fixed by clamping `T` itself, with `SeqGasCapacity`. The value looked at first like a genesis-frozen economic decision — picking it appears to pick an assumed gas-per-byte density — and the reviewer dissolved that: preserving the ratio the genesis parameters *already* chose (`SeqGasCapacity / SeqGasTargetGenesis == BlockByteCapacity / BlockByteLimitGenesis`) makes gas and bytes reach their walls together, and the terminal state comes out **exactly** as well calibrated as block 0. Verified as an identity rather than an approximation: `applied/target` for a physically full block is identical at genesis and at the terminal state, at every density swept. No new assumption was needed, only the one already made.

**And the fix shipped with a hole of its own, found by the same reviewer on the next pass.** `Validate` checked the pairing as `BlockByteLimit(SeqGasCapacity) == BlockByteCapacity` — the obvious form, and nearly useless, because `BlockByteLimit` *saturates* at the capacity: 20,000,000 and 100,000,000 both sailed through it, and either would have put the gas wall after the byte wall and reinstated I6-C2 exactly. The parameter's own comment said "which Validate checks rather than asserts" while the only real check lived in a test that runs against the two parameter files this project ships, never against an operator's. Fixed by moving the cross-multiplication into `Validate`. Worth recording next to I6-M1 rather than quietly: a confident false claim about the codebase, written *in the same commit that documented I6-M1*, about the very function being introduced.

**Two lessons, and the second is the one to keep.** A clamp applied to a derived quantity bounds the symptom while the controller keeps running against whatever was not clamped — that is the bug. But the review turned on something else: the first response to it was to hand the decision back as "an economic parameter someone must choose", and that was wrong. The constraint was already implicit in the parameters, and the work of finding it was mistaken for the work of deciding it. Handing back a decision that has not been reduced to its real degrees of freedom is a way of not finishing.
- **I6-M2 — the differential could not see any of it.** ✅ *fixed.* The release gate for `core/fold` never reached one line §8.1 added, and by arithmetic rather than luck: at `seq_gas_target_genesis` of 2,000,000 against devnet blocks holding a few thousand gas, `2·median` never approaches the decay floor, so the controller clamps `T` to the floor and the floor clamps to genesis — measured across five epoch boundaries, `T` unmoved, max applied gas 1,800, burst valve never armed, `cited_count` 0. Every new rule was verified only by hand-written tests written separately against each implementation, never by the one mechanism whose job is catching an error *shared* between them, which is exactly how I6-H1 survived. Closed by making the code reachable — the harness can now propose a genuine competitor of its own parent, the generator emits citations with a fault mix covering all six rules, and a dense traffic mode fixes the median that the deliberately adversarial default mix pins at zero. Four coverage counters (grew, decayed, gate-withheld, burst) assert per run that each branch actually ran. Two things this cost, both worth recording: adding citation faults to the shared generator broke the *existing* differential tests by drowning their certificate-traffic signal, caught in CI and scoped to the new run; and the first version of the counters read `T` after the block had already been applied, so it compared a value against itself and reported "never moved" for every seed.

- **I6-M3 — the corpus did not pin the lower-median convention.** ✅ *fixed.* §8 frames that convention as what stops "two conforming implementations disagreeing on the last bit of a number that gates real money" — a claim about *other* implementations, which are measured by `spec/vectors` and not by this tree's differential. Mutating `samples[(L-1)/2]` to `samples[L/2]` passed all 33 vectors. It was caught, but only by `sim/refold` reimplementing the index independently, which protects this tree against itself and an independent implementer against nothing. The cause was mechanical and is worth stating because it generalises: every controller vector seeded *one value* across the whole ring, so the two midpoint entries were equal and no convention could be distinguished. A vector that seeds half the epoch idle and half busy separates them — the lower median reads the idle half and T holds at its floor, the upper reads the busy half and T grows by T/Γ. Mutation-proven both ways. **The lesson is about vector design rather than about medians:** a scenario built from a uniform input cannot pin a rule that only fires on non-uniform input, and uniform inputs are what a generator reaches for first.

**Newly named, not fixed:**

- **The health gate ships inert.** No production path fills `Block.Cites`, so `cited_count` is permanently 0, `healthy` is always true, and growth is never withheld. Documented in §12 and gated on M5 — but I6-C1 changes its weight: the gate is the *only* mechanism §8.1 gives for keeping capacity inside what propagation carries, and `block_byte_capacity` is now the sole backstop standing between a healthy chain and the frame limit.
- **The one-block citation window is narrower than §8.1's "recent"**, and undercounts competitors exactly when propagation is slow — so the gate fails *permissive* in the regime it exists to detect, the opposite of the direction the paper asks it to lean. Recorded with the fix it would take (a windowed cited-id set in consensus state) rather than fixed, because the signal has no producer yet.
- **Two divergences from the whitepaper were open when this review ran, and both have since closed — in the direction this bullet demanded.** They were producer-only forfeiture where §8.1 then said "full-subsidy", and scaling all three ceilings where §8.1 then made only sequential gas elastic; both were deliberate and both were moved into the ARCHITECTURE header rather than left argued only in §15. The paper was then amended to match this document, ratified by the repository owner: §8.1 now says "forfeiting *producer* subsidy quadratically" with a constants list reading "producer-subsidy forfeiture at the bound", and it now states that the certificate-count and byte ceilings scale with the target too. The rule this bullet stated is why it closed and it stands unchanged: documenting a divergence does not resolve it — the paper is amended or the code changes, before the M5 freeze. *(Status and both quotations corrected since; the sentence above quoted paper text that no longer exists and described as open a finding that had been discharged.)*

**Disposition.** §8.1 is implemented, and the two defects that would have been frozen into genesis — the unbounded byte ceiling and the unaccounted forfeiture — are fixed, tested and pinned. `make ci` is green; all benchmarks are green; the vector corpus regenerates deterministically and the genesis id moved, as any consensus-root change must.

What this milestone does not get to claim is that its own process found everything. Half of what mattered came from a second reader, including the only defect that could ever have partitioned the network. The instruments were sound and the coverage was real; the gap was in what the author already believed, and the only thing that closes that gap is somebody else reading it.

## Addendum — auditing with instruments that report success

Two findings from the explorer-RPC work that belong here rather than in
CONTRIBUTING, because they are about method rather than policy. Both are the
family I4 and I5 named: **an instrument that reports success without measuring
anything.** Neither was found by a test, because neither could be.

### I6-A1 — The filter that removed the noise removed the signal

Retaining the headers of reorged-out blocks — needed so that a block leaving the
chain does not become a permanent 404 — silently changed what `chain.Header`
answers. Callers that asked it and meant *"is this on my chain?"* had been right
by accident, because a reorg used to delete the loser's header, so existence and
canonicality were the same test.

Finding them was a grep. The grep was:

```sh
grep -rn "\.Header(\|headerLocked(" --include='*.go' . | grep -v _test | grep -v "\.Header\."
```

The last filter existed to drop `w.Header().Set(...)` and struct-field accesses.
It also dropped `current.Header.ParentID` — the argument at
`node/p2p/engine.go`'s branch-assembly walk, which is the worst of the five call
sites and the one the audit therefore missed. It was found later by a reviewer
reading the diff.

Four sites were fixed, the fix was reported as complete, and the report was
wrong in a way nothing could contradict: the audit's own output was the
evidence, and the evidence had been filtered.

**The rule.** An exclusion filter in an audit is a claim that what it removes
cannot matter. Run the sweep unfiltered at least once and read the noise, or
make the filter an exclusion of *files* rather than of *lines*. The redone
sweep here returns seven hits, five of them `w.Header()`, and takes ten seconds
to read.

### I6-A2 — A mutation that does not apply looks exactly like a mutation that does not kill

The discipline this project uses to defend a test — revert the property, confirm
the test fails — has a failure mode of its own. While arming the bounded mempool
selection, the mutation was applied by a script that mis-spliced the file: the
naive implementation was inserted, the optimised one stayed live, and the file
still compiled. The test passed.

Read at face value, that says *the test does not see the property* — the exact
shape of a vacuity finding, and it was nearly reported as one. Redone cleanly,
the mutant died on the first assertion.

**The rule.** A mutation is evidence only if the mutant was actually built and
actually differs. Print the mutated region, or assert the mutant fails a test
you already know it should fail, before concluding anything from a green run. A
passing test under a mutation that never landed and a passing test under a
mutation that landed are indistinguishable from the exit code, and only one of
them is a finding.

### The shared shape

I4 found instruments that measured nothing and said "ok". I5 audited its own
instruments and found four more. These two are the next layer down: the
*procedures* used to audit and to defend can report success without having run.
A filtered grep and an unapplied mutation both produce clean output, and clean
output is what both are read as meaning.
