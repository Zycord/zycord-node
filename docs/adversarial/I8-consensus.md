# Zycord — Implementation Findings I8 (consensus)

**Scope:** the consensus rules as they stand after the rx/2 landing — the work check and the 43-byte hashing blob, the 260-byte header's malleability, `ExtraNonce` as grinding space, the seed-epoch schedule, chain-id binding, the LWMA retarget, the median-time-past and future-time rules, and the work accumulation fork choice decides by. Run against the tree as it stands with all of that in place — rx/2 at genesis, the commitment work check in force, and the wallet shipping its own node — the public testnet live on it and the parameter freeze eight days out.

**Persona:** the implementer asked to re-prove what he already believes. I7's build was lying, and the reflex that came out of it was to distrust instruments. This pass inherits a subtler version of the same problem: **the consensus rules are largely correct and extensively commented, and the comments are load-bearing evidence nobody re-derived.** `types.PoWInput` asserts "there is no header field that can reach these bytes" and cites a proof made against a 228-byte header that no longer exists. The header is 260 bytes now. A claim about a different serialization is not a claim about this one, and the distance between "true" and "still true" is the whole of this milestone.

**Nothing below is a consensus defect.** No path forges work, splits the chain, or makes an honest node reject a valid block. That is the headline and it is stated first because the freeze depends on it. What the pass produced instead is eighteen tests where there were arguments, one documentation gap that would bite a second implementer, and a clear statement of what it could not reach.

## MEDIUM

### I8-M1 — The median convention is unpinned on the windows a young chain actually uses ⚠️ *found by asking I6-M3's question of a different median*

**Problem.** `params.Validate` requires `median_time_blocks` to be **odd**, and says why: *"so the median is unambiguous"*. With an odd count `times[len(times)/2]` is the true middle element and no convention question arises.

`pow.MedianTime` does not always see `median_time_blocks` headers. It truncates:

```go
n := p.MedianTimeBlocks
if len(recent) < n {
    n = len(recent)
}
```

So for the first ten blocks of any chain — and for any caller that supplies a shorter window — the window length is whatever it is, **even lengths included**, and the validator's odd-parity guarantee does not apply to it. On an even window `times[len/2]` is the **upper** of the two middle elements.

**Why this is not a defect in this tree.** The convention is a pure function of the window, so every node running this code computes the same value from the same headers, and there is no fork. It is also the **stricter** of the two conventions — a higher median is a higher floor on the next timestamp — so the truncation cannot be used to date a block earlier than a lower-median implementation would allow. Both properties are asserted rather than argued (`TestTheMedianWindowIsEvenSizedEarlyInTheChain`).

**Why it is recorded anyway.** This is I6-M3's finding in a different controller. There, the vector corpus failed to pin the lower-median convention for the gas-target ring, and mutating `samples[(L-1)/2]` to `samples[L/2]` passed all 33 vectors because every vector seeded one value across the whole ring. The lesson drawn then was about vector design. The same question asked of *this* median gets a worse answer: the gas-target median has its convention written normatively in ARCHITECTURE §472 — *"the element at sorted index `(EpochLength−1)/2` — one real sample, never an interpolation"* — and **the median-time-past median has no such sentence anywhere.** `spec/` cannot carry it either, for the reason `PoWInput`'s reserved gap cannot be carried by a block corpus: a chain that has passed height 11 never exhibits an even window again, so no corpus of blocks distinguishes the two conventions.

A second implementer reading only the normative documents would have no way to know which element to take, would have a 50 % chance of choosing the lower, and would then **accept headers this tree rejects** for the first ten blocks of every network it launches — including its own devnets, which is exactly where a new implementation gets tested.

**Disposition.** ⚠️ Recorded, not fixed in code, because the code is right. **What it wants is one sentence in ARCHITECTURE §12 stating the convention** — the upper middle element on an even window, matching `times[len(times)/2]` — in the same place and the same voice §472 states it for the gas median. Named here rather than written into the normative doc by this pass, because a consensus sentence added during an audit should be reviewed as a consensus change and not slipped in beside its own evidence.

## LOW / NOTES

- **I8-L1 — `PoWInput`'s unreachability claim re-derived against the 260-byte header.** ✅ *re-proved.* The claim in `types.PoWInput`'s comment was proved once by exhaustive bit-flipping against a **228-byte** header. `HeaderSize` is 260 today: `PoWHash` was added and the seal resplit into two `uint32`s. `TestTheReservedBytesAreUnreachableFromA260ByteHeader` re-derives it exhaustively — all **2080** single-bit corruptions of the serialized header, each decoded and rebuilt into a blob, gap zero in every one, **zero decode failures** so the sweep's reach is the whole header rather than the part that happens to survive `UnmarshalHeader`. The test fails outright if `HeaderSize` moves, rather than adapting to it, because a proof about a 260-byte header is not a proof about a 292-byte one and the next person to widen the header should be made to re-run this rather than watch it silently re-scope. Mutation-checked two ways: leaking `byte(ExtraNonce)` into offset 32 fails on the baseline assertion; a gap byte set only when `Height & (1<<40)` is non-zero — invisible to any baseline check and to any sampled sweep — fails with *"REACHABLE: flipping bit 0 of header byte 9"*. The vacuity guard is its own test (`TestTheGapCheckWouldNotice`), since a sweep that passes and a sweep that cannot fail look identical from the outside.

- **I8-L2 — one proof of work cannot pay for two headers.** ✅ *proved.* The reserved-gap sweep shows an attacker cannot dirty the gap; it does not show that two *different* headers cannot produce the *same* blob, which is the actual work-forgery primitive — mine once, claim two block ids, spend one solution on both sides of a fork. `TestTheBlobIsInjectiveOverTheFieldsAnAttackerControls` varies every attacker-chosen field one at a time and requires each to move the 43 bytes: `Version`, `Height`, `Time`, `ParentID`, `CertRoot`, `CitesRoot`, `StateRoot`, `EmissionAddr`, `Target`, `Nonce`, `ExtraNonce`, `SeedEpoch`. `PoWHash` is the deliberate exception and is asserted in the opposite direction — it must **not** move the blob, because it is zeroed in the seed preimage, and if it ever did the seed would be a function of itself and no header could be valid at all.

- **I8-L3 — `PoWHash` is outside the blob and bound by the commitment.** ✅ *proved.* The exception above is the whole cheap-path optimisation, so it is checked rather than trusted: all **256** single-bit changes to `PoWHash` must move `blake2b(PoWInput ‖ PoWHash)`. Mutation-checked by dropping `PoWHash` from the commitment preimage, which fails with *"the digest is unbound and one solution mints many headers"*.

- **I8-L4 — grinding `ExtraNonce` buys nothing over grinding the nonce.** ✅ *measured.* `ExtraNonce` is unconstrained — `checkSeedEpoch` pins `SeedEpoch`, B7 pins `Version`, three sites pin `Target`, and **nothing pins `ExtraNonce`** — and it sits inside the seed preimage, which is what makes the question worth asking rather than dismissing. It is not a better lever than the nonce, and the property that makes the argument hold is that it produces an *independent* search space rather than a correlated one: 4096 digests walking the nonce and 4096 walking `ExtraNonce`, all distinct within each walk, **overlapping in exactly the one digest the two walks share by construction** (`Nonce=0, ExtraNonce=0`), and neither walk biased in the little-endian low word the work check reads — 1985/4096 and 2002/4096 against a mean of 2048 and a 5σ band of ±160. Mutation-checked by zeroing `ExtraNonce` in `PoWSeed` — the pool-unsharding mistake `PoWSeal`'s own comment warns about, which "breaks nothing a test would notice" — and it is now noticed twice: the walk collapses to **1 distinct digest out of 4096** and the injectivity test reports a blob collision.

  **The first version of this test was wrong, and against correct code.** It asserted on the mean of the low 64-bit word, accumulated in a `uint64`. Four thousand uniform 64-bit values overflow that by a factor of 2048, so the "mean" was noise and the test failed on the shipped implementation. The statistic is now a *count* of samples in the lower half, which cannot overflow and is also the better question — the work check accepts a commitment at or below the target, so a grinding advantage is precisely a way of making low values more frequent. Recorded rather than quietly fixed, because an assertion written before checking that its statistic can be computed is the same class of error as an instrument that reports success without measuring.

- **I8-L5 — work does not replay across networks, epochs, or heights.** ✅ *proved.* Three separate replay routes, three tests. **Networks:** the chain id is in the `KeyFor` preimage, so two mirrored parameter sets differing only in `ChainID` must key differently at every height — including the epoch-zero heights where `SeedEpochFor` collapses to 0 and the chain id is the *only* thing separating the two preimages, which is the case a spot check at height 1000 would miss. End-to-end: a header solved under one chain id is refused under the other. Mutation-checked by dropping `ChainID` from the preimage. **Epochs:** the key is constant within an interval (or the dataset would be rebuilt mid-epoch) and changes at the boundary, not one block early or late. **Heights:** every height inside one epoch keys *identically* — deliberately — so the obvious question is whether one solution can be spent at several heights. It cannot, because `Height` is inside the seed preimage; `TestAHeaderCannotBeReplayedAtAnotherHeight` re-presents one real solution at five same-key heights and requires all five to be refused, failing loudly if the fixture ever stops actually sharing a key.

- **I8-L6 — the time and target rules are pure functions of the window's values.** ✅ *proved.* ARCHITECTURE §12 asserts the two time rules and the target rule are enforced at three ingress sites — `node/sync.ValidateHeaders`, `node/p2p`'s tip-extension branch, `node/chain.validateBranchDifficultyLocked` — and concludes they are *"therefore path-independent"*. **That is the exact shape of claim I5-H19 falsified for `pow.CheckWork`**, which had no call site at all on the path blocks arrive by, so it is worth an experiment. All three sites were read and all three do call both rules; what a `core/pow` test can add is the half a `node/p2p` test could not isolate. The three sites build their windows three different ways — sync accumulates `st.window`, p2p calls `RecentHeaders`, fork choice calls `headersEndingAtHeightLocked` and appends — so they agree only if the rules read nothing but the values. `TestTheTimeAndTargetRulesArePureFunctionsOfTheWindowsValues` drives one logical window through four representations differing in length, capacity and backing array, including a window that is the tail of a longer array whose earlier entries carry `MaxTarget`, and requires one answer.

- **I8-L7 — `MedianTime` sorts a copy, and that is load-bearing.** ✅ *pinned.* `MedianTime` needs sorted timestamps; the cheap way is to sort the window in place and the correct way is to extract the times first. It does the latter, and nothing pinned it. The in-place version **returns the correct median** and passes every functional test — it corrupts only the *caller's* slice, whose next use is a difficulty computation that would then read headers in timestamp order rather than height order. `node/p2p` hands `NextTarget` the very slice `Chain.RecentHeaders` returned. That is a fork with no bad block in it, arrived at by aliasing rather than by content, so it gets its own test alongside the general no-mutation one. Mutation-checked: the in-place sort fails with *"MedianTime reordered the caller's window: index 0 holds height 11, was 10"*.

- **I8-L8 — what a miner's own timestamps buy, stated as bounds rather than as prose.** ✅ *pinned.* The backdating floor is exactly `MedianTime + 1` and nothing else moves it: the median itself is refused (the rule is `<=`), one below is refused, one above is accepted, and **the floor does not depend on the parent's timestamp at all** — the property that makes backdating possible in the first place, and the one a reader who assumes "later than the parent" will misjudge every downstream timestamp argument by. The median is over values and not positions, so a miner holding several of the last eleven slots cannot place one extreme sample at the midpoint and move the bound: five permutations of one multiset, one answer. The future limit withholds rather than rejects, its boundary is inclusive at exactly `now + FTL`, and the median rule is indifferent to how far ahead a timestamp is — without which validity would depend on the receiver's clock. And the retarget absorbs the extremes: `Time` is attacker-chosen and unvalidated in magnitude, so `0` and `2^64-1` are both reachable wire values, and at both — plus `1`, `2^62`, and a value just below the parent — the next target stays inside the per-block clamp, below `MaxTarget`, above zero, with no overflow. These duplicate no existing coverage: `backdate_sweep_test.go` sweeps the *controller* and `median_bound_test.go` pins the *ratchet rate*; what was missing was the statement of the rule's own bounds.

- **I8-L9 — the work curve does not collapse at any shipped parameter set.** ✅ *proved at the values, not at the validator.* I3-M2 turned the risk into F-PARAM-1 — above `2^255` every target is worth one unit and fork choice degenerates into a block count — and `Params.Validate` refuses such a `MaxTarget`. **A validator is not a parameter set, and a freeze freezes parameter sets.** `TestTheWorkCurveDoesNotCollapseAtAnyShippedParameterSet` asserts against `BlockWork`'s *output* at the shipped ceilings: mainnet 63, devnet 31, testnet 15, each strictly greater than one, each strictly increased by halving the target. The collapse constant is written out in the test rather than imported from `core/params`, deliberately — a test borrowing the validator's own constant agrees with it by construction and cannot catch the constant being wrong. Monotonicity is then swept across 200 halvings from the ceiling down, because a flat interval anywhere a live chain can occupy is a tie, and ties resolve to first-seen.

- **I8-L10 — accumulated work cannot saturate within any reachable chain.** ✅ *bounded.* Total work accumulates with `SatAdd`, which clamps rather than wraps. Clamping is right — a wrap would let an attacker make a long chain look light — but it has its own failure: once two branches both saturate they compare **equal**, the `Gt` in `considerBranchLocked` is false, and the incumbent is kept forever no matter how much work arrives. Fork choice would stop working silently, with no invalid block anywhere. Measured rather than assumed, and pessimistically: at a target **80 halvings below `max_target`** — far harder than any chain has reached — saturation still needs ~1.5×10^51 blocks, past 2^64 by thirty orders of magnitude. `SatAdd` is separately asserted to clamp rather than wrap at both `Max+1` and `Max+Max`.

- **I8-L11 — the equal-work tie is a strict comparison, and this boundary is reached constantly.** ✅ *pinned.* Fork choice is `!br.Work().Gt(replaced)`, so a branch must be **strictly** heavier to displace the incumbent; equal work keeps first-seen, which I3's confidence section records as deliberate and MEV-unmodelled and which this pass does not reopen. What it pins is only the comparator, both directions — equal must not win, one unit more must — because either assertion alone is satisfied by a constant. This is worth distinguishing from randomx-v2 §8.8's mutation E, the `Gt`/`Gte` boundary in `CheckCommitment`, which was correctly left uncovered as unreachable: that boundary needs `commitment == target` exactly, a fixed point of BLAKE2b∘BLAKE3 at 1-in-2^256. **This boundary is the ordinary case** — two siblings at the same height with the same target carry exactly equal work — so flipping this comparator would turn every announced sibling into a reorg and hand the chain to whoever announces *last*.

## What was attacked and found sound, without a finding

Recorded so a later pass does not re-derive them from scratch, and so the negative results are visible rather than implied by silence.

- **The seven reserved bytes are enforced by construction and cannot be otherwise.** `PoWInput` starts from a zeroed `make` and copies exactly two things into it — the seed at 0 and the nonce at 39. There is no expression anywhere that writes offsets 32..38 from header data, which is why the sweep in I8-L1 finds nothing: the property is structural, not defended. The rule binds *implementations of this function* and no corpus of blocks can carry it, which is why the cross-check against XMRig's own published offsets (`TestTheBlobThisTreeBuildsIsTheBlobXMRigSearches`) is the guard that matters and this sweep is the second one.
- **`PoWHash` inside the header encoding is not circular.** It is inside `ID()` and inside the SSZ encoding, and `PoWSeed` zeroes it — without which the seed would be a function of itself and *no* header could ever be valid. Asserted in both directions (I8-L2, I8-L3).
- **`SeedEpoch` is decorative to the work rule and pinned anyway.** `CheckWork` derives the epoch from the height and never reads the field; B0b requires the field to equal the schedule. The risk is therefore not that a lie is believed but that the two could disagree — a header valid on one path and invalid on another — and they cannot: the schedule is monotone, steps by exactly one at each boundary, and never skips or repeats an epoch across four boundaries swept block by block.
- **Short windows are defined and equal at every length.** A syncing node reaches window lengths 0, 1, 2 … at different moments on each of the three ingress paths. `NextTarget` returns a non-zero target at or below `MaxTarget` at every length from 0 to 12, and the median rule rejects nothing plausible at any of them.
- **Height and `ParentID` are both bound at apply** (`applyLocked` requires `Height == c.height+1` *and* `ParentID == tip`), and `ParentID` is inside the seed preimage, so a header cannot be moved between branches without invalidating its work.

## What this pass could not reach

Stated in the vocabulary I7 established, and not upgraded quietly.

- **The three-path differential itself is not written.** I8-L6 proves the *shared kernel* is path-independent — the rules read only the window's values — and all three call sites were read and confirmed to call both rules. What is **not** written is a test that feeds one bad-timestamp header into all three ingress paths and requires three identical verdicts. That belongs in `node/p2p`, whose suite is ~23 minutes, and it is the test that would have caught I5-H19. **Classified as read-verified, never observed.** It is the single most valuable thing this pass leaves undone and it is cheap in engineering terms and expensive only in CI minutes.
- **Nothing here ran the real engine.** Every proof-of-work test in this pass drives `pow.Dev`, and that is sound for what it checks — the blob layout, the commitment, the key schedule and the replay questions are all *upstream* of the engine, and `blobpath_internal_test.go`'s own comment makes the argument. But no assertion in this pass would catch a RandomX-specific defect, and randomx-v2 §8.8's open list — real arm64 hardware, the line-by-line read of the ~800-line delta, the 1-in-2^28 class, the shallower hard-AES sweep — is untouched by it and still stands.
- **The LWMA was attacked at its bounds, not at its dynamics.** I8-L8 shows extreme timestamps stay inside the clamp. It says nothing about a *sustained* campaign of many manipulated blocks, which is what `backdate_sweep_test.go` and `sim/timestamp_test.go` measure and which this pass deliberately did not duplicate. **A multi-block adaptive strategy — one that varies its manipulation in response to the target it is moving — has not been tried by anyone**, here or in the prior passes, and I have no evidence either way about it.
- **The withhold queue's interaction with fork choice is unexamined.** Future-dated blocks are withheld rather than rejected. What a withheld block does to branch assembly, the orphan pool's bounds, or an accumulated-work comparison *while it waits* was not tested by this pass and has no finding in I1–I7 either. Named rather than left implicit.
- **`MedianTime`'s even-window convention is the one place a second implementation can silently diverge**, and I8-M1 asks for a sentence rather than a patch. Until that sentence exists, the tree is right and the specification is silent.

**What this milestone should be read for.** Not a defect, because there was not one. The finding is that **a correct rule and a re-derived rule are different claims, and this tree had been carrying the first while its comments asserted the second.** `PoWInput`'s unreachability proof was true of a header that had not existed for two commits. ARCHITECTURE's path-independence claim was the same sentence I5-H19 had already falsified once, re-made about different rules and never re-tested. Both turned out fine. The cost of finding that out was an afternoon, and the cost of *not* finding it out would have been discovering which one had rotted after the freeze — when a consensus defect stops being a patch and becomes a hard fork.
