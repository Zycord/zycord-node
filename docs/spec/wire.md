# Zycord — Wire Protocol Specification

**Version:** protocol 1 · **Status:** normative for M3

This document specifies the Zycord peer-to-peer protocol independently of any implementation. It is written so that a second implementation can be built from it alone, and so that the Go code in `node/p2p` can be replaced — by a rewrite, or by libp2p under the reopen conditions in [networking](../decisions/networking.md) §6 — without a fork.

Where this document and the implementation disagree, **this document is wrong**, and the fix is to correct it here. That is the opposite of the rule for `spec/` and `core/`, and the asymmetry is deliberate: consensus is defined by the specification, the network is defined by what peers actually accept.

Nothing in this document is consensus. A node that speaks none of it and receives blocks on a USB stick computes the same chain.

---

## 1. Transport

**TCP**, then **TLS 1.3** (`crypto/tls`, `MinVersion: VersionTLS13`).

Peer identity is an **Ed25519** key carried in a self-signed X.509 certificate. Both sides present one. Certificate *chains* are not validated — there is no certificate authority and there is nothing for one to attest — so verification is:

1. `InsecureSkipVerify: true`, which disables hostname and chain checking only.
2. A `VerifyPeerCertificate` callback that requires exactly one certificate, requires its public key to be Ed25519, and extracts that key as the peer's identity.

The security property obtained is **channel binding to a key**, not authorisation: TLS guarantees that whoever completed the handshake holds the private key for the identity presented, and that the stream cannot be read or modified in transit. It says nothing about whether that peer is honest. Nothing in the protocol grants authority on the basis of identity.

Certificate validity dates are fixed at `2000-01-01T00:00:00Z` to `2999-01-01T00:00:00Z`. They are constants rather than a window around the current time on purpose: a relative window makes certificate acceptance depend on clock agreement, and a network that partitions along clock skew is a network that partitions for a reason unrelated to consensus.

Implementations MUST NOT reuse a key from any other layer as the peer identity. See [networking](../decisions/networking.md) §10.

## 2. Framing

Every message is a 5-byte header followed by a payload:

```
offset  size  field
0       4     length   uint32, little-endian — payload length, excluding this header
4       1     kind     uint8  — see §3
5       n     payload
```

- `length` MUST be checked against `MaxMessageBytes = 8388608` (8 MiB) **before any allocation**. A receiver that allocates on a claimed length has a remote memory-exhaustion bug regardless of what follows.
- `kind` MUST be in `[1, 9]`. `0` and anything above the highest known kind are a protocol violation, not an unknown extension: there is no forward-compatibility escape hatch at protocol 1, because a version field that is checked at the handshake makes one unnecessary.

## 3. Message kinds

| Value | Name | Direction | Payload |
|---|---|---|---|
| 1 | `hello` | both, first | §4 |
| 2 | `certificate` | gossip | `ssz(Certificate)` |
| 3 | `block-announce` | gossip | §5 |
| 4 | `get-block` | request | §5.1: 32-byte block id ‖ u32 chunk index |
| 5 | `block` | response | §5.1: one chunk of `ssz(Block)` |
| 6 | `get-headers` | request | §6 |
| 7 | `headers` | response | §6 |
| 8 | `get-peers` | request | empty |
| 9 | `peers` | response | §7 |

`ssz(Certificate)` and `ssz(Block)` are defined in [the consensus specification](../../spec/README.md). There is no network-specific encoding of a consensus object, which is what makes "the id of what I received" a checkable statement.

### 3.1 Certificate identity, and what it does *not* cover

Two digests of a certificate exist, they answer different questions, and an implementation that confuses them is monetarily broken in a way its own tests will not reveal. This section is normative.

- **The certificate id** is `blake3("zcd/certid/v1" ‖ ssz(certificate with an empty signature list))`. It names an **authorization**. It is the key of the seen set, the key of the fold's `(underwriter, seq, id)` order, and the identity a mempool, a gossip dedupe, an RPC handle and a wallet's "already sent" check MUST use.
- **The exemplar hash** is `blake3("zcd/cert/v1" ‖ ssz(certificate))`. It names one **encoding** of a certificate, signatures included. A block's `CertRoot` is a root over these, and nothing else in the protocol keys on it.

**The id MUST NOT cover the signature list**, and the reason is not taste. Ed25519 is a Schnorr proof of knowledge: the signer chooses a nonce, and every nonce yields a different valid, canonical signature over the same message. RFC 8032's deterministic derivation is a rule for signers that no verifier can check and no encoding rule can impose. So one authorization has unboundedly many valid encodings, and an implementation whose id covered them would give one authorization unboundedly many seen-set keys — each producible by **any one** of its required signers, carrying the other signers' bytes across untouched, and each billable in a block of its own. That is a double spend of a signed payment.

Two obligations follow.

1. **A block MUST commit to the signature bytes it carries.** Signatures are outside the id's preimage, so they are bytes anyone in transit can replace; `CertRoot` being a root over exemplar hashes is what keeps "this block is valid" a statement about bytes the block itself pins. An implementation that built `CertRoot` from ids instead would commit to no particular signature bytes at all: two bodies carrying different signatures over the same authorizations would produce the same `CertRoot`, the same header and the same block id, so two nodes holding different bytes would both hold "the same block" and both be right. And it would be free — `CertRoot` is a header field and the header is the proof-of-work preimage, so under **this** rule swapping an exemplar moves `CertRoot`, moves the proof-of-work seed and invalidates the work, while under an id-keyed root it moves nothing and the work still stands. That is an equivocation primitive at zero cost, and it is why this is a MUST.

   What this obligation does **not** close, named here so that no implementation reads it as closed: a receiver that fetches a body, refuses it, and has already recorded the block id as seen while clearing its pending request will refuse the honest body afterwards. That is a property of a receiver's own bookkeeping, it fires for **any** refusal reason including this rule's own `certificate root does not commit to the bodies`, and it is neither caused nor cured by what `CertRoot` commits to. A receiver MUST NOT treat a refused body as evidence about the block id.

   **The reference implementation does not yet meet that MUST NOT**, and saying so here is the point of writing it down. `node/p2p` records a block id as seen when the header is *announced* and clears the awaited flag as soon as a body decodes, before judging it — so one refused body makes every later delivery of the honest body answer "already known", permanently. Reproduced on the reference node. An independent implementation should read this clause as normative and the reference node as non-conforming on it, not the other way round.
2. **Relay MUST treat exemplars, not ids.** A node that receives a certificate whose signatures do not verify discards *that exemplar* and holds nothing against the id — not marked, not cached as invalid — because a later exemplar of the same authorization may be perfectly good.

   The converse is **not** required, and MUST NOT be inferred from that sentence: a node MAY answer "already known" from the id alone, without looking at the exemplar it was sent. Deduplication is keyed on the id because that is what makes it a bounded question — the pool and the committed set both key on it, and neither stores the bytes that carried a committed authorization — and because verifying before deduplicating is a validation-cost denial of service. The consequence is that a mutilated exemplar of an authorization a node already holds is dropped as a duplicate rather than charged as an invalid message. That is permitted. It costs an implementation nothing it did not already concede: replaying the honest bytes reaches the same branch at the same price. What obligation 2 forbids is the other direction — recording anything *against* the id — and that a node MUST NOT do in either case.

**A note for wallets, because the obligation moved.** A retry of a stuck payment reproduces the certificate id as long as the body is reproduced, and the body does not contain the signatures. An implementation is therefore free to sign with a randomised or hedged nonce, including in an HSM, without turning a retry into a second payment. This used to be false and unstated: the id covered the signatures, so idempotency rested on the signer being byte-for-byte deterministic — a property no rule anywhere required and this document never mentioned.

## 4. Handshake — `hello`

Sent by **both** sides immediately on connection, before anything else, without waiting for the peer's.

```
offset  size  field
0       4     protocol     uint32 LE — MUST be 1
4       32    network_id   the genesis block id
36      8     height       uint64 LE — sender's tip height
44      32    work         big-endian uint256 — sender's accumulated work
76      4     addr_len     uint32 LE — MUST be ≤ 108
80      n     listen_addr  UTF-8, no NUL, may be empty
```

Total length MUST be exactly `80 + addr_len`. A trailing byte is a malformed message.

**`network_id` is the genesis block id**, which commits to every consensus parameter (R3-1). A receiver whose own network id differs MUST close the connection immediately, before parsing any further message. This is what makes devnet and mainnet structurally unable to cross-connect: not a name comparison, but the fact that a different parameter produces a different genesis.

**The receiving side of that rule is also normative, and stating only the sending side was not enough.** A receiver MUST treat the first message on a connection as `hello` and MUST refuse every other kind until one has been accepted, scoring the refusal as a protocol violation (§10). Without it the network-id check above is optional in practice rather than in principle: an implementation that dispatches whatever arrives serves `get-headers`, `get-block` and `get-peers` — and validates and forwards certificates, announcements and bodies — for a peer whose network it never compared, at a cost of one TCP connection and no identification of any kind. The handshake is what makes every later message attributable to a peer that has said which network it is on; a message that precedes it is not early, it is unattributable. The gate is per connection: it is satisfied once, by that connection's own `hello`, and a second `hello` on the same connection is itself a protocol violation (nothing a peer could legitimately restate).

**`listen_addr` is what peers can dial, which is not always what the sender binds.** A node behind a forwarded port binds a private address and is reachable at a public one. Implementations MUST provide a way to advertise an address different from the bind address (`--advertise` in `zycordd`), and MUST advertise empty when the node accepts no inbound connections.

**`height` and `work` are claims, not facts.** They exist so a receiver knows whether a peer is worth a round trip. Neither may be used to accept anything: `work` in particular is trivially forgeable, because the accumulated work of a chain nobody has the headers for cannot be checked. See §9.

## 5. Block announcement — `block-announce`

```
offset  size          field
0       HeaderSize    ssz(Header)
H       4             count   uint32 LE — MUST be ≤ 100000
H+4     count × 32    cert_exemplars   in block order
```

Total length MUST be exactly `HeaderSize + 4 + count × 32`.

A receiver MUST, in this order, and MUST NOT request a body before all of them pass:

1. Reject an unknown header version.
2. **Reject height 0.** Genesis is never announced: every node already holds it, so an announcement of it cannot be useful, and it is the one height at which step 5's proof-of-work check is free — `CheckWork` returns success immediately for genesis, because genesis carries no work. Without this rejection a height-0 header walks past step 5 at zero cost and into everything downstream of it.
3. **Reject `count` above what a block can hold.** `count` MUST be ≤ the certificate-count ceiling a valid block at any height can reach — the same bound block validity itself enforces (`MaxCertsPerBlock` at its maximal argument; [architecture](../ARCHITECTURE.md) §15), which is smaller than, and clamped by, the merkle/decode capacity `cert_list_capacity` above. This check is stricter than the `count ≤ 100000` transport bound already enforced at decode, and it is the one that matters: step 6 merkleises `cert_exemplars` against `cert_list_capacity` to verify `CertRoot`, and a receiver that merkleises an oversized list has a remote crash or unbounded-work bug on its hands. The transport bound alone does not prevent that — it sits far above the capacity the merkle step is built for — so this rejection MUST run before step 6.
4. **Where the header names the receiver's own tip as its parent, reject it unless its height is that tip's height plus one; and then reject it unless its declared target is the one the difficulty rule gives.** Two rules on one branch, in that order, and §10.3 carries a row for each. The height first, because it is the condition under which the second question means anything at all: the target the rule gives is the target for the block *after* this tip, and a header claiming some other height is not a candidate for that block.
   **The height clause.** A block whose parent is a given block is at that block's height plus one. Every state-driven path already holds that — the fold's citation rules, block application, and the branch checks a reorg runs — but the announcement wire carries the pair unconstrained, so without this clause a header may name the receiver's own tip as its parent and claim any height at all. Past the target clause below such a header carries the tip's real difficulty target, a public value, so producing one costs its announcer a real block's work rather than the few dozen expected hashes a `MAX_TARGET` header costs; what the missing comparison left **free** was the height on an already-paid header, and the height is what selects the proof-of-work key (§12). So it bought the right to name a key epoch the receiver does not hold — the resource the price below this list rations, for the sake of the honest peers a node behind the chain depends on — for a block no chain can ever contain.
   **The target clause.** The rule is a pure function of the window preceding the parent (§9 rule 1), and a receiver holds that window exactly when the parent is its own tip — so this is the one distance at which an announcement's declared target is checkable at all, and it is also the common case. Without it a header declaring `max_target` is accepted for about sixty-four expected hashes on mainnet, requested, and held pending a body that never comes, which is what makes step 5 a check the sender passes by choosing what it is checked against. It was also **relayed**, under the unqualified flood rule §8 used to carry, and that is what put the resulting charge on an honest relay rather than on the announcer; §8 now forwards an announcement only from a node that holds the body, so the relaying half of this sentence describes what this rule used to cost and not what it costs now. **This is R4-H1 and it is the same rule §9 rule 1 already requires of `node/sync`, of a gossiped *block* extending the tip, and of `ConsiderBranch`; the announcement path was the only ingress that did not carry it**. A receiver MUST NOT extend **either** rejection to a header whose parent it does not hold: it holds neither that parent's height nor the window its target is derived from, and refusing or withholding on that ground silences the lagging fringe of the mesh — measured on the reference implementation, a receiver one block behind its peer sees 19 of 20 honest announcements name a parent it does not hold, and a node rejoining after fifteen blocks sees 14 of 15 or more.
5. **Verify the header's proof of work against its declared target.** This is before any fetch, so a ghost announcement costs the announcer real work rather than costing every receiver a round trip.
6. Verify that `cert_exemplars` produces the header's `CertRoot`. An announcement that does not is describing a block that does not exist.

The list is **exemplar hashes** (§3.1) and not certificate ids, because recomputing `CertRoot` is the only thing it is for and `CertRoot` is a root over exemplars. A receiver that wants to know which *authorizations* a block commits has to fetch the bodies.

An announcement carries no cited-header list, so the header's `CitesRoot` is **not** checkable here and MUST NOT be treated as if it were. It is checked when the body arrives, along with the proof of work of each header cited (§9 rule 7) — the announcement's job is to let a receiver decide whether the block is worth a round trip, and the work in step 5 is what already makes that decision costly to abuse.

A receiver that has already seen the header's id MUST NOT re-request or re-forward it.

Note the asymmetry with §9, and note that step 4 closes exactly one distance of it. The proof of work in step 5 is checked against the target the header *declares*, which is a weaker statement than the target the difficulty rule *requires*. Where the parent is the receiver's own tip, step 4 supplies the stronger statement and the asymmetry is gone. Where it is not, the receiver has no window and the weaker statement is all there is.

**The justification this paragraph used to give for the weaker statement was wrong, and it is worth stating why rather than deleting it.** It said the declared target is "acceptable for gossip, where the block attaches to a known chain". Announcements routinely do not attach to a known chain — that is what a node one block behind sees for 19 of 20 honest announcements — and the case where they *do* attach is precisely the case step 4 now checks. So the sentence excused the weaker statement on the strength of the one condition under which it was never needed. What actually remains open is an announcement whose parent this receiver does not hold: its declared target is unverifiable here, so it is admitted, requested and priced like any other. What used to follow from that no longer does — §8 relayed it, and §10.3's unserved-body charge then landed on whichever peer forwarded it rather than on the party that announced it. §8 now forwards a block announcement only from a node that holds the body, so every charge names a peer that chose to announce. The wire format still carries no origin; what closed the mis-aiming was removing the hop, not adding a field, and the declared target of such an announcement is still unverifiable at this distance.

**Step 5 has a price, and a receiver MAY refuse to pay it.** Under a keyed work function the cost of step 5 is chosen by the sender: the key comes from the header's height (`pow.KeyFor`), and a height in a key epoch the receiver is not already working in costs a full key initialisation rather than a hash — about thirty times as much under `randomx-v1`. Since step 5 accepts the target the header declares, that cost is payable with no proof of work at all. A receiver therefore MAY refuse an announcement **before** step 5 when its key epoch is outside the epochs the receiver is itself working in and the budget for such refusals is exhausted. **That budget has two layers, for the reason §10.4 gives about the reply-byte budget one primitive over: no single axis is both exact and unmintable.** The per-payer layer MUST be keyed on the **authenticated identity** and never on the connection — a connection-keyed budget is re-bought for the price of one TLS handshake, measured at 40 epochs against a budget of 5 — and the reference implementation admits `MaxUnheldKeyEpochsPerPeer` of them per identity, refilled one per `randomx_key_interval × target_block_seconds`. Beside it a receiver MUST carry a node-wide ceiling keyed on nothing a sender presents, since minting an identity is free and a per-identity rate therefore bounds no total; both layers MUST recover inside their own window. Three constraints on any such refusal, and each of them is what stops it becoming a rejection:

- It MUST be unscored, **except against an identity whose announcement this receiver's own work check has already refused, and then only where that identity's own attributable budget is what refused it or is already spent** (§10.3, and see the ceiling bullet below for why the second half of that disjunction has to be there). A node that is behind receives announcements far ahead from precisely the peers it depends on to catch up, and scoring for that bans them; an honest peer cannot acquire the work-refused fact, because a header meets the target its own header declares. This bullet used to require the refusal be unscored *unconditionally*, which stopped being true when the score conjunct landed and left a normative MUST contradicting the table it cites.
- **A refusal by the shared node-wide ceiling MUST NOT be scored on the strength of the ceiling, and MUST NOT be reported as the payer's own budget being spent.** That ceiling is keyed on nothing, so a refusal there can be caused entirely by traffic the refused peer never sent; charging it is scoring somebody for another peer's flood. Measured: 48 minted identities × 5 announcements — 55,680 bytes and **no proof of work at all**, since this refusal stands ahead of step 5 — drain the ceiling, after which a caught identity holding an untouched budget was scored and banned in five. **The one exception, and it is a fact about the identity rather than about which layer refused: a ceiling refusal MAY be scored where that identity's own attributable budget is *already spent* and this receiver's own work check has already refused an announcement from it.** Keying the exception on "did the payer's own budget refuse THIS message" instead made it inert for every sender at once while the ceiling was down, including one already caught, which switched off the only class that terminates a distinct-message flood for as long as an attacker held the ceiling at zero. Asking whether the budget is spent still has an answer when the ceiling is what refused, and it MUST be asked with a **non-mutating read**: the per-payer layer MUST NOT be consulted first and MUST NOT be charged here, since that would spend a credit for a refusal the ceiling caused — measured at 26 of 30 refusals scored, −520 against a ban threshold of −100. An identity holding any of its own budget is still never scored for a ceiling somebody else drained, so the rule above keeps its whole purpose.
- It MUST NOT enter the announcement's id into the seen-set. The refusal is a refusal to spend *now*; marking it seen would dedupe away the re-announcement that arrives once a credit is back, which is a permanent rejection wearing a cache's clothes — the same reason the future-time path in §9 rule 8 keeps its ids out.

Refusing **after** step 5 satisfies neither purpose: the key has been built by then, and the refusal bounds a verdict rather than a resource.

**Where a receiver takes this refusal it MUST take it ahead of step 4 as well, and that is a totality requirement rather than a cost one.** "Before step 5" alone permits running the price *between* steps 4 and 5, and the two orders disagree on a reachable input: a header naming the receiver's own tip, at a height whole key epochs away, declaring a target the rule does not give. Priced first it is `Budgeted` once the budget is out and `Scored(invalid)` while it is not; checked first it is `Scored(invalid)` throughout. §10.3 must name one, so the order is pinned here and the step 4 rows carry the matching exclusion. The header is also one no valid block can produce — a block whose parent is the tip is at `tip.Height + 1` — and step 4's height clause now refuses it on that ground too. That does not soften the pin, it widens what it decides: the same input is now reachable by **three** refusals rather than two, and the order fixed here is what says the price answers first and step 4's height clause second, so it is `Budgeted` once the budget is out and `Scored(invalid)` while it is not, whichever of step 4's clauses would otherwise have named it.

### 5.1 Block transfer — `get-block` / `block`

A block body travels as chunks, so the frame limit of §2 bounds a *message* and never a *block*: the consensus byte capacity can be re-pinned at an era boundary (whitepaper §8.1) without a wire change. The transfer bound is `MaxBlockChunks × BlockChunkBytes` with `BlockChunkBytes = 4194304` and `MaxBlockChunks = 4`, so 16,777,216 bytes, and a release accompanying a byte-capacity re-pin MUST keep the consensus capacity under it.

Request — length MUST be exactly 36:

```
offset  size  field
0       32    block id
32      4     chunk   uint32 LE — MUST be < MaxBlockChunks
```

Response:

```
offset  size  field
0       32    block id
32      4     chunk   uint32 LE
36      4     total   uint32 LE
40      rest  data
```

A responder slices `ssz(Block)` into `total = ceil(len / BlockChunkBytes)` chunks and serves the one requested; a request at or past `total` is a protocol violation. Serving is stateless — the requester names the chunk, so the responder holds nothing between requests.

A receiver MUST reject, before any use: `total = 0`, `total > MaxBlockChunks`, `chunk ≥ total`, `data` longer than `BlockChunkBytes`, `data` shorter than `BlockChunkBytes` on any chunk but the last, and an empty last chunk — the fixed chunk size is what stops a peer stretching one transfer across arbitrarily many messages. Reassembly is keyed by (peer, block id), and a peer MAY hold several transfers at once: a receiver requests a body for every announcement it accepts, and nothing bounds how many a peer sends, so one buffer per peer would let two overlapping fetches evict each other. A chunk 0 starts or restarts the transfer under its id; any later chunk MUST match the total and the next index of the transfer held under that id, and one that does not drops **that transfer only**.

Three bounds apply to reassembly, and they bound different things: transfers per peer (`MaxTransfersPerPeer`), peers holding transfers (`MaxPartialTransfers`), and — the only one that bounds memory — total bytes held across all buffers (`MaxReassemblyBytes`). The count bounds multiply, so a receiver that enforces only those has no bound on the memory behind them. Past the per-peer bound a receiver evicts its own oldest transfer for that peer; past the byte budget it refuses the chunk.

**A receiver MUST NOT penalise a peer for a chunk that continues no transfer, for the per-peer eviction, or for the byte budget.** A receiver drops transfers of its own accord — on disconnect, on eviction, on saturation — so these outcomes do not distinguish a hostile sender from an honest one serving a request that this receiver stopped tracking. Penalising them bans honest peers. The malformed shapes listed above are a different matter and remain the sender's fault.

The claimed `total` MUST NOT be treated as an allocation: the buffer grows only as chunks arrive, and a transfer whose accumulated bytes exceed the consensus byte capacity (`block_byte_capacity`) is rejected at the chunk that crosses it.

A transfer with `total = 1` is a single request/response pair, exactly the shape a single-frame protocol would have had. A block at the genesis byte ceiling is one such transfer, since `BlockChunkBytes` exceeds `block_byte_limit_genesis`; blocks become multi-chunk as the elastic ceiling grows past it, so the multi-chunk path is reachable within the launch era and is not future-era machinery.

Chunks are fetched one round trip each. A block of `n` chunks therefore costs `n` sequential round trips, which is a propagation cost and feeds the competing-header rate the health gate reads (whitepaper §8.1). At the genesis byte capacity `n ≤ 2`; a large capacity re-pin makes it material, and pipelined requests — which require answering one message with several — are the work that must precede one.

## 6. Header sync — `get-headers` / `headers`

Request:

```
offset  size  field
0       8     from    uint64 LE — first height requested
8       4     count   uint32 LE
```

Length MUST be exactly 12. A responder MUST clamp `count` to `MaxHeadersPerResponse = 512` rather than reject, so a client need not know the limit.

Response:

```
offset  size              field
0       4                 count   uint32 LE — MUST be ≤ 512
4       count × HeaderSize   ssz(Header) each, contiguous ascending
```

Total length MUST be exactly `4 + count × HeaderSize`.

A responder serves from its own canonical chain, starting at `from`, stopping at its tip or at `count`, whichever comes first. An empty response is valid and means "I have nothing at that height".

**A `headers` frame is a response and never an unprompted message.** §12 removes request ids deliberately, so a receiver cannot correlate a response to a request — which means it also cannot establish that a `headers` frame answers anything. A node MUST NOT treat one as useful on any connection it did not itself send `get-headers` on; the frame MUST still be decoded, so that a malformed one is scored as invalid, and a well-formed one scores neither way (§10). Rewarding it instead is the cheapest positive score in the protocol: the payload is checkable against nothing, so a well-formed empty response is a few bytes for a point, and score farmed this way pays for the misbehaviour it offsets.

## 7. Peer exchange — `get-peers` / `peers`

`get-peers` has an empty payload. The response is:

```
4                  count   uint32 LE — MUST be ≤ 64
then, count times:
  4                len     uint32 LE — MUST be ≤ 108
  len              addr    UTF-8
```

The payload MUST be exactly consumed; trailing bytes are malformed.

A responder SHOULD return an address-diverse selection rather than its most recent peers, so that peer exchange cannot be steered by an attacker who fills a victim's store from one network range. `node/p2p` groups IPv4 addresses by `/16` and IPv6 by `/32` and takes at most one per group per round.

A `peers` frame is a response, and the same rule as §6 applies to it: a node MUST NOT score one positively unless it sent the `get-peers` it answers. Recording the addresses is a separate question from rewarding the sender, and a node MAY do the first while doing neither of the others — an address costs a store entry to record and is worth nothing until it is dialled successfully, so recording is not a reward and MUST NOT be scored as one.

**Recording is work, so the rate a node accepts `peers` frames at MUST also be bounded per connection, and a repeat inside that window MUST be charged under the excess-request class (§10.4).** The asymmetry with `get-peers` is the trap: the request side is obviously an amplifier and got a minimum interval, while the response side looks like bookkeeping and got nothing — but recording one frame is up to the 64 insertions the count field above permits into a store that is also read by every dial selection and written by every scored message, and §12 leaves a receiver no way to tell a volunteered frame from an answer, so *the sender chooses when and how often*. Measured on an implementation with no such bound, one 64-address frame cost between 0.58 ms and 46 ms depending on how full the store was, i.e. one core saturated somewhere between ~35 KB/s and ~4 Mbit/s of attacker upload — for a message class that returned `Free` and was never scored. The bound is also what prices the address-injection rate the two eclipse defences in §11 (arrival order, and the per-source bound) are otherwise made cheap to grind against. A node SHOULD size the ingress window to its own `get-peers` minimum interval, so that an implementation obeying one is never punished by the other; a conforming answerer replies once per `get-peers` and so never approaches it.

## 8. Gossip

Flood with a seen-cache: a valid message is forwarded to every connected peer except the one it arrived from, and a message whose id is already in the seen-cache is neither processed nor forwarded.

**`block-announce` is qualified: a node MUST NOT forward a block announcement until it holds that block's body.** The `block` kind is qualified with it, further down, and by the same rule rather than by an exception to it — a node that has just reassembled a body holds it, so what it floods is an announcement.

The unqualified rule and §9 rule 5 cannot both be obeyed. Rule 5 requires a receiver to charge the announcer once when its window elapses with no body, and the only party a receiver can name is the peer the message arrived from — §12 removes request ids and nothing on this wire carries an origin — so under the unqualified rule the charged party is the **last hop**. The last hop is also the one party that is guaranteed to be unable to serve: a node that already holds the body has nothing outstanding, so an announcement it forwards is by construction one whose body it has just asked for itself, and the `get-block` its own forward provokes comes back not held. §9 rule 5 defines misbehaviour as advertising what you will not back; the unqualified flood rule required every relay to do exactly that, and then charged it for doing so.

Measured on the reference implementation, over two engines, with ghost announcements naming an invented parent at a height a hundred above the tip and declaring `max_target`: an honest relay starting at the score ceiling is banned by its own downstream, at 232 bytes per announcement, while that downstream never scores the announcer at all. **How many announcements it takes is a property of the receiver's reap schedule and not of the protocol** — the same finding has been recorded at 23, at 12 and at 6. What is a property of the protocol is the pair: the relay is banned and the announcer is not.

**Propagation is unaffected, and that is a measurement rather than an expectation.** What carries a block past the first hop is the body a node floods to every peer but the sender on accepting one, not the announcement. Measured paired on the reference implementation — lock-step rounds, single-chunk bodies, devnet parameters, one miner — a line of six and a ring of eight reach full propagation in the **same** number of rounds with the announcement relayed and without it, at 0.43x and 0.46x the bytes. Round counts are a property of that harness's schedule and are not a maximum; the equality between the two columns is the claim, and it is stated as the axis it was searched along.

**The rule has a second half, on the path the first half leaves carrying the block: a node that accepts a body it reassembled from more than one chunk MUST flood an *announcement* for it, and MUST NOT flood the chunk that completed the transfer.** It holds the body, so this is the same rule and not an exception to it.

Without that half the first one opens a partition. Flood gossip re-sends the frame that arrived, and only the chunk that *completes* a transfer is a frame worth re-sending at all — the ones before it are answered by a `get-block` for the next index and carry nothing a peer could act on. So the single frame a completing node would flood is the **last** chunk, and §5.1 requires a receiver holding no transfer under that id to drop it, unscored and without a reply. The announcement flood is what used to make every node open its own transfer; once it stops travelling, a body past one chunk stops with it. This is invisible at every genesis parameter set — `block_byte_limit_genesis` is below `BlockChunkBytes`, so every block a chain can produce at launch is one chunk — and arrives with the elastic byte ceiling, which is to say under sustained load.

**Flooding chunk 0 instead does not satisfy this rule and MUST NOT be read as satisfying it.** A receiver handed chunk 0 opens a transfer and begins pulling a body nobody has yet vouched for, which is re-propagation ahead of the body and is the property the first half of this rule removes. The announcement is the frame that says "I have this and will serve it", and that is the claim a node completing a transfer is entitled to make.

A single-chunk body is unaffected and MUST stay so: the frame that arrived is already the whole body, so flooding it is both correct and free, and re-framing it would copy the body for no change.

**What this does not change.** The announcement is still *processed*: its id still enters the seen-cache, its body is still requested, and it still refreshes the announcer's sync candidacy — a node that is behind depends on that signal (§12), and this rule decides who hears an announcement, not who this node is willing to ask. §9 rule 5's charge is unchanged and still fires; what changes is that every entry it can charge now names a peer that *chose* to announce, which is what makes the charge attributable at all. **A node MUST NOT read this as permission to stop recording the obligation.** That charge is the only thing that terminates a flood of distinct ghost announcements from a directly connected peer — removing it was measured at sixty ghosts accepted and forwarded with no score ever going negative — and §10.2 says why: a negative score is the only class that bounds a flood of *distinct* messages.

**And it has a precondition an implementation must already have met.** A node fed only through relays now learns of a block as a body rather than as an announcement, so an implementation whose peer candidacy is refreshed only by the handshake and by announcements learns nothing about who is ahead of it and stops being able to sync at all — `LAUNCH.md` §3 case 4 on the reference project's own gate. §12's candidacy note already contemplates a peer held as a candidate by an unplaceable block "announced **or** delivered", and that is the clause this rule leans on. Measured: fifteen blocks behind and fed only through relays, a node refreshing candidacy from announcements alone holds **zero** candidates under this rule, and one refreshing from a delivered body holds one per peer that actually fed it — where the announce path refreshed only the peer that won the announce race for each block.

**Validity is checked before re-propagation, always.** A certificate is checkable from its own bytes with no consensus state (this is the property the whole design is built on), so a node forwards nothing it has not verified. That single rule is the spam firewall; there is no separate rate limit doing the real work.

The scaling ceiling and the ladder past it are in [networking](../decisions/networking.md) §9.

## 9. Chain sync — normative rules

This section is the part of the protocol where a permissive implementation is a vulnerability rather than a nuisance.

**A node MUST NOT hold blocks whose difficulty target it cannot verify.** The difficulty rule (`NextTarget`) is a pure function of the preceding `DifficultyWindow` headers, and its result is clamped into `[1, MAX_TARGET]` — an absolute bound, applied after the ±`DifficultyClampFactor` relative one, with `MAX_TARGET` a consensus parameter in `spec/params.json` (ARCHITECTURE §12, F-PARAM-1). An implementation that omits the ceiling computes a different target the first time the relative clamp would have gone past it, and from that point it is on a different chain. Two requirements follow, and both are normative: a producer MUST apply the ceiling when deriving a target, and a validator MUST reject a header whose declared target is not the one the rule — ceiling included — derives from the preceding window. **Both requirements now hold on every ingress path**: `node/sync` re-derives the target during headers-first validation (rule 1 below), `node/p2p` re-derives it for a gossiped block that extends the current tip **and, now, for a block *announcement* that names the current tip as its parent (§5 step 4) — the announce path was the one ingress this list used to omit, and a header at `MAX_TARGET` naming an unheld parent is still admitted by that omission's remaining half, though §8 no longer relays it onward**, and `node/chain`'s fork choice (`ConsiderBranch` → `switchTo`, reached through the orphan pool) re-derives it — and the median-time floor below, rule 1's other clause — for every block on a candidate branch, against the same preceding-window construction rule 1 uses, before that branch's declared work is weighed against the tip's. A header a real chain could not have produced is refused there too, not merely on the two paths that happened to check it first. The window a reorg needs is guaranteed to be held at exactly the point it needs it: `ConsiderBranch` establishes that a branch's ancestor is canonical, and within the undo horizon, before it re-derives anything — the same precondition that makes the difficulty window computable at all. A block that does not attach to known history has no such window, so its declared target is unverifiable — and an attacker who declares a trivial target produces structurally-valid blocks at negligible cost and prices the victim's memory. Declared accumulated work is forgeable by the same route, so work-based eviction does not close it. This is R4-H1.

The consequence is **headers-first sync**, and its rules are:

1. Headers are validated as a sequence against a chain they attach to. For each header, in order: version, height contiguity, parent linkage, **the declared target equals the target the difficulty rule computes from the preceding window**, the proof of work meets that target, and the timestamp exceeds the median of its predecessors.

   **"Meets that target" means `le256(digest) ≤ Target`: the work-function digest is read as a *little-endian* 256-bit integer, byte 0 least significant.** This is the one 256-bit quantity in the protocol that is not big-endian, and the exception is deliberate — every other one is a number this protocol encoded, while a digest is 32 opaque bytes whose producer is RandomX, and the whole Monero-family ecosystem reads a RandomX digest little-endian. The two conventions read opposite ends of the digest and the ends are independent, so an implementation that reads it big-endian is not merely on a different chain: no proxy or pool can translate between the two, and every stock miner's shares are noise to it. ARCHITECTURE §12 carries the full entry, including the truncation identity a 64-bit job target rests on.
2. Accumulated work is computed from targets that were *validated by rule 1*, never from a peer's claim. Only then is it a fact.
3. **Bodies are requested only along a header chain that has already been validated and has already won on accumulated work.** A peer cannot make a node do work by describing a chain.
4. Every body MUST hash to the header it was requested for. A peer that answers with a different block is lying, and lying is scored differently from being unable to serve.
5. **Body availability is consensus.** A block whose bodies cannot be retrieved is not a valid block, and a peer that advertises headers it will not back MUST be scored down. This holds on the gossip path as well as the sync one, and on the gossip path it needs a clock to hold at all: nothing but time distinguishes a body that is late from one that is never coming. A node MUST therefore bound how long it will wait on an accepted announcement, MUST charge the announcer **once** when that window elapses with no body, and MUST forget the outstanding announcement either way — a window with no expiry leaves the rule unenforced and the bookkeeping unbounded at the same time, so one announcement whose body never comes is both free and permanent.

Three constraints on that window, and each of them is a way of getting it wrong:

- It MUST be generous relative to a body's transfer time. A body may travel as many chunks (§5.1) and each is its own round trip, so a peer honestly serving a large block over a slow link must not be mistaken for one that will not serve at all.
- A body that **arrives** answers the announcement, whatever the receiver then decides about it. A block refused as invalid, or queued under rule 8 rather than judged, was still served; it is priced by its own verdict, and charging it here as well bills one delivery twice.
- A block already on the receiver's canonical chain when the window elapses MUST NOT be charged, however it got there — a block that arrived by sync answers no announcement and is recorded against none, whichever connection the sync ran over (§12). That the receiver no longer needs the body is a fact about the receiver, not a fault of the peer. A block that arrived but is *not* canonical — held as an orphan, or on a losing branch — is outside this exemption: the announcer still owes the body it advertised.
6. **A syncing node never accepts state it did not re-derive.** There is no trusted snapshot, no checkpoint set, and no fast-sync path in Era 0. A fair-launch chain whose new nodes trust somebody else's state is not one.
7. **Every competing header a body cites MUST be verified for proof of work, and this is consensus rather than policy.** A block body carries `Cites`, the competing headers its proposer reports seeing (whitepaper §8.1); the header commits to them through `CitesRoot`, and the fold counts them into the epoch's health signal, which gates whether the sequential ceiling may grow. A node that skipped this check would accept citations backed by no work, count them, and derive a different target `T` from its peers — the same state divergence a skipped block-level work check produces, arrived at one step later. The fold cannot make this check itself: it is a hash evaluation against a difficulty engine, and the consensus core holds no engine. Everything else about a citation — its header version, its height, its parentage, that it is not the block's own parent, and that it declares the target the fold pins from state — **is** checked inside the fold, so this one rule is the whole of what a node layer must add. Those six checks are also **exhaustive**: a cited header's `Time`, `CertRoot`, `CitesRoot`, `StateRoot`, `EmissionAddr` and `PoW.SeedEpoch` are unconstrained, and a node that constrains one of them counts fewer citations than its peers, derives a different sequential target, and forks. Adding a check here is as much a consensus change as removing one. **`PoW.SeedEpoch` deserves a sentence of its own now that block headers *are* constrained in that field.** A block's own header must declare the key epoch its height implies (§12); a cited header must not be held to it. The two rules are consistent because no verifier ever reads the field to find a key — the key comes from the header's height, for a citation exactly as for a block — so a citation carrying any value at all is still checked against the key its miner used. The consequence to state rather than leave to be discovered: a valid citation may be a header that would be invalid as a block. That is already true of the five fields beside it, and constraining this one to remove the oddity would cost a fork.

8. **A header dated more than `FUTURE_TIME_LIMIT_SECONDS` ahead of the receiver's clock MUST NOT be applied, and MUST NOT be treated as invalid.** The lower time bound (rule 1) is validity and every node computes it from the same chain; the upper bound is a comparison against a wall clock, and making it validity would let a miner date a block exactly at the boundary and have half the network accept it. So a node withholds: it holds the block, judges nothing, relays nothing, scores the sender neither up nor down, and re-evaluates as its clock advances — on the header path the equivalent is to truncate the range at the first such header and request the rest later. Withholding is what bounds how far the median-time-past can be pushed, and the median-time-past is what the difficulty rule reads solve times from, so an implementation that skips it can be walked to the target floor by timestamps alone. A node MUST bound whatever it holds — by count and by bytes, as with the orphan pool — and MAY drop a header dated beyond a local horizon far larger than the limit, since a block held for a period the sender chose is storage the sender priced. **The byte bound MUST account for every representation the node retains of a held block, and the simplest way to satisfy that is to retain exactly one.** The unit is the block's canonical encoding — exact, agreed by every node, and not the sender's to inflate — so a pool that keeps one representation and counts that block's encoded length has bounded what it holds, whichever representation it keeps. What the rule forbids is holding a block in two forms — the frame as delivered and a decoded object beside it — while counting one of them: that bounds a fraction of what is held, and the fraction is the decode expansion factor, which is a function of the block's contents and therefore of the sender's choice (measured at roughly 1.05x to 1.4x in the Go implementation, worst at the shape maximising certificate count for a given byte budget). For the same reason the count MUST be of the block's own length and not of a copy's capacity, where an allocator's size classes put slack the sender selects by choosing a block size (up to 25% in the Go implementation). This is a sizing rule and not a consensus one: a node that gets it wrong holds more memory than it meant to, it does not fork. That bound is the whole of the memory argument: a queued block's proof of work is checked only against the target the header *declares*, and nothing has bounded that declared target *at the point of queue admission* — the future-time check runs before any `NextTarget` comparison could — so admission costs a few dozen expected hashes rather than real work. This is about admission ordering, not about the target rule: by the time such a block is judged, the rule is re-derived on whichever path judges it (rule 1 above). `node/p2p/withhold.go` and `node/sync.ValidateHeaders` are the implementations, and they are the two *ingress* points: every block reaching `node/chain.ConsiderBranch` has already passed one of them, so fork choice does not re-apply the bound. That is deliberate rather than a gap. Unlike the target and median-time rules — which are consensus validity, computed from the chain, and therefore enforced on every path including fork choice — this bound is a comparison against a local wall clock. Re-applying it during a reorg would make the same branch adoptable by one node and not another purely by clock skew, which is the split this rule exists to avoid; and a withheld block is never judged in the first place, so there is nothing for fork choice to reconsider.

   **The withhold check MUST be ordered after every clock-free check the node can already perform.** Withholding is not a judgement and scores nobody, so a node that tests it first converts a header carrying no proof of work at all into "nothing to do this pass": an unauthenticated peer then makes every sync attempt it is selected for a silent, unscored no-op at a cost of zero hashes. On the **header** path every clock-free check is available at once, so all of them — version, height, linkage, declared target, the median lower bound, and proof of work — MUST precede it, and only an otherwise-valid header may be withheld. **Among those, the median lower bound MUST precede the proof-of-work check.** Both are consensus and both must pass, so the order cannot change which headers are accepted; what it changes is what a peer feeding garbage costs the receiver. A work evaluation under a memory-hard function is roughly three orders of magnitude more expensive than a median of eleven integers, so checking work first lets a peer buy milliseconds of CPU per header with one wrong timestamp byte. This is a bound on the free half of that attack and not a defence against the attack: a header with a plausible timestamp still reaches the work check, which is the design — proving work is what an honest header does — and what limits the rest is per-peer scoring and rate limiting, which are policy rather than consensus. On the **body** path the declared-target and median checks are functions of the preceding window and are therefore reachable only once the block is known to extend the tip, which is a decision that must itself come *after* the withhold — so what MUST precede it there is the decode and the proof of work, which is the check the ordering exists to make the attacker pay for.

   **What this rule bounds, and what it does not.** It bounds the push in one direction. A miner dating at exactly `local + FUTURE_TIME_LIMIT_SECONDS − 1` is never withheld and never scored, and because the difficulty rule reads `max(0, Δt)`, such a block adds `FTL − 1` to the weighted solve-time sum while the honest block after it — whose true step is negative — contributes zero instead of cancelling it. The inflation is therefore cumulative per attacker block, and a fixed point exists only where `p < TARGET_BLOCK_SECONDS / FUTURE_TIME_LIMIT_SECONDS` (16.7 % on mainnet, 2.8 % on devnet; the threshold scales with the block goal, so a faster network is proportionally more exposed). Above that share the target walks to `MAX_TARGET` and stays there, where `BlockWork` is 63 for every header and fork choice degenerates toward a block count. `MAX_TARGET` (§9 rule 6, F-PARAM-1) is the only backstop against this, and a chain pinned there is compromised rather than safe. Implementations MUST NOT read rule 8 as bounding timestamp manipulation generally; it bounds the downward collapse described above only. The upward direction is bounded elsewhere: by signing the solve-time accumulator and clamping it symmetrically, and by normalising the retarget against the window's *average* target rather than its last one.

   **That threshold is a necessary condition, not a safe margin, and the difference is measurable.** It is derived from the *mean* solve time, i.e. from a model in which block arrivals carry no dispersion. It assumes away two kinds of dispersion, and each breaks it on its own. Real proof-of-work arrivals are exponential, and driving the same `NextTarget` with exponential intervals and **no attacker at all** reaches `MAX_TARGET` in roughly two thirds of long mainnet runs — about as often with the modelled interval floored at one second, so it is the controller and not timestamp granularity; that cause is separate from rule 8, being the retarget's normalisation against the window's *last* target rather than its average. And the derivation assumes the attacker's blocks are evenly spaced, which is the minimum-variance placement: with the same dispersion-free clock and the same share placed at random, mainnet reaches `MAX_TARGET` well below the threshold. So `p < TARGET_BLOCK_SECONDS / FUTURE_TIME_LIMIT_SECONDS` says what a *deterministically spaced* attacker needs in order to move the target against a *dispersion-free* chain; it does not say the chain is stable below it. Both of those two rules have to be in place before the number means what it looks like it means.

Height 0 is never requested: the genesis header's parent slot carries the consensus root rather than a block, so it can never attach.

**Nor is it ever announced, delivered or cited, and a node MUST refuse a height-0 header on all three paths.** The work check is defined to pass unconditionally at height 0 — genesis carries no work, correctly — so a height-0 header is the one header that costs its sender nothing, and every node already holds genesis from its own parameters. A node that does not refuse it hands an attacker a free path into everything downstream of the work check, including any orphan pool, whose plausibility bounds constrain a *declared* target and never ask whether it was earned. The citation case is the one that looks like a consensus change and is not: a height-0 citation is already refused by the block rules on every path that applies a block (no block below height 2 may cite, and above it a citation must be at the block's height minus one), so refusing it at ingress rejects earlier — and scores — only blocks that were already unconditionally invalid. Refusing a citation the block rules would *accept* remains a consensus change, as rule 7 states.

A node MAY hold blocks that do not attach to its chain (an orphan pool) as an optimisation, but if it does it MUST bound them by count, by total bytes, and by height distance from its own tip, and MUST NOT treat their declared work as meaningful.

## 10. What an inbound message costs its sender

This section is the ingress cost contract. It exists because fifteen separate findings in one implementation were one defect: **the node had no unified notion of what a peer's bytes are allowed to cost.** Each handler decided locally whether to score, dedup, rate-limit or serve, so each adversarial sweep found the next handler that had decided wrong, and fixing them one at a time could not converge — any new handler, and any reordering of the checks inside an old one, mints a fresh instance. What follows is the rule those findings are instances of. It is policy and not consensus: a node that gets it wrong is cheap to attack, it does not fork.

### 10.1 The cost-ordering rule

**An ingress pipeline MUST order its checks so that the cheapest check that can refuse a message is the one that does.** Concretely, in this order:

1. **Structural checks** — integer and byte comparisons decidable from the frame alone: length, kind, version, height, declared target, parent linkage, the payload being exactly consumed.
2. **Dedup and window checks** — is this already held, already committed, already seen; is it inside the height, time or TTL window this node will consider at all.
3. **Read-only rate and budget checks** — is the peer inside its request window; would the result fit the bounds this node keeps.
4. **Signature verification and proof-of-work evaluation.**
5. **Any gate that mutates shared state** — charging, reserving, evicting, recording, admitting.

Steps 4 and 5 are in that order and not the other one, and the boundary between step 3 and step 5 is the whole reason those are two steps rather than one "budget" step. A budget gate is safe to run before authentication **precisely while it only reads.** The moment a gate charges, reserves, evicts or records, running it early hands an unauthenticated stranger a write — a worse ingress-cost failure than the wasted CPU the ordering was introduced to remove. Measured on an implementation that hoisted a mempool eviction pass in front of signature verification because eviction is nominally a budget check: one certificate carrying a garbage signature removed ten honest residents, for the price of one gossip message. The old order wasted CPU; that order let a stranger empty the pool.

Two consequences, both normative:

- **A message that fails at step 1, 2 or 3 MUST NOT have caused a signature verification or a proof-of-work evaluation.** This is a property an implementation is expected to pin with a test rather than assert in a comment, because it is an *ordering*, and orderings are what a refactor changes silently while every unit test stays green.
- **A structurally-valid but unauthenticated message MUST NOT cause an observable mutation of shared state.** Admission to a pool, an eviction, a budget charge and a dedup record are all mutations; a peer that has not yet been shown to be sending something real MUST NOT be able to buy one.

**That second consequence has exactly one enumerated exception, and enumerating it is the point.** The four classes of §10.2 price what a refusal *cost*; none of them can say that a refusal also **granted** something, so a grant nobody wrote down is the unnamed `Free` one level up. The one grant permitted here is a refresh of the sender's **sync candidacy** — the record that this peer offered a header this node cannot place, `PeerTip.OffersUnknown` in `node/p2p` — made on the two `block-announce` refusals that stand ahead of the work check: the future-time refusal of §9 rule 8 and the key-epoch refusal of §10.3. Nothing else is written on either path: no admission, no eviction, and deliberately no dedup record, because marking the id seen would dedupe away the re-announcement that arrives once the clock or the budget recovers.

The reason is liveness rather than economy. A node whose clock is slow past the future-time limit, or whose key-epoch budget is spent because it is behind, stops accepting that peer's gossip; a refusal that also stopped refreshing candidacy would degrade its view of who is worth asking at the exact moment asking is the only mechanism it has left. **What makes the grant affordable is what it decides, not what it costs** — it costs nothing at all, since both refusals stand ahead of the work check, so no proof of work is evaluated and the header need carry none. It is safe because candidacy decides **who is asked, never what is believed**: every header a sync answer carries is re-derived from the difficulty rule before any body is fetched (§9 rules 1, 2, 4, 6), and how many such candidates there may be is bounded by §11 rather than by this record. **A further grant of any kind MUST be added to this list rather than left to be discovered.**

One further rule of the same kind, about a lock rather than about state: **signature verification MUST NOT be performed while holding a lock this node's readers contend on.** A forged certificate is never pooled, so it never raises the deposit screen or the per-underwriter count that bound honest traffic — one funded deposit cell therefore screens an unbounded stream of *distinct* forgeries, and no step-2 or step-3 gate ever sees one of them twice. Verifying those under a pool's write lock converts a parallel CPU cost into serialized unavailability of the pool.

### 10.2 Every outcome is priced

**Every outcome of every ingress handler MUST name what the sender paid.** There are four classes and no fifth:

| Class | What bounds the repetition |
|---|---|
| `Free` | Nothing. Permitted only where this section says so, and only with the reason stated. |
| `Scored(n)` | The peer's score moves by `n`, and a peer far enough below zero is disconnected and not re-dialled. This is the only class that terminates a flood of *distinct* messages. |
| `Deduped` | A record this node already holds answers it, so the second and later copies cost a lookup and nothing behind it. A dedup answer with **no** record behind it is `Free` wearing a disguise; the record is the bound, and it MUST itself be bounded. |
| `Budgeted` | A bounded resource — reassembly bytes, a transfer slot, a request window, reply bytes — was consumed or was already exhausted. The budget is the bound, and it MUST be bounded independently of anything the sender chooses. |

`Free` is a category, not a hole. Duplicate gossip is free because in flood gossip every node receives every message several times *by design*, so penalising duplicates penalises the topology working correctly. A withheld block is free because whether a block is early is a fact about the receiver's clock (§9 rule 8). A refusal that is this node's own condition — its disk, its pool being full, its tip having moved — is free because it is not the peer's fault, and charging it makes a node in trouble ban the peers still willing to serve it. What this section forbids is the **unnamed** free: an outcome nobody decided the price of. Every one of the fifteen findings was one of those.

An implementation is expected to carry the class in the value its handlers return, so that "this outcome has no cost class" is a build failure rather than a reading. `node/p2p` carries it as `Verdict.Cost`, whose zero value is `CostUnpriced` and is never a valid answer; `TestEveryVerdictIsPriced` reads that package's syntax tree and fails on a literal that leaves it there.

### 10.3 The table, per message kind and outcome

This table is **total**: every kind in §3, and for each kind every outcome its receiver can reach, has a row. Adding a message kind without adding its rows is an incomplete change, and reaching an outcome that has no row is the defect this section exists to stop.

It MUST also be a **function**: no two rows may match one reachable outcome. Totality alone is the weaker property and the more dangerous failure of the two, because a table that answers everything and answers some things twice still reads as authoritative — an implementer looking up a condition finds a row, stops, and never learns that the row next to it says a different class for the same input. The way this breaks in practice is by refinement rather than by omission: a later finding splits one row's condition into two cases and adds a row for the new one, and unless the **old** row gains the qualifier that excludes it, one condition now names two classes. Four cases have happened here. Two — the key-epoch refusal and the reply-byte refusal — were split on the same fact, whether this node's own work check has already refused an announcement from the sender, and in both the pre-existing row carries the negation explicitly for this reason. The third is **the split by layer**, and it is worth naming separately because it is not a fact about the sender at all: a refusal by a budget keyed on the sender's identity and a refusal by a ceiling keyed on nothing are different outcomes with different classes, and the two are reachable together whenever both counters are exhausted. The reply-byte rows gained that exclusion and the `block-announce` key-epoch rows did not, so the node-wide announce ceiling had **no row at all** while its outcome silently matched two rows whose conditions were false. Both halves of that are now fixed. **The fourth is the plainest instance of the refinement this paragraph warns about, and it is recorded because it went the right way rather than because it went wrong**: §5 step 4 carried one row, a new rule on the same branch split its condition in two, and the pre-existing target row gained the height qualifier in the same change that added the height row — rather than leaving one reachable header matching both. The lesson is the one this paragraph already states from the other direction: **a new layer needs a row of its own *and* an exclusion on every row it can be reached beside.**

| Kind | Outcome | Class |
|---|---|---|
| `hello` | Accepted | `Scored(+1)` |
| `hello` | Malformed, wrong network, wrong protocol, a second handshake on one connection, or any other kind arriving before it | `Scored(protocol violation)`, then disconnect |
| `certificate` | Accepted and forwarded | `Scored(+1)` |
| `certificate` | Malformed, or fails a V-rule | `Scored(invalid)` |
| `certificate` | Already pooled or already committed | `Deduped` — the pool and the chain's TTL-pruned seen-set are the records, and both are bounded |
| `certificate` | Refused because this node's pool is full and would not evict for it | `Free` — local condition, not the sender's fault |
| `certificate` | Refused below the eviction floor, or as unpoolable and **not established invalid** — the signature pass runs last, behind every O(1) policy gate, so a certificate a policy gate names is refused without this node having reached any verdict on its validity (§10.5) | `Free` today; MUST become `Scored` or `Deduped` — see below |

That phrasing is a stated gap and not an endorsement, and writing the table out is what makes the gaps countable instead of discoverable. There were more: `get-block` and `get-headers` served became `Budgeted` when the per-identity reply-byte budget landed, and `get-peers` served when its bytes moved onto the node-wide ceiling — which is what a gap being countable is for.

`get-peers` served was the last of those three, and it moved for a reason worth keeping in view because it is not the reason the other two moved. The bytes were never large — one connection buys at most one ~1.2 KB reply per memo window, so every connection this node admits asking as fast as it may is a fraction of a percent of the node-wide ceiling, and no arrangement of peers exhausts anything. What was wrong was the *claim*: §10.4's second normative bullet and the counter behind it are derived from "the total this node emits", and while one served kind stood outside that counter the total it held was a different total. A reader checking the invariant against the code would have found it false and repaired the sentence rather than the code. So the reply bytes are charged against the layer keyed on nothing, and the per-identity budget is deliberately still not charged here — see §10.4.

The certificate refused below the eviction floor is the one that remains, and it is the sharper one because it is not about bandwidth. **A refusal that scores nothing and is recorded nowhere is replayable forever**, and that is a property of the *refusal*, not of how expensive the check behind it is. Making the walk that produces it cheaper reduces the cost per replay and does not bound the number of replays, so it does not close the finding — only a score or a record does. That is the whole content of the `Free` row's obligation to give a reason: "it was cheap" is not one. The two shapes are — an out-of-window body that re-buys its checks forever at score 0, and an unpoolable-but-valid certificate that is an unscored signature flood.

Every other `Free` row names a reason, and each of those reasons is about the *sender not being at fault* rather than about the check being cheap: duplicate gossip is the topology working, a withheld block is this node's clock, a refusal from this node's disk or a moved tip is this node's condition. **One row's reason is of a second kind, and it is admitted here rather than folded into the first:** the certificate refused as unpoolable and not established invalid is free because *this node did not reach a verdict*, which is a statement about the receiver's knowledge and not about the sender's conduct. It does not collapse into the other — the sender may well be at fault, and this node has simply not established that it is — and it is legitimate for the reason §10.1's ordering exists at all: a refusal that stopped at a cheaper gate never evaluated the predicate a charge would have to name (§10.5). A row that could name a reason of neither kind — in particular one whose reason is that the check was cheap — would be the finding.

### 10.4 Serving is metered

**A handler that answers a query MUST NOT do work proportional to the size of this node's state, and MUST serve from what the node already holds.** A request frame is a fixed number of bytes and its answer is not, so anything the responder recomputes per request is an amplifier whose lever is the requester's frame. Three rules follow:

- Serve **stored bytes**. A node that decodes a block and re-encodes it to answer `get-block`, or decodes a block to read the one header `get-headers` wanted, has made a fixed-size frame buy a decode of arbitrary size.
- Where an answer is a **selection over state** rather than a lookup — the address-diverse selection of §7 is the case — it MUST be computed at most once per window and reused, and the memo MUST be invalidated by the state it summarises changing, not by the passage of time alone.
- **Asking again inside that window MUST NOT be free.** Memoising bounds what one request costs this node in CPU; charging for the repeat is what makes a flood of them terminate. A 5-byte `get-peers` frame whose answer is 1.2 KB is a ~240x bandwidth amplifier however fast the selection becomes.

**A node MUST bound the rate at which a peer may issue requests and the total bytes it can make this node send in reply,** and the exhaustion path MUST itself be priced under §10.2. This is the `Budgeted` case. `get-headers` (one 12-byte frame buys on the order of 116 KB of headers) and `get-block` (a fixed-size frame buys up to one 4 MiB chunk, and a peer may walk every chunk of every block this node holds) are bounded per message; what was unbounded is the aggregate, and that is closed for those two with a per-identity reply-byte budget refilled once per block interval. `get-peers` is bounded by the memo window above rather than by that per-identity budget, **and its reply bytes are now charged against the node-wide layer below, so its `Served` row reads `Budgeted`.** Only one of the two layers moved, and which one is the whole content of the change: the node-wide ceiling is keyed on nothing a sender presents, so charging it conflates nothing with the memo window's own key, while the per-identity budget is keyed on the authenticated identity and the memo window is keyed on the connection — charging that budget without first moving the window onto the identity keyspace would put two limits on one handler under two different names, which is the defect measured next door rather than a fix. The magnitude never was the argument: the memo window bounds one connection to about 1.2 KB per window, so the whole of peer exchange is a fraction of a percent of the ceiling. What the change buys is that "the total this node emits" is the total the counter holds. **The MUST above has two conjuncts, and where the second is discharged the first is discharged only in part.** The reply bytes are bounded, at two layers (below). The request *rate* is bounded only for a sender this node has independently established is not honest, and that is a deliberate limit rather than an oversight. §10.2 says a negative score is the only class that terminates a flood of *distinct* messages, so an unconditionally unscored refusal leaves a peer past its budget free to go on asking, be answered nothing, and accumulate nothing against itself. **But scoring every such refusal is the worse failure**, and it is a measured one: the budget is sized at the sustained-bandwidth floor, so an honest peer on a faster link reaches it by bulk-syncing rather than by misbehaving, and a refusal at `Scored(excess request)` bans a fast honest syncer inside twenty frames. So the score is conditioned on a fact this node established for itself and that an honest peer cannot acquire — an announcement from that identity already refused by the work check (§5) — and it is charged only where the sender's **own** budget refused it, never where the shared node-wide ceiling did. What remains unbounded is the refusal rate of an identity this node has never caught, and the reason it is left there is that a count per window would need a refusal rate an honest bulk syncer never exceeds, which no measurement supplies; what bounds it meanwhile is that a refusal costs the responder strictly less than the answer it replaces, and costs the sender a frame and a round trip, so the amplification is below 1. Closed on those terms.

Two properties of such a budget are normative, and neither is incidental to how one happens to be written.

- **It MUST be keyed on the most durable name the transport authenticates, and never on a value the sender is handed a fresh copy of for free.** A budget keyed on the connection is re-bought for the price of one TLS handshake, which is a rate limit at handshake cost and not a bound — the same defect §10.5's scoring carried until an identity-keyed tally was added beside the address-keyed one. §10.2's `Budgeted` row is what this serves: the budget MUST be bounded independently of anything the sender chooses, and an inbound connection's `ip:ephemeral_port` is picked for the peer by the OS rather than by the peer. **Keying it on the authenticated identity is not the same as bounding the aggregate, and an implementation MUST NOT read it as though it were.** Minting a fresh identity is free — `docs/decisions/networking.md` says so in as many words about the identity-keyed scoring this budget sits beside, "rotating its own key every connection, which is free by design and which this never claimed to prevent" — so a per-peer budget bounds one peer and leaves this node's total egress bounded by how many peers it admits at once. That second bound belongs to connection admission rather than to this budget, and leaving it to the socket leaves it to nobody. **So a conforming implementation MUST carry a second layer keyed on nothing at all** — one counter, no table to evict from, no identifier a sender presents — sized as the concurrent connection set the node admits multiplied by one identity's window, so that no arrangement of peers the node could serve before the ceiling existed is refused by it at an instant, while identity churn no longer multiplies the aggregate. Two layers, because no single axis is both exact and unmintable: the per-identity layer is what makes one peer's demand attributable, and the node-wide layer is what makes the total a number somebody picked. Both MUST recover inside one window; a ceiling whose recovery is longer than its own window is a one-way latch rather than a bound. **What this deliberately does not do is size the ceiling against the operator's own link**, which is the tighter number and is a policy input rather than a derivation; recording the obligation here is what keeps that a decision somebody takes rather than a gap somebody rediscovers.
- **It MUST be sized against a stated sync-throughput target rather than picked as a round number, and the sizing MUST be demonstrated on the honest workload as well as the hostile one.** Honest bulk sync is the workload that legitimately issues these requests at rate. A conforming implementation is therefore expected to carry two tests and not one: one driving a peer past the budget and asserting the answer stops, and one driving an honest bulk-sync rate and asserting it is never refused. A budget that denies service to the workload it exists to protect is not a fix.

### 10.5 Peer scoring

Scoring is local policy, not protocol: two implementations may score differently without diverging, because scoring decides who a node talks to and never what it accepts. It is the `Scored(n)` class of §10.2, and the categories that MUST be distinguished, because they mean different things:

| Category | Meaning |
|---|---|
| Protocol violation | Malformed frame, unknown kind, wrong network. Disconnect immediately. |
| Invalid message | Decodes but fails validation — bad work, forged target, inconsistent announcement. Strongly negative. **A verdict this node evaluated, never one it inferred:** where a cheaper gate refused first the validation did not run, so the outcome is not this category however invalid the message would have turned out to be. Charging for a verdict not reached is the mirror of §10.2's unnamed `Free`, and the certificate row of §10.3 is the instance. |
| Unserved body | Advertised something and would not serve it. Negative; may be honest failure. |
| Unsolicited | Well-formed, but a response this node cannot attribute to a request it sent (§6, §7). Neither: it is not a false claim about anything, and paying for it is a positive score at the price of a few bytes. |
| Useful message | New and valid. Positive. |
| Already known | Neither. Duplicate gossip is normal and MUST NOT be penalised. |
| Withheld | Dated past the future-time limit (§9 rule 8). Neither: whether a block is early is a fact about the receiver's clock, so charging for it lets a node with a fast clock score down every honest relay, and lets clock skew look like misbehaviour. |

The last row is the one that is easy to get wrong and expensive to get wrong: in flood gossip every node receives every message several times by design, so penalising duplicates penalises the topology working correctly.

The `Unsolicited` category is stated as *cannot attribute*, and that wording is load-bearing now that a node asks for peers. It used to send no `get-peers` at all, so "a request this node never sent" and "a frame the receiver cannot match to a request" were the same set. A conforming node now sends one `get-peers` per interval to one outbound peer, so a `peers` frame may well be answering something. §12 removes request ids deliberately, and nothing else correlates a `peers` frame to the `get-peers` it claims to answer, so a receiver still cannot decide "solicited" — which is why this table gains **no** `solicited reply` row. §7's rule is the safe form of the same idea and stays as it is: a node MUST NOT score a `peers` frame positively unless it sent the `get-peers` it answers, and where it cannot establish that, it does not score. `docs/decisions/networking.md` §12.2 records why per-connection solicitation tracking was rejected and what the residual is.

The `headers` half of this row moved for a different reason and ends in the same place. A node used to send `get-headers` only on the dedicated sync connection, which never reached this table's handlers at all, so a `headers` frame arriving on the gossip loop was unsolicited *by construction*. §12 now lets a sync request travel over the gossip connection an undialable peer opened, so this node does send `get-headers` there and a well-formed `headers` frame on that connection may be answering it. What keeps the row right is §12's matching rule rather than construction: **only** a frame the outstanding request could answer is ever claimed, so the frames that reach this table are the ones no outstanding request **did** claim. The rule is only-if and not if — an implementation whose waiter already holds an answer declines the next frame, and that frame reaches the ordinary handling and is scored there like any other, which is what the second of §12's three MUSTs requires. So the right description is *cannot attribute* rather than *never asked*, exactly as for `peers`. The attributable case earns no row here either, and for a further reason: a claimed frame is never an outcome of an ingress handler at all.

## 11. Connection management

- Outbound targets MUST be selected with address diversity (§7), so that one hosting range cannot fill a node's outbound slots. This is the eclipse defence, together with the per-source inbound bound and a peer store that survives restart.
- Outbound targets MUST also be bounded **per gossip source**: a node MUST NOT let the addresses it learned from any one peer take more than a small fixed share of its outbound slots. Address diversity alone does not supply this, and the reason is arithmetic rather than judgement. An address group is a property of an address an attacker *owns*; an address a peer *claims* — one carried in a `peers` frame, and equally the `listen_addr` a peer advertises in its `hello` (§4) — is four bytes it *invented*, and any four bytes are a valid IPv4 host, so an attacker with no addresses at all mints one fresh diversity group per string for the price of one frame, or one TCP connection. What it cannot invent is the connection the claim arrived on. An implementation that records only the address and not its teller satisfies the previous bullet and is still eclipsed by one frame — and a claim is a claim whichever message carries it, so an implementation that records the teller for `peers` but not for `hello` leaves the same eclipse open through the second door. `node/p2p` records the teller's address group on each learned address and allows at most two selected slots per teller; addresses the node was not told about — bootstrap entries the operator supplied, sockets it connected to — have no teller and are not bounded by this. A socket a node was *connected by* has no teller either, and is not an outbound candidate at all: see the next bullet.
- **The socket an inbound connection arrived on MUST NOT become an outbound target.** It is the peer's *source* address — an ephemeral port the peer's OS chose, not something it listens on — so a slot spent dialling it is a slot spent on an address that cannot answer, and a dial loop that dials serially loses the whole dial timeout with it. The peer's dialable address is the `listen_addr` in its `hello` (§4), which arrives separately and is a *claim*, bounded by the bullet above. Recording the socket is still correct — it is the key a node scores and bans the connection under — so the rule is on candidacy, not on admission, and it belongs to the path that records the address rather than to the selector, which could only guess from the port number. Measured on an implementation without it: twenty `hello`s from ephemeral ports on one address took two outbound slots on invented `listen_addr`s, which the per-source bound permits, *and* two more on the sockets themselves, which nothing bounded but the per-group fallback allowance — four of eight outbound slots from a single `/16`, half of them provably unreachable. A node that later learns the same address as a `listen_addr` MAY treat it as dialable again, because a claim is what makes an address a candidate; it is then bounded per source like any other claim.
- **Both outbound bounds MUST be counted against the connections a node holds, not against one selection call.** This is the bullet that makes the two above mean anything, and it is stated separately because omitting it does not look like omitting anything: a dial loop that asks for targets each round, passing the peers it is already connected to as an exclusion, removes them from the candidate set *before* the per-group and per-source counters are built, so every round begins with both budgets full again. The bound then delays an attacker by one round per allowance instead of bounding it. Measured on an implementation that did this: one teller took 2, then 4, then 6, then 8 of 8 outbound slots over four rounds, and one `/16` did the same, which is the first bullet's MUST failing by accretion. Count the held outbound connections into both budgets before selecting. Inbound connections MUST NOT be counted: they are chosen by the peer, so counting them would let an attacker connecting from many groups veto this node's dials into exactly those groups.
- The per-source bound belongs to the **dial** path and MUST NOT be applied to a `peers` response (§7). Whose gossip taught a node an address says nothing about the eclipse risk of the node receiving it, and applying the bound there throttles honest dissemination rather than an attacker — measured, a young node holding several hundred addresses learned from one honest bootstrap peer answered with 2 addresses where 64 were permitted.
- Inbound connections MUST be bounded **per source address** as well as in total. A single source that can open the whole inbound allowance can eclipse alone.
- **A node MUST NOT let the addresses it has itself connected to stay bounded by whoever first mentioned them.** The per-source bound prices what a peer *claims*; a completed connection is the node's own check of that claim, so an implementation that stamps the teller once, at creation, and never revisits it hands an attacker a permanent hold over every honest address it manages to name first — and if the field is persisted, one that survives restarts. Measured on an implementation that did this: 20 honest addresses first named by one attacker, re-gossiped afterwards by 20 distinct honest tellers and then all 20 actually connected to, yielded **exactly 2** of 8 outbound slots, and 0 on the following round. Clearing or exempting the teller on a completed connection is the fix; it relaxes nothing else, because such an address is still bounded by address diversity, which is the bound that prices addresses an attacker *owns*. The relaxation MUST NOT extend to the *held* connections counted into the budget under the bullet above, or a teller converts its allowance into more allowance one round at a time and the accretion that bullet closes returns.
- **The admitted-connection table MUST evict at capacity, and MUST NOT be first-come-first-served.** This is the same rule as the peer store's two bullets below, at the layer above it, and stating it only for the store was not enough: a table that refuses at capacity and never evicts is held permanently by whoever fills it first, and a connection is cheap to hold — any small keep-alive frame inside the read timeout costs the holder nothing and is scored nothing. Measured by inspection on an implementation without it, roughly fourteen addresses in distinct groups at three connections each exceed a forty-slot table, after which no honest peer can ever open an inbound connection again. **The victim MUST be chosen by address-group share, and a diverse, recently-useful subset MUST be protected**: a connection alone in its group is not a candidate while a more concentrated group has one, a connection that has recently delivered something scored positively outranks one that has only held its slot, and the youngest goes before the oldest of equal standing, because an attacker that churns keeps its connections newest. Two exclusions are load-bearing. **Outbound connections MUST NOT be candidates** — they are the ones this node chose, under the bounds above, so evicting one on an inbound arrival's behalf hands a peer that merely connects the power to unpick the node's own dialling. And **an arrival MUST NOT be able to concentrate the table**: where no group is more concentrated than the arrival's own would be, the arrival is refused and nothing is evicted, so a table of peers in distinct groups is never churned.
- The peer store MUST be persisted, and MUST be bounded. Unbounded admission is the same defect from the other side: **the arrival of a `peers` frame is the sender's decision**, so a store with no cap is memory an attacker writes to for free, and one that is persisted is memory it writes to across restarts. (This bullet used to say a `peers` frame is *unsolicited by construction*. A conforming node now sends one `get-peers` per interval, so that premise is false — but it was never the premise the conclusion needed. What makes the store attacker-writable is that the sender chooses when to send, and how many addresses to put in the frame, and §12 leaves the receiver no way to tell an answer from a volunteer. Asking for peers does not make what arrives bounded.) A node that starts with a blank slate after every restart hands an attacker a fresh opportunity on every restart; a node that starts with the attacker's slate hands it the same opportunity permanently.
- A bounded peer store MUST NOT refuse a well-formed address because it is full; it evicts for it. Refusing is the failure this bullet exists to name: a never-contacted honest address is never better than a never-contacted invented one, so an attacker who fills the store first locks it shut against everything offered afterwards, the operator's own bootstrap list included.
- What eviction chooses matters more than that it happens, and it MUST NOT be decided by group share alone. "Take the victim from the largest population" reads as *a flood displaces itself*, and is that only while the flood is the largest thing in the store; on a node bootstrapped from one helpful peer the largest population is that peer's address book. Measured on an implementation ordered that way, 200 invented addresses from one source evicted 200 honest addresses at no cost to the attacker. Three rules together avoid it.
  - **A store SHOULD bound how many of its entries any one source may hold**, so that a source at its ceiling evicts strictly from itself and no source can grow large enough to be everyone else's eviction source. Filling the store then costs real addresses in real groups rather than one frame.
  - **Entries a node has evidence about — a connection it completed, or score it earned — MUST outrank group share when choosing a victim**, and entries it has evidence *against* — dialled and never once answered, or scored below zero — MUST rank below both. Share is only meaningful among entries that are otherwise indistinguishable, which unproven entries are and the other two are not.
  - **Among indistinguishable entries the final tie-break MUST NOT be anything the gossiping peer chooses**, the address included, **and this applies to selection exactly as it applies to eviction.** The rule was written for the victim comparator and discharged only there, which left the identical defect standing one function away and cost nothing to reach: an honest address learned by gossip and not yet dialled is identical by score, evidence and failure count to a freshly invented one, so on the dial path too the last key is the whole policy. Measured on an implementation whose selector fell through to the address string, 8 honest addresses from 8 honest tellers against 8 invented ones from 4 source groups returned **8 of 8 invented** and 0 honest, and 0 honest outbound connections over ten rounds. Two consequences follow and both are normative here. Arrival order is the key on both paths (the sign differs: newest given up first, earliest dialled first). And where arrival order cannot separate — every entry restored from a persisted store shares one arrival, deliberately, since the writer of that file chooses the relative order otherwise — **the remaining order MUST be randomised** rather than left to fall through to anything derived from the entries themselves. An attacker that gossips real addresses before anyone else has them attributed to itself by first-teller-wins, and can then evict exactly those by flooding its own population with addresses that sort ahead of them — measured, 30 of 30 real addresses removed for about 32 `peers` frames, while the tie-break was the address string. Arrival order is a key the sender cannot choose after the fact.
- Where a store charges a gossiped address to its teller and an ungossiped one to its own address group, **the two MUST NOT share a keyspace**. Both are group identifiers, so unnamespaced, an attacker connecting from the same group as a node's bootstrap peers is charged to their population and evicts them from inside — measured, 30 of 30 operator bootstrap addresses for eight `peers` frames, and co-location in a `/16` with a bootstrap peer is ordinary in a cloud region.
- A node SHOULD keep dialling toward its outbound target: being under-connected is itself an eclipse risk. This is a preference and not a licence: where the bounds above leave a node unable to fill its slots without breaching them, it stays under-connected. An under-connected node syncs slowly; an eclipsed one accepts a false chain.

## 12. What is deliberately absent

- **No NAT traversal.** Cost stated in [networking](../decisions/networking.md) §5, reopen condition in §6.
- **No compression.** A compressor on an attacker-controlled stream is an attack surface for a bandwidth saving nobody has measured a need for.
- **No message-level signatures.** The transport authenticates the channel; consensus objects carry their own signatures. A third signature layer would authenticate the relay, which is not something any decision depends on.
- **No request ids.** Request/response is matched by connection and order. Sync therefore runs on its own connection rather than sharing the gossip loop — which removes a state machine.

  *Amended.* The original reason given here was "costs one socket", and that was incomplete in a way only the long-distance catch-up regime made visible. The real cost is that the socket competes for the **inbound budget**: the per-source bound (§11) counts it against the same allowance as long-lived gossip connections, so a node whose slots were full by ordinary peering refused exactly the connection a peer needed to catch up. Behind CGNAT or any shared prefix — the common case for the miners this design targets — honest peers land in one address group by default and sync doubles the demand precisely when a node is behind.

  The decision stands, for a narrower reason than first stated, and with an explicit dependency: it is safe **because** the listener reserves a small separate allowance for connections that do not hold. An implementation that adopts the dedicated sync connection without that reservation inherits the bug. A conforming implementation MUST NOT let a node's ordinary peering exhaust the capacity for inbound sync connections from the same address group.

  *Amended again.* "Sync runs on its own connection" is the rule, and it is no longer unconditional. A peer that advertises no listen address cannot be dialled — §7 MUSTs that a node accepting no inbound connections advertises empty, and an inbound socket is recorded as `ip:ephemeral_port`, which is nothing this node can connect back to — so a node that syncs only over connections it opened can never catch up from a peer that opened the connection to it, which is the ordinary shape of a NAT'd network. **"Not dialable" is a fact about a route, not about a field.** An advertised address that refuses or swallows the connection is as undialable as an absent one, and it is the commoner case rather than the exotic one: a node that binds a wildcard or a private address and advertises what it bound has published somewhere nobody outside can reach, and every listening node it dials records that as its dialable address. An implementation that reads this rule as "advertises nothing" leaves the identical freeze open through the branch it did not close, and leaves it *harder* to see — such a peer is a candidate, so the `ahead_peers` signal that named the first freeze reports the second as healthy. Only a connection attempt establishes reachability; a claim is where to look first, never what to conclude. Three MUSTs:

  - The dedicated sync connection remains the rule, with the inbound-reserve dependency above unchanged.
  - A conforming implementation **MAY** conduct sync over an existing gossip connection when the peer is not dialable — including when a dial it attempted produced no connection at all, which is the only way an unreachable advertisement can be told from a reachable one, and the node running it is the one that is behind, so it is the requester rather than the responder — and **MUST** then match a response to the request it answers **by content**: a frame is claimed only if it *could* answer the outstanding request. For a body chunk that means it decodes **and** carries the block id and chunk index the request named; for a `headers` frame it means only that it decodes, since §6 states that nothing else about one is checkable. Every frame not claimed reaches the ordinary gossip handling and is scored there under §10. That is narrower than request ids and it is more than "connection and order"; naming it here is what stops the next reader concluding the matching is unspecified.

    **The decodability term is load-bearing, not a detail.** §6 is normative that a `headers` frame MUST still be decoded so a malformed one is scored as invalid, and the ordinary gossip handling is the only place that charges it. An implementation that claims *any* frame of the awaited kind diverts a malformed one away from its only scorer, and a sync attempt that then merely fails charges nothing — so a malformed frame is free for as long as a request is outstanding. That is exactly the unnamed `Free` §10.2 forbids, reached without adding a row to any table.
  - Candidacy decides **who is asked**, never **what is believed**. Admitting inbound peers as sync candidates therefore adds no trust: every header and every body is re-derived exactly as it is from a dialled peer (§9 rules 1, 2, 4, 6). Nor does it add an eclipse surface: a peer reached this way already holds an inbound connection, so the inbound candidates are a subset of the inbound connections, and how many there may be is carried by the bounds of §11 — the total inbound bound, and the per-source inbound bound for any one source.

    **Those bounds carry what a hostile candidate costs this node. They are not a bound on service.** Least-recently-tried rotation serves one candidate per sync interval, so a candidate that qualifies on neither height nor claimed work — one holding candidacy only through an unplaceable *block*, announced or delivered, which expires and is refreshed by gossip — is reached only while a whole cycle fits inside the staleness window: `len(candidates) × SyncInterval ≤ offersUnknownWindow`. Nothing in §11 bounds the candidate set below that size; at the reference implementation's values the window admits ten where the connection maxima admit forty, so the crossing needs no attacker, and past it such a candidate is starved rather than delayed. This is a property of the rotation rather than of the **MAY** above — an implementation that keeps the dedicated sync connection has the same rotation — and it is open.

  (The mechanism is `syncOverGossip` in `node/p2p/syncdriver.go`.)
- **No forward-compatible extension mechanism.** Protocol 1 checks its version at the handshake and disconnects on mismatch. Extensions arrive as protocol 2.
