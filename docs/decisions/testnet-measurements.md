# Zycord — What the public testnet must measure before genesis

Some numbers in this project are arguments and some are guesses, and the difference is not always visible from inside. This is the list of numbers that **must be measured on the public testnet before the parameter freeze**, kept in one place because scattered across eight documents they are easy to agree with and impossible to act on.

Each entry says what to measure, what the current value rests on, and — the part that decides how much care it needs — **whether it can be changed after genesis**.

The distinction is not academic. A tunable number that turns out wrong is a release. A consensus parameter that turns out wrong is a fork, and for a chain whose entire proposition is that nobody can change the rules, a fork is the failure the design exists to prevent.

---

## 1. Irreversible at genesis — a wrong value is permanent

These are consensus parameters. They are committed to by the genesis id (R3-1), which *is* the network id, so changing one produces a different network. There is no upgrade path and that is deliberate.

### `undo_depth` — mainnet **1024**

**What it does.** The horizon past which a reorg is refused outright rather than performed. A node asked to reorganise deeper than this returns `ErrBeyondUndoHorizon` and does not move; recovering means resyncing from a common ancestor.

**What the value rests on.** Nothing measured. It was chosen as comfortably deeper than any reorg anyone expected.

**What we now know.** A 30-minute continuous-contention soak observed a reorg **43 blocks deep**, against a harness value of 128 — and the chain performed it atomically, with no rejected block and no state-root disagreement. Two readings, and both matter:

- *Reassuring:* R4-M1's crash-atomic reorg held at five times the depth anything had previously exercised, and roughly 24x below the mainnet value.
- *Uncomfortable:* nobody had previously produced a reorg deeper than about 9, so the distribution's tail was completely unmeasured, and the first serious attempt at measuring it moved the observed maximum by a factor of five.

**Why the harness number does not transfer.** It is more hostile than reality on one axis — something is killed or partitioned every two seconds — and far less hostile on another: four nodes, not thousands, so there is no long-tail propagation, no geographic partition, and no genuinely independent mining population. Tuning `undo_depth` on this data would be fitting a parameter to a distribution the harness invented.

**The instrument was blind, and finding that out is the actual result.** A later run observed a reorg of exactly **128** — which is precisely the harness's `undo_depth`. That is not a coincidence and not a maximum: `ConsiderBranch` refuses anything deeper, so the observation is *right-censored at the parameter being measured*. The earlier figure of 43 looked like a maximum only because the sample had not yet reached its ceiling. What we learned was not that the maximum rose, but that it is unknown — and was unknown before, without anyone knowing it was.

Any margin computed against a censored sample is unsound, including the "roughly 24x" that appeared in an earlier draft of this file. A censored sample says the distribution reaches *at least* the ceiling and nothing whatever about how far past it goes.

The soak now runs at `undo_depth` 1024 — mainnet's value — purely so the tail can be seen. That is a harness parameter serving a measurement, and it is deliberately not the same decision as the mainnet value, which stays here in §1.

**Every reorg-depth figure below predates a correction, and the correction is large.**

The numbers in this section — 43, 99, 122, 123, 297 — were all measured while the development
miner paced itself with a **fixed ticker** at exactly `target_block_seconds`. The dev
proof-of-work target solves instantly, so every miner emitted a block at the same instant as
every other one, forever: three chains of *identical* accumulated weight, which no fork-choice
rule can separate because equal work correctly never triggers a switch. The harness was not
simulating a slow network; it was simulating a coin that always lands on its edge, and the
deep reorgs were the network repeatedly resolving ties that should never have existed.

With pacing drawn from an exponential distribution — a Poisson process, which is what real
proof of work is and what RandomX produces at M3 with no pacing at all — the picture is
**regime-dependent**, and a first attempt at stating this correction got it wrong by
generalising one regime's number:

| regime | fixed ticker | Poisson |
|---|---|---|
| long-distance catch-up | 297 | **24** |
| continuous contention (three miners, never stopping) | 99, 123, 297 | **128** |

So the artifact inflated the catch-up figure enormously and the contention figure hardly at
all. "The real number is 24" was a catch-up observation carried past its regime; the honest
lab figure for the deepest regime is **128**.

That is close to the pre-correction contention numbers, which means the tail those runs
reported was largely real. The correction removes the 297 outlier and the alarm attached to
it; it does not remove the finding that reorgs reach ~130 under sustained three-way
contention with kills every two seconds.

Reorg depth is a property of the regime, not of the chain — which is itself the thing the
public testnet has to characterise, because the regime a real network occupies is not one this
harness can construct.

What does *not* change: the tail is still unmeasured on a real network, `undo_depth` below the
real tail is still a permanent-partition boundary rather than a margin, and only the public
testnet can characterise it. The correction lowers the alarm; it does not remove the
measurement.

**The first uncensored figure: 99 (superseded, see above).** Re-run at `undo_depth` 1024, the observed maximum was **99 blocks** — *below* the 128 of the run before it, which is the proof that 128 was the ceiling being struck rather than a measurement. With room to express, the tail landed near 99.

Read it precisely: a **lab lower bound from a single run**, a sample point of a heavy tail. It means "under this pressure, uncensored, the tail reaches at least 99" — not "the maximum is 99". Against mainnet's 1024 that is roughly 10x, and the comfort is not the number but that the instrument is no longer blind.

**The instrument had a second defect, and this one leaves a signature in the number.** The sync driver used to walk back to the common ancestor a whole `syncBatch` — 128 — at a time: `from -= batch`, anchoring the candidate at `from - 1`, and reorganising to that anchor rather than to the fork. `from` starts at `min(height + 1, peerHeight)`, so a reorg the walk stepped back for at all records `(height − from + 1) + k × 128` for some k ≥ 1 — **never less than 128**, and exactly `k × 128` in the ordinary catch-up case where this node is strictly behind. It is fixed: the walk now searches for the fork point instead of striding past it.

**So every 128 in this section is exactly one stride, and one of them is load-bearing.** The censored observation at a harness `undo_depth` of 128 is the harmless one — it was already discarded as right-censored, and it merely had two ways to be 128 rather than one. The one that matters is in the table above: the continuous-contention maximum under Poisson pacing, **128 at `undo_depth` 1024**, which this section then adopts as "the honest lab figure for the deepest regime", and which `sim/chaos/soak_test.go` turns into `contentionDepth = 256` as "2x that". That soak runs real `zycordd` processes, so its reorgs go through `node/sync` at `syncBatch` 128. The number cannot distinguish a fork 128 deep from a fork of any depth that cost the walk one backward step, and the shape of the jump is not reassuring: the same regime measured 99 and 123 before the pacing correction — both below the stride floor, so both true depths — and then landed on the batch size exactly.

**Stated at its real strength:** this is not a demonstration that the contention figure was an artifact. It is that the figure cannot be read either way, and that the reading which would settle it is cheap — re-run the contention soak on a build carrying this fix. Until that is done, 128 is not evidence about the tail, and neither is the 256 derived from it. Nothing here argues for *lowering* `contentionDepth`: a horizon that clears a number which may be an overshoot still clears the real one.

**The figures below 128 are untouched, and that is why the section's conclusion survives.** A walk that stepped back recorded at least one whole stride, so 43, 99 and 123 cannot have come from one — they are reorgs whose first candidate attached, or reorgs performed off the gossip path, and either way the depth is the fork's own. They keep exactly the standing they had above, and everything this section concludes stands unchanged: the tail is still unmeasured on a real network, `undo_depth` below it is still a permanent partition boundary rather than a margin, and only the public testnet can characterise it.

**The actionable part is forward-looking.** `deepest_reorg` collected from a node older than this fix carries a floor of `syncBatch` wherever sync stepped back to perform the reorg, so those readings do not pool with readings from a node carrying it. The public testnet's collection of this distribution starts at this version.

**What to measure on the testnet.** The distribution of reorg depth, not its mean: the 99th and 99.9th percentiles, and the maximum, over a period long enough to include real network incidents. `deepest_reorg` and `reorg_events` are on `/metrics` and are now persisted across restarts, so this is collectable from ordinary nodes.

**And the lab figure is not the answer.** Whatever uncensored maximum the soak produces against 1024 is *this harness's* number: more hostile than reality on one axis — something killed or partitioned every two seconds — and far less on another, with four nodes rather than thousands, no geography, and no independent mining population. It moves `undo_depth` from *unmeasurable* to *measured under known lab conditions*. Only the public testnet moves it to *validated under real ones*. Both steps are needed and the first does not substitute for the second; a future reader finding a soak number in this file should not mistake it for the verdict.

**The trade being decided, sharpened by a second finding.** Too high and every node carries undo history it will never use — disk, and the thing a laptop miner notices first.

Too low is worse than "a rare recoverable event becomes reachable", which is how this was first written. `ConsiderBranch` refuses a reorg deeper than `undo_depth` with `ErrBeyondUndoHorizon`, and **nothing anywhere triggers a resync when that happens**: the error appears in the fork-choice path, is swallowed into a `Verdict` on the gossip path, and has no other consumer. A node on the wrong side of a fork deeper than `undo_depth` therefore stays there permanently, refusing the heavier chain on every attempt, with no error surfaced and no alarm raised.

So the parameter is not a disk/latency trade with a safety margin attached. Below the real reorg-depth tail it is a **permanent partition boundary**, and the failure it produces is silent — the same shape as the batch-capped sync bug that hid behind it, which is how a four-node network was observed running as three separate chains for 358 blocks while every health signal read normal.

That gives the measurement its urgency: the tail is what decides whether a value is a margin or a cliff, and a censored instrument cannot see a tail.

### `epoch_length` — mainnet **2880**

State roots are checked only at epoch boundaries, so this is also the detection latency for a node that has silently diverged. I4-H3 is the cautionary tale: a soak converged at height 63 against a boundary of 64 and reported success, having never once run the only check that could have failed. Measure how long divergence actually takes to surface on a live network, and whether 2880 blocks — a day at 30-second blocks — is a tolerable window for a node to be wrong before anything says so.

### The emission constants — `genesis_emission`, `emission_decay_divisor`, `tail_emission`, `treasury_share_bps`

**Listed here to record that they are deliberately *not* on the measurement list**, which is the kind of omission that otherwise reads as an oversight in a review two years from now.

They are consensus parameters in the strongest sense — all four enter the consensus root, so any of them moves the genesis id — but nothing a testnet can do will validate them. The curve is an economic argument (whitepaper §14.2): a half-life of two years, a pre-tail supply of ≈62.74M, a tail sized to stay under 1% of supply annually. A testnet has no market, no holders and no security budget, so it cannot tell you whether that argument is right; it can only confirm the arithmetic, which the unit tests and the differential fold already do more cheaply and more exactly.

What the testnet *should* confirm about them is mechanical and cheap: that `zcd emission --height N` matches the schedule at the tail boundary, that the 97/3 split sums to the subsidy at every epoch's rate, and that the treasury cell's balance equals 3% of cumulative subsidy at any height a node is asked. Those are conservation checks, not measurements.

The honest statement of the residual risk: these are the parameters most likely to be *wrong in hindsight* and least likely to be *shown wrong before genesis*. The mitigation is that they are argued in public, in §14.2, with the arithmetic exposed rather than asserted — so the review window is where they get challenged, not the testnet.

### `ttl_max`, `max_certs_per_block_genesis`, the gas ceilings

The fee markets and the mempool are all downstream of these, and none has been observed under real demand. The testnet is the first time anyone will contend for sequential gas for a reason other than a test wanting them to.

### The sequential gas *density* of real traffic — and the calibration it decides

**The number to measure:** sequential gas per byte of block, over the traffic the network actually carries, as a distribution rather than a mean.

**Why it is on this list rather than merely interesting.** Two ceilings bound a block independently — `block_byte_limit` and the sequential gas ceiling `2T` — and which one binds first is decided entirely by this density. The break-even is where a physically full block lands exactly on the base-fee target:

```
break-even density = seq_gas_target_genesis / block_byte_limit_genesis
                   = 1,600,000 / 2,500,000  =  0.64 sequential gas per byte
```

Measured against the reference wallet, a plain transfer is **0.704** (600 gas in 852 bytes of block), which is now **above** the break-even by 9.1%: a block physically full of ordinary payments reports `applied/target = 1.0999` and pushes the fee *up*. **This entry is written in the past tense from here on, because the target was lowered and it is closed.** Until then the target was 2,000,000, the break-even was 0.8, the density was below it, and the consequence was that **bytes bound first and the sequential base fee could never rise** — the same byte-full block reported `applied/target = 0.880` and pushed the fee *down*, so congestion of the network's most common transaction never priced. It was the same failure as I6-C2 one order weaker, it predated the elastic ceiling, and it was invisible to every test that does not fill a block with one shape of traffic. (Both figures were off by the block's own overhead until they were re-derived, and the unit matters: the break-even is gas per byte **of block**, so the density has to be measured in the same unit. A one-move transfer encodes to 848 B of body and costs 852 B of block once its SSZ offset is counted, giving `600/852 = 0.704`; body-only accounting gives 0.708, which is the figure this line carried and which does not compose with what follows it. A byte-full block of them is 2,933 certificates — `852 × 2933 + 236 = 2,499,152` — applying 1,759,800 sequential gas, which was 0.880 of the old 2,000,000 target rather than the 0.885 that dropping the overhead gave, and is 1.0999 of the 1,600,000 that replaced it. The conclusion under the old target was unchanged in both cases: 0.704 and 0.708 were both under the 0.8 break-even, and both are above 0.64. The sizes are pinned in `core/fold/cert_budget_test.go`.)

Denser shapes sit the other side of it — a `MARK_SPENT` write is 700 gas in 97 bytes — so the honest question is not "what is the density" but "where does the distribution of *real* traffic sit relative to 0.64", which is exactly what a testnet under load answers and what nothing before it can. That question survives the decision — the margin chosen there is 9.1% against one measured shape, and a distribution is not a shape.

**Why measuring does not finish it.** Both levers are frozen at genesis: raise `block_byte_limit_genesis` to **≈2.84 MB** (`852 × 3,334 + 236 = 2,840,804`), or lower `seq_gas_target_genesis` to **≈1.76 M** (`2,933 × 600 = 1,759,800`), and either puts a full block of transfers exactly on target. *(These read ≈2.82 MB and ≈1.77 M until they were re-derived — `2,000,000 / 0.708` and `0.708 × 2,500,000`, the body-only figures the paragraph four lines above already retracts as not composing with what follows. Both levers are genesis-frozen and this is the entry a measurement will be read against, so the two values now match [ARCHITECTURE §20](../ARCHITECTURE.md)'s statement of the same gate, and the 13.6% below — `2,840,804 / 2,500,000` — which was already derived from the corrected one.)* The elastic ceiling then carries whichever choice is made to the top unchanged, because `seq_gas_capacity` is pinned to preserve the genesis ratio ([ARCHITECTURE §15](../ARCHITECTURE.md)). So this is a **calibration decision informed by a measurement**, not a measurement that decides itself — and it was an M5 gate on that basis until the decision that took the second lever and moved `seq_gas_target_genesis` to 1,600,000, past the on-target 1.76 M and down to a 9.1% margin under the measured density.

**Both halves are now decided; what the testnet owes is validation rather than the number.** The rule the owner ratified is that the genesis ratio must sit *below* the density of the traffic the network is built for, so a block full of ordinary payments raises the sequential base fee rather than lowering it — a subsidy on payments is acceptable only as a stated policy, and it is not the policy. Whitepaper §8.1 now carries that rule in one sentence. What the testnet decides is the value, and the recorded inclination is to move **`seq_gas_target_genesis` down** rather than `block_byte_limit_genesis` up: both land a full block of transfers on target and the elastic ceiling carries either to the top unchanged, but lowering the target changes no byte the transport must move, so it leaves the bandwidth entry below and every capacity re-pin sized against it untouched, and it leaves the launch throughput claim — byte-bound at ~2,933 certificates per block either way — exactly where §8.1 states it. Raising the byte ceiling buys the same calibration by asking every node for 13.6% more sustained bandwidth at genesis, which is a decision about who can run a node, taken to fix a fee-market constant. **That inclination was taken and closed, and it had to be closed here rather than on the testnet for a reason this list should record about itself: the number is in the `ConsensusRoot`, so a testnet whose value differs from mainnet's is not rehearsing mainnet's economics but measuring its own.** "Deferred to a testnet measurement" is not a state a frozen parameter can ship in. The value is 1,600,000, chosen over 1,700,000 because 3.5% of margin is inside the ~1% these densities have already moved twice under re-derivation and this number has no repair path after block 0. What the testnet now measures is whether the *distribution* of real traffic sits where the one measured shape does; if it lands below 0.64 plus margin, the magnitude returns to the owner and the direction does not.

### `block_byte_capacity` paired with the chunked-transfer bound — whether the measurement *sets* them or *confirms* them

**The number to measure is already on this list** — the sustained per-node bandwidth distribution of §2. What is not settled is *what that measurement is allowed to decide*. The [ARCHITECTURE §20](../ARCHITECTURE.md) M5 gate over this pairing **stands**; this entry states the dispute the gate turns on, and settles nothing.

**What is pinned is the pairing, not the value.** `block_byte_capacity` = 8,000,000 bytes and the transport's `MaxBlockChunks × BlockChunkBytes` = 4 × 4,194,304 = 16,777,216 bytes are tied to each other by `node/p2p.TestBlockByteCapacityFitsChunkedTransfer`, in both directions and over every parameter set `spec/` embeds, so neither can move without the other in the same release. The transport half was sized against the consensus half. Whether the consensus half is itself the right number — and whether a testnet measurement may only confirm it — is precisely what is open, so this paragraph is not an argument that the sizing is finished.

**What is open is the standing of the comparison the sizing rests on.** 8,000,000 — 2.1 Mbit/s sustained at a 30-second interval — was justified against a data-availability network already carrying 8 MB per 6-second block in production, which is conservative by roughly 5× **in byte rate**, and on that basis this entry was demoted from *"the public testnet is what should set them"* to *"the testnet's bandwidth distribution confirms it rather than sets it"*. Against that demotion: a DA network's nodes carry **opaque blobs**, while a Zycord node must carry *and* fold, verify and write every byte, and whitepaper §8.1 itself asks for capacity sized *"against propagation the health gate has measured"* — on which reading the comparison supports *"8 MB per 30 s is not reckless"* and nothing stronger. For it: the 5× margin is real and the byte rate is the quantity the transport is bounded by.

**Deliberately not resolved here, in either direction.** Which of *sets* and *confirms* the measurement earns is a decision about who can run a node, and it belongs to the owner — the same authority that ratified the capacity decisions. It is recorded so the measurement arrives with the question still open rather than pre-answered.

## 2. Tunable after genesis — node policy, not consensus

A wrong value here is a release, not a fork. They still need measuring, because a default every node inherits is a de facto standard.

- **The gossip ceiling.** [networking §5](networking.md) states flood gossip as "comfortable into the low thousands of nodes" — an estimate from message sizes and block time, never a measurement. It is the reopen condition most likely to fire. The ladder past it is in §9; rung 1 (announce-request for certificate bodies) is designed and not built, and should be built on evidence rather than pre-emptively.
- **The sustained bandwidth a commodity node holds**, as a distribution across the testnet's population. Every future capacity re-pin ([capacity-eras](capacity-eras.md)) reduces to this number: the genesis byte ceiling is ~0.7 Mbit/s sustained and the capacity 2.1, both far under any modern link, so the first era's re-pin will be sized by the measured tail of this distribution — the slowest node the network intends to keep — not by the genesis defaults. `/network` reports bytes in/out; what needs adding is only the aggregation.
- **The inbound-capable share of the network.** `/network` reports `listening`, `inbound`, `outbound` and `reachable` per node. The aggregate decides whether shipping without NAT traversal holds ([networking §6](networking.md)). `listening: true, inbound: 0` is the trap: unreachable while looking healthy in every other view.
- **Peer-scoring magnitudes and the ban threshold.** `-20`, `-50`, `-100`, ceiling `+100`. The shape is defended; the magnitudes are invented. I5-M5 is why this matters more than it looks: a ban now also removes a peer from sync candidacy, so an over-eager score is a liveness bug, not just a dropped connection.

  **What RandomX does to this entry.** The magnitudes are still invented, but they are no longer only a reputation question: they now price CPU. A peer can send headers that pass every cheap check — the target the rule itself computes, a plausible timestamp — and fail only at the work check, and each one costs the receiver a full memory-hard evaluation — 15–55 ms depending on the machine, across the three readings this tree carries (`BenchmarkVerify` at 15.1 ms on an idle machine, `randomx.go`'s 24.8 ms, I7-H3's 18 H/s table). `ScoreInvalidMessage = -20` against `ScoreBanThreshold = -100` means **five such headers per peer identity, measured, then a ban** — roughly **0.1 seconds of CPU bought per identity** when every header sits in a key epoch the node already holds (`node/p2p.TestAUniqueInvalidHeaderFloodIsSelfLimiting` measures that case and fails if the bound moves). **THE WORST CASE IS ABOUT THIRTY TIMES THAT AND IS NOT YET BOUNDED IN AGGREGATE**, and it is now measured rather than argued: `node/p2p.TestAHeightVaryingFloodIsBoundedInEpochsToo` aims the heights at key-epoch starts and reports **5 headers forcing 5 distinct epochs this node does not hold** before the ban — about 2.7 s of cache initialisation against the 0.1 s of hashing the same five headers cost when they share one epoch. The proof-of-work key is derived from the header's HEIGHT, and an announcement's height is chosen by the sender, so headers at widely separated heights select key epochs the node has never seen — and a new epoch costs a 256 MiB allocation and an Argon2 fill of it, **about 0.55 s**, before any hash is computed. (This entry said 1.7 s. Nothing in the tree produces that figure; the two readings that exist — `randomx.go`'s 574.9 ms cold and `BenchmarkInitCache`'s 552.9 ms — agree on roughly a third of it. The RATIO this paragraph turns on survives, because both absolutes were out by about the same factor: taken per machine it is 22× and 36×.) **Aiming the heights is the difference between four forced epochs and five, and it is not a rounding detail:** `SeedEpochFor` subtracts `randomx_key_lag` before dividing, so heights merely one interval apart from the tip collapse two messages into the epoch the node already holds — an attacker has no reason to make that mistake, and the first draft of the test above did, which is why it now excludes any key the node holds and asserts the count EQUALS the scoring budget instead of merely staying under it. (Five *concurrent* 256 MiB allocations is what this sentence used to add, and that part was wrong — see the correction below.) The obvious fix — refusing announcements far from the tip, before the work check — was tried and reverted: a node that is behind legitimately receives announcements far ahead and must act on them to request the block, so the guard broke catch-up. It traded a cost bug for a liveness bug, which is the trade I5-M5 exists to warn against. Tracked as an open finding in [I7](../adversarial/I7.md) under the ingress-cost work, carried to M3.5 deliberately (ARCHITECTURE §20). The recorded direction — take the bound from what the peer claimed in its handshake rather than from a fixed window around our own tip — **does not survive review as stated**: `Hello.Height` is accepted unvalidated and unbounded (`OnHello` → `recordTip`, `node/p2p`), so a peer that wants a wide window simply claims one, and the guard it would buy is a guard the attacker sets the size of. What the two tests bound is narrower than the flood, and the narrowing is the important part: **for headers the work check REFUSES**, five charged messages buy at most five epochs (`TestAUniqueInvalidHeaderFloodIsSelfLimiting` for the same-epoch case, `TestAHeightVaryingFloodIsBoundedInEpochsToo` for the epoch-forcing one; both DERIVE the budget from `ScoreBanThreshold`/`ScoreInvalidMessage` rather than restating it, so the assertion cannot drift from the comment beside it — which also means they track those constants rather than pin the 0.1 s and 2.7 s prices, so a re-derivation on the testnet moves the price without failing a test). **THE DECLARED-TARGET HALF IS PRICED PER CONNECTION AND NOT YET BOUNDED PER IDENTITY — one identity re-buys the budget for the cost of a TLS handshake, measured at 40 epochs across 8 reconnects — and the two sentences that follow describe the behaviour it replaced, kept because the mechanism they name is unchanged and only the price in front of it is new.** `pow.CheckWork` still takes the declared target; what stands ahead of it now is a per-connection budget of `MaxUnheldKeyEpochsPerPeer` announcements naming a key epoch outside the two this node is working in, refilled one per `randomx_key_interval x target_block_seconds`, refused at `CostBudgeted` **before** the work check and **unscored**. On the same fifty-message arrangement both variants now force **6** distinct key epochs rather than 50 — one working epoch that is free by design plus the budget — with 44 refused unevaluated and the identity still not banned, because banning for this is what reverted the tip-window guard. `node/p2p.TestAnAnnouncersOwnTargetBuysABoundedNumberOfKeyEpochs` supersedes the characterisation test named below and asserts that bound in both directions. Two residuals stay: a flood inside the two working epochs still costs a hash each and is priced only by the unserved-body reaper (present-dated) or by nothing (future-dated), and an over-budget announcement reaches `recordAnnounce`'s chain lookup without paying even that hash. Neither is an epoch, and neither is what this paragraph measured. **The flood as a class was NOT self-limiting per identity, and the declared-target half was that half.** `pow.CheckWork` compares against `h.Target`, the header's own declared field, with no clamp; at `u256.Max` the check passes, the epoch has already been built at the sender's chosen height, and `OnBlockAnnounce` returns `ScoreUsefulMessage` and `Forward: true`. `Header.Time` then decides whether anything charges. **Present-dated:** 50 announcements, 0 charged at announce, **50 forwarded** — so one message asks every peer for the same epoch — and the identity is banned only when `ReapUnservedBodies` charges for the unserved bodies, one `PendingBodyTimeout` after the CPU was spent. **Future-dated:** 50 announcements, 0 charged, 0 forwarded, 0 reaped, **never banned** — `tooFarAhead` is `CostFree` at `ScoreFutureBlock = 0` and enters the id into neither `seenBlocks` nor `pending`, both deliberately (R1-H2, and so that the re-announcement is not deduped away when the clock catches up), so nothing charges and nothing dedupes. The work check runs before either. So the CPU price per identity is bounded for the charged half, bounded a minute late for the present-dated declared-target half, and not bounded at all for the future-dated one (`TestAnAnnouncersOwnTargetForcesEpochsTheScoringNeverBounds` held both until it was, and has been replaced by the guarantee test named above). **The residual of the FLOOD is latency rather than memory, and the memory arithmetic has two corrections rather than one — the second of which makes the resident figure LARGER than the sentence it corrects.** A review of this entry proposed that the queued builds hold a cache each, making the exposure five concurrent 256 MiB allocations per identity; they do not. `Engine.build` takes the `building` semaphore **before** `randomx_alloc_cache` (`core/pow/randomx/randomx_cgo.go`), so a queued caller is parked holding nothing and concurrent ALLOCATION is bounded globally at `Keys`, not per peer — pinned by `core/pow/randomx.TestConcurrentEpochDemandIsAdmittedKeysAtATime`. **That is not the same as resident memory, and reading it as though it were is the second correction.** The semaphore is released when the build returns; the cache lives in the table entry until the entry is destroyed, and an entry evicted while a borrower still holds it keeps everything it has until that borrower's last `put`. Residency is therefore the table's `Keys`, PLUS the builds still being filled (a cache is resident from `randomx_alloc_cache`, and the Argon2 fill is what follows it), PLUS any entry evicted while a borrower still holds it. Measured in both regimes: **four caches, 1024 MiB, under a two-entry table** with sixteen concurrent demands (`TestConcurrentEpochDemandIsAdmittedKeysAtATime`), and **three** under a single long-lived borrower (`TestAnEvictedEntryStillHeldKeepsItsCache`), which `MineOn` reaches in production by holding its reference across the ten-to-thirty-second dataset fill. Composed — a borrower pinned across the fill while peers keep announcing unheld epochs, which is what a mining node meets — **five caches, 1280 MiB**, the derived ceiling `2×Keys + holders` exactly. So for a MINING node the resident total is the ~2.03 GiB dataset plus 1.25 GiB of caches plus 2 MiB of scratchpad per VM, **about 3.3 GiB**, with nothing bounding the holders term — and that is the number an operator sizes a machine against. What the same arrangement does produce is the cost that is real — builds are admitted `Keys` at a time at ~0.55 s each, so sixteen concurrent demands for unheld epochs serialise into eight rounds, and an honest header needing a never-held epoch queues behind them. (The wall-clock figure is the machine's; the shape is the test's.) The exposure to characterise on the testnet is therefore head-of-line delay on the build gate under an aggregate of identities, not an out-of-memory kill. What the testnet has to characterise is the AGGREGATE — for the charged half, which is the half a Sybil count is the missing input for: how many distinct identities an attacker can present per unit time against `MaxInbound`, the `/16` diversity rule and the reserved inbound slot. **That sentence stands, and measurement now backs it — but only for the half it is scoped to, and the OTHER half's aggregate is a different quantity that is now measured too (`node/p2p/keyepochaggregate_internal_test.go`).**

*The charged half, which this sentence is about.* Headers carrying the target the rule itself computes are refused by the work check at `ScoreInvalidMessage`, and `node.go` applies that verdict as `Peers.AdjustKey(conn.PeerKey, …)` and gates on `Peers.BannedKey` — one ed25519 key, one tally, across every connection it holds. Measured: one identity spread across the whole 48-connection set forces **5** never-held key epochs from score 0 and **10** from `ScoreCeiling`, and is banned both times. So this half really is bounded per identity, its aggregate really is that bound times the number of identities an attacker can present, and **a Sybil count really is the missing input** — exactly as written.

*The uncharged half — the declared-target one — which it is not about.* There the announcement declares `Target = u256.Max`, the work check **passes**, the verdict is `ScoreUsefulMessage` and no ban is reachable, so the identity costs nothing and the aggregate is bounded by address resources alone. The engine applies nothing across connections, so it is the per-connection budget times the connection set exactly: **200 never-held key epochs held at once** across a saturated 40-connection inbound table, rising to **240 across the full concurrent set of 48** because `Node.register`'s capacity gate is inbound-only and this node's own `MaxOutbound` dialled connections are admitted above it (`MaxInbound` + 2 × `MaxOutbound`, the product `engine.go` and `syncdriver.go` both already state for this set) — and **800 across four rounds of reconnects with the clock frozen**, because the budget dies with the connection. This half does not wait on a Sybil count, since **one** identity already reaches those totals for the price of handshakes — which is what the parenthesis below already said of this half, now with numbers.

*What the inbound table costs in address groups.* **8**, not 14: `acceptRaw` admits while `held[group] < perSource` **or** `probationary[group] < reserve`, both classes reach `register` and get their own budget, and `expireProbationLocked` reclaims nothing, so one `/16` holds `perSource + reserve` = **5** at once — measured by dialling the shipped listener rather than read off its field, and `node/p2p.TestTheReserveIsBounded` asserts the same bound next door. Holding the table *without re-handshaking* is the durable figure and costs **14**, since probationary connections are closed after `DefaultInboundProbation`.

*Which of the three constants named above bound it.* `MaxInbound` and the reserved inbound slot do. The *“`/16` diversity rule”* is two different rules and they answer differently: the **listener's** per-group inbound share is `/16`-keyed (`AddressGroup`) and **does** bound this — it is what makes the table cost 8 groups, and it is the currency a bound would be denominated in — while the **peer store's** diversity machinery does not, because `SelectDiverse` and `SelectDialTargets` choose which addresses this node **dials** or **serves** and are never consulted when a connection arrives. Measured, and the two arms separate exactly that: the aggregate is identical with an empty peer store and with one saturated from a single teller, and identical inside one `/16` and across eight — so the price is charged per address, and an `ip:port` is a second socket. A budget keyed on the address group and outliving the connection takes the 800 to 200 and the 200 to **40**; what sizing it needs is the honest `/16` distribution, which this section already carries in its own right one bullet below.

(The uncharged half does not wait on that number. It is already unbounded from ONE identity, so a Sybil count is not what is missing from it.) That is the same Sybil question this section already carries, now with a CPU price attached to each identity rather than only a connection slot.
- **`/16` as the address-diversity group.** The conventional proxy for "one entity", and wrong in both directions — one `/16` can hold several operators, one operator can hold many `/16`s.
- **Mempool policy:** `MaxCertificates`, `MaxPerUnderwriter`, the eviction bump and the water marks. Reasonable, not derived ([mempool §4](../adversarial/mempool.md)).
- **The chain's coarse lock.** Every cell read takes the lock every block application holds. Irrelevant at Era 0 volumes and a known scaling limit; measure before optimising ([concurrency §6](../adversarial/concurrency.md)).

## 3. How to use this list

Before the parameter freeze, every entry in §1 needs a number from the public testnet and a written argument, in the style of the decision documents. An entry that reaches the freeze with "it seemed reasonable" is an entry nobody has measured, and §1 values cannot be revisited afterwards by anyone, including whoever wrote them.

§2 entries need measurements too, but a wrong one is survivable, so they can ship on the current defaults with the measurement pending.

The soak is not a substitute for any of this. It is more hostile than reality in ways that inflate some numbers and less hostile in ways that deflate others, and it has four nodes. It is very good at finding bugs and it is not evidence about parameters.
