# Decision — the networking stack

**Question:** does `node/p2p` use libp2p, or a transport written in this repository?

**Decision:** written here, on TCP with standard-library TLS 1.3 and Ed25519 peer identities. libp2p is weighed and rejected, with reopen conditions stated in §6.

**Status:** decided at M2. This document exists because the post-M1 review named this "the §1 dependency rule's hardest case" and required the reasoning on the record either way, symmetric with the storage reversal in [I2-C1](../adversarial/I2.md).

---

## 1. The rule this is weighed under

From the architecture spec's decisions log, added after the storage reversal:

> A dependency is weighed against **auditability**, not only against maintenance and cgo. The trust case for Zycord is that there is very little to read. A dependency earns its place only if the problem it solves is one Zycord actually has.

The rule cuts both ways, which is the point. It sent storage in-tree because durability is a sentence and Pebble solves write throughput for an execution chain that Zycord is not. It should send security-critical, genuinely hard problems *toward* a vetted dependency. Peer-to-peer networking is the case where those two pulls meet.

## 2. What was measured

`go get github.com/libp2p/go-libp2p github.com/libp2p/go-libp2p-pubsub`, on a clean module:

| | |
|---|---|
| Transitive modules | **141** |
| Distinct organisations | **69** |

Among them: a complete WebRTC stack (`pion/srtp`, `pion/rtp`, `pion/rtcp`, `pion/sdp`, `pion/ice`, `pion/dtls` ×2, `pion/sctp`, `pion/stun` ×2, `pion/interceptor`, `pion/mdns`, …), a DNS resolver, a websocket library, two protobuf runtimes, and a QUIC implementation.

## 3. What Zycord's network actually needs

| Need | Real? | libp2p's answer | Cost to build here |
|---|---|---|---|
| Authenticated, encrypted transport | **yes, security-critical** | Noise / TLS | stdlib `crypto/tls` |
| Message framing and multiplexing | yes | yamux / mplex | ~100 lines |
| Certificate and block gossip | yes | gossipsub | flood + seen-cache, ~200 lines |
| Peer discovery | modest | DHT, mDNS, bootstrap | bootstrap + peer exchange (§12) |
| Peer scoring | yes | gossipsub scoring | counters, ~100 lines |
| NAT traversal / hole punching | **yes, and this is the real loss** | AutoNAT, circuit relay, DCUtR | not built |
| Browser peers, WebRTC | **no** | ~20 modules | — |
| Content routing / DHT | **no** | a large subsystem | — |
| Multiple transports (QUIC, WS, WebTransport) | **no** | several | — |

So: 141 modules for six problems, of which the security-critical one is answered by the standard library, and roughly a third of the tree serves needs Zycord does not have at all.

## 4. The Zycord-specific argument

There is one argument here that is not generic, and it is what tips the decision.

Whitepaper §13: *"A relay node needs no state whatsoever to fully filter spam — stateless validity plus underwriter signature is checkable from bytes, which makes running relay infrastructure nearly free on the transparent rail."*

gossipsub's mesh maintenance and peer scoring exist largely to contain **amplification**: on a typical chain, deciding whether a message is worth forwarding is expensive, needs state, or cannot be done at all before forwarding, so a flood of plausible-looking garbage is costly to absorb and cheap to send.

Zycord does not have that problem in the same strength. A certificate is checkable from its bytes, with no database, no history and no tip — that is the design's central property, not a convenience. An invalid certificate is dropped *before re-propagation* at the cost of a signature check, and the sender is scored down for it. The amplification attack gossipsub is built to survive is structurally weaker here, **by construction**.

That is the §1 rule applied honestly: the hardest part of the problem libp2p solves is a part Zycord has already solved in its consensus design.

**The qualifier in that quotation is new, and it is honest to carry it here rather than quote around it.** Whitepaper v1.1 makes relay nearly-free a property of the *transparent* rail, and names the shielded rail of its §12 as the priced exception: a stateless check that includes a range-proof verification costs three orders of magnitude more than a signature check, so the free-to-publish default becomes an amplifier, and the paper turns check-cheap-before-expensive ordering and per-underwriter quotas from relay preferences into requirements. Nothing about that changes this decision, and it is worth being exact about why. The argument above is about *what a receiver must do before forwarding*, and on the shielded rail the answer is still "check the bytes" — the cheap half of the check (signature, declared liveness, quota) runs first and rejects the flood, and only what survives pays for the verifier. That is a policy this node's own relay layer can express directly; it is not a mesh-scoring problem, and gossipsub would not supply it. What it does change is the standing of the policy: today's relay defaults are documented as non-consensus and uniform, and an era that ships confidential payments makes one of them mandatory. If `node/p2p` is ever replaced — by libp2p or by a second implementation — the ordering discipline has to survive the replacement, so it belongs in [spec/wire](../spec/wire.md) as a stated requirement when that era is specified, not in whichever implementation happens to be running.

## 5. What is given up, stated plainly

**NAT traversal.** This is the real cost and it is not small. Without hole punching, a node behind a home router can make outbound connections but cannot accept inbound ones. The network therefore needs enough publicly-reachable nodes to serve as connection targets — exactly Bitcoin's topology, which has worked for fifteen years, but it does mean a laptop miner is a leaf rather than a peer. Given that Era 0's demographic *is* laptop miners (whitepaper §14), this deserves to be uncomfortable rather than waved past. Mitigations available without libp2p: UPnP/NAT-PMP port mapping where the router allows it, and an explicit `--listen` for operators who can forward a port. Reopen condition in §6.

**Gossip efficiency at scale.** Flood gossip costs O(peers × messages) in bandwidth where a gossipsub mesh costs roughly O(mesh degree × messages). At 30-second blocks, ~850-byte certificates and a few thousand certificates per block, flood is comfortable into the low thousands of nodes. It is not comfortable at a hundred thousand. That is a scaling ceiling with a number attached, which is the honest way to hold it.

**Maintenance.** This repository now maintains a gossip protocol. That is a standing cost and the reviewer named it correctly.

## 6. Reopen conditions

This decision is reversed, without embarrassment, if any of these becomes true:

- **NAT traversal becomes the binding constraint on participation** — measured on the M3 testnet as a share of would-be miners who cannot get inbound connections and cannot port-forward. This is the most likely trigger and the one to watch first.
- **Flood gossip's bandwidth becomes the binding constraint**, measured rather than assumed.
- **A transport vulnerability is found in this code.** One is enough. Hand-maintained network code that has failed once should be replaced by code that has survived more eyes.

If reopened, the replacement is libp2p behind the existing `p2p.Transport` interface, confined to `node/p2p`, with `core/` and the rest of `node/` still third-party-free.

## 7. The shape of what is built instead

- **Transport:** TCP, then TLS 1.3 from `crypto/tls`. Peer identity is an Ed25519 key carried in a self-signed certificate and checked in `VerifyPeerCertificate`. The security-critical part is therefore standard library, not hand-rolled: no custom handshake state machine, no custom AEAD framing, no custom key schedule.
- **Framing:** length-prefixed SSZ messages, with the same canonical-decoding discipline as everything else.
- **Handshake:** genesis id exchanged as the network id (R3-1). A mismatch disconnects immediately, before a block is evaluated — devnet and mainnet cannot cross-connect, structurally rather than by filtering.
- **Gossip:** flood with a seen-cache and a hop budget. Validity is checked before re-propagation, always.
- **Discovery:** a bootstrap list plus peer exchange, with a persisted peer store so a restart does not hand an attacker a blank slate. The node asks for addresses rather than waiting to be told — §12, which is also the record of how long it did not.
- **Scoring:** counters for invalid messages, unserved bodies and protocol violations, with disconnection thresholds.

The wire protocol is specified in `docs/ARCHITECTURE.md` §13 independently of this implementation, so a from-scratch stack — or libp2p — can replace it without a fork.

## 8. Rejected alternatives

- **libp2p.** §2–§4. The decision is about 141 modules for six problems, one third of which serve needs Zycord does not have, with the hardest part already answered by the consensus design.
- **libp2p with a minimal host** (TCP + Noise + yamux only). Module-graph pruning means unused packages are not linked, so the *binary* would be smaller than the tree suggests — but `go.mod` and `go.sum` still enumerate the graph, and the supply-chain surface is what is being minimised, not the binary. It also does not solve NAT traversal without pulling the parts that do, which is most of the reason to have taken libp2p.
- **A hand-rolled Noise handshake on `x/crypto` primitives.** Rejected: it puts a custom handshake state machine on the security-critical path, which is precisely the thing the §1 rule says to buy rather than build. Standard-library TLS 1.3 is strictly better on that axis and costs nothing.
- **Plaintext TCP with signed messages.** Rejected: it leaks the network graph and every certificate to any observer, and offers no protection against an active man-in-the-middle reordering or withholding. Certificates are public data, but *who is talking to whom* is not, and for a network whose users are anonymous by design that is not a detail.
- **QUIC via `quic-go`.** Rejected for now: it is a genuine improvement on connection setup and head-of-line blocking, and a much smaller tree than libp2p, but it is not needed at 30-second blocks and it is a dependency this milestone does not have to take. Reopen alongside the §6 conditions.

## 9. The gossip scale ladder

§5 states flood gossip's ceiling as a number rather than a shrug: comfortable into the low thousands of nodes, not comfortable at a hundred thousand. A ceiling with no stated way past it is a trap, so this is the ladder, in the order the rungs should be climbed. Each rung is cheap relative to the one above it, and none of them is an architecture change until the last.

**Rung 0 — flood with a seen-cache. Where the implementation is today.** Every valid message is forwarded to every peer but the sender; the seen-cache stops the echo. Cost per node is O(peers × messages). Certificates dominate: at ~850 bytes, a few thousand per block, and eight peers, that is a few tens of megabytes per block period per node. Fine at the size Era 0 will actually be.

**Rung 1 — announce-request for certificate bodies.** Gossip the certificate *id*; a peer that does not have it asks for the body. This is the rung that blocks are already on (`BlockAnnounce` → `GetBlock`), and extending it to certificates is a protocol tweak of the same shape — two message kinds and a pending map — not a redesign. It replaces the O(peers) cost of a body with the O(peers) cost of a 32-byte id plus one body fetch, which is roughly a 25× reduction on the dominant term. **This is the first rung to climb, and it should be climbed on evidence from the M3 testnet rather than pre-emptively.**

**Rung 2 — degree management.** Bound how many peers a message is forwarded to (a fanout below the connection count) and pick the subset per-message rather than per-node, so no fixed subgraph decides delivery. Cost is a small increase in propagation delay and a small increase in the chance a message needs a second path; benefit is that bandwidth stops scaling with connection count.

**Rung 3 — a mesh with grafting and pruning (gossipsub's shape).** Maintain a stable mesh of a fixed degree, gossip *have* messages to the rest, and let peers graft themselves in when they notice they are missing things. This is where the protocol stops being simple, and it is also where the libp2p reopen condition in §6 becomes tempting — building rung 3 by hand is most of the work of adopting a maintained implementation, without the eyes.

The honest statement of position: **the implementation is on rung 0, rung 1 is designed and not built, and rung 3 is where this decision should be revisited rather than extended.**

## 10. Peer identity and key separation

A node's peer identity is an Ed25519 key in a self-signed TLS certificate. Three properties, and the reasons they are not accidents:

**No key is reused across layers, ever.** The peer key is generated by `ed25519.GenerateKey(crypto/rand.Reader)` in `p2p.NewIdentity` and is derived from nothing. There is no KDF from a wallet seed, no shared master secret, no domain-separation tag — because there is no derivation to separate. A signing key and a transport key that share an origin let an observer link a network address to an on-chain identity, and for an anonymous project that is the whole threat model in one line. The absence of a derivation is the strongest form of the property, and it is worth stating explicitly precisely because it is invisible in the code: nothing there says "do not derive this from the wallet", it simply does not.

**The node process holds no wallet key at all.** This is M1-G4 and it composes: even if a peer key derivation were added later by mistake, there would be nothing in the process to derive it from. Signing happens in `zcd`.

**The peer key is ephemeral by default.** It is regenerated on every start and never written to disk. The anonymity benefit is that a node's network identity does not survive a restart, so an observer cannot correlate sessions by key. The cost is real and should be stated: peer *reputation* cannot be keyed to identity across a restart, because there is no identity left to key it to — a node that regenerates its key and reconnects arrives with a clean record, indistinguishable from a peer nobody has met before.

Within one process's uptime this is not as weak as it first reads. `p2p.PeerStore.AdjustKey`/`BannedKey` key *live* scoring and bans on `Conn.PeerKey` — the identity TLS actually authenticated — rather than on `Conn.Addr`, which for an inbound connection carries an ephemeral source port the OS picks fresh on every reconnect. An *ordinary* reconnect, same identity on a new source port, therefore keeps whatever reputation it had; only a deliberate new keypair sheds it, which costs the same one TLS handshake this node's own rotation does. The persisted, address-keyed `PeerStore` is unaffected by any of this — it is also the dial store, and an address is dialable where a key is not — so it keeps scoring and banning by address exactly as before, for connections and candidates the live, identity-keyed store has no opinion about.

**Rotation.** Because the key is ephemeral, rotation is a restart. If a future release persists the peer key — the argument for doing so is long-lived reputation, and it is a real argument — then rotation must become an explicit operator action with documented semantics, and the anonymity cost above becomes a default rather than an option. That trade should be made deliberately and written down, not arrived at by adding a file.

## 11. What a bound does when it binds

Two bounds guard the inbound path — the number of TLS handshakes that may be in flight at once, and the number of authenticated identities the live score store may hold. Both are necessary: without them an attacker's cost per unit of this node's memory, goroutines and file descriptors is a free keypair and a socket. Neither number is the interesting part of the decision. What the code does at the moment the number is reached is, because that is the only moment an attacker ever arranges to happen, and both bounds were first written with the behaviour at that moment inverted.

**A full handshake budget preempts the oldest handshake; it does not refuse the newest.** `DefaultMaxHandshakes` (512) caps concurrent in-flight TLS handshakes across every address group, which the per-group `perSource + reserve` bound does not: that one caps a single group's share, so an attacker's total still grew with the address diversity it could present. Capping the sum is right. Refusing at the cap is not, and it re-creates the issue the accept path was rewritten for. A connection that completes the TCP handshake and then says nothing holds a slot for the full handshake timeout, so an attacker that keeps the cap full — 512 sockets, about 103 distinct /16 groups at five apiece, re-established every ten seconds — turns "one silent connection halts all inbound accepts" back on with a larger constant in front of it. It was measured on the refusing revision: against a held cap, a peer offering a real and valid TLS handshake got EOF.

Preempting keeps the ceiling and drops the starvation, and it is worth stating what it buys as a price rather than as a guarantee, because the first version of this section claimed the guarantee and the claim was wrong. It read: preemption is self-targeting, since holding a slot requires staying, so an attacker's own connections are always the oldest. That is false against an attacker who churns — connect, hold briefly, reset — because it controls its own connection lifetime and can always arrive later than an honest peer. Oldest-first, on its own, is a rule that says *evict the slowest*, and the slowest handshake in the map is a distant honest peer on a long round trip. Measured: under a churn flood, ten out of ten honest peers at a 120 ms round trip were locked out.

What preemption actually changes is the price. To lock a peer out, an attacker must hold every slot for as long as that peer's handshake takes. Against refusal that costs `maxHandshakes / handshakeTimeout` — about 51 connections a second, because a silent connection holds its slot for the full ten. Against preemption it must instead replace its own connections faster than the honest handshake completes: `maxHandshakes /` that duration, roughly 5,700 a second against a 100 ms peer. Two orders of magnitude, and not an impossibility.

The rest of the margin is bought by choosing the victim by address group rather than by age alone. Group share is the one signal that does not invert: `perSource + reserve` bounds a single group to five handshakes in flight, so filling the cap takes breadth — about a hundred groups — while an honest peer arrives as the only connection from its own. Taking from the heaviest group therefore takes from the attacker and spares the singleton, and age decides only *within* that group. What is left is an attacker with enough address diversity to hold the cap at one connection per group, which is a far larger asset than the flood this started from.

An authenticated connection waiting to be handed to `Accept` is removed from the budget the instant its handshake completes, so a peer that has already proved its identity is never a victim. `preempted_in` joins `refused_in` in the heartbeat for the same reason that one exists: the peer on the other end sees a bare connection reset, which is what a flaky link looks like too, and the counter is the only thing that separates them.

**A full peer store evicts from the crowd, and never refuses the newcomer.** `MaxPeers` (4096) caps the persisted, address-keyed `PeerStore`, which before the cap grew without bound: nothing correlates a `peers` frame to a request (`wire.md` §12 removes request ids), so a peer sends one whenever it likes and every address in it reached `Add`. When this was written the stronger form held — `KindGetPeers` was sent nowhere, so every `peers` frame was unsolicited *by construction* — and §12 has since changed that. The cap is unaffected, which is the point: it never rested on the asking, only on arrival being the sender's decision. The cap is the easy half. Its first behaviour at the cap was to refuse — a new address was declined whenever the worst entry already held was at least as good as a brand-new, never-contacted one — on the reasoning that an unbounded stream of interchangeable unproven addresses would otherwise churn the store forever, evicting an honest entry per arrival. The reasoning is right about the churn and wrong about the remedy, and the third bound in this section came out backwards for the third distinct reason: a never-contacted honest address is never *better* than a never-contacted junk one, so 4096 invented addresses — one flood, all well-formed, all score 0 — fill the store and every honest address offered afterwards is refused, the operator's own `--peers` list on the next start included. Measured on the refusing revision: after the flood, `Add` of an honest address left the store unchanged. The cap closed the unbounded growth by making the store unable to learn anything again, and it persists, so it survives the restart too.

What answers the churn is not refusing the arrival but charging it to the population it arrives with — a cohort, being the peer that told this node about an address (`Peer.Src`, reduced to that peer's address group), or the address's own group where nobody told it. "Take the victim from the largest cohort" is the obvious rule and is wrong on its own, which is worth recording because it reads as *a flood evicts itself* and is that only while the flood is the largest thing in the store. On a node bootstrapped from one helpful peer the largest cohort is that peer's address book, and it was measured: 200 invented addresses from one source evicted 200 honest ones at no cost to the attacker, and claim-then-flood — gossip real addresses first, so first-teller-wins attributes them to the attacker, then flood from the same source — removed 30 of 30 real peer addresses, persistently.

Four rules together, instead, and each of the last three closes a way the first one alone was measured to fail.

`MaxPerSourceStored` (`MaxPeers/8`) bounds what any one cohort may hold, so a cohort at its ceiling evicts strictly from itself — the marginal invented address costs its teller one of its own entries and costs nobody else anything — and no cohort can grow large enough to be everyone else's eviction source. Filling the store then takes eight distinct tellers, which is eight real addresses in eight real /16s.

**Cohort keys are namespaced by kind.** A gossiped address is charged to its teller and an ungossiped one to its own address group, and both are `AddressGroup` strings, so without a prefix they are the same key. An attacker whose *connection* sits in the same /16 as the operator's bootstrap peers then shares their cohort and floods it to the ceiling from inside: 512 gossiped strings, eight `peers` frames, 30 of 30 bootstrap addresses gone. Co-location in a /16 with a bootstrap peer is the ordinary case for a cloud-region deployment, and the ceiling had handed the attacker something the unbounded store did not give it.

**Quality outranks share, in both directions.** An entry this node has connected to, or that earned score, is never given up for an unproven newcomer; an entry it has dialled and that has never once answered is given up before either. Share is only meaningful among entries that are otherwise indistinguishable, which unproven entries are and the other two are not. Ordered without this, three score-100 peers sharing one teller were evicted ahead of 4093 score-0 invented entries that each had a cohort to themselves.

**Eviction has to be cheap on the shape an attacker actually creates, and the obvious reasoning about which path it takes was wrong.** The per-cohort ceiling suggests a flood evicts from itself through a scan of one cohort. It does not: a flood is by construction the largest cohort, so the general path evicts from it, so it never grows to its ceiling and the cheap path never fires — measured, 3000 flood admissions took the general path 3000 times, and the attacker's cohort never approached its ceiling of 512 — how far below depends on how the rest of the store is shaped, measured between 99 and 456. Good behaviour, and a false comment that hid a cost: an O(store) scan per admission, 160µs, so one attacker held about 10ms of the peer store's write lock per `peers` frame — the same lock `Engine.Handle` needs to score every message from every peer. Tier 0 is therefore kept as a set, and the second phase visits cohorts largest first and stops at the first one holding an unproven entry, so a flood costs its own cohort rather than the store: **20.5µs an admission**, against 123µs for the uncapped store this replaced. The load path trims by one sort rather than by repeated eviction for the same reason — an over-cap `peers.json` was O(excess × n), and 40,000 entries cost 92 seconds of startup, which is a node that looks hung; it is now 1.2s.

**Arrival order is not persisted at all: a restored store is one arrival bucket, and it is the oldest.** `peers.json` is an operator-visible file and this loader already assumes it may have been edited — that is what the `Src` validation is for — and `Seq` has to meet the same standard, because it decides which entry a full cohort gives up. An earlier revision renumbered to a dense 1..N in the order the file implies. That closed the absolute-value bug — a file claiming `Seq = MaxInt64` overflowed the counter, and every address the node learned afterwards got a negative `Seq`, sorted as the oldest thing in the store, and became the entry eviction never reaches — but it kept the *relative* order, which is the half the writer of the file still chooses. Measured: 511 entries packed into the operator's bootstrap address's own /16 make it the largest cohort and the operator's freshly-added address the newest tier-1 entry in it, so a single gossip admission evicts it. So the load collapses every entry to one bucket, `Seq = 1`: a file can no longer order its own entries against each other at all. The bucket is the *oldest* one, so a flood arriving after the load must spend its own arrivals before it reaches anything this node chose to remember. What this costs is the only legitimate thing the order carried — a restart no longer re-ages the store relative to itself — and nothing distinguishes two restored unproven entries anyway once the loader drops their score and failures. The other half of that fix is the eviction exemption for an operator-supplied address this node has not yet dialled: with one bucket and no exemption, a freshly-added configured address is always the newest entry in its cohort, which is the eviction attack that exemption exists for.

**The operator's list is the fresher assertion, so a file cannot accuse it and cannot claim to have spent it.** Two consequences of taking the hostile file writer seriously, both of which the first revision of that fix missed. (1) `selectLocked` filters `Banned()` *before* it consults `dialRank`, so a file that writes `Score = ScoreFloor` for every `--peers` address makes `SelectDialTargets` return nothing at all — a cheaper and more complete eclipse than the score inflation the loader closes. `AddBootstrap` therefore clears a *restored* negative score; a ban this process adjudicated online is evidence this node gathered and is untouched, and `addBootstrap()` runs once per process so this cannot launder one. **The stated cost:** a ban this node itself adjudicated does not survive a restart for a *configured* address — `Save` writes the negative score, the load restores it, and the operator re-supplying the address clears it, so a peer banned for protocol violations is a dial candidate again on the next start; and because the `--peers` list may contain names, a poisoned resolver for one can name a previously banned address (up to `maxBootstrapAddrs` per name) and clear its ban. Accepted, because the alternative is that whoever can write `peers.json` deletes the operator's whole list from the candidate set — a total eclipse against a strictly weaker precondition — and the ban is re-earned online in the round it takes the peer to violate the protocol again. A ban on an address the *network* gave this node still survives the restart unchanged. The exemption also leans on a choice made in another unit: `Engine.OnHello` records a peer's claimed listen address with `AddFrom` and marks only the connection's own address with `MarkConnected`. Were it to mark the claimed address, an inbound peer could name an operator address in a hello, set its `LastSeen`, and strip the exemption from an address that has never been dialled. (2) The eviction exemption for a configured address must not read the file's `LastSeen`: stamping `last_seen` on the operator's own addresses made the exemption false for them, and the oldest-bucket rule does not save them because `betterVictim` falls through to `worsePeer`'s `LastSeen` key, which the same file chose. The predicate is `p.bootstrap && (p.restored || p.LastSeen == 0) && p.Failures == 0 && p.Score >= 0` — restored claims are not evidence, exactly as in `proven()`, and the `Score` clause keeps it disjoint from `evictionTier`'s tier 0, which no exemption may cover.

**A dial that did not answer refutes every dial rank, uniformly.** `dialRank` sits above the failures key and `Failures` is never reset on success, so any rank that survived a failure would be a one-way ratchet with no way down: a stale `--peers` list would hold every outbound slot forever and the node could never fall back to gossip, and a scoreless inbound `ip:ephemeral_port` entry would sit above every untried address forever. `main` self-heals from both on the failures key. `dialRank` returns 0 for any entry with `Failures > 0`, which hands the decision back to that key. Restored entries are unaffected — the loader zeroes `Failures`.

**Inside the indistinguishable tier the tie-break is arrival order, not the address.** This is the one that is easy to miss, because the address tie-break is there for determinism and looks neutral. It is not neutral: the attacker picks the addresses it gossips. First-teller-wins files real addresses it named first under its own cohort, and it then floods that cohort with addresses that sort ahead of them — 2030 gossiped strings, about 32 `peers` frames, and 30 of 30 real addresses removed. Arrival order (`Peer.Seq`, monotonic within a process) is the one key a *sender* cannot choose after the fact — the writer of `peers.json` can, which is why a restored store shares one bucket (above), so a cohort at its ceiling recycles its own most recent arrivals and the flood pays for itself.

Within that tier, share still decides ahead of arrival, and there it is the same finding as the handshake budget's, in the same section, for the same reason: group share is the one signal that does not invert.

**Address diversity prices addresses an attacker owns; source diversity prices the ones it merely claims.** The two are not the same bound and the peer store needs both, which is a thing the store did not do for as long as it had only the first. `SelectDiverse` spreads outbound connections across distinct /16s so a thousand addresses in one hosting range count once. That is exactly correct about *hosting a thousand nodes* and says nothing at all about *typing a thousand addresses*: any four bytes are a valid IPv4 host, and 65,536 of them are 65,536 distinct /16 groups, so an attacker with no addresses at all mints diversity for the price of a gossip frame. Measured: twenty invented IPv4 addresses in twenty /16s, in one unsolicited `peers` frame, took **8 of 8** outbound slots from a victim that already knew three honest peers, winning the primary diverse pass outright.

The intermediate fix — requiring a peer address to have an IP host, so a non-IP string can no longer fall through `AddressGroup` and become its own group — is necessary and is not sufficient, and the gap between those two is worth recording because a regression test written with hostname-shaped junk reports the attack as closed when it is not. It changes which characters the junk is spelled with. What an attacker cannot invent is the connection it is speaking *from*: that one is a real, authenticated TCP connection this node accepted or dialled, and widening it means acquiring real addresses in real /16s. `MaxPerSource` (2) bounds how many outbound slots everything one teller gossiped may take, which prices the attack in the one resource that is not free. Bitcoin Core's `addrman` reaches the same property by hashing the *source* group into an address's bucket assignment, so everything one peer gossips lands in a bounded slice of the table; this is that property expressed at selection rather than at insertion, which is where a store this size can carry it.

The fallback pass relaxes the per-group bound and deliberately does not relax the per-source one, so a cold node fed nothing but one peer's gossip comes away under-connected rather than eclipsed. `wire.md` §11 asks a node to keep dialling toward its outbound target; it does not ask it to dial anything at all rather than dial less. An under-connected node syncs slowly. An eclipsed one accepts a false chain.

**A budget counted per call is not a budget.** Both outbound bounds are counters built inside one selection call, and the dial loop calls the selector once per round with the peers it already holds passed as an *exclusion* — which drops them from the candidate list before either counter exists. Every round therefore started both budgets at zero and handed the same teller, or the same /16, another full allowance. Measured: one teller took 2, then 4, then 6, then 8 of 8 outbound slots across four rounds, roughly eight seconds at the default `DialInterval`, and the same laundering applied to the /16 bound that predates the per-source one — which is §11's own MUST failing by accretion rather than by omission. The held outbound connections are now charged into both budgets before anything new is selected. Held *outbound* only: an inbound connection is chosen by the peer, so counting it would let an attacker connecting from many groups spend this node's dial budget on its behalf and veto its dials into exactly those groups.

**The source bound is a dial-path rule and does not belong on the gossip response.** `OnGetPeers` answers with `SelectDiverse`, which applies address diversity and not the source bound, and the split is deliberate: whose gossip taught *this* node an address says nothing about the eclipse risk of the node asking for it. Applied there, the bound throttles honest dissemination instead of an attacker — measured, a young node holding several hundred addresses from one honest bootstrap peer answered a `get-peers` with 2 addresses where 64 were permitted, a 32× reduction in how fast honest addresses spread.

**A full identity store gives up the entries nothing reads, not the entries it exists for.** `MaxIdentities` (4096) caps the live, unpersisted store `AdjustKey`/`BannedKey` write to. Its first eviction policy was lowest-score-first, borrowed from the address-keyed store, where it is correct — that store's readers pick peers to *dial*, so its worst entry is its least useful one. This store has exactly one reader, `BannedKey`, and it asks whether a score is at or under the ban threshold. An entry above the threshold answers that with the same "no" a key that was never stored at all gets; the lowest-scoring entry is the single record the store exists to hold. A retention policy copied from a store that selects into a store that refuses comes out backwards, and this one did: filling the store to its cap with free identities left it holding 4096 entries of which none were banned, and cleared a standing ban on the way. Ordinary honest gossip does the same thing more slowly — a long-running node meets far more than 4096 well-behaved identities, and under that ordering each one it meets walks a ban a step closer to the door.

The correction to that was itself wrong twice over, and both errors are worth recording because they are the same error seen from two sides. The first read the store as a ban ledger and evicted the highest score first. But a score is not only an answer to `BannedKey`: up at the ceiling it is *earned headroom*, how many more penalties a peer with a long good history absorbs before it crosses the threshold, so discarding it lets an attacker halve an honest peer's budget on demand — measured, banned in five invalid messages where ten were owed. The second added an admission rule — a newcomer may displace a held entry only by being worth more than it — which reads as the tighter rule and is a door that locks from the inside. Fill the store with entries at the threshold and no first delta a newcomer can have is ever worth more than −100, nothing is admitted again, nothing expires to undo it, and identity banning is off for the life of the process. The bill was 4096 connections and 20,480 invalid messages, payable sequentially from one address in minutes, because a single invalid message is not a protocol violation and does not disconnect.

What both missed is that the store's value lives at *both* extremes, and the worthless entry is the one in the middle — it answers `BannedKey` with the same "no" an absent key gets and buys its peer no headroom either. So the entry given up is the one nearest zero, then the stalest of those; and a newcomer is never refused, because a bound that can refuse everything is a bound an attacker closes.

A third claim was made for that ordering and it was also wrong, so it is recorded here with the others rather than quietly dropped: that the staleness tie-break lets a peer escalate against a flood of one-shot identities, since the escalating peer is the one still sending and therefore the freshest of its tier. It is the freshest only until the next arrival. Measured: one flood arrival between the target's messages — one TLS handshake apiece — keeps a peer at −20 out of the store indefinitely, with no key grinding and no clock games required.

That limit is inherent and not a property of this ordering. A bounded store and free identities cannot both hold, so a sustained flood of fresh identities can always displace an entry that has not yet distinguished itself from a one-shot. What an ordering decides is how far the flood reaches, and this is where the choice earns itself: here it reaches the first tier only, because worth separates the tiers and a peer carrying one more penalty than the flood — worth 40 against worth 20 — is out of reach, measured untouched across 12,288 arrivals. Under the previous ordering there was no such line at all: lowest-score-first made escalating a peer into the *preferred* victim, so the same flood evicted it at every tier rather than only the first.

None of this weakens what §10 claims for identity-keyed scoring, which is narrow: an ordinary reconnect — same key, new source port — no longer resets reputation. That needs no flood, and absent a flood escalation works against a full store. An attacker who can sustain the flood can already shed identity bans far more cheaply by rotating its own key every connection, which is free by design and which this never claimed to prevent.

What remains beyond that is likewise not claimed otherwise: an attacker who drives each of 4096 throwaway identities all the way to the threshold — five invalid messages apiece, since one does not disconnect — can push an older ban out. That is five times the price of the one cheap message the first ordering charged, it buys one eviction rather than the whole store, and it cannot stop a new ban from being recorded.

## 12. Discovery: whether the node asks

§7 lists discovery as "a bootstrap list plus peer exchange" and §3 prices it as a *modest* need. Both were written as descriptions of a design and neither was a description of the code, which is the gap this section answers. **Decision: the node asks — `Node.askForPeers` sends one `get-peers` per `GetPeersInterval` to one outbound peer.** The alternative was to write the inertness down as an Era-0 decision, and §12.2 records why it lost.

### 12.1 What was actually true before

`KindGetPeers` is defined, dispatched and served. It was sent by nothing, and two comments in the tree said so — each using the fact to justify a *different* bound, neither saying whether not asking was a decision.

The fact is one step stronger than that description, and the stronger form is what decides this. `OnGetPeers` is the only site in the tree that constructs a `KindPeers` frame; it runs only in answer to a `get-peers`; and nothing sent one. So on a network composed of conforming nodes, **the number of `peers` frames in existence is zero**. Discovery beyond the bootstrap list is not modest, it is nil, and the address pool is not merely "whatever bootstrap gave us" — it is whatever bootstrap gave us, plus whatever was volunteered by parties that deviate from the reference implementation in order to volunteer it.

That is the whole argument. Every bound in §11 is an arbitration among addresses: `MaxPerSource` decides how many outbound slots one teller's gossip may take, cohort eviction decides which teller pays for a full store, the tier ordering decides which claims outrank which. All of them are relative, and all of them were sized, argued and measured against a population of tellers whose honest half does not exist. A defence that rations a resource nobody supplies is not conservative; it is untested in the only configuration that matters, and the launch is the moment it is thinnest.

### 12.2 Rejected alternatives

**(b) Write the inertness down as an Era-0 decision.** This is the option that suggests itself first, and it is the one recommended against. It loses on §12.1: "record the condition that would reverse it" presupposes that inertness has a safe regime, and the regime it would have to be safe in is one where an attacker is the only contributor to a node's address set. It is also not free — the reply path stays, so the node keeps paying the serving cost for a message nobody conforming sends, which is the worst of both.

**Ask every peer, or ask on the gossip path.** Rejected: a node's request rate would scale with its connection count, which is how a discovery timer becomes a network-wide load multiplier on the one frame whose cost was proportional to the whole peer store rather than to the reply. It buys nothing — one reply already carries up to `MaxPeersPerResponse` addresses, which is more than an Era-0 bootstrap list.

**Ask inbound peers as well.** Rejected: an inbound connection is chosen by the peer, so asking it lets anything that can connect here nominate itself as this node's address source. It is *not* the reasoning by which an inbound peer was once excluded from sync candidacy — that exclusion was removed, and the two questions come apart at exactly this point: candidacy decides who is *asked*, and every header and body an answer carries is re-derived before it is believed, whereas an address source decides what this node *keeps and dials later*, and nothing re-derives an address. It costs nothing honest, because an inbound peer that wants to teach this node addresses can still volunteer a frame — which is the only way any address has reached this node until now.

**Ask only when the store is thin.** Rejected, and it is the alternative most worth recording because it reads as the careful one, and it is the form the question usually arrives in. A thinness trigger is off in exactly the state it exists for: the eclipse condition is a store that is *full* of an attacker's addresses, not an empty one. "Thin" is also a threshold an attacker sets, for the price of one frame. A flat rate is not cleverer, it is merely not steerable.

**Track solicitation per connection, and score or gate the reply on it.** Rejected for this change, and it is a rejection with a residual (§12.4). `wire.md` §12 removes request ids deliberately, so nothing correlates a `peers` frame to the `get-peers` it claims to answer; a per-connection flag would record only that this node asked *someone* recently, which any peer can race. `wire.md` §7 forbids the positive score in any case. The flag would therefore buy a distinction the wire cannot carry, and would replace a true statement — nothing here establishes that this frame was asked for — with a plausible one.

**Record addresses only from replies believed solicited.** Rejected on the same ground, and it is the larger version of the same mistake: it would make the store's admission depend on a belief the protocol cannot support, and it would invalidate the eviction reasoning in §11, all of which was derived and measured against a world in which arrival is the sender's decision. That property is unchanged by this section, and it is why the store's bounds survive it.

### 12.3 What the change is, and why each narrowing is there

One `get-peers`, to one peer, per interval, from the dial loop:

- **From the dial loop**, not a goroutine of its own: it asks about exactly the resource that loop consumes, and the peers it may ask are the ones that loop chose.
- **One outbound peer per ask**, drawn *uniformly* from a sorted candidate list. The sort is for reproducibility under a seeded run; the uniform draw is a defence and is stated as one here because it does not look like one. A fixed choice — the first candidate, say — would make whichever peer wins that position this node's standing and only address source, permanently and across restarts, which turns the bound in §12.4 (an attacker holding one of `MaxOutbound` slots draws about 1/`MaxOutbound` of the asks) into 1/1 for the price of choosing an address that sorts low. Rotation is what keeps that bound a bound.
- **`DefaultGetPeersInterval` = five minutes**, chosen from the cost of the answer rather than the value of it. `OnGetPeers` no longer rebuilds the whole peer-store selection per request: `SelectDiverse` memoizes that selection for `DiverseCacheTTL`, so a served request costs a walk of the memo — at most `MaxPeersPerResponse` map lookups through `liveSubset` — plus a ~1.2 KB reply, flat in store size (`TestGetPeersCostDoesNotScaleWithStoreSize` holds it under 8 KB of allocation from 64 entries up to `MaxPeers`, against 428,609 B per request on the revision before it). The asker is still not who pays, so the rate is still sized against the *serving* node, but what that node pays is now bounded by elapsed time rather than by request count: **at most `GetPeersInterval` / `DiverseCacheTTL` = ten rebuilds per interval, and that ceiling holds at any request rate, hostile included.** Ten rebuilds at the ~5.7 ms this section measured for one is 57 ms per 300 s, **under 0.02% of a core**, and that is an upper bound twice over, because the rebuild itself is cheaper than it was and because a node asked less often than the window expires rebuilds fewer than ten times. The arithmetic it replaces was 32 x 5.7 ms per 300 s, under 0.07% of a core, sized on `MaxInbound` = 32 — a node is asked by the peers that dialled *it*, so a saturated inbound set could be asked 32 times per interval where the network mean is one and the expectation is four. `MaxInbound` is out of the ceiling now and the TTL sets it, so the worst case stops rising as soon as requests arrive faster than one per `DiverseCacheTTL`; the mean case is unchanged at 0.002%, one rebuild per interval, and the gap between mean and worst is bounded by `GetPeersInterval` / `DiverseCacheTTL` rather than by how many peers dialled in. **Both figures here are one machine's, and figures of this kind do not travel between machines.** The same rebuild is recorded twice in this tree at two speeds — ~5.7 ms here, 3.0 ms in `Engine.OnGetPeers` — against allocation figures that agree to a rounding (~429 KB); allocation does not vary with the machine and wall time does, so the difference is the machine and not the code, and reading one against the other is how the two were briefly taken for a disagreement. **The interval is also bounded from below by `GetPeersMinInterval`**, which is `DiverseCacheTTL` = 30 s and charges `ScoreExcessRequest` = -5 for a second request on one connection inside it: `GetPeersInterval` must stay at least ten times `GetPeersMinInterval`, or this section prescribes a rate at which a conforming peer is charged for asking. It is still not chosen to bound a hostile peer — the memo and `GetPeersMinInterval` do that, both on the serving side, and neither depends on this node's timer.
- **The first ask is due immediately** (`Node.nextGetPeers` zero value), because a node that has just made its first outbound connection is the node with the thinnest address set it will ever have.
- **The interval is armed only when a frame is actually sent**, so a node with no outbound connections does not spend an ask on an empty peer set and then fall silent for a full interval once it finally has one.
- **The jitter is re-drawn per ask.** A fixed period would make the send times across every connection this node holds one recognisable phase.
- **`GetPeersInterval <= 0` disables asking**, which is the behaviour before the node asked at all, kept reachable.

The verdict on the receiving side is deliberately unchanged: `OnPeers` still returns `ErrUnsolicited` and still scores zero, for the reason in §12.2 — this node cannot show that a given frame answers its request, so `ErrUnsolicited` remains the honest record and `wire.md` §7's rule still binds.

### 12.4 What this costs, stated as costs

- **The serving cost moves onto the ordinary path, and the memo bounded it there.** Until now, every `get-peers` a node served was, by construction, sent by something that was not a conforming node. Now conforming nodes send them too, so the handler's cost is a baseline load and not only an attack. What that load is has changed since this bullet was written: a served request no longer buys work proportional to the store, and the store-sized selection it used to buy runs at most once per `DiverseCacheTTL` however many peers ask. The healthier node still pays more *per rebuild* — the diversity pass is over everything it holds — but it no longer pays that *per request*, so "the node that did the diversity work is the softer target" is now a bounded residual, under 0.02% of a core at the worst honest rate (§12.3), rather than one that rises with how often it is asked. What makes the residual safe rather than merely small is where the check on the memo sits: `liveSubset` filters it against the live store on **every** hit, so a banned or evicted address is never served from it, and the TTL therefore bounds *freshness* only. Stale freshness has no downstream failure mode, because a `peers` reply is a hint the receiver has to dial to believe. That is also why the memo does not become a liability when the peer store's eviction rules are reworked: what it rests on is that the store is consulted on every hit, not on any particular rule about what the store keeps.
- **Honest address supply still earns nothing.** The reply cannot be scored positively (§12.2), so a peer that answers usefully is indistinguishable, to the scorer, from one that answers with 64 invented strings. What limits the second is not scoring but `MaxPerSource` and cohort eviction, i.e. exactly the machinery §11 describes.
- **The reply is an amplification of the request** — five bytes on the wire buy up to `MaxPeersPerResponse` addresses. It is not a *reflection* vector: the request arrives over an authenticated TLS session on an established TCP connection, so the requester's address is proved and cannot be a victim's. The asymmetry that remains is bandwidth rather than CPU: the memo took the store-sized work off the served path, and `GetPeersMinInterval` now prices the bytes per connection — one reply per 30 s, `ScoreExcessRequest` and no reply for a repeat inside it. Neither of those is this change's doing and neither depends on it: an attacker never needed this node's timer to send `get-peers`.
- **An ask can stall the dial loop.** `SendDeadline` is called on the dial-loop goroutine and takes the connection's `writeMu`, under `writeTimeout` (10 s), so a peer that accepts the connection and then stops reading holds that loop for the full timeout. **The ceiling is `writeTimeout` over the interval floor** — 10 s in 300 s, a ~3% duty cycle — and that arithmetic contains no term for rotation at all; jitter only lowers it, since the mean gap is 375 s rather than 300. **Rotation is a separate and weaker claim:** it improves the *expected* case, because one hostile peer among k candidates is drawn with probability 1/k, so the expected stall is nearer 3%/k. **The regime where it contributes nothing is k = 1** — a node with a single outbound candidate — which is exactly the thin-bootstrap state discovery exists to escape, so this cost sits at its ceiling precisely when the mechanism is most needed. An earlier revision of this bullet said the 3% was "no worse, because the target is re-drawn every ask", which credited rotation for a bound whose arithmetic has no rotation in it, and offered the reassurance in the one regime where it does not apply. It is bounded and it is not free, and it is recorded here rather than fixed because moving discovery to its own goroutine would give up the reason it rides the dial loop (§12.3).
- **A node with no outbound connections never asks.** That is the bootstrap-failure case, and it gets no help here. Its answer is the operator's `--peers` list and the §6 NAT reopen condition, not discovery.
- **Asking at all, and at this rate, is an implementation fingerprint.** Nothing here tries to hide it, and the jitter does not: a passive observer can distinguish this node from an implementation that does not ask. Accepted. The node is already distinguishable by its dial interval, its hello and its certificate shape, and the anonymity property §10 claims is about not linking a network address to an on-chain identity, which this does not touch.
- **Whatever an attacker's outbound slot buys, it now buys sooner.** An attacker holding one of this node's outbound slots was always able to volunteer addresses; now it is asked, so first-teller attribution on real addresses — its own stated residual — reaches it more reliably. The bound is that it had to win a slot under `SelectDialTargets`' diversity and per-source rules to be asked at all, and that `MaxPerSource` caps what its answers can then take. This is not an argument that the residual went away; it is the reason it is bounded by the mechanisms §11 already prices.

### 12.5 Why this makes the rest of the epic load-bearing

The peer-trust work's own recommendation was that asking is what turns it from precaution into mechanism, and that is the accurate statement of it. `hello`'s advertised address being recorded with the teller that supplied it, a restored entry being unproven with one arrival bucket and a configured address not evicted before its first dial, and a node refusing to connect to itself, all price a stream of claims. Before this section that stream had no honest source. The eclipse-resistance simulation (after launch) is the thing that measures whether the prices are right, and it now has something to measure.

### 12.6 Whitepaper

No change. The whitepaper's only network prose is §13's *"a relay node needs no state whatsoever to fully filter spam"*, which is about the cost of relaying a message and says nothing about how a node acquires addresses; there is no eclipse or discovery clause for this to contradict. The wire contract already anticipated the send — `wire.md` §7 states the rule *"a node MUST NOT score one positively unless it sent the `get-peers` it answers"*, which is a rule about a node that sends one — so this change moves the implementation toward the spec rather than the other way. `wire.md` §10 still has no category for a solicited `peers` reply, and after §12.2 it should not acquire one while there are no request ids.
